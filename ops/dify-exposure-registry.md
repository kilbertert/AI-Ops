# Dify 可达的公司系统面 —— 登记表（#583 / PRD #577）

> **这份文件是唯一声明处。** PRD #577 把这条判据写成一句可回归的话：
> **Dify 能触达的公司系统面 = 我们显式暴露、逐个审过的工具端点集合。**
> 集合在这里；集合**之外**一律不可达。`tests/test_dify_exposure_registry.py` 在 CI 里
> 断言"实际暴露的端点集合 == 本表声明的集合"，新增端点却漏登记即失败。

登记的是**面**，不是通道：Dify 打到我们的那一跳叫什么、谁鉴权、哪些方法在跑。
地址、端口、凭据一律不在这里 —— 那些在库外的运维记录里。

> **下面那张表的列序是契约**：`面 | 路径 | 方法 | 鉴权 | 为什么它在集合里`。
> 路径写在反引号里，方法是大写 HTTP 动词，**最后两列不得留空**。CI 按**单元格位置**
> 解析它（不是按"以路径开头"匹配），所以加一列或换顺序会让判据当场变红，
> 而不是安静地解析出空集合。

## 一、暴露给 Dify 的端点

| 面 | 路径 | 方法 | 鉴权 | 为什么它在集合里 |
|---|---|---|---|---|
| 知识检索适配 | `/v1/dify/retrieval` | POST | 共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_KNOWLEDGE_API_KEY`） | Dify 的 External Knowledge API 目标。Dify 控制台里挂"外接知识库"时，运营填的 endpoint 加 `/retrieval` 就打到这里（#581）。租户与知识库集合由**我们的** `AIOPS_GATEWAY_DIFY_KNOWLEDGE_BINDINGS` 决定，请求体里两者都没有 |
| **知识源清单（只读）** | `/v1/dify/knowledge` | GET | 共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_KNOWLEDGE_API_KEY`，与检索同一把） | 让 Dify 控制台的「连接外部知识库」对话框能把 `knowledge_id` 渲染成**下拉选择**而不是空白输入框（PRD「前端点击完成知识库配置」）。返回的正是**检索会接受的那组** `knowledge_id`：同一凭据、同一登记表，所以选项里出现的每一个都检索得到；不读取任何数据源、不执行检索、不写任何状态。调试身份只看到它自己的子集 —— 预览界面不得展示预览用不了的选项 |
| **试运行（提交）** | `/v1/dify/trial` | POST | **独立**共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_TRIAL_API_KEY`） | 拿一份**草稿**（方法论提示词 + 工具白名单）在一张订单上跑一次真实 harness（#772 F / #781）。范围**不来自请求**：订单可见性由服务端配置的 `dify_trial_debug_tenant` 决定，与 `/v1/standard/diagnoses` 同一条判据。**不产生智能体版本、不写注册表、不改任何生产路由**；超出预算时结果标为未完成。它触发一次真实模型执行，所以钥匙必须与其余每一把都不同 |
| **试运行（读结果）** | `/v1/dify/trial/{trial_id}` | GET | **独立**共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_TRIAL_API_KEY`） | 读一次试运行的状态与结果：诊断报告、证据编号、被白名单挡掉的工具、数据源失败。只读；`trial_id` 不认识即 404 |
| **管家试用（取消）** | `/v1/dify/trial/{trial_id}/cancel` | POST | 独立 trial 凭据 + 原公司登录会话 | 核对当前主体、范围、应用与 trial 标记后取消该任务；不可取消正式任务；不接受浏览器自报身份 |
| **运营自助发布** | `/v1/dify/publish` | POST | **独立**共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_PUBLISH_API_KEY`） | 运营改完 Dify 正文之后**自己**触发的那一步（#577）：把这个 app 的**当前内容**过一遍我方发布门，冻结成新的已发布版本。请求体**只有一个 `app_id`**，租户/agent 名/类型/契约/知识库全部来自运行时注册表 ⇒ 能做的就是"重新发布一个**已声明**绑定的**当前**内容"。见下「**为什么这里有一个写端点**」 |
| **恢复历史版** | `/v1/dify/restore` | POST | **独立**共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_PUBLISH_API_KEY`，与发布/撤回同一把） | 把正式指针推回一个**已验证的历史版本**：从不可变 `agent_versions` 快照取 `workflow_id`，用该 id 导出并**逐字核对**内容与快照一致，不成立就 409。请求体是 `app_id` + `version_no`（`extra="forbid"`）。**不接受**任意 workflow/租户/凭据；恢复 ≠ "再发一次当前草稿" |
| **版本列表** | `/v1/dify/versions` | POST | 同上 | 列出这个 app **可恢复**的版本号（只列快照里 `app_id` 与 `workspace_id` 都对得上的）。它让运营在界面上看见"能回到哪一版"，不是"最新是哪一版" |
| **撤回** | `/v1/dify/retract` | POST | **独立**共享凭据（Bearer，`AIOPS_GATEWAY_DIFY_PUBLISH_API_KEY`，与发布同一把） | 运营撤回这一版：停止对**新请求**与**尚未放行结果**的交付。请求体同样只有一个 `app_id`。三件事必须同时成立：管理行改成 `retracted`（**不删行** —— 删行会让请求掉回直读，那是冒充停用）、在飞运行被收敛（本地终态 + 撤销取数凭据 + 请求 Dify stop）、历史与在飞正文不再交付（回读守卫发现当前绑定不再指向签发时那一版）。**不自动恢复任何旧版**：恢复是另一次显式发布。已发出的数据不承诺追回 |
| **工作区查询（内部，非 Dify）** | `/v1/dify/workspace` | GET | **网关自己的内部令牌**（`X-Internal-Token` + `X-Request-Timestamp`，HMAC，`AIOPS_GATEWAY_INTERNAL_TOKEN_SECRET`） | 回答"这个租户在本环境里的 workspace 是哪一个"（#879 / ADR-0059）。**调用方是我们自己的另外两个进程**（登录代理、发布桥），不是 Dify —— 它登记在这里，是因为 CI 的判据按 `/v1/dify/` 前缀取集合，不登记等于在这条判据里开一个洞。Dify 拿不到这把令牌，所以它**不**扩大 Dify 的可达面；输出也只有一个 UUID，拿到它还得有 `ADMIN_API_KEY` |

**当前十行。** PRD #577 说集合"至少包含知识检索适配路由，以及智能体运行所需的只读工具
端点"。第二类**今天一个都还没有**：智能体的运行在我们侧（那是 PRD 的核心边界），Dify 侧
只负责编排与调试预览；预览要打公司数据需要一条**专门的调试身份**（#586），而那条身份还不
存在。所以给 Dify 的只有这几跳。
**新增任何面向 Dify 的端点，必须同时加进这张表** —— CI 会拦漏登记的那次。

### 为什么这里有一个**写**端点（这是一个显式例外，不是把定义放宽）

本节原来写着「任何会改生产数据的端点都不得进这张表」。第二行**确实**会改状态，
所以必须把它论证清楚，而不是把"写"重新定义成别的词：

- **它改的不是生产业务数据，是我们自己的智能体配置。** 它不碰充电库、不碰任何订单/
  用户/TDengine 数据，也不执行任何公司侧写操作。它写的是 `gateway.db` 里一个 agent
  的**新版本行**（`agent_versions`）——与 `/v1/agents/{id}/publish`、`aiops admin
  reconcile`、`aiops-admin sync-from-dify` **同一条**生产发布路径、同一道发布门。
- **它的爆炸半径恰好等于已声明的绑定集合。** 请求体只有一个 `app_id`（模型是
  `extra="forbid"`，多一个字段就是 400）；租户、agent 名、类型、输出契约、知识库绑定
  全部从 `dify_app_registry` 读 —— 那是 `[[dify_apps]]` 收敛出来的。所以拿到这把钥匙的人
  **不能**：加一个绑定、改一条路由、换一个类型、挂一个知识库、注入任意正文。
- **最坏情况是 no-op。** 重复发布**内容没变**的绑定什么都不写（sync 先与已发布快照
  逐字比较），所以"最坏"收敛成"什么都没发生"。
- **它没用用户凭据。** 挂在这条路由上的是一把**独立**的共享密钥，且**必须**独立：
  与 `DIFY_KNOWLEDGE_API_KEY` 同值会让"能读知识库"等于"能发布"；与
  `DIFY_CONSOLE_API_KEY` 同值会把服务端凭据交到触发方手里。

**为什么不能用用户 JWT（哪怕是 operator 的）**：本部署是 company-parity 模式
（`AIOPS_GATEWAY_COMPANY_TRUST_PAYLOAD` 未设 ⇒ 不验签）。41 实测：一个**用编造密钥
签名**的令牌打 `/v1/standard/diagnoses` 得到的是 `404 ORDER_NOT_FOUND` —— 它**穿过了
鉴权层**（不是 401）。拿这样的凭据当发布授权，等于没有授权。

**这个例外的完整论证（含被否掉的四种替代形态）记在 ADR-0018**。

**为什么不做成定时器**：Dify 的 chat app **没有草稿区**（`export_dsl` 读
`app.app_model_config_id` 这个单指针，保存即覆盖）。定时拉取会把运营**打字打到一半**的
正文推给真实用户。人来触发是唯一诚实的"我改完了"信号。


## 二、集合**之外**一律不可达

这条是判据的后半句，与前表同等重要：

- **无数据库连接**：Dify 侧没有任何 MySQL / PostgreSQL / TDengine 凭据，也不在能到这些
  端口的网络位置。本仓的直连库能力（`AIOPS_MYSQL_*` 等）只在网关与诊断主机上存在。
- **无 Redis**：同上。会话/游标那类 Redis 语义只在我们的运行时里。
- **无 kb-service / RAGFlow 内部端口**：Dify 打知识那一跳**只能**落在上表的适配路由上；
  kb-service 与 RAGFlow 的端口不向 Dify 暴露，也不加入它的可达网段。
- **无写端点**：上表的方法列是 `POST`，但它调的是 kb-service 的**检索**端点，语义是只读
  （`KnowledgeSearchGuard` 同一条纪律）。任何会改生产数据的端点都不得进这张表 ——
  见 `AGENTS.md` 的业务边界：第一版只允许诊断和证据交付。

## 二·补、公网入口那一跳：`Authorization` 由谁提供（#614）

适配路由自己认的是**共享凭据**（`AIOPS_GATEWAY_DIFY_KNOWLEDGE_API_KEY`），而它在公网上
**前面还有一跳 nginx**。41 的 `location ^~ /v1/` 会用自己的服务令牌**覆盖** `Authorization`，
那样 Dify 的 key 到不了门（403 `DIFY_CREDENTIAL_REJECTED`，2026-10-09 实测）。

因此为 `/v1/dify/` 单开了一条**更长的前缀** location：保留客户端带来的 `Authorization`，
并且**不**注入入口 / 来源密钥 / 会话 —— Dify 是服务器，不是我们的用户。
形状、理由与验收三处观察点见 `docs/agents/env-41-runbook.md` §1.10。
这是**暴露形态的一次显式决定**（记录在 #614），不是布局细节。

## 二·补二、两种身份：凭据决定，请求不参与（#586）

同一条路由上有**两把凭据**，各自对应一个身份，且**只有凭据能决定它是谁**：

| 凭据 | 身份 | 能到哪 |
|---|---|---|
| `AIOPS_GATEWAY_DIFY_KNOWLEDGE_API_KEY` | `production` | 登记表里全部已登记的 `knowledge_id` |
| `AIOPS_GATEWAY_DIFY_DEBUG_API_KEY` | `debug` | **只有**固定测试租户下、列在调试子集里的 id |

- 身份只**收窄**：调试身份取不到生产范围内的东西；生产身份不受调试子集约束。
- 越权与「未登记」**同为 404** —— 403 会说「这条存在但你不能用」，那本身就是一次对登记表的泄漏。
- 请求里的头、查询串、body 字段**一个都不参与**判定（解析函数连请求对象都不接）。
- 调试三键（凭据 / 固定租户 / 子集）与生产两键一样走**服务端配置**文件；缺一不可、
  半配置是**启动错误**。子集为空 ⇒ 什么都取不到，**不是**「不收窄」。

## 三、三段落地，只有第 1 段进 CI

| 段 | 在哪跑 | 做什么 | 状态 |
|---|---|---|---|
| **1** | **CI**（`tests/test_dify_exposure_registry.py`） | 静态回归：路由表里"面向 Dify 暴露的端点集合" == 本表声明的集合；挂接跳数只能是我们网关的适配路由，且**只读** | ✅ 已落地（11 例） |
| 2 | 验收制品（不进 CI） | 运行时探测：每个已暴露端点验证未授权被拒、授权按只读语义返回 | ✅ `tools/check_dify_exposure.py --runtime`；结果随验收留档 |
| 3 | 验收制品（不进 CI） | 网络面探测：从 Dify 所在宿主的视角验证除登记集合外的公司系统面不可达 | ✅ `tools/check_dify_exposure.py --network`；同上 |

段 2/段 3 要连真实端点与真实 Dify 宿主，**不进 CI**（CI 是 GitHub-hosted，没有那些东西）；
它们的脚本与结果随验收制品留档、可复跑。脚本的退出码与 `verify_banner_car_lookup.py`
同一纪律：`0` 通过 / `1` 有失败 / `2` **未取证**（没给做法、什么都没发）。

## 四、这条判据**不**证明什么

- 它不证明 Dify 那边**配了**这个 endpoint —— 那是运营在控制台里填的动作。
- 段 1 是**静态**的：它读路由表与源码，证明"我们这边暴露了什么"，不证明"运行中的进程
  真的只暴露这些"（那要有真进程才算，段 2 补这一半）。
- 它不证明网络可达性方向上的封锁 —— 段 3 才碰网络，且只在**有真实 Dify 宿主可达**时才
  算取证；否则如实记 2。
