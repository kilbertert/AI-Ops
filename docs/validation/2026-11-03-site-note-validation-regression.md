## 三、当前生产缺陷（本文最重要的一节）

`SITE_NAME_SHAPE` 之外新增的「整词替换通用短语」在**字符层**分不开类别词与名字：

```text
「站点名称」    的前缀「站点」本身就是站名合法尾部
「虚构乙站点名称」                   ↑ 同一个「站点」
→ 整词替换必然吞掉名字末字 → 名字变「虚构乙」，不再是站名形状 → 放行
```

**在 41 生产环境实测确认**（只用 `validate_site_note`，未发真实请求）：

```text
ACCEPT  我帮你找到了虚构乙站点详情。
ACCEPT  我帮你找到了虚构乙充电站名称。
```

即：模型若这样写，虚构站名会进入用户正文。旧实现（#1310 之前）会拒。

**2026-11-03 本机复现**（`main` `7116edd0`，`uv run python -I` 直接调 `validate_site_note`，
不连生产、不发请求）：

```text
ACCEPT  我帮你找到了虚构乙站点详情。
ACCEPT  我帮你找到了虚构乙充电站名称。
REJECT  我帮你找到了虚构乙站详情。      → OPERATOR_INVALID_ANSWER (note_site_name)
REJECT  我帮你找到了虚构乙站。          → OPERATOR_INVALID_ANSWER (note_site_name)
```

四条同时跑的意义在于**区分"缺陷"与"能力"**：不带通用后缀的编造站名仍被拒，
说明判据没坏；带通用后缀的两条被放行，恰好是第三节说的字符重叠。本机复现证明
**仓库源码**如此；它与 11-02 在 41 上的观测一致，但本轮**没有**回读 41 的模块字节。

## 五、待决策方向（Codex 离线评估中，未实施）

用户提出：这个环节是否应该由大模型理解语义，而不是关键字匹配。讨论后形成的候选：

**A. 语气槽位化（讨论中最省事的一条，未采纳）**
`text` 不再接受自由文本，只接受 `{{tone:xxx}}` 受控槽位；校验退化为"槽位名是否在词表内"，
是闭集检查。可删除 `SITE_NAME_SHAPE` / `GENERIC_TAILS` / `GENERIC_STOPWORDS` /
`_mentions_a_site_name` / `_concrete_chars` 约 60 行及 5 处测试。**代价**：模型不能再自由
表达语气，需维护语气词表。

**B. 开场由系统生成**：模型不写 `text`，按 `kind` 出固定文案。最彻底，改变产品形态。

**C. Dify 语义节点判定**：由编排侧判定"是否含未授权事实"，网关只信判定结果。多一次模型
调用，且把安全判定放到模型侧需要重新论证。

**为什么不直接"让大模型判断"**：这段代码是**校验器**。让模型自判"我有没有写站名"，
等于让被审计方签审计报告。同链路的 `check_status_prose` / `check_notice` /
`validate_reply` 出于同样理由都是确定性判据。

**状态：Codex 离线评估中，未实施。** 本批不改词表、不改判据、不动 #1315；
语义方案与是否改动验收合同由 Codex 评估后决定。本轮只是把这三种候选与它们各自的代价
如实留在记录里，供评估使用。
