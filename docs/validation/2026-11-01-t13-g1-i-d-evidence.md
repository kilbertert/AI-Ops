## D 现役原客服迁移 —— **通过（迁移态正确），附一条必须记住的事实**

### 事实：正式指针已从原客服应用迁到新开通应用

同一 agent（`agt_0df26d268297431f95f3cbe8bc616e94`）的版本历史里，应用身份在 v10 处换过一次：

```
v1  -> （空）
v2–v9  -> 394b5399-7ad…   ← 现役原客服 WF01-Ulink-只读客服
v10–v13 -> 07d15c42-c2a…  ← 本次开通的 Ulink－真实页面双端开通
```

当前正式路由：v13、rev 13–14、`consumer_service`、engine=dify。

### 迁移态是干净的

| 检查 | 结果 |
| --- | --- |
| 原客服应用在 Dify 里是否还在 | **在**，`200 name=WF01-Ulink-只读客服` |
| 原应用是否还有 Gateway 路由 | 无（已被新应用取代） |
| 原应用是否还在 `dify_app_registry` | 无 |
| 原应用在 `operator_apps` 的登记 | **仍在**（`managed-adoption`，revision 1） |
| 历史版本快照 v2–v9 是否完整 | 完整（含 `app_id`/`workflow_id`/`consumer_service`） |

**结论**：资源没有被重建或销毁——原应用与其历史版本都还在，只是正式指针换到了新应用。
`operator_apps` 保留那一行登记，正是"可追溯"需要的。

### 跨应用回滚被正确拒绝

尝试把正式指针回滚到 v9（原客服应用的版本）：

```
restore v9: 403
bridge: console publish refused by gateway: HTTP 409 code=DIFY_VERSION_MISMATCH
```

这是设计：v9 的 `app_id` 是 `394b5399`，当前受管行是 `07d15c42`，跨应用回滚会让路由
指向一个已不在 registry 里的应用。**要回到原客服，正确做法是恢复登记 + 切指针，不是
直接 restore 一个跨应用版本**——这一点值得写进手册（见下）。

恢复 v13 后：`v=13 rev=14 published=True`。

## 一个小提醒（手册没说、但这次差点又踩）

按手机号从 Redis 匹配会话是**不安全**的：同一个手机号可能在不同租户下有账号，
而这个验收号的会话恰好属于一个**未开通**的租户。取会话时必须按 `tenantId` 精确匹配，
或先打印 `tenantId` 确认后再用。建议在手册那条"先证明租户"下补一句操作方法。
