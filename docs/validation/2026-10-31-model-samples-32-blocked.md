# 固定 32 次真实模型样本：执行器就绪，被上游额度阻塞（2026-10-31）

## 结论先说

**32 次样本没有跑完，结果不能当作通过或失败的证据。**
阻塞原因是**上游模型账户余额不足**，与代码、提示词和校验器无关。

```
HTTP 403  insufficient_user_quota
[sk-x4CF**********86yU] 预扣费额度失败, 用户剩余额度: ¥0.002093,
需要预扣费额度: ¥0.003745 (request id: 202610311147197286087136obuzDzR)
```

复现方式：在 41 上用节点自己的出口配置发一个 `max_tokens=2000` 的请求即 403；
把 `max_tokens` 降到 5 则 200 —— 说明**密钥有效、模型可用，是余额不够预付**。
两次采样余额从 ¥0.002606 降到 ¥0.002093，确实在消耗。

## 为什么没有"想办法跑完"

可以做的取巧手段都被明确排除，因为它们会改变被判定的对象：

- **调小 `max_tokens`**：样本要证明的是"真实配置下的模型能否交出合规正文"，
  把额度相关参数改小，验的就不是线上配置。
- **换模型/换端点**：被测对象就变了。
- **反复重试直到蒙过一次**：把余额抖动的偶然成功当成稳定性证据，正是本项目已经吃过亏的做法。

所以：保留失败，记录原因，等额度恢复后按同一份冻结清单重跑。

## 恢复后怎么跑

额度恢复后（由账户持有人充值），在开发机执行：

```bash
uv run python tools/verification/model_samples_32.py --out <新的私有空目录> --workers 2
```

退出码 0 表示 32/32 通过；任何失败都在 `results.json` 里带原始输出与错误，
按失败原因分类修复，**不重试凑绿**。
