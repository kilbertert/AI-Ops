## 2026-10-23 · `grep -q` + `pipefail` 把命中读成未命中

> **未完成业务验收。** 这一篇记的是一个 shell 判据缺陷：判据是可复现的构造输入与
> 真实脚本的执行结果。它**不**包含工程师确认的真实故障案例，也**不**是用户侧业务验收。

### 一、症状

`verify` 在 `test_rollback_classifier_branches` 上间歇性失败（期望 exit 2 含「严重」，
实际 exit 1）。同一 SHA 重跑即过；本地连跑 40 次全过。

### 二、根因（四步）

`set -o pipefail` + `printf … | grep -q`：

1. `grep -q` 首个命中即退出
2. 生产者收到 SIGPIPE
3. `pipefail` 取到 141
4. `if` 把命中判成未命中

**只有「命中点之后还有大量数据」才触发** —— 数据少时缓冲区吸收，SIGPIPE 不发生。
这是它小 fixture 复现不出来、CI 上随机的全部原因。

### 三、实测

| 写法 | 结果 |
|---|---|
| `grep -q`（命中在首行 + 20 万行） | hit=0 / miss=40 |
| `grep -c >/dev/null`（同上） | ok=30 / bad=0 |

在生产分类器上：输入含 `rollback=also-failed` 时，旧版报「状态未知，须人工确认」——
**把严重故障降级为不确定**，这是最坏的误报方向。

`deploy-41.sh` 的 `/health` 断言同形状，100k 行时 30/30 误判。

### 四、修复与守卫

`grep -q` → `grep -c … >/dev/null`（`-c` 读完 stdin）。

回归用例「大输入下的标记识别（SIGPIPE 回归）」。**变异验证**：把修复撤回，
该用例转红，失败文本与当初 CI 的失败**逐字一致**（同一个测试名、同一条分支）。

另一处变异诚实标注：测试层自己的 `grep -q` 改成 `-c` 是**防御性**的，实测改回去仍全绿
（分类器输出不够大）。它是没被验证的改动，不当成已覆盖。
