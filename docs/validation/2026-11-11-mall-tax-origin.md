# 商城增值税与充电查询字段：只读调查

日期：2026-11-11。分支`docs/mall-tax-origin-investigation`，base `3931c5d6`。
任务：产品反馈税费由商城计算，怀疑客服接口取得的4.62、4.71、0.09口径有问题。
本次不修改公司仓库、业务表、消息游标、模型或正式客服配置，不重放支付/退款。
全部数据按本次已授权订单的同租户、同用户关联，原始订单号、日志和制品取证私有保留。

## 结论

1. 本样本税费0.09由商城计算并存成独立税项；充电侧接收商城支付结果后回写vat_fee。
   当前客服从充电详情取得的4.62/4.71/0.09，与商城费用、税项、成功支付记录逐值一致。
   没有发现这三个字段在客服reader或当前接口查询时被二次运算、漏税或重复加税。
2. 对该订单，4.62是增值税加入前的订单费用记录，0.09是商城税项，4.71是商城含该税项的
   支付记录。此关系来自商城计税代码、真实税项和当时日志，不是将两项相减后猜成税。
3. 我方工具只标记`cpms.orderDetail`，未携带商城税项/支付证据及其关系。客服只能并列字段，
   又把它们描述成“数值不同、原因未知”，使用户误以为对账异常。缺口是来源和业务口径关联，
   不能靠模型自主算差额或把totalAmount改成payAmount解决。
4. 另外确认商城父单的真实旧值覆盖缺陷：成功回调先写paid_amount=4.71，365ms后状态更新
   又用旧对象写回4.62。子单和支付记录仍为4.71。它不是本截图税额错误的原因，
   但其他接口如果把父单paid_amount当权威“实付”，就可能报错金额。

## 谁计算税、谁回写

固定缓存源码`cloud-charging-pile:release@77c037e7`用于定位；关键商城行为另用现役JAR字节码与
该订单发生时的真实日志核实，未把缓存源码当生产构建身份。现役商城JAR SHA256私有证据已记录。

- 充电`MallOrderServiceImpl.buildItemList`把增值税作为type=9项目发给商城，初始金额0、税率2；
  普通汽车异步订单的请求paymentPrice/totalAmount为4.62。
- 商城现役`SaveOtherBeforeAction.process`针对orderType=11、skuCode=9，使用当时支付基数与税率，
  保留两位小数/HALF_UP，写税项salesPrice/paymentPrice，并加入子单paymentPrice/salesPrice。
  该段没有同步修改原totalAmount；因此两者本来就有不同口径。
- 商城当时日志明确记录税项0.09和支付请求4.71。余额支付`BalancePay`以支付金额转成资产最小单位，
  真实请求value=-471.0、资产接口返回code=0；支付记录state=1、amount=4.71。
- 商城`ChargeOrderPaySuccessListener`发送该订单的父子单与明细回执：paymentPrice=4.71、sku9=0.09。
- 充电日志随后记录收到该回执及“增值税重算结果为0.09”；`OrderPayResultKafkaListener`将
  content.paymentPrice写payAmount，sku9.paymentPrice写vatFee，未把税再加到totalAmount。

所以对本样本，“税在商城算”和“充电接口返回税额”同时成立：后者是回写结果，不是充电查询时重新计税。
不推广到未支付、退款、特殊套餐、余额抵扣、保险/占位单或回调未完成的全部订单。

## 商城父单paid_amount覆盖根因

以下时刻沿日志原始`+08:00`时区，均是同一父单，未以附近其他订单日志作为依据：

| 时刻 | 动作 | 结果 |
|---|---|---|
| 10:34:42.757 | 创建阶段对象仍带税前paidAmount | 4.62 |
| 10:34:43.804 | 支付总记录成功回调 | amount=4.71 |
| 10:34:44.013 | 同父单定点更新 | paid_amount=4.71 |
| 10:34:44.378 | 支付状态流程整行updateById，36个SET列 | payment_price=4.71，但paid_amount=4.62 |
| 10:34:44.381 | 子单单独更新 | paid_amount=4.71 |
| 当前只读复核 | 数据库父单/子单/支付记录 | 4.62 / 4.71 / 4.71 |

现役JAR的对象路径解释了两次更新：

1. `OrderInfoPaySuccessListener.payResult`先读取父单到对象A。
2. 新建对象B，只写ID和成功回调金额等字段，updateById把B的paidAmount=4.71写数据库。
3. 仍把旧对象A放进`PayOrderResultContext`并异步运行order-pay-result，没有刷新A的已付字段。
4. `UpdateOrderPayStatusAction.process`从context取A，只改isPay/status，就updateById(A)。
   A中非空的paidAmount=4.62随整行更新覆盖B刚写的值。

这是“更新数据库后继续使用旧对象，再整行回写”的丢失更新，不能简单称税费计算错误或前端显示错误。
本次未改该商城代码，也未批量修复历史父单；公司仓库由其流程治理。

## 修复建议与先后关系

### 我方客服数据合同

保留来源原值，补全该字段的来源、口径和关联证据。普通记录查询应清楚区分费用基数、商城税项、
支付记录，不主动把不同口径字段当作异常；支付核实时通过已授权的充电订单关联到商城父子单、
税项和成功支付记录，在同租户/主体边界下对照。
仅当关联、状态与来源证据完整时说明“支付记录包含商城税项”；否则报告缺证/同步待核验。
不能将4.62一律加税/替换为4.71，不能对所有订单硬编码“差额就是增值税”，不读父单paid_amount作为
唯一实际支付权威。正式接口扩展要明确权限、时效、部分失败和同步冲突表现，再进入实现。

### 商城侧根因

优先把`UpdateOrderPayStatusAction`的父单更新收窄到它拥有的状态字段，禁止携带旧金额/支付字段；
同时统一回调后传入context的对象状态，避免其他后续节点继续使用旧值。不能仅刷新一次然后仍整行
覆盖来假设消除所有并发问题。回归应执行已记录顺序：加载旧父单→回调更新4.71→状态更新，
最终paid_amount保持4.71，并保留其他同期字段。历史修复仅针对已核准支付证据，另行审查授权。
