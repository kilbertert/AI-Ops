## 二、顺序：节点声明先于网关

证据字段集合是**两端精确相等比对**（`OPERATOR_EVIDENCE_MISMATCH`），所以「网关新、节点声明旧」
的任何一个窗口里，所有订单诊断都会失败。CD 是合并后自动触发的，不会等节点，因此执行顺序是：

1. **CD 运行中**即把新声明经 `dev-host write 41 --artifact-sha256` 传上 41；
2. 备份旧声明 → 原子安装（先写 `.operator-tools.json.new` 再 `mv`）→ 644 / `aiops41:aiops41`；
3. 定点重建节点容器（`--no-deps --pull never --force-recreate node`，**不重建 JAR** ——
   声明是独立 bind mount，字段来自声明）；
4. 等节点上报新摘要。

节点重启后**首次心跳仍报旧摘要**，约 90 秒后才变成 `ad967010…`。这不是故障：
`CapabilityReporter` 每 30 秒一次，而容器冷启动本身用了 49.8 秒。判据要连 `observed_at`
一起看，不能只看 `tools_sha256` 的值。

- **口令必须先 AES 加密**：本环境明文口令得到 **HTTP 500**（网关 `PasswordDecoderFilter`

这条链与 41 的「公司一致」模式一致：网关**不验签、不判 `exp`**，身份取自令牌里的 `id`。

### 5.5 顺带发现一个真实缺陷（**未修完，已开 PR**）

同一句原话连跑 3 次：**2 次整轮 failed**，网关日志 `reason=unsupported_fact`。

根因是 #1305 在输出契约里枚举了费用字段名，与紧随其后的「不要在其它行复述这些值」打架，
模型开场就写金额/百分比 → `check_notice` 判「非事实段行不许有数字」→ 整轮拒绝。

已开 **PR #1307** 收紧措辞。**但它尚未部署、且改后成功率未测** —— 提示词冻结在每次运行
签发的清单里，必须部署 Gateway 并重新发布才生效。所以第 5.3 节的 `completed` 是**能跑通**
的证据，**不是**「稳定可用」的证据。

### 5.6 关于裸打公网 CPMS

`curl https://api.mall.qushiyun.com/charging-pile/chOrderInfo/getOrderInfoDetail/<单号>` 返回
`{"code":1,"msg":"订单不存在"}` —— **这不代表订单不存在**：那条路径没有身份头。网关走的是
`/v1/internal/operator-runs/{run}/cpms/…` 代理，自带用户令牌与 `tenant-id`。两条腿不能混用。
