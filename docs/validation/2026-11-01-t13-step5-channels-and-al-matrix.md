## 5. 那个 409：**已查清，是正确的拒绝，不是回归**

> **本节订正了本文档第一版的结论。** 第一版写的是"稳定复现的回归，建议单独开票"，
> 那个判断是错的。保留订正过程，因为错法本身值得记。

### 结论

409 `CHAT_ROUTE_UNAVAILABLE` 来自一个**从未开通的租户**，是正确拒绝。

用临时探针（已还原，见下）抓到真实请求的身份：

```
PROBE entered chatflow branch tenant=2005573840461369344
PROBE service_binding=False
```

该租户在库里：

| 查询 | 结果 |
| --- | --- |
| `chat_route_bindings` 中该租户的行 | **0** |
| `operator_apps` 中该租户的开通记录 | **0** |

所以"业务执行路由未配置"这句话是字面成立的：这个客户没有开通，本来就没有路由可用。
分支进入了、`platform=consumer` 也对，只是 `select_binding` 找不到绑定——因为确实没有。

### 第一版为什么判错

第一版说"几小时前能答、现在答不了，可能是回归"。两个错误叠在一起：

1. **没有在每次调用前证明请求租户。** 我从 Redis 里按手机号 `13333555555` 匹配会话，
   取到的是**某个已开通租户**的会话；后来又重取过几次，拿到的是另一个租户
   （`2005573840461369344`）。整个排查都在拿一个没开通的租户测一个只有已开通租户才有的路径。
2. **把 409 当成"渠道坏了"。** 409 是一条明确的业务拒绝，与"渠道不通"（401/5xx）是两件事。
   我先下了"渠道坏了"的判断，再去凑证据。

这和仓库里已有的一条教训同形：**只查结果、不查路由的判据会假 PASS**——这里反过来，
是**没证明请求打在哪、就判了回归**。
