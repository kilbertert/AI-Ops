## 2026-10-23 · 版本号由 VERSION 文件决定

> **未完成业务验收。** 这一篇记的是版本机制：判据是分节行为的实测、三处一致性测试
> 与变异验证。它**不**包含工程师确认的真实故障案例，也**不**是用户侧业务验收。

### 一、此前没有版本号

`pyproject.toml` 与 `__init__.py` 都停在 `0.1.0` 且**各写各的**；Release tag 是
`release-<sha12>`。所以「这次发布是什么版本」没有答案，`dev-changelog` 只产出
一个 `Unreleased` 节。

### 二、机制

| 文件 | 角色 |
|---|---|
| `VERSION`（新） | 权威；**人**改它来发布 |
| `pyproject.toml` | 副本（打包元数据） |
| `__init__.py` | 副本（运行时 `/health` 读它） |

三者相等由 `tests/test_release_version.py` 强制；`deploy-41.sh` 另加运行时断言，
不一致就停止部署。

### 三、tag 语义（实测依据）

| tag | 何时打 | 会移动吗 |
|---|---|---|
| `v<version>` | 该版本**首次**部署 | **不会**；再部署同版本时打印它指向哪 |
| `release-<sha12>` | 每次部署 | 不适用（key 含 sha） |

**版本 tag 不带 `+<sha>`**：实测 2026-10-23，若每次部署都打 `v0.1.0+<sha>`，
`dev-changelog` 会给它们各开一节：

```
## [Unreleased]
## [0.1.0+def456]
## [0.1.0+abc123]
## [0.1.0]
```

changelog 于是变成「一次部署一节」—— 正是版本号要消除的碎片化。只打 `v0.1.0`
时行为正确：

```
## [Unreleased]
- C
- B
## [0.1.0]
- A
```

### 四、判据

```bash
pytest tests/test_release_version.py     # 4 passed
```

四处变异逐一验证，全部转红：

| 变异 | 转红条数 |
|---|---|
| `VERSION` 改成 `0.2.0`（另两处不动） | 2 |
| `pyproject.toml` 单独改成 `0.2.0` | 1 |
| `__init__.py` 单独改成 `0.2.0` | 1 |
| `VERSION` 写成 `v0.1.0`（带前缀） | 3 |

### 五、没有做的事

**没有推进版本号。** 本次只建立机制，`VERSION` 仍是 `0.1.0`。历史那 664 条
changelog 条目全部落在 `[0.1.0]` 一个节里 —— 它们从未被分过版本，这次也不该凭空
编造。**下一个真正要发布的东西才是 `VERSION` 第一次被改动的时机。**
