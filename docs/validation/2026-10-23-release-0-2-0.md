## 2026-10-23 · 发布 0.2.0

> **未完成业务验收。** 这一篇记的是版本推进与发布说明整理：判据是三处版本一致性测试
> 与门禁。它**不**包含工程师确认的真实故障案例，也**不**是用户侧业务验收。

### 一、改了什么

- `VERSION`、`pyproject.toml`、`__init__.py` 三处同步到 `0.2.0`
- `RELEASE-NOTES.md` 的 `[Unreleased]` 提升为 `[0.2.0] - 2026-10-23`（15 条，均为实质变更）
- `[0.1.0]` 一节由 509 条混合转载冻结为指向 git 历史的指针

### 二、为什么冻结 0.1.0

那 509 条里 266 条是英文 commit 标题、243 条是中文条目。它们记的是「谁提交了什么」，
而本文开头声明的是「用户会感知到什么」。两个不同的事实堆在一节里，会让人以为发布说明
已经覆盖了那些改动，实际上没有。

逐条改写不可行：那是 509 条的大规模重写，且无法验证有没有改错。

### 三、判据

```bash
pytest tests/test_release_version.py    # 4 passed
node .sandcastle/policy-check.mjs all   # passed
```

历史记录（`docs/开发进度/*` 里的 `0.1.0+<sha>`）**未改** —— 那是当时的生产事实。

### 四、发版暴露的写死版本号

三处测试因改 `VERSION` 变红，逐条查过，都不是误报：

1. **`test_receipt_reports_the_version_gap_instead_of_pretending`** 断言写死
   `receipt["gateway_version"] == "0.1.0"`。它钉的是「回执报告版本」，不是「版本是 0.1.0」。
   改为从 `VERSION` 读。
2. **`test_gateway_context_digest_is_reproducible_and_matches_the_lock`** —— `src/`
   变了摘要必变，重算 `images.lock.json` 的 `source_sha256`。
3. **`test_remote_block_renders_and_parses`** —— 未提交时失败，提交后自愈。

第 3 条顺带暴露一个**未修复**的缺陷：`deploy-41.sh` 的 `INIT` 取自目标 commit 的产物，
而 `FILE_VERSION` 取自当前工作树。两棵不同的树，工作树有未提交改动时断言会在与部署无关的
时刻失败。本次靠「先提交」绕过，没有修——它需要单独的设计决定（比的应该是同一个 commit 的
两份文件）。

### 五、发版顺带暴露的第二处：`uv.lock` 也被字节比

`uv.lock` 的记录含本项目版本号（`name = "aiops-diagnostics"` + `version`），所以
`0.1.0 → 0.2.0` 会改写它。依赖漂移门按**字节**比，会把「发布 0.2.0」判成依赖漂移，
**拦住这次发布的部署**——正是上一片（#1032）只修了 `pyproject.toml` 留下的缺口。

改为比「解析出的包与版本集合」，并**排除本项目**：本项目的版本不是任何东西的依赖。

双向实测：

| 输入 | 判据 |
|---|---|
| 只改本项目的 version | 包集合相同 → **放行** |
| 改 `redis` 的版本 | 包集合不同 → **拦下** |

**已知盲区（如实记录）**：`test_deploy_compares_uv_lock_semantically` 跑的是脚本里的
`lock_packages` 函数本体。把调用处整个禁用（`if false`）**不会**让它转红——函数定义还在。
它钉住了「函数行为」，没有钉住「这段代码会不会被执行」。后者需要一条端到端 dry-run，
超出本片范围。
