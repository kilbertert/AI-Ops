## 已完成

### 一、订单提取

`common/order_reference.order_candidates()` 成为唯一候选集来源，正式入口
（`gateway_api`）与原生预览桥（`_native_order`）都只调它。判据与归并规则：

- **整条消息就是一个标识符**（用户直接粘贴）→ 它就是单号本身，可带字母前缀；
- 有「订单」标记时**显式写法优先**，并并入 15 位以上裸数字段；
- 「已被某个标识符覆盖」按**该标识符自己包含的全部数字段**判，不是只看第一个；
- `订单 A2116… 和 2116…` 里第二段是**独立出现**的，仍是第二张单 → 澄清；
- 句末句读（`.` `。` `，` 等）不算单号的一部分。

正式入口在两个以上候选时返回 `CLARIFY_ORDER_REQUIRED`，**不查 CPMS**。

### 二、费用渲染（依据真实 CPMS 响应）

- `vat` 是百分数（真实值 `2.0`，后台写「2%」）→ 带 `%` 显示；
- 缺值 / 零值 / 不适用三种空值语义在同一张真实订单上同时出现，分别处理。

### 三、结算状态类断言

真实响应 34 个字段里**没有** settlement 字段（接口缺口）。但正文里写
「这单尚未结算 / 已经结算完成 / 结算状态是已结算」原本**四句全被放行**。
已在 `consumer_facts.check_status_prose` 补上拒绝，不做肯定/否定之分。

### 四、失败取证

失败 run 不保存模型原文（`snapshot_json.answer` 恒为 `None`，实测）。拒绝点现在记
`detail=<检查名> line=<行号> len=<该行长度>` —— 不记原文、不记金额。

### 五、#1307 回滚

理由与数字见验证文档。**回滚理由是「没有证据支持它更好」，不是「它更差」。**
