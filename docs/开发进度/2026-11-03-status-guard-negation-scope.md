# 里程碑：修掉管家订单诊断的概率性失败

日期：2026-11-03。分支：`fix/operator-status-guard-scope`；基线：`2a9f8b3f`；ADR-0196。

## 目标

用户报「分析这笔单的电费 2116050516255272961」时好时坏，界面报
`OPERATOR_DIAGNOSIS_FAILED`。目标是找到确定性根因并修掉，而不是加重试。

## 已完成

- 只读统计该订单 72 次运行：**19 成功 / 53 失败**，不是偶发。
- 网关日志归因：最大单项是 `unsupported_fact detail=status line=3`（13 次），
  其次是 `json_parse`（14 次，含 5 次 `json_syntax`）。
- 失败 run **不保存模型原文**，改用重放：取 run 的 `execution_manifest`，
  经节点同款 model-proxy 重放 10 次真实调用，喂给生产同一批校验函数 → **4/10 被拒**。
- 根因：`check_status_prose` 的否定分支判「同子句共现」，把「未取到**充电**样本」
  这类**如实说明缺证**的句子判成状态改写；而提示词明确要求写缺证。两端规格打架。
- 修复：否定词必须**紧跟**状态词才算改写（`订单还没结束` 仍拒，`未取到…样本` 放行）。
- 顺带补取证：`json_syntax` 现在多记 `len=` 与 `closed=`，能分开「上游截断」与「模型拼错」。

## 验证

- 重放样本误拒 4/10 → **0/10**；9 条真状态改写仍全部拒绝。
- 全量 `3987 passed / 9 skipped`（基线 3977，新增 10 条断言）。
- 镜像内容锁按手册真实重建，`context_digest.py --check` 一致，镜像内可导入 Gateway。

证据、定位链条与保留的一处误拒见
[validation 回执](../validation/2026-11-03-status-guard-negation-scope.md)。

## 已知缺口与下一步

- **本次未部署**：生产仍是 `1.0.17+07717e66d32c`，合并后由 CD 部署再复测该订单。
- `json_parse` 的成因仍未定性（失败 run 不存原文）；本轮只补了取证字段，
  下次再发生时能分开「截断」与「语法错」。
