# 2026-10-24 · APP-RUNTIME-01：现有 App 聊天接入客户执行节点

## 目标

把已经做好的客户节点执行能力接到用户实际使用的 App 聊天入口：
现有 `POST /v1/assistant/questions` → Gateway 验权并按可信配置选节点 → 建 QA 并后台委派 →
节点跑完 → 返回**同一 run** 的状态快照 → App 用原 GET 轮询与 blocks 显示答案。

**App 不新增字段、不换接口、不换域名；公司仓库零改动。**

## 已完成

### 1. 新路线（默认关闭）

| 层 | 改动 |
|---|---|
| 路由 | `_consumer_order_chat` 在直读之前判一次**服务端绑定**；未命中则原分支一字未改 |
| 授权 | 最新单按**原本人 SQL 范围**选出；指定单核可见性；两者都在**派发之前**完成 |
| 异步 | POST 只建 QA 并立即 202；等待节点发生在既有 QA worker 里 |
| 关联 | `agent_runs.qa_id`（幂等迁移，旧行 NULL 不回填）—— **存储关联**，不从字符串猜 |
| 共享 | `chat_execution` 从既有委派入口抽出签发/派发/等结果；两个入口复用同一份判据 |
| 读取 | GET 按 QA 反查 run，只交付该 run 的 succeeded 快照；排队/失败/取消按原协议可读 |
| 取消 | 先落终态，**同时撤销已关联的 run**；迟到成功不覆盖取消 |
| 失败 | 节点失败 / 漂移 / 未预期异常 ⇒ QA `failed`；**不回落直读、旧模型或别的节点** |

### 2. 配置

新增一键，**默认空 = 关闭**：

```dotenv
AIOPS_GATEWAY_CHAT_EXECUTION_BINDINGS_FILE=
```

指向一张 0600 的登记表（`schema=aiops-chat-execution/1`），每条绑定钉住
（环境，租户，consumer 入口，本场景）与它自己的执行配置/清单。不复用
`AIOPS_GATEWAY_AGENT_RUN_*`：委派入口与聊天入口是两条独立的启用路径。

> **续办修订（2026-10-24）**：原实现只有 `..._CONFIG_FILE` / `..._MANIFEST_FILE` 两个全局键，
> 复核证明那样等于「任何能通过本人授权的租户都派到同一个节点」。改为按租户登记后，
> 未登记租户走原直读、一次派发都不发生（`test_unregistered_tenant_keeps_...`）。

## 已知缺口

1. **未做真实 Java 节点整链验收**：本片的「节点端点」是真的（真领取/真完成 HTTP、
   真 `AgentRunStore`、真执行配置核对），但**节点进程本身**用的是测试里的同步派发器，
   不是 `tools/m2_close/m3node` 的真节点。真节点整链另列。
2. **真实外部平台/供应商未接**：派发器替代的是「通知编排平台」这一跳传输。
3. **登录 App 验收未做**：本片证明接口契约与路由行为，不证明 App 端到端。
4. **SOP 发布绑定未做**：执行配置摘要只是"这一条记录核对过"，不是运营 SOP 发布绑定；
   后者明确留待 M3，本片不造假版本。
