## 2026-10-23 · 外部视频地址改回 `media.url`（适配既有前端）

**起因**：用户问「前端不是已经预留好视频 url 了吗，为什么还要前端调整」。

**去查了才发现自己错了。** 解开 APK（`app-service.js`）读到的实际渲染代码：

```js
var c = t.url || "";                                  // 读的就是 media.url
var l = "video" === a ? parseYoutubeUrl(c) : null;    // 自己去认 YouTube
```

`parseYoutubeUrl` 自己处理了 `youtu.be/<id>`、`watch?v=`、`embed/`、`shorts/`、`live/`，
还解析 `start`、生成 `i.ytimg.com` 封面、跳专门播放页；mock 数据里本来就有一条
`url: "https://youtu.be/…"` 的样本。

**结论：前端从来没把 `media.url` 当成"只能是我们托管的字节"**，它把它当"视频地址"并
已经为两种形态实现了渲染。ADR-0111 要求它改代码，是为了"字段名更精确"。

**改法**：外部链接直接写进 `media.url`，删掉 `external_url` / `embed`。服务端的
host+path 白名单保留（ADR-0113），但那是给字段填值的规则，不是新契约。**前端零改动。**

**判据**：新增一条用例照抄前端 `parseYoutubeUrl` 的判据（去 `www.` 后匹配域名、按
path 取 id），断言签发出来的 `url` 能被它认出来 —— 前端零改动是这个方案成立的唯一前提。
变异「外链仍签本地路径」让 4 条转红。

**代价写明**：`media.url` 从此两种形态。以后任何按 `url` 做转发/缓存/鉴权的代码都得先
判是不是外部地址。今天没有这样的代码（媒体代理只处理 `/v1/media/` 前缀）。

**方法论**：ADR-0111 的错误不是推理错，是**没有核对客户端**。设计跨系统字段时，"我觉得
它会怎么用"不能替代"去看它实际怎么用"，尤其当客户端已是既成事实。

见 ADR-0120；ADR-0111 状态改为「已反转」，原文保留不改写。
