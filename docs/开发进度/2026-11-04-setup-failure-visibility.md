# 开通失败的通用码带上位置：从"查不出来"到"能查到哪一步"

日期：2026-11-04。分支 `fix/setup-step-failure-visibility`（PR #1331）。

## 目标

一次开通失败在生产上要能**事后**回答"哪一步、哪一类异常"。判据：页面上通用失败不再只有
一句"这一端未完成"，journal 里有栈，且异常正文不外泄。

## 起因（一次真实的查不出来）

2026-11-04 在 41 上给优链充跑开通，第一轮重试返回 `SETUP_STEP_FAILED`。资源字段已写到
`key_ref`，但失败点无从确定；journal 里没有栈。为了定位，我在两次重试之间用服务身份
单独调了一次 `service_keys.ensure` —— 那个动作本身改变了现场，于是"第一次为什么失败"
再也无法从生产证据里证明。**定位手段破坏证据，本身就是缺陷。**

## 已完成内容

- 逐端失败记 `failed_step`（步骤名，代码里的固定字面量）与 `failure_kind`（异常类名）；
  作业级异常同样记录。
- 每轮开始时清掉上一次的定位字段（避免旧位置冒充新失败）。
- 客户端第一步补 `consumer:source`，来源校验失败不再归到上一端。
- 异常正文与栈只进 journal；任务行与公开形状只保留步骤与种类。
- 前端追加文案；受控业务码不动。

## 未做 / 下一步

- Dify web 镜像未重建，页面文案尚未上线；后端字段随 CD 生效。
- 没有造真实开通失败（需要可用 Dify 控制台）；归因链靠确定性用例 + 一次性数据根的
  公开形状检查。
- **那次生产失败的真实原因仍未确定**；要等下一次同类失败按新字段定位。
