# C 端站点只读接口（#1192）

分支 `feat/consumer-site-api`，基线 `7b5d62f3`。

## 已完成

**`GET /v1/sites`**：C 端可拉取的站点列表，范围只含**本人订单里出现过的站点**。

- 新模块 `consumer/consumer_sites.py`：本人订单 → 站点集合的推导、C 端凭据形状的读取函数、
  关键词与 `limit` 的校验、以及把三者接起来的唯一入口 `sites_for_consumer`。
- 端点复用既有 C 端入口判据（拆出与订单无关的那一半 `_require_consumer_self`），
  `no-store` 与入口检查与现役 C 端订单接口逐字一致。
- `query_sites` 增加一个显式参数 `outside_scope`（`reject` / `skip`）：管家仍是 `reject`
  ——上游带了站点集合却返回范围外的行是违约；C 端是 `skip`——上游按租户返回，
  范围外的行是预期内的。范围推导、读取、结果对齐、分页上限仍然只有一份实现。
- 登记进公网 OpenAPI，并同步 `docs/testing-api-guide.md` 的表格（那张表与规范逐条相等，
  是 ADR-0156「显式登记」的机械形式）。

## 取数是核对过源码的，不是猜的

按公司源码只读规程读了 `iot/cloud-charging-pile:release`：

- `ChOrderInfoMapper.xml` 的 `getOrderPage`：过滤条件是
  `<if test="param.userId != null and param.userId != ''">`，**头缺失或空串时整段消失**
  → 返回整个租户。控制器 `getOrderUserPage` 只在 `orderRequest.userId` 为空时回落到请求头，
  所以「不带」与「带空串」同一种后果。
- `OrderPageResp` 用 `select coi.*` 带出 `site_id` 与 `tenant_id`，两者都逐行核对。
- 分页是 MyBatis-Plus 的 `Page`，参数 `current` / `size`；响应
  `{records,total,current,size,pages}`。

## 四条口径

1. **永远带 `user-id`**，服务端从会话推导，不来自任何请求参数；标识缺失时**拒绝**，
   连请求都不构造。
2. **范围外的站点本地过滤**，不当违约——否则「本人只有一个站点」的用户会永远查不到自己的站。
3. **`total` 恒为 `null`**：上游那个数是租户口径的匹配数，与「本人可见」不是同一个集合。
4. **空结果分两种**：`none_visible`（本人订单里确实没有站点）与 `no_match`（有站点但
   关键词没匹配），下一步不同。

## 缺口与边界

- **#1192 的一条验收标准只满足了一半。** 它要求「该接口与 **C 端对话回合**共用同一份范围
  推导」。C 端对话回合今天**根本没有站点查询**（那是 #1193 的范围），所以字面上无法成立。
  本片做到的是它的实质：范围推导是**一个函数**，接口不自己实现第二份，并由一致性断言证明；
  等 #1193 给 C 端对话与工具接上站点时，它们直接调同一个函数。这一点在 PR 与 issue 里都写明，
  不当作已满足。
- **本人站点很多时可能漏。** 站点接口本身是「最多 4 页、展示最多 10 条」的既有预算，
  本人订单站点在页外就找不到。如实写进 ADR，不在本片放宽。
- **未完成业务验收**：没有真实 CPMS、没有真实账号、没有真实页面。本片证明的是契约与授权
  模型，不是站点在真实租户里列得对。
