## 一、推荐的 Dify 编排架构

C 端 App / Web 客服

文字提问 · 图片上传 · 多轮对话

Start / 用户上下文

问题、语言、租户和用户身份

Question Classifier + 安全规则

识别安全事件、实时查询、操作咨询及其他问题

路径 A：知识问答

Knowledge Retrieval

FAQ、操作说明、图片关联、视频链接

LLM 生成回答

路径 B：实时业务

HTTP Request / Tool

站点、枪口、会话、订单和支付查询

校验结果并解释

路径 C：安全事件 / 未解决问题

优先安全提示、事件通知、创建工单或转人工

Answer 节点

标准答案 + 图片/视频入口 + 下一步操作

这里的关键是：不是每个问题都走同一条链路。

例如，“如何开始充电”走知识检索；“我的充电还在进行吗”走实时 API；“充电枪冒烟了”应优先进入安全处理路径，不应先等待普通 FAQ 检索。

## 二、Dify 画布应该怎样配置？

建议按下面的顺序落地。

| 顺序 | Dify 节点 | 具体职责 |
| --- | --- | --- |
| 1 | Start | 接收用户消息、可选图片以及可信业务上下文 |
| 2 | Question Classifier | 将问题分成安全事件、实时业务、常规咨询、其他/未知 |
| 3A | Knowledge Retrieval | 查询 C 端 FAQ 知识库 |
| 3B | HTTP Request / Tool | 调用 CPMS API 或客户侧 Agent 提供的受控接口 |
| 4 | IF/ELSE | 判断是否查到知识、API 是否成功、是否需要升级处理 |
| 5 | LLM | 根据检索结果或实时数据组织答案 |
| 6 | Answer | 返回用户可读的回答、图片和媒体链接 |

Question Classifier 可以为每种意图配置不同的下游分支；Knowledge Retrieval 也支持使用元数据过滤检索范围。

### 重点配置一：问题分类

先设置四类主要意图，足够支持 V1.0：

A. 安全事件

例如冒烟、火花、异常高温、触电风险、线缆破损。

路径：安全提示 → 按配置发出告警/建单 → 必要时人工介入。

B. 实时业务查询与操作

例如充电桩是否在线、充电进度、订单金额、支付状态、停止充电。

路径：权限校验 → 调用 CPMS API → 检查结果 → 回复。

C. 操作指导与常见问题

例如扫码失败、如何启动充电、如何查看订单、如何申请退款。

路径：检索知识 → 组合标准答案及相关媒体。

D. 其他或无法解决

无法识别意图、知识未命中、重复处理仍无效。

路径：澄清问题 → 提供人工客服入口或创建工单。

安全事件最好再用明确的规则做兜底，不要完全依赖大模型的意图分类。

### 重点配置二：知识检索节点

把刚才生成的 C 端 FAQ 工作簿导入 Dify，作为独立的知识库数据源。接下来需要在 Knowledge Retrieval 节点选择该知识库，并做以下设置：

| 配置项 | 建议 |
| --- | --- |
| Query | 当前用户的问题 |
| 检索模式 | 优先测试混合检索：关键词 + 语义 |
| Top K | 初始设为 3–5 条，按测试效果调整 |
| 元数据 | 语言、国家/地区、运营商、版本、生效状态 |
| 无命中处理 | 澄清问题、给出人工客服入口，不凭空编造 |

Dify 支持混合检索、重排序及元数据过滤；最终参数应通过真实用户问法测试来调优。

知识检索后的 LLM 节点，建议明确规定：

- 操作步骤必须来源于已审核的知识库。
- 实时状态必须来源于 API，不得靠语言模型推断。
- 退款、费用和运营商政策只采用对应租户已生效的规则。
- 找不到答案时明确告知，并引导转人工。
- 根据用户语言输出，并关联对应语言的图片或视频。

### 重点配置三：CPMS API 调用

这里是 AI 客服从普通 FAQ 机器人升级为真正的 CPMS 智能客服的关键。

Dify 的 HTTP Request 节点可以请求外部 API，并将返回结果交给后续节点。

建议首批开放以下接口：

| API 能力 | 客服场景 |
| --- | --- |
| `getStationStatus` | 查询站点和充电枪状态 |
| `getChargingSession` | 查询当前充电会话及进度 |
| `getOrderDetail` | 查询用户自己的订单 |
| `getPaymentStatus` | 查询支付状态 |
| `getRefundStatus` | 查询退款处理状态 |
| `requestStopCharging` | 请求停止充电 |
| `createSupportTicket` | 创建客服工单 |

这些是建议的逻辑接口名称，不是 TrendPower 现有 API 的确认名称，需要由研发按实际接口规范实现。

特别注意：用户身份和 `tenant_id` 必须由可信的业务后端注入并验证。涉及停止充电等有副作用的操作，还需要权限校验、必要的用户确认、操作审计及失败兜底。AI 不应直接访问客户数据库，也不能仅凭用户在对话里声称的订单号就读取他人的订单。

## 四、结合 TrendPower 的部署架构

你们的产品既有 SaaS，也有客户私有部署，因此不建议让 Dify 直接连接所有客户的 MySQL。

TrendPower C 端 App / Web

TrendPower AI Gateway

用户认证 · 租户隔离 · 接口权限

Dify Chatflow

分类 · RAG · LLM · 业务调用编排

知识库

FAQ、规则、多媒体索引

受控业务接口

CPMS API / 客户侧 Agent

对于私有部署客户，客户服务器上的 Agent 负责执行经过授权的本地数据查询和业务操作，再把必要的结构化结果返回给 Dify。网络连通可以通过经过认证的 API 或受控的安全连接实现。

不建议让客户侧 Agent 与 Dify 各自重复调用一次 LLM 来处理相同的问题。 默认让 Dify 负责意图理解、知识检索和最终答复，Agent 负责数据访问与工具执行即可；只有确实需要本地推理的场景，才单独考虑本地 LLM。

## 五、首版的开发范围

我建议先完成一个端到端闭环，而不是一次性把所有 AI Operation 功能都塞进一个工作流：

| 项目 | V1.0 要求 |
| --- | --- |
| Dify 应用 | 1 个 WF01 AI Customer Service Chatflow |
| 知识库 | 导入现有 C 端 FAQ，完成检索测试 |
| 多媒体 | 先接入开始充电、停止充电、故障排查等核心素材 |
| API | 优先打通充电状态、订单查询、支付状态及建单 |
| 安全与权限 | 租户隔离、身份验证、失败兜底、审计 |
| 验收 | 高频问题测试、API 异常测试、越权测试、安全问题测试 |

后续再把 WF02 订单失败分析、WF03 充电桩离线分析、WF04 OCPP 错误分析和 WF05 日常运维报告设计成独立工作流；WF06 知识助手则根据其使用对象决定是否单独提供 Chatflow。

我的建议：先把 WF01 做成“知识检索 + 受控 API + Answer 输出”的 Chatflow。 这既能复用刚才的知识库内容，也能让 TrendPower 的 AI 客服真正具备查询实时业务信息和处理用户问题的能力。
