## 里程碑

### M0：只读确定性诊断

已完成：

- MySQL、TDengine、Redis 固定参数化查询和安全上限。
- 订单、计费、设备、时序和消息证据聚合。
- 禁止任何订单修改、退款、补发、重算和服务控制动作。
- 合成 fixture、PII/密钥脱敏和基础自动化测试。

### M1：生产只读边界与业务规则

已完成：

- 专用只读身份、SSH 本地转发和 TDengine 严格代理边界。
- OCPP、AYK、YKC、operator 等协议和计费侧差异。
- 30 天生产只读回放与代表性路径抽样。

尚未完成：

- 仍没有工程师确认的真实故障结论，不能宣称业务准确率完成验收。
- 两轮车规则暂不完整，第一版必须低置信度或明确不支持。

### M2：Codex-native thin harness

已完成：

- Codex 负责选择证据工具和形成因果判断，Python harness 只负责身份、只读边界、日志、脱敏、验证和恢复。
- Responses API provider、同一 `base_url` 下可插拔 key slot、真实模型 fixture 验证。
- 运行目录、证据哈希、超时、provider 失败和 thread resume。

边界：真实模型验证和生产只读回放不是工程师确认的真实故障验收，必须在后续记录中分开表述。

## 更新规则

每次里程碑提交前必须同时检查：

- `docs/开发进度.md` 是否记录本次目标、提交、验证、缺口和下一步。
- `docs/validation.md` 是否记录新增测试、真实环境结果和失败修复。
- README、部署和架构文档是否与用户入口和安全边界一致。
- 所有“通过”“完成”“验收”结论是否能在 CI、artifact、测试输出或工程师确认记录中找到证据。
