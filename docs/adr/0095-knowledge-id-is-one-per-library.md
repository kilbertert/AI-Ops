# 95. `knowledge_id` 一个库一条，租户级保留

日期：2026-10-23
状态：Accepted
影响版本：`src/aiops_diagnostics/knowledge_sources.py`、`tests/test_dify_knowledge_api.py`、`README.md`

## 背景

#925 的自动登记把 `knowledge_id` 定成**租户级**一个串：`tenant-<tenant_id>`，检索时把该
租户名下的**全部**库一起查。当时的理由是对的 —— 运营的心智模型是"我租户的库"，而且
不需要为每个新库再登记一次。

**它在 Dify 上不成立。**（2026-10-23，编排页实测）

Dify 的编排页里，"一个知识库"就是**一条 external dataset**，而一条 dataset 只带一个
`external_knowledge_id`。租户级 id 把 N 个库合成一个源，于是：

- 编排页上只能看到"整个租户一个库"，选不出「客服手册」和「售后流程」；
- 运营在 RAGFlow 里新建一个库，Dify 侧**没有任何东西需要点** —— 也就没有任何东西变化。

最终用户的诉求原话是「最终的目的是要给 dify 上的智能体使用」。租户级粒度做不到这件事。

## 决策

**两种 `knowledge_id` 并存，都永久保留。**

```
tenant-<tenant_id>                  → 该租户名下全部库   （#925 的形态，逐字不变）
tenant-<tenant_id>:<dataset_id>     → 恰好那一个库        （本决策）
```

- **旧的逐字不变。** 它已经写在别人 Dify 的配置里。改它的语义等于让线上 app 换一套
  检索结果，而没人会知道这件事发生过。
- **新的按库派生**，与旧的一样是**派生**而不是开户时生成的 UUID：Dify 把这个串存进
  外部知识库配置，改名就 404。派生值在任何进程、任何时候算出同一个结果。
- **带 dataset id，不带库名。** 库名会变；改了名 Dify 侧立刻 404。dataset id 不变。

## 归属校验是这条决策的代价，不是可选项

新形态里，租户 id 与 dataset id 是**两个独立可猜**的段。租户 id 是公开的 —— 它就以
`tenant-<id>` 的形式躺在 Dify 的配置里。所以 `tenant-T-8:<T-9 的库>` 是一次廉价的猜测。

因此 `tenant-<T>:<D>` 只在 **`D` 出现在 T 自己的 RAGFlow 清单里**时可服务；否则与
"未登记"同答 404。这个 404 既不确认库存在，也不透露它归谁 —— 与 #586 的调试身份是同
一条纪律：**"不该你看"和"不存在"必须是同一个答案**。

## 被否掉的替代形态

- **只保留库级，把租户级删掉。** 最干净，但会立刻打断每一个已经配好 `tenant-<id>` 的
  Dify app —— 换一次检索结果、或直接 404。为了一个还没上线的形态去断线上，方向反了。

- **库级 id 不带租户前缀，直接用 RAGFlow dataset id。** 少一个可猜的段，但 Dify 的配置
  从此和"哪个租户"脱钩：一条 dataset 无法回答"这是谁的库"，检索侧只能全表反查 dataset
  归属，而那恰好是我们没有的映射。

- **库级 id 用库名（`tenant-T:客服手册`）。** 人能读懂，但库名是**可变**的。运营在
  RAGFlow 里改个名，Dify 那边配置里的串就指向一个不存在的源。可读性换不来这种脆弱。

- **在 Dify 侧给一个租户建一条 dataset，内部换库。** 需要改 Dify 的 dataset 编辑界面，
  而且编排页上仍然只有一个选项 —— 和租户级 id 一样达不到目的。

## 后果

更容易：一个 RAGFlow 库对应一条 Dify external dataset，编排页上可以逐个选。

更难：**清单路由从 O(租户数) 变成 O(租户的库数)**。实现上按租户取一次清单再展开，
所以上游调用次数不变（仍是一租户一次），变的只是返回条目数。这一条写在这里，是因为
41 上真实租户的库数会继续增长。

未解决：**派生只解决了 id，没解决 Dify 侧有没有那条 dataset。** 建 dataset 是 #1001
（`sync-knowledge-datasets`），在它落地之前，库级 id 只是在检索侧可用，编排页仍然看不见。
