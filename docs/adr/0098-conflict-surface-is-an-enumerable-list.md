# 98. 冲突面是一个可枚举的清单，不是一句「已归零」

日期：2026-10-23
状态：已采纳
影响版本：`.sandcastle/conflict-surface.mjs`（新增）、`.sandcastle/repo-map.check.mjs`、
`.gitignore`、`.sandcastle/REPO-MAP.md`（移出版本控制）、
`.sandcastle/implement*.md` 与 `.sandcastle/implement*/prompt.md`、
`.github/workflows/{afk-policy,agent-implement,agent-implement-prd}.yml`

## 背景：上一轮修了 58%，却说成了「归零」

ADR 0097 把两个证据日志拆成一条记录一个文件，消掉了它们 65 + 60 个分支的冲突面。
但当时只在两个文件上做了这件事，就用了「冲突面归零」这个词。对 105 个远程分支
把冲突文件完整枚举一遍，真实分布是：

| 文件 | 冲突分支 | 性质 |
|---|---|---|
| `docs/validation.md` | 65 | 手写追加式 — 已由 0097 解决 |
| `docs/开发进度.md` | 60 | 手写追加式 — 已由 0097 解决 |
| `.sandcastle/REPO-MAP.md` | 34 | **生成物，被提交** |
| `.afk-bootstrap.json` | 15 | 生成物（版本号） |
| `docs/agents/current-delivery-state.md` | 12 | 手写索引 |
| `deploy/m2-live-03/images.lock.json` | 8 | 生成物（构建身份） |

另外 60 个源码模块各自只有 1–2 个分支冲突。**「已归零」漏掉了将近一半的冲突面，
而漏掉的那一半恰好全部是生成物。**

## 第一性原理：冲突只有三个来源

一个文件会在两个并行分支上冲突，当且仅当两个分支都改了它且改动区域重叠。所以
消除来源只有三条，而且必须**按文件**归入其中一条：

1. **生成物被提交。** 它对每一个改动了仓库形状的分支都冲突，而冲突内容毫无信息量
   （`173 → 174 markdown file(s)`）。可彻底消除：不入库，或只由单一动作写。
2. **多人手写同一个追加式文件。** 可彻底消除：按写入者分片，或改成生成物。
3. **同一份源码被两个分支改同一处。** **数学上不可消除**，除非同一文件永远只有一个
   写者。任何声称消除它的方案（merge queue / 自动 rebase / `merge=union`）都只是把
   成本转移到串行等待或错误合并。

因此「彻底解决」的准确含义是：**前两类清零，第三类靠调度控制并发写者。**

## 决定

### 一、把冲突面变成一个可执行的清单

`.sandcastle/conflict-surface.mjs` 对每个远程分支跑 `git merge-tree --write-tree`，
输出每个冲突路径及其**处置**。判据是：清单里没有 `hotspot`（3 个写者以上的手写散文）。
这个数不是估计，是每次运行现算的。

四种处置：

| 处置 | 含义 |
|---|---|
| `removed` | 已移出版本控制，不存在可分歧的副本 |
| `exclusive` | 仍入库，但只有一种动作会写它，且该动作天然串行 |
| `serial` | 文件形态值得保留，成本付在调度上而不是文件布局上 |
| `source` | 两个分支都在同一个模块里做事，是并发不是格式缺陷 |

`--check` 只问一件事：**一个已移出版本控制的路径，在这棵树里是否又被跟踪了**。
它不问「仓库现在冲突吗」—— 那永远为真，且不可行动。`exclusive` 与 `serial` 是报告，
不对它们设门禁：分支没做错，让它们变红只会让检查被无视。

这个门禁的第一次写法是错的，值得记下来：它把「与 `origin/main` 的 merge-tree 冲突」
当成了回归判据，于是**在引入它的那个 PR 上就红了** —— 存量分支还带着被跟踪的副本。
判据必须问被测的这棵树，而不是问移动的基。

### 二、REPO-MAP 移出版本控制

它是被跟踪文件集的纯函数。入库等于给每个改动了文件集的分支开第二条写入路径到同一个
文件。改为 `.gitignore` + 按需生成；**新鲜度门禁一并去掉** —— 它只能断言「有人跑过
生成器」，而一个每次读取前现生成的地图按构造就是正确的，陈旧地图正是它想抓的东西。

替代它的检查是**确定性**：同一棵树两次渲染必须逐字节相同。地图从「提交的副本」变成
「读取时产生」，若生成器每次给出不同结果，冲突只是从 git 转移到了读者脑子里。

### 三、AFK prompt 的冲突是升级机制的症状，不是文件的问题

5 个 live prompt 的唯一内容来源是脚手架升级。所有升级分支都在改它们 —— 冲突来自
**并行跑多个升级**，不是文件形态。处置是 `serial`：升级按版本锚定、一次一个。

### 四、ADR 0033 的追加形态与证据日志同源

它的「落地情况」小节每次都插在同一个位置（实测 `@@ -86 +87`、`@@ -97 +98`、
`@@ -108 +109`），与 `validation.md` 完全同一类。处置是继续把落地记录写进新的证据
文件，而不是接着往这里追加。

## 备选方案与取舍（被否的路线）

- **用 merge queue 解决一切。** 需要组织账号或 Enterprise Cloud；本仓库是个人账号。
  更要紧的是它**不解冲突**，只把 PR 踢出队列，治的是「每次合并都让所有人落后」。
- **`.gitattributes merge=union`。** GitHub 的 PR 冲突计算不读用户 gitattributes，
  本地能自动合、远端照标 DIRTY。危险不在于无效，而在于看起来有效。
- **把源码按模块拆碎以避开冲突。** 拒绝。为 git 发明模块边界，是对代码结构最坏的
  一种改动 —— 冲突是症状，拆错了是永久的。
- **对 `serial` 项设门禁。** 拒绝。它们的分支没有做错，让检查为不可行动的原因变红，
  是检查被无视的最快路径。

## 后果

- 清单从「98 个路径、92 个未决」收敛到「**0 个 hotspot**」：1 removed、2 exclusive、
  29 阈值以下、6 serial、60 source。
- 一个问题被诚实地留在清单里而不是被解决：`CHANGELOG.md` 能从 Conventional Commits
  完整重建，却仍被手改并入库，是下一个该 `removed` 的候选。写进表里而不是悄悄略过。
- **`acceptance.feature` / `qa-plan.md` / `runbook` / `GLOSSARY` 的冲突不会消失。**
  它们七天里被改了 12–18 次，横跨整个文件，没有可拆的插入点。这是第三类，代价是调度。
  任何声称「冲突已彻底解决」的说法，如果不区分这两类，就是本文开头纠正过的那个错误。
