# 52. 执行配置身份在**签发时**固定，在**领取时**对照，两者都落记录

日期：2026-10-19
状态：已采纳
影响版本：`src/aiops_diagnostics/execution_manifest.py`、`agent_runs.py`、`gateway_api.py`、`gateway_config.py`

## 背景

节点片已能让真实节点在调用模型前拒绝配置漂移（#842）。但那只是**节点自己**拒绝；
Gateway 手上没有任何关于「这次委派应当跑在什么配置上」的记录，于是：

- 无法回答「这次 run 用的到底是哪份配置」——回执里的 `agent_version` 一直硬编码 `None`；
- 也无法拦住「节点跑的是另一份配置」这种情形，因为没有任何可比对的期望值。

## 决策

1. **期望值只来自受控清单**（`AIOPS_GATEWAY_EXECUTION_MANIFEST_FILE`），身份＝清单**原始字节**
   的 sha256。不对解析后的对象做序列化再算摘要 —— 那会把 JSON 归一化差异引成身份差异，
   让两端算出不同的值。这与节点侧是同一个算法，因此可以直接逐字比较。
2. **签发时固定**：每次签发写入 `expected_agent_version`。**每次重读清单**，不缓存到进程生命周期 ——
   撤销/轮换必须像节点凭据一样「下一次立刻生效」（既有纪律：
   `AgentRunConfig.load` 的「每次调用都重读」）。代价是每次签发多一次 read + sha256。
3. **领取时对照**：节点回传 `X-AI-Ops-Exec-Config`，与记录里的期望逐字相等才放行；
   不等或缺失 ⇒ `refuse("exec_config_drift")`，**不返回快照**。相等时把实际值写入
   `observed_agent_version` 供审计。**三条放行路径共用同一段判定**（首次领取、成功快照的重试、
   领取竞争失败后读到的那份结果）—— R1-1 的教训就是放行路径各有一次机会，只覆盖一条会漏。
4. **列变更做真迁移**：`CREATE TABLE IF NOT EXISTS` 不会给已有库加列。用
   `PRAGMA table_info` + `ALTER TABLE` 幂等补列；旧行保持 `NULL`，**不回填、不猜**。
5. **回执取自记录**：`agent_version` 来自 `expected_agent_version`，绝不取自模型文本或节点
   自报以外的解析结果。未启用清单时保持 `null` + `not_wired`。

## 备选方案（被否）

1. **把身份放进 run_id 或对话上下文**：被否 —— run_id 只是关联编号，契约明确它不承载身份；
   把身份塞进去会让「知道 run_id」变成「知道配置」，且不可审计。
2. **启动时读一次清单、进程内缓存**：被否 —— 撤销时延从「下一次领取」变成「下一次重启」，
   与节点凭据的既有纪律相反。
3. **只记一个摘要、不落期望与实际两列**：被否 —— 那样无法区分「期望是什么」与「实际是什么」，
   漂移时也就无法审计到底差在哪一侧。
4. **把节点自报的摘要当作制品证明**：被否 —— 节点自报是**受信声明**，部署侧核验是另一件事，
   两者分开记录，不合并成「已验证」。

## 后果

- 回执里多了 `agent_version_observed`；`exec_config_state` 目前只有 `expected`/`matched`
  两个取值（漂移时不写，因为记录已被 `refuse` 钉成终态）。
- 未启用清单时行为与今天逐字一致 —— 这本身是一条用例（GW-04），不是口头保证。
- 本片改 `src/**`，**命中生产 CD 触发路径**，与节点片不同：合并前需单独评估部署影响。
- 仍未证明：真实供应商、真实订单、生产装配。`verify-aiops-gateway` 证明的是 API 契约与
  鉴权模型，不证明模型驱动路径。
