# 207. 地址词是「或」不是「且」：多给一个地名不该把真实站点筛掉

日期：2026-11-04
状态：已采纳

## 问题

用户问「帮我找出广州天河的充电桩」，AI 回答**没找到**。但 CPMS 里明明有：

```text
HuaJing Station
49P4+2PV, Zhong Shan Da Dao Xi, 天河公园 Tian He Qu, Guang Zhou Shi,
Guang Dong Sheng, China, 510630
```

## 根因

`SiteKeywords.matches()` 用 `all()`：

```python
return self.name in name and all(term in haystack for term in self.address_terms)
```

地址里写的是**拼音** `Guang Zhou Shi`，而用户说的是**汉字**「广州」。
于是「天河」命中（`天河公园`）、「广州」命不中 —— `all()` 一票否决，整条记录被本地过滤器丢掉。

同一段代码在 2026-10-29 是**成功**的：那次模型只提取了 `["天河"]`，单词语义下
`all` 与 `any` 等价。也就是说这个缺陷**取决于模型这一次提取了几个词**，
表现为「同一个地点，有时查得到、有时查不到」。

上游并没有错：`total` 是 CPMS 按 `address` 过滤后的真实计数；错的是我们在拿到结果之后
**用更严的规则又筛了一遍**。

## 决策

### 一、逐词查询上游（`address_queries()`）

**这才是真正解决问题的那一条。** 上游 `address` 是**子串匹配**，实测：

| 传给上游的 address | 结果 |
|---|---|
| `广州天河`（整串） | `total: 0` |
| `天河` | 命中 `HuaJing Station` |

用户说的「广州天河」是**上级地名叠下级地名**，不是一个字面串。所以按词分别查、按 `id` 合并。

多词查询有两个代价，都已收口：

- **`total` 不再可信**：每个词各数一次，同一个站会被数两遍。多词时 `total` 返回 0，
  渲染层本来就有一条「本次读取到 N 个」的路径。
- **请求数 = 词数 × 页数**：词数受协议上限（至多 4 个）约束；凑满展示上限后停止后续词。

### 二、本地匹配改 `any`

地址词之间改为 `any`：

- 用户说「广州天河」指的是**广州市天河区这一带**，不是要求两个字面串同时出现；
- 多给一个地名只会让查询**更宽**，不会筛掉真实结果 —— 这与产品的直觉一致；
- **站名仍保持 `all`**：站名通常只有一个词；真给了多个时，「名字里都要出现」才是对的。

## 被否掉的替代

- **去掉本地过滤，只信上游**：C 端路径上游按**租户**返回，本地过滤是越权防线，
  去掉会让「本人只有一个站点」的用户看到整个租户（`outside_scope="skip"` 正是为此）。
- **加拼音/英文别名表**：治本但覆盖不全、维护成本高，且这次的真实地址本身就同时含
  汉字与拼音（`天河公园 Tian He Qu`）—— 只要不要求「全部命中」就够了。
- **只改本地 `any`、不动上游查询**：**第一版就是这么写的，它不解决问题** ——
  上游收到「广州天河」时返回 0 条，本地 `matches()` 拿到的是空列表，`any` 与 `all`
  根本没有机会执行。2026-11-04 复审指出后才发现（我自己先前的判断也是错的）。

## 代价

- **不解决跨语言匹配**：只给「广州」一个词时，仍命不中拼音地址 `Guang Zhou`。
  这次的修复靠的是「天河」这个**在地址里确实以汉字出现**的词。别名表属于另一个决策。
- 语义放宽：多词查询会比以前返回更多行。这是**有意的**，且仍受站点范围与展示上限约束。
