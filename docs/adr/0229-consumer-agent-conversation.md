# 229. 客服由一个 Agent 决策，会话与短期取数授权分离

Status: Accepted

日期：2026-11-05。用户确认客户端架构方案并授权实施。客服处理单位是用户问题及其解决过程，
一个问题可以需要订单状态、账务和操作资料；前置互斥分类、固定三分支和最终事实占位符
将取证与表达绑在一起，且180秒运行寿命导致对话失忆。

采用 Dify 官方 Function Calling Agent（工具循环），Gateway保留身份、本人订单、租户/知识库
授权、调用预算、取消及来源账本。会话复用已完成问答，逐次核对依赖对象权限；历史标明非当前事实，
实时状态重新读。最终是自然正文，结构化仅用于工具与证据。仍需真实业务评价，来源关联不证明语义全对。

官方平台依据：[Dify Agent 节点](https://docs.dify.ai/en/guides/workflow/node/agent)。
固定策略包 `langgenius/agent:0.0.51@3c6c32e593b33476cb52f4e5aaf1bf23e1c71b3d07ba64d40690e0dbce3a7e34`。
隔离1.17.1实测：Agent默认version1正确处理常量选库与手动凭据；
额外设置tool_node_version=2会造成选库参数丢失，因此沿用平台当前可执行的默认格式。

新发布合同callback_version6，旧1–5保留供显式恢复。迁移不新建Python模型循环，不引入新的会话库，
不提供业务写工具。受控工具复用原consumer_knowledge插件及其编辑者选库权限；
resource决定资料类型，query/order_no由模型提供，身份与短期grant不由模型提供。

代价：一条被撤销的历史依赖会阻止该会话继续，用户须新建；这保证历史复述不能绕过撤权。
已完成答案作为历史保留，取数授权仍180秒且完成即撤销；答案不表示现在的状态。
原APK缺少conversation_id无法由服务端安全补猜，等待公司发包；原H5与APK验收分开记录。

## 被否掉的替代方案

- 保留前置分类与三分支：可复用已有流程，但无法一次组合证据，也未解决对话失忆。
- 新建Python工具循环：可以自行定制，但重复Dify已有Agent运行能力，增加第二个编排主控。
- 直接保留Dify隐式历史：接线最短，但历史对象撤权后无法在进入模型前逐条核验。

工具层实现上述会话与授权决定：运行内累计预算，历史复用重新核验来源对象。

发布层执行上述合同：官方Agent与受控工具，凭据固定注入，正文无JSON协议。

HTTP接线执行上述决定：callback6绕开旧分类，原回调与回读共用本人授权。
