# 42. 出口的凭据目录按进程分开，而不是按用途命名

日期：2026-10-19
状态：已采纳
影响版本：`deploy/m2-live-03/`（`model-proxy/` 目录、`prepare-secrets.sh`、compose 挂载）

## 背景

受控模型出口最初把凭据放在 `gateway/` 里（`proxy_token`、`upstream_api_key`），出口容器
挂的也是整个 `gateway/`。这带来两个方向相反的泄漏：

- **出口能读业务凭据**：`gateway/` 里同时有 `runtime.env`（业务 Redis/MySQL/UPMS 凭据）
  与绑定表。一个只该持有供应商 key 的进程，因此能读到生产业务依赖的凭据。
- **Gateway 能读供应商 key**：同一目录对 Gateway 是挂载着的，于是「供应商凭据只在出口」
  这句话在文件系统上不成立。

另一边，`M2LIVE_MODEL_API_KEY_FILE` 同时被 `prepare-secrets.sh` 与 `bootstrap.sh` 使用，
正式模式沿用同一环境时会把**供应商 key** 当作「节点凭据」下发。

## 决策

**凭据按「哪个进程需要它」分目录，凭据名不承担这个职责。**

- `model-proxy/` 独立目录：`proxy_token`（节点→出口）与 `upstream_api_key`
  （出口→供应商）。只有出口容器挂它。
- `gateway/` 只放 Gateway 自己的配置与绑定表；出口不再挂它。
- `bootstrap.sh` **固定**读 `model-proxy/proxy_token` 下发给节点，不再看
  `M2LIVE_MODEL_API_KEY_FILE` —— 后者只属于 `prepare-secrets.sh`（它把供应商 key 写进
  出口目录）。
- 正式模式拒绝 HTTP 上游；合成模式要显式标记才容许（合成上游在栈内）。

## 被否掉的替代形态

- **保留一个共享的 `secrets/` 目录，靠文件名区分。** 文件名不是权限边界：任何挂载该目录
  的进程都能读全部文件。要让它成立就得在容器里再做一次读权限隔离，那比按进程分目录复杂。

- **让 Gateway 通过出口的 API 取供应商 key。** 那等于把「出口只转发」变成「出口是密钥
  服务」，扩大出口的职责面，也要求 Gateway 能连出口。

- **只改 bootstrap 的变量，不改目录。** 那修好了「供应商 key 下发节点」，但两个方向的文件
  可见性泄漏仍然存在 —— 它们是同一类错误的两面。

## 后果

更容易：每个容器能读到的凭据集合可以按挂载一眼看出；「供应商 key 只在出口」变成文件系统
事实而非约定。

更难：新增一个凭据就要决定它属于哪个进程，并同时改挂载与 preflight 的白名单；误把业务配置
放进 `model-proxy/` 会被出口读到（这是目录语义的自然结果，靠审查与白名单约束）。

上限：分目录只限制**挂载可见性**，不限制容器内被攻破后的能力 —— 出口仍持有供应商 key，
这是它的职责。

## 2026-10-19 修订：覆盖生产凭据入口与初始化传输

Gateway 同样不得挂整份生产 `keys/`：即使只读，该目录仍可能含供应商 key。
本栈订单读取只需要生成的业务依赖白名单 `runtime.env`；Gateway 自有 `key_home`
继续留在隔离状态根内。compose、启动 guard 和挂载白名单同时移除生产目录入口。
验证枚举实际挂载及可读来源，不能只检查一个约定的出口路径不存在。

初始化文件通过 `docker exec` 标准流传输，避免目标 daemon 在含嵌套只读挂载的
容器上执行 `docker cp` 失败。管理员轮换目标在平台改变前就以服务属主/0600 原子保存
在宿主，然后传入容器；后续传输失败并重建 Gateway 也能恢复。输入由容器服务 UID
以 0600 创建；绑定与节点输出全部成功且非空后，通过同一文件系统的 `os.replace`
逐文件发布。传输失败保留旧绑定；这不是跨两个文件的事务。退出时删除容器临时凭据，
清理失败判非零。凭据不进入参数和日志，不更改 Docker 或放宽只读挂载来兼容复制。
