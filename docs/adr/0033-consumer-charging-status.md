# 本人充电状态经既有授权后读取业务 API

日期：2026-10-16
状态：已采纳（2026-10-16；实现与单测完成，**尚未在任何真实环境部署，见文末「仍未证明」**）

## 背景

平台重整 M1 已证明按 appId 分开执行节点的可行性；M2 需要真实业务能力，
不能把节点返回的合成订单当成已实现。公司现有 chargingInfo 接口可按订单号读取状态，
但入口本身不足以证明本人所有权。公开接口不能把用户声称的订单号当作授权。

## 决定

新增默认关闭的 `GET /v1/orders/{order_no}/charging-status`。
沿用标准调用者解析及 `aiops:orders:read`，只接受 consumer 的非代查本人范围，
先复用既有订单授权，再请求配置钉住的 CPMS（充电管理业务系统）接口。
基础地址只由部署配置提供；禁止重定向，禁止转发浏览器自报的身份字段。

响应只含订单号、原始状态码、既有 `StatusRole`、UTC 读取时间、固定来源、逻辑环境与
Gateway 构建版本。读取时间不是设备上报时间，也不意味着物理枪状态实时。
状态码不重新定义，复用 `order_status.py`；未知码不映射成充电结束。
此版本不返回金额、车牌或完整订单，亦不支持任何写动作。

HTTP 判据沿用仓库标准接口：缺身份 401、错误身份范围 403、无可见订单 404、
授权源不可用 503、上游失败/不一致 502；GET 读取不执行业务变更。
接口语义遵循 RFC 9110 的 GET 与状态码约定。


### 授权记录的存储落实（2026-10-17）

为受控执行保留请求级记录：公司身份与订单号留在 Gateway，外部只传高熵 `run_id` 作为
关联编号；它不是凭证。记录冻结范围上下文、环境、appId、agentId 与预期节点，固定有效期
180 秒。节点凭据以 SHA-256 映射身份；绑定配置为私有文件，非法/重复摘要和非布尔启用值拒绝加载。
范围指纹沿用 `ScopeContext`，不把它误称为完整快照签名，也不防持有数据库写权限的攻击者。

复用既有 SQLite 文件、独立建表，用带状态和期限条件的 UPDATE 原子领取与交回；重启保留
running，避免重复业务读取。撤销后或到期时交回结果不落库；成功记录允许被拒绝释放或撤销。
这里依赖 SQLite 的事务与单写入者语义，不增加分布式队列或锁服务。代价是进程崩溃后的
running 不自动重试，客户端需重新授权；跨主机协调不在本片范围。

本片只落实记录、配置和回执，未接 HTTP 委派/领取。后续接线必须重新核对订单授权与当前
节点绑定，不能把已保存的成功快照直接放行。`agent_version=null`、`not_wired` 如实保留。
证据见 `test_agent_run_records.py` 与 QA 的 AR-REC：含并发领取、重启、撤销、到期交回与事务回滚。


### 委派与领取的接线落实（2026-10-17）

新增两个默认关闭的 POST 入口：消费者提交空对象发起委派，节点持独立凭据领取。
平台仅收到服务端选定的 agentId、sid=run_id 与固定提问；订单和公司身份不进入派发请求。
两个入口复用本人范围与订单授权判据，领取后读取仍复用 `read_charging_status`。

释放新结果、缓存或竞争后结果前，先完成订单授权，再重读配置和记录，核对环境、appId、
agentId、当前预期节点与凭据。拒绝使记录进入失败终态；授权期间发生并发完成也不能恢复
旧记录。临时授权故障首次返回 503，但恢复后需从消费者入口重新授权，不能复用失败 run。
所有这些响应带 no-store；已发送的数据无法撤回，跨授权源不提供分布式事务。

## Alternatives considered

- 将身份授权装进可转发票据：可少一次回呼，但撤销与订单授权变化仍需服务端复核；保留 Gateway 记录和无权关联编号。
- 直接把公司 API 注册给平台工具：接线少，但没有本人的订单授权保证，拒绝。
- 从数据库状态列直接回答：可复用查询，但会绕开公司 API 的状态组装；本期使用已有 API。
- 同时移植所有工具、登录、发布：范围过大，难以区分业务接口和平台接线的失败，暂不做。

## 落地情况与仍未证明

实现见 `src/aiops_diagnostics/charging_status.py` 与 `gateway_api.py` 的路由，
单测 `tests/test_consumer_charging_status.py`（17 项），
验收 `acceptance.feature` 的同名 Feature。

本仓库的公开面只有合成验证：`tests/test_consumer_charging_status.py`（17 项）与
`tools/verify_consumer_charging_status_http.py`（真 `aiops-gateway serve` + 一次性数据根，
22 项检查，含默认关闭、401/403/404/502/503 与 no-store）。替身模型与替身 CPMS 的取舍
沿用 ADR-0030 的判据。

一条非显而易见的事实保留在这里：真实信封是 `code`/`msg`/`data` 形状，
不是 `ok`/`data`（ADR-0030 同一结论）。

**尚未证明**：路由没有部署到任何真实环境，端到端（客户端 → 路由 → CPMS）没有真实
客户端走过；只覆盖 consumer 本人这一条范围路径；真实业务数据的字段裁剪只在合成
上游上验证。

## 后果与边界

这是 M2 的受控读取能力，不等于公司会话到 Snail 工具上下文的完整可信传递已经实现。
Gateway 版本不是智能体版本；逻辑环境来自部署配置，不是对 Snail 调度位置的独立证明。
启用前必须核对该环境的会话、授权数据源和 CPMS 地址匹配；真实业务验收另记证据。

## 2026-10-21 接线审查：同 run 快照的消费者交付（已选方案，未实施）

消费者委派成功后增加五字段 `charging_status`，取自同一 run 已持久化的快照；共用
`AgentRun.receipt()` 保持原样。交付业务正文前必须重新授权，并在外部授权完成后复核
现行绑定、run 状态与期限；领取时授权不能覆盖稍后向消费者释放这一跳。

只展示执行回执不能回答业务状态；另外直读得到另一观察，不能假称同 run。
选择同步成功分支交付，暂不增加轮询、幂等键或服务端本地化字段。代价是超时后结果未知，
客户端不自动重发，且 App 需自有错误分类和状态文案。详细要求及反例见
[App/BFF 接线契约](../agents/m3-app-bff-contract.md)。本节不宣称字段已上线或业务已验收。

## 2026-10-21 消费者快照实现（待 PR）

消费者成功响应在原回执旁增加同 run 的五字段 charging_status，摘要算法不变。
最终放行先复核本人订单，再读取绑定与运行记录；AgentRunStore.get 的到期收敛与读取
合并在同一事务中，复用现有 TTL。失效绑定、主体或配置身份不符、损坏快照均拒绝正文。
共用 receipt 与节点完成协议保持原样；未启用清单的消费者成功响应也增加该对象。
既有 Java 验收的成功响应键集合据此更新，独立 receipt 的旧键集合判据保留。

代价：每次成功交付多一次只读授权查询；外部授权源与本地事务之间仍无分布式原子性，
本地最终读取是放行时点。API、节点失败路径和真实业务验收继续分别记录。
