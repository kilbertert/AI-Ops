# 330. 知识命名空间迁移保留原owner，不新建知识账户

状态：已采纳。Refs #1535、#1537；适用旧知识账号迁入已批准环境目录，不授权生产迁移。

## 问题与决定

旧实例的KB映射使用裸公司租户ID；新实例使用环境与租户复合命名空间。
直接启用运行目录会找不到原库；把本地登录名改成新派生邮箱也不能登录原owner。
部署版RAGFlow的`PATCH /users/me`忽略email，重建账户会改变知识库归属。

只以受控一次性工件重键KB自有映射，保留owner登录名、库ID、密码和API token。
继续准备旧owner之前，从新`GET /kb/tenants/current`只读精确环境命名空间，
核同一登录名并验证原密码；跨计划继承资源的新任务也不沿用旧密码验证结果。
同一有效计划内重复提交按幂等返回同一回执，计划到期后新任务才重新验证。没有映射、错环境或错误凭据均拒绝，不回落裸租户。
任务必须显式登记原库ID；缺项拒绝，不创建空库替代现役资料；旧owner不再重复注册。
本片不提供登记原库ID的管理入口：已迁移旧owner的首次准备保持阻塞。登记入口须把原库绑定到
精确环境、租户与准备任务并纳入任务摘要，随41成套切换另行裁决，不以继承旧候选任务资源代替。
已发出且结果未知的建库例外：只按原名对账、不再POST，避免把已存在的库误判为缺项。
新账号继续沿原派生命名流程，未启用迁移的部署保持原行为。

工件默认只读，写入前独占持久备份、事务内比较源owner和目标缺席；恢复比较整条迁移后映射，
凭据或归属漂移即拒绝。命名空间编码沿`knowledge_tenant`的JSON与[RFC 4648 §5](https://www.rfc-editor.org/rfc/rfc4648.html#section-5)的base64url合同，
独立部署脚本不依赖目标安装AI-Ops Python包，检查规范编码且第二个元素必须为指定源租户。
SQLite使用[官方URI参数](https://www.sqlite.org/uri.html)的`mode=ro/rw`和`BEGIN IMMEDIATE`语义，不声称跨宿主原子事务。

## 被否方案

- 新owner复制原库：能避免改映射，但改变身份和库ID，重复索引并破坏现役应用引用。
- 保留运行时别名或双读：切换较方便，却让旧来源长期参与决策，无法证明唯一环境归属。
- 只改本地邮箱：差异最小，但上游没有对应登录账号，登录与开户检查立即失败。
- 仅以已校验时间戳接纳旧账户：少一次读取，但不能证明新环境已取得该owner的映射。

## 后果与上线顺序

旧库和账户不重建；重键本身不解除阻塞，须另有获准的原库登记入口才能继续准备；旧owner需要增加一次精确映射与密码确认。
先部署兼容的KB只读接口，再部署Gateway；新接口不可用只阻塞已迁移旧owner，旧流程可用。
生产重键须在成套切换窗口暂停受影响业务并与运行目录、发布快照和会话接续一起安排，
不能把本片当41全部迁移。公司知识控制台若仍发送裸租户头，也必须纳入切换；
没有全部现役调用方的获准方案时只预演，不执行重键。备份含原API token，保持私有；恢复不会复活已变化的凭据。
