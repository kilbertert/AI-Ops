# 198. 对象后面的装饰字符是供应商的毛病，不是交付失败

日期：2026-11-03
状态：已采纳

## 问题

#1326 部署后复测同一张单 20 次：16 成功 / 4 失败。4 次失败里有 3 次
`json_parse json_syntax`，其中一次的原文结尾是：

```text
…你想先核对哪一项？"}"
```

**多了一个引号。** JSON 本身完整、可解析，只是最后多包了一层。整轮诊断因此失败。

## 事实

- 显式设 `max_tokens`（4096 / 8192 / 16000）**没有帮助**，截断率不降反升：
  说明这不是长度上限问题，是模型偶尔把自己的输出多包一层。
- 同一实验里换提醒措辞也没有系统性改善（现有措辞反而最好，9/12 合规）。
- 也就是说：**这类失败不是「我们没要求好」，是供应商的装饰**。

## 决策

`parse_answer` 在围栏解析之后，加第三道：按 `_object_end` 扫出**第一个完整对象**重解析，
但**只在残余是装饰字符**（空白、引号、逗号、闭合括号）时接受。

拒绝的仍然拒绝：

| 形状 | 判决 | 理由 |
|---|---|---|
| `{"a":1}{"b":2}` | 拒绝 | 两个对象，挑哪个都没有依据 |
| `我帮你核对了…` | 拒绝 | 散文 |
| `{"a":"b` | 拒绝 | 截断，结构没闭合 |

## 与 ADR-0197 的分工

- **0197** 管「模型没吐 JSON」：靠提醒降低概率、靠有界重派兜住；
- **0198** 管「吐了 JSON 但多一个字符」：这是**确定性的**解析宽容，
  不需要重派、不花额外调用、不降低任何判据。

两者是不同层：0198 修好之后，一部分原本会被重派的 run 直接一次成功。

## 被否掉的替代

- **显式设 `max_tokens`**：实测无效（4096 / 8192 / 16000 三组截断率不降反升），
  因为它根本不是长度上限问题。设它只会让配置看起来像解决了什么。
- **换更严格的提醒措辞**：A/B 过三种，现有措辞反而最好（9/12 合规，
  简版 5/12、不带提醒 3/12）。措辞不是瓶颈。
- **无限重派直到成功**：截断是概率性的，重派确实能提高成功率，但它把
  「供应商持续不稳定」伪装成「只是慢」，而且每次重派都是一次完整模型调用。
  有界重派（ADR-0197）保留，但**先修掉这个确定性的解析失败更划算** ——
  一个字符的装饰不值得再花一次调用。
- **什么都不做，只靠重派**：那样每次遇到都要多一次调用与一倍延迟，
  而这类失败本来可以零成本消除。

## 代价

残余白名单是 `"` `}` `{` `,` 与空白。若供应商以后出现别的装饰（例如多余的中括号），
仍会被判失败 —— 那时再补，不预先放宽。
