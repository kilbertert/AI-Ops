# 51. 执行配置的期望值必须**逐字（无有损归一化）**比较，并在构造之后每轮复查

日期：2026-10-19（R1、R2 修订）
状态：已采纳
影响版本：`tools/m2_close/node/`（`exec/` 守卫、`GovernedToolRuntime`）、`tools/m2_close/m3node/`

## 背景（含一次被证伪的概括）

要让真实节点在调用模型之前拒绝配置漂移，本片第一版把「最靠近模型的地方包一层」拆成
「消息面留在最终边界、模型与工具面放到构造期查」。**第一版是错的，Codex 用独立探针证伪**：
一个 order 晚于 `ToolCallingAdvisor` 的 advisor 在最终调用前改写有效选项，
`model` / `temperature` / 同名工具 description / 同名工具 schema 四种改法**全部通过**，
每次都 `chatCalls=2`、`claimCalls=1`、无异常 —— 也就是说，构造期查过一次之后，
运行时改写完全没人管。

错误出在一个被过度推广的观察。我此前实测到「不经过 `PromptFactory` 的路径上
`prompt.getOptions()` 是 `null`」，并把它写成「最终 `Prompt` 上没有模型与工具」，
据此把这两面从最终边界撤掉。**这个推广不成立**：本节点的真实路径**是**经过 `PromptFactory`
的，而在那条路径上最终 `Prompt` 携带的 options 是完整填充的（本片私有诊断实测）：

```
class=OpenAiChatOptions model=synthetic-model temperature=0.2 topP=0.9 maxTokens=64
baseUrl=http://127.0.0.1:…/v1 apiKeyPresent=true tools=1 toolCtx=[aiops.run_id]
```

`ChatClient` 会把模型构造时铸出的 `OpenAiChatOptions` 作为请求选项合并进本次 `Prompt`，
而排在 `ToolCallingAdvisor` **之后**的 advisor 还能继续改写它。所以最终边界**看得见**
模型标识、选项、工具定义 —— 只是必须主动去查，而且要**每次调用都查**。

另外两条实测仍成立，保留在决策里：`DefaultChatClientFactory` 从不调用 `defaultOptions`
（所以没有 `PromptFactory` 的路径上确实看不到这些）；`ToolRuntime.resolve` 交付的工具集合
是「只解析一个受控工具」该被校验的地方。

调查中一度出现的第二个「发现」也被自己推翻：观察到 `claimCalls=0`、第二轮 Prompt 里是
「工具错误」时，判断是框架的默认解析器解析不到本次交付的工具，于是写了一个
`ToolCallingManagerFactory` 覆盖。**它是错的**：真正原因是验收夹具用了 9 个字符的 `run_id`，
而工具的契约形状是 `run_[A-Za-z0-9_-]{20,64}`，工具按设计拒绝了它。改用合法编号后，
**不改任何装配**，工具即执行。

## 决策

**期望值按「哪一面真的能被观测到」分发，并且凡是运行期还能被改写的面，都在最终边界每轮复查。**

| 面 | 校验什么 | 谁校验 | 频率 |
|---|---|---|---|
| 派发体的 `ModelConfig` | provider / adapter / 模型标识 / endpoint | `GuardedChatModelFactory.requireRunConfig` | 发模型**之前**一次（同步） |
| 构造出来的模型 | 模型标识、有效选项旋钮 | `GuardedChatModelFactory.build` → `verifyModelOptions` | 构造期 |
| 解析出来的工具集合 | name + description + schema | `GovernedToolRuntime.resolve` → `requireResolvedTools` | 解析期 |
| **最终 `Prompt` 的有效选项** | **模型标识、选项旋钮、工具定义、baseUrl** | `GuardedChatModel.ExecGuard.verifyPrompt` | **每次 call/stream** |
| 最终 `Prompt` 的消息 | **完整** system 消息集合、消息形状 | 同上 | 每次 call/stream |

构造期与解析期的检查**保留**（它们让失败更早、错误信息更贴近根因），但**不构成最终保证**：
最终保证在 `verifyPrompt` 里，因为它检查的是本轮真正交给模型的那些对象。

改写用**框架自己的 `mutate()`** 造出被改写的有效选项，不自造一套与框架行为脱节的解释器；
`baseUrl` 一并纳入（构造期已用派发体的 `apiEndpoint` 核过，但运行时仍可改 —— 实测
「只改 baseUrl 不会把请求改道」，模型自带的 baseUrl 优先，所以这条是纵深防御而非已知绕过）。

**拒绝路径必须是同步的**：`ChatSessionRuntime.execute` 的异常表覆盖 `resolve` 调用
（24–101），抛出即走 `cleanup(resolution)` + `acceptError`。把「发模型之前」的漂移放在
`resolve` 里拒绝，就同时得到三件事：失败发生在任何模型与业务调用之前（计数天然为 0）、
不需要为拒绝路径再实现一套「释放工具资源」的机制、也不会退化成「返回空工具集合」这种假拒绝。

配置面上还接受一个既定事实：**清单身份是清单原始字节的 sha256**，不对解析后的对象做
序列化再算摘要 —— 那会把 JSON 归一化差异引成身份差异，让跨语言两侧算出不同的值。

## R2 追加：比较必须是逐字的，请求扩展一律拒绝

R1 之后仍有四条绕过，全部在守卫启用时完成（模型 2 次、业务 1 次）。三条落在**比较方式**上，
一条落在**覆盖层**上：

| 绕过 | 上游实际收到 | 原因 |
|---|---|---|
| `extraBody.model=evil-model` | `evil-model` | 扩展字段按原样合并进上行体，覆盖已检查的字段 |
| `extraBody.messages=[…]` | `system=EVIL-SYSTEM` | 同上，覆盖已检查的消息 |
| 模型 `evil/synthetic-model` | 完整的不同模型名 | 比较时把最后一个 `/` 之前的内容截掉了 |
| `temperature=0.2000001` | `0.2000001` | 比较时两侧都格式化成六位小数再比字符串 |

三条决定：

1. **请求扩展一律拒绝**。本片是固定配置模式，清单没有批准任何扩展字段，目前也没有扩展字段
   需求 —— 所以对非空 `extraBody` 直接拒绝，而不是只查 typed getter 之后继续放行覆盖层，
   也不新增通用配置框架。
2. **模型身份按完整标识比较**，不做任何有损归一化。此前「抹掉最后一个 `/` 之前的内容」
   是我为了迁就「清单声明模型名、派发体可能带 `provider/` 前缀」而加的 —— 那等于把任意
   命名空间判成同一模型。要支持映射，必须有经实测证明的**明确**映射，不能靠截字符串。
3. **数值按数值比较**，不先格式化成字符串。`0.2` 与 `0.20` 是同一个浮点值，
   `Double.equals` 自然等价，不需要格式化来达成；而 `0.2000001` 必须被判为不同。

教训（**限定在本片实测的两处**，不推广成「任何归一化都有损」）：这两次比较失利各自
来自一个**具体的**有损投影 —— (a) 模型名先按最后一个 `/` 截断再比，(b) 数值先格式化成
六位小数再比字符串。两者都把「不同的值」映成了「相同的值」。正确做法是：比较要按
**被消费的那个语义**进行（标识按完整字符串、数值按数值），表示层面的差异（如 `0.2` 与
`0.20`）由类型自身的相等语义解决，而不是把两侧投影到更粗的表示上。

## 备选方案（被否）

1. **只在最终 `ChatModel` 边界校验全部配置**（最直觉的一版）：单看消息面成立，
   但当时误以为 `Prompt` 上没有模型与工具而放弃。R1 实测证明可行，**已改为采用**
   （见上表第四行）；同时保留构造期与解析期的检查作为更早、更明确的失败点。
2. **只在构造期与 `ToolRuntime.resolve` 校验**（R1 之前的第一版）：**被证伪**。
   运行时 advisor 可以在这两处之后改写有效模型、选项与同名工具定义，旧实现全放行。
3. **把期望值做成一整套可扩展的配置 schema 平台**：被否，属于本片明确排除的范围
   （不新建通用版本平台）；本片只接受固定 profile，取值不受支持就拒绝，不做兼容扩展。
4. **在 `ToolCallingManagerFactory` 上覆盖解析器**（一度写下又被撤回）：被否，因为
   「交付的工具不可执行」这个缺口**不存在** —— 观察到的 `claimCalls=0` 是夹具自己的
   `run_id` 违反契约形状造成的。在错前提上加一层装配改动只会多留一个无用接缝。
5. **让工具自己反向核对本轮配置**（把守卫经 `ToolContext` 递给受控工具）：被否，
   逻辑上冗余（工具每次调用之前，模型边界已经逐轮校验过），且把装配知识耦合进工具。
6. **在受控工具里放一个「漂移触发器」生产钩子**（R1 之前用于制造中途漂移）：**已删除**。
   生产代码不该带验收开关；中途漂移改由测试侧一个 order 晚于 `ToolCallingAdvisor` 的
   真实 advisor 注入（`BaseAdvisor`，call 与 stream 两条路径都生效）。
7. **让模型名比较容忍 `provider/` 前缀**（R1 的做法）：**被证伪**。它把 `evil/synthetic-model`
   当成 `synthetic-model` 放行。要支持映射就必须是有证据的明确映射，不能截字符串。
8. **数值比较先格式化成六位小数**（R1 的做法）：**被证伪**。`0.2000001` 被抹成 `0.2`。
9. **在生产工具里保留验收计数器**（R1 的 `EXECUTIONS`）：**已删除**。生产代码不该带验收
   专用状态；工具是否真的执行，用测试侧可观测的**业务领取计数**来证明。

## 后果

- 「已验证的配置」这句话现在是：**构造期与解析期各查一次（早失败），最终边界每轮再查一次
  （最终保证）**。不能简写成「最终边界校验了全部配置」而不提它**每轮**都查，
  也不能简写成「构造期查过就够」—— 后者正是 R1 修掉的绕过。
- 验收必须覆盖 **call 与真实订阅的 stream 两条路径**：只实现 `CallAdvisor` 的漂移在流式
  路径上根本不会生效，那样 stream 用例就是空跑（本轮踩过）。
- 反向控制的 `RED-AS-EXPECTED` **只在真的观测到被改写的值时才记**；正对照（无漂移变体）
  不参与敏感性断言。
- 工具的可执行性**没有**被改动：框架默认的管理器与解析器照旧，可解析集合由
  `GovernedToolRuntime` 交付的那一个受控工具决定。
- 本片只在本地合成环境验证；Gateway 签发与持久化、`agent_version` 回执留到下一片。
