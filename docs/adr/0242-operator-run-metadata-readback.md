# 242. Java 运行元数据按当前本人权限读取，与业务结果时效分离

Status: Accepted

用户已批准 #1452 规格中的 LOG #1455。受管管家应用由 Java 执行，Dify 原生日志不能代表
这些运行。决定在原 logs 入口读取既有 `agent_run_store` 的实际记录和 RUN 的有界 trace，
不创建另一份日志账本，也不伪造 Dify 会话；其他应用保留原生日志。

## 读取与授权边界

列表与详情每次核对同源 Dify 会话及当前应用访问权，再解析当前公司身份并刷新场站权限。
仅返回当前本人、当前租户、当前权限指纹及实际 `publication_app_id` 同时匹配的运行；
执行节点的 Snail `app_id` 不代表用户访问的 Dify 应用。请求体不能覆盖身份或范围。
权限指纹变化即不再显示旧记录，包括范围扩大；首版不扩展到员工互看。

输出限定为运行/QA 引用、有效状态、开始时间、阶段/工具名、耗时及版本/来源。
trace 字段白名单为 `phase`、`at`、`elapsed_ms`、`duration_ms`、`tool`、`status`，最多 128 项；
无问题全文、订单号、答案、快照、原始工具 data、参数或凭据。使用已有 store 的只读连接，
不在读取中建表或更改运行状态。列表分页有界，详情使用相同授权条件；JSON 响应均为 no-store。

## 元数据与结果时效

持久元数据可解释过去发生的执行，不代表业务结果仍可交付。结果过期单独标示：成功/失败
终态保持账本值；到期的 `issued/running` 只在响应中显示 `expired`，不伪装为失败。
日志从不调用或替代 `authorize_readback`，因此不能通过过期记录重新取得答案或业务证据。

总耗时优先取最后已采集事件的 `elapsed_ms`，工具本次耗时只使用实际 `duration_ms`；
未采集则明确缺失，不能从累计值猜测。旧记录无 trace 时标注“阶段耗时未采集”，
已有起止时间差仅以 `recorded_timestamps` 来源标识，不冒充单调时钟阶段测量。
时间戳沿用 RFC 3339 UTC；缓存语义对应 RFC 9111 §5.2.2.5 的 `Cache-Control: no-store`。

## 备选方案

- 把 Java 运行伪造为 Dify 原生会话：可复用原生日志界面，但来源与执行事实不一致，故保留明确的 Java 来源。
- 直接展示业务快照或复用结果回读：接线较少，却让日志与有时效的证据交付耦合，可能扩大敏感输出，故只投影元数据。
- 仅按租户或签发时权限筛选：可展示更多历史记录，但会暴露他人记录或沿用已撤销范围，故每次核对当前本人权限。
- 新建通用遥测后端或日志 store：可独立查询，却增加持久化与授权副本；本需求由既有账本承担。

## 后果与验证边界

当前权限变化后部分历史元数据不可见，是保守的授权取舍；缺少应用归属的旧运行不猜测回填。
Gateway、同源 bridge 和 Dify web 需配套发布。元数据、工具阶段和构建通过都不证明业务答案正确。
日志权限、过期只读投影及 UI 检查见[运行说明](../agents/operator-cpms/run-logs.md)与
[补验记录](../validation/2026-11-10-dify-operator-run-logs-followup.md)；
RUN 合入 main 后，联动检查通过 `record_trace` 写入真实账本，再从列表及详情 API 读取，
不以构造对象替代持久化。只读判据观察 SQL 操作并核对完整运行记录不变；
不比较 SQLite 文件字节，因为 WAL checkpoint 可改变物理页而不改变任何逻辑数据。
写入尝试由 SQLite authorizer 拒绝并使检查失败，真实整链由父任务验收。
