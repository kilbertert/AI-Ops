# 251. 运行日志行级明细：工具入参/结果摘要投影与人话渲染

Status: Accepted（2026-11-12 用户确认四层明细范围后实施）。

ADR-0249 的运行日志白名单只放行执行元数据，运营反馈行级内容「还是一样简陋」
——trace 行只有阶段·状态·耗时，看不到每步查了什么、拿到什么。本决定把白名单
向外推一格：**有界**入参与结果字段进入运行日志，答复正文、原始证据载荷、凭据、
scope 指纹仍不投影。

## 决定

- 新增 `agent_runs.tool_summaries_json` 列（`gateway_schema` VERSION 升 2）：按工具名
  存一张展示用字段表 `{tool: {显示键: 值}}`。store 写入口 `record_tool_summary`
  硬约束：每工具 ≤8 字段、键 ≤12 字符、值取标量 `str()[:32]`/列表记 `N项`/字典取
  压缩 JSON `[:32]`，全 run ≤16 个工具、同工具后写覆盖——与 `trace_json` 的
  「机器码、有界、可截断」同族，但承载的是**面向展示的摘要**。
- 发射点在 `operator_cpms.proxy()`：成功路径在 `task.evidence[tool]` 落库后，按
  `TOOL_SUMMARY_FIELDS` 的每工具字段白名单摘要 `data`；入参从 `task.arguments`
  摘要（`k=v`、`v≤24`、总长 ≤48）；拒绝路径同样记录入参+拒绝码。摘要写库失败
  不阻断业务（同 `record_trace` 的吞错模式）。
- trace `detail` 边界不变（仍 ≤64 机器码）：新增 `tools=N`（派发携带工具数）、
  `allowed`（复核通过）两个码；拒绝行的拒绝码仍在 `detail` 里、入参进摘要不挤
  detail 预算。
- 前端把每行渲染成整句：「第 N 轮 · 调用{工具中文名}：结果…」+ 行下展示摘要
  （入参 + 白名单字段 + 拒绝原因）；派发/复核/终态各一句人话。模型轮次按 tool
  事件序号推演标注，不改节点上报协议。摘要按工具名后写覆盖，内容属于该工具
  **最近一次**调用，页面只把它挂在该工具最后一个完成事件下——同工具先拒后成
  时，历史拒绝行只显示自己的拒绝码，不背上后来才取得的结果。
- 首次 bump `user_version`（1→2）同时固化版本语义：`_version` 接受
  `0..VERSION`（0=版本化之前、中间值=已知历史发布），只拒更晚版本写出的库；
  `check`/`ensure` 对低于当前版本的库走 `legacy` 校验，缺列以 `LEGACY_COLUMNS`
  为白名单补齐。现网 v1 库部署后自动迁移，不是启动阻断。

## 边界

- 摘要值来自 `task.evidence[tool].data`——执行层已授权证据；读取仍走既有
  `scope_fingerprint` 闸，可见范围不变。变的是**信息密度**：运营在控制台直接看到
  订单状态/金额/站点名等字段原值，无需再翻业务库。
- 字段表在代码里固定（`TOOL_SUMMARY_FIELDS`），不是任意字段透传：新增工具要先
  加表才出摘要，漏配只是「这行没摘要」不是泄漏。
- 不投影：答复正文、证据全文 JSON、CPMS 原始响应、授权参数（token/grant）、
  scope_fingerprint、自由文本错误。`stoppedReasonContent` 等长文本按 32 字截断。

## 备选方案

- **detail 码携带全部信息**：64 字预算放不下字段名+值，且 store 明确要求机器码；
  会逼出不透明的压缩编码，判读成本更高。
- **前端直接调证据接口**：控制台读证据需要另一条授权链，复制网关闸到前端不可行，
  且证据全文比摘要大一个量级。
- **逐工具自定义渲染器**：11 个工具各写展示组件，收益递减且漏配即空白；字段表
  一处维护、前端统一渲染更省。
- **真·逐轮模型决策上报**：改 Java 节点回调协议，工作量单独一档；本轮按 tool
  事件序号推演轮次，后续需要再立项。
