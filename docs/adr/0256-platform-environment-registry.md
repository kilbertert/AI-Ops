# 256. 平台维护业务环境和租户接入登记

> 后续状态：95试验已撤回；平台维护环境登记的原则保留。公司正式网关、集中页面与一键开通的后续目标见[新方案](../architecture/2026-11-14-company-gateway-onboarding.md)，尚待确认，不能把历史部署拓扑当推广模板。

Status: Accepted

2026-11-14，已采纳。用户经后端确认，公司没有从登录身份到环境服务地址的完整发现能力，
明确由AI-Ops维护映射，并指定95作为第二环境验证。停止等待公司目录投用；其源码中的platformCode映射不是运行前提。

沿用ADR0253的每环境独立Gateway/登录代理/数据根，平台登记环境、租户启用状态与业务配置引用。
公司认证仍提供用户与租户身份，登记只决定是否开通和去哪取数；不逐个维护公司用户。
首轮以aiops-admin发布私有JSON，版本比较和文件锁防并发覆盖，状态与审计同次原子替换。
没有引入集中共享库或新的常驻目录服务；多宿主采用受控副本，生效以各宿主回读版本为准。

启用登记的实例不从默认CPMS推断租户归属；缺项/损坏拒绝。环境连接变化须重新部署/绑定，
已有会话不得静默迁到另一数据源；租户/环境停用在下一次经过准入校验时生效。
Dify自身会话不由此全局吊销，其控制台只读页面仍受原会话寿命约束；业务调用和新登录另行校验登记。
旧41未启用登记时维持既有行为，95必须显式启用。

替代方案与权衡：进程隔离复用现有权限和存储约束，增加每环境少量进程/配置；共享单进程需同时迁移身份、
会话、管理映射与缓存，当前没有足够收益抵消风险。95实测资源、开通/回退步骤与故障隔离后再判断适配程度，不宣称全局最优。
