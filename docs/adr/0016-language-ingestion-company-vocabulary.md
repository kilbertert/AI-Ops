# 语言标识的接入：认平台词汇 + 让中文地区决定脚本

日期：2026-10-12
状态：已采纳
影响版本：issue #712

## 背景

`Accept-Language` 是回答面上**唯一**一处「客户端说了什么，服务端照着做」的输入。
它的解析规则一直写在 `i18n._declared_tag` 里，规则是两条：

1. 整串正好是一个已声明的标签 ⇒ 用它（`zh-Hant` 因此能活下来，`#531`）；
2. 否则**丢掉地区子标签**，取第一段（`en-GB → en`、`zh-Hans-CN → zh`）。

这条规则的前提是「调用方发的是 BCP 47 标签」。**这个前提在真实客户端上不成立。**

2026-10-12 前端反馈「切了语言之后快捷指令与预设问题没跟着变」。在 41 上抓包 + 用抓到的
真实生产 JWT 逐值回放，拿到的是一张**词汇表对不上**的图景——公司平台自己的后台
「语言配置」页（`sys_language.lan`，9 行）是客户端取值的**权威**，而它的值是：

| 语言 | `lan` 值 | 是 BCP 47 标签吗 |
|---|---|---|
| 中文-简体 | `zh-CN` | 是 |
| English | `en` | 是 |
| Portugal | `portuguese` | **不是**——是语言*名* |
| España | `spanish` | **不是**——是语言*名* |
| 中文-繁體 | `zh-HK` | 是，但地区是**香港**（默认脚本是繁体） |

于是三格各**静默回退**一次，而响应里的 `language` 回显的仍是**请求的语言**。
用户看到的是：切了葡语/繁体，拿回来的是中文，而 `language:"zh"` 看起来又不像错误。
**他分不出「设置没被听懂」与「这门语言还没有译文」** —— 这正是本项目反复要消灭的
「假陈述」形态（同一个形状此前在 FAQ 目录、快捷动作、健康报告三处都出现过）。

实测对照（同一真实 JWT，只改 `Accept-Language`）：

| 值 | 修复前 | 修复后 |
|---|---|---|
| `portuguese` / `spanish` | `served=zh`，中文题面 | `pt` / `es` |
| `zh-HK` | `served=zh`，简体 | `zh-Hant`，繁体 |
| `zh-CN` / `en` / `th` / `vi` / `mn` / `km` | 正常 | 逐字不变 |

同一批前端还指出第二层：请求头的**缺省**是 `getStorageSync("lang") || "en"`，
而同一页 UI 的缺省是 `"" == c ? "zh-Hans" : c` —— 同一个 key、两套词汇、两个缺省。
那一层属前端，本决策不动它，但它是「这个键没有单一权威」的同一个病。

## 决定

**四点。前两点是判据，后两点是配套。**

### 一、解析层的输入是「客户端真实会发的值」，不是「标准标签」

新增一张**显式别名表**：`portuguese → pt`、`spanish → es`。

它刻意**不做模糊匹配**。对未知词做相似度猜测，会在猜错时静默用一门**没有人要**的语言
回答——那比回退中文更糟，因为回退至少是可解释的（「这门语言还没有译文」）。表里只放
已经确证有真实客户端在发的值，加一个词要走一次评审。

同类词汇还有 `pt`（平台写 `portuguese` 但索引写的 `pt`）这一层对不上，因此这张表是
**兼容层**而不是翻译层：它只把词规范化到清单里的标签，不改变清单本身。

### 二、中文地区**决定脚本**，而不是被丢掉

按 CLDR 的 `likelySubtags`（这是回答「这个地区的默认脚本是什么」的标准）：

- `zh-TW` / `zh-HK` / `zh-MO` → **`zh-Hant`**（繁体）
- `zh-CN` / `zh-SG` → `zh`（简体）
- **写出了脚本时脚本优先**：`zh-Hans-TW → zh`、`zh-Hant-HK → zh-Hant`

判据是「标准怎么说」，不是「哪些地区码我记得」。CLDR 的 likelySubtags 覆盖全部地区，
因此新增一个地区码不需要改这张表——这是它与「枚举几个繁体地区」的差别。

### 三、回退保留，但**不再静默**

契约不变：无法识别的标签仍然回退 `zh`、仍然 200、仍然回显「实际服务的语言」。
新增的是一行 INFO：

```
language tag not recognized, falling back to zh: <tag>
```

语言标签是**代码不是用户内容**，写出来不涉隐私。这一行的用途是把上面那种
「两种成因长得一模一样」拆开——下一次再有人问「我切了语言怎么没生效」，
运维能先看这一行，而不是重走一遍抓包。

### 四、顺手修掉脚本分支的段数判据

原实现用 `len(parts) >= 3` 才尝试脚本匹配，于是 **`zh-Hant-TW` 返回 `zh`**（不是
`zh-Hant`）——注释明确宣称支持它，而 `test_i18n` 从未覆盖这一格。改成 `>= 2`。
它与决定二同向（都是在问「脚本是什么」），因此**在同一个改动里修**，不另立票。

## 被否掉的方案

- **只在前端改，把平台值映射成标准标签再发。** 这是爆炸半径最小的做法，也不必让服务端
  认识非标准值。它输在**覆盖范围**：平台后续还会加语言，而每一个新客户端都得各自复制
  这张映射表；服务端认下来是**一处**修，且新旧客户端一起好。选它等于把「多语言支持」
  的一部分责任放在一个我们既不拥有、也无法回归测试的仓库里。
- **对未知词做模糊匹配**（编辑距离 / 前缀 / 语言名的词干）。它能自动接住未来没见过的
  写法，看起来更"聪明"。它输在**猜错的代价方向**：猜错时用户拿到一门没人要的语言，
  而那是**静默**的——比回退中文更难被发现。表 + 可发现性（决定三）覆盖了同样的目标
  （「下次能很快发现」）而不会在猜错时撒谎。
- **地区一律折叠维持不变，繁体只认写出来的 `zh-Hant`。** 这是改动量最小的选项，也与
  「原有契约」逐字一致。它输在**它本来就是这条缺陷的一半**：契约里「地区折叠」这条
  规则写在 `frontend-api-brief.md` 里，而它没有一个字说明「地区会影响脚本」这件事，
  于是实现照着字面做、看起来完全合规。留在原位等于把 `zh-HK` 这个真实客户端会发的值
  长期判成简体。
- **把平台词汇表烧进 `SUPPORTED_LANGUAGES`**（即真的"支持" `portuguese` 这门语言）。
  它输在**清单的语义**：清单是「我们有哪些文案」，不是「调用方可能发什么字符串」。
  混进去之后，覆盖度门、`starter_gaps()`、语言覆盖测试全都要跟着学会处理同义词，
  而它们问的问题（「这门语言的内容齐了吗」）会变得没有唯一答案。

## 后果

**变容易了**：

- 新增语言时，服务端只需要在清单里加一条；客户端的平台语言值只要落在别名表或 CLDR
  推断范围内，不用改前端。
- 「切了语言没生效」这类报告第一次有了**一个成本很低的判据**：看 journal 里有没有
  那行 `language tag not recognized`。有 ⇒ 词不认识；没有 ⇒ 词认识了，去看文案。
- 响应字节数在 nginx 层压缩后是稳定的语言指纹（`/v1/faq/recommendations`：
  en `1189` / zh `1179` / zh-Hant `1555`），因此**不解包**就能从访问日志判断客户端
  发的是哪门语言。这是本轮排查里最省事的工具，记在 `qa-plan.md` 的 PLANG 一节。

**变难了 / 被限住了**：

- 服务端从此要认一批**非标准**的输入。这是知识面的债：别名表是兼容层，不是规范；
  客户端若哪天改发标准标签，这张表仍然要留着（存量客户端不会一起升级）。
- `zh-HK → zh-Hant` 这条推断会**改变既有行为**：此前发 `zh-HK` 的调用方拿到简体，
  现在拿到繁体。这是有意的修正，但它确实是一次行为变更，因此写进了
  `frontend-api-brief.md` §2.4 与 `acceptance.feature`。
- 推断依赖 CLDR 的语义而**不**依赖我们对地区的记忆，因此读代码的人必须知道
  「为什么是 hk/tw/mo 而不是别的」——注释与本节都指向 `likelySubtags` 这个名字。
- **本轮没有覆盖**：客户端的缺省链（`|| "en"` 那条）。服务端已能认出平台值，但
  缺省仍应在前端侧收敛成同一个值，否则「没设置过语言」的用户仍会拿到英文。
