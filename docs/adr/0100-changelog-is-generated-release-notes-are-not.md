# 100. CHANGELOG 是生成物，发布说明是另一份文件

日期：2026-10-23
状态：已采纳
影响版本：`CHANGELOG.md`（改为生成物）、`RELEASE-NOTES.md`（由 `CHANGELOG.md` 改名）、
`.github/workflows/afk-policy.yml`（新增生成物门禁）、`.sandcastle/conflict-surface.mjs`

## 背景：上一轮把它记为「生成物被手改」，验证后发现是两件事

ADR 0098 的未决清单里写着：`CHANGELOG.md` 能从 Conventional Commits 重建却仍手改入库，
是下一个该 `removed` 的候选。动手前先验证「能从 commit 重建」是否成立，结论是**不成立**：

| | 生成版（`git-cliff`） | 仓库里的 `CHANGELOG.md` |
|---|---|---|
| 行数 | 435 | 580 |
| 条目数 | 416 | 524 |
| 内容形态 | 纯 commit 标题 | 含解释、ADR 引用、取舍与代价 |
| 交集 | **0 行** | |

零交集说明它们记录的不是同一件事：前者是「谁提交了什么」，后者是「用户会感知到什么、
为什么、有什么代价」。把后者当成「被误提交的生成物」移出版本控制，会丢掉 524 条人工
撰写的发布说明。

**真正的缺陷是命名混淆**：一个名字叫 `CHANGELOG.md` 的文件，同时被两种角色占用。

## 决定

### 一、名字分开

- `CHANGELOG.md` —— **生成物**。由 `dev-changelog` 从 Conventional Commits 产生。
- `RELEASE-NOTES.md` —— **人工发布说明**，由 `CHANGELOG.md` 改名而来，内容不动。

### 二、门禁跑在能跑到它的地方：开发机，不是 CI

生成物的警示头写在共享策略工具的模板里，重生成必然被覆盖，改它要动整个 release unit。
所以「不要手改」必须靠**门禁**而非文案。

门禁本来打算放进 `AFK Policy`。实测行不通：那个 job 跑在 `ubuntu-latest`，上面既没有
`dev-changelog`（它随 release unit 安装），也没有它的依赖 `git-cliff`。在 CI 里装一套，
门禁断言的就会是**第二个生成器**，而不是产出这个文件的那一个。

所以门禁放在生成器真正在的地方：`dev-policy-audit`，每日在开发机上跑——那也是手改
发生的地方。CI 里保留一句说明，而不是一个假装在检查的步骤。

在 CI 里的第一版写成 `command -v dev-changelog || echo "skipping"`，被立刻删掉：
那正是本仓已有专名的失败形态——把「没检查」报成「通过」。

### 三、它仍留在版本控制里，但要如实说明它仍会冲突

`CHANGELOG.md` 是**给消费方看的产物**：读发布的人不该先跑一个工具，所以它不像
`REPO-MAP.md` 那样移出。但**这并不意味着冲突消失**，必须说清楚：

生成器的输入是 commit 范围，所以**每次 `main` 前进，它都会过期**。任何 PR 只要想
通过门禁就必须重新生成，于是每个 PR 都会写它 —— 冲突从「手写造成」变成「重新生成
造成」，频率几乎没变。

实测（2026-10-23）：两侧各在文件末尾追加一条，`git merge` **会**冲突
（`<<<<<<< HEAD` / `- Y` vs `- X`），因为追加落在同一区域。

诚实结论：**`CHANGELOG.md` 只是从 `undecided` 变成了「有理由的共享」，没有变成
「无冲突」。** 真正的解法是把它的生成时机从「每个 PR」挪到「发布时」（交给 CD 或
发布工作流），那样 PR 不再触碰它。这需要在发布链上决定，不在本片范围，已列为后续项。

## 备选方案与取舍（被否的路线）

- **直接移出版本控制**（上一轮的原计划）。被否：验证表明生成结果与人工版零交集，照做会
  丢掉 524 条发布说明。**这个方案之所以看起来正确，是因为我把「生成物」这个词用在了
  一个其实不是生成物的文件上。**
- **把人工版内容合并进生成版**。被否：416 条 commit 标题对 524 条发布说明，没有可自动
  对齐的主键；合计是两份内容互相淹没，不是一份更好的文档。
- **改共享工具的 header 模板加警示**。被否：那是 release unit 的一部分，为单个仓库的
  需要去改它，会让所有项目都背上本仓的历史；门禁能达到同样效果且不扩散。

## 后果

- 冲突面上 `CHANGELOG.md` 从「待决」变成「已解释」：只有生成器写它。
- `RELEASE-NOTES.md` 进入清单，理由与 `README.md` 同类：里程碑改变用户可见行为时追加。
- 一份发布说明的**事实来源**变清楚了：要 commit 明细看 `CHANGELOG.md`，要用户视角看
  `RELEASE-NOTES.md`。此前两者都在 `CHANGELOG.md` 里，谁都不知道自己在改哪一半。
