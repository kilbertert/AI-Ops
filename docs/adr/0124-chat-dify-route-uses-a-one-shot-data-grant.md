# 124. 聊天可以交给 Dify 跑，但取数凭据是「这一次、这一单」的一次性授权

日期：2026-10-24
状态：已采纳
影响版本：`src/aiops_diagnostics/chat_execution.py`（`engine` 判别）、
`chat_data_grant.py`（新增）、`dify_chat_workflow.py`（新增）、
`dify_run_store.py`（新增，表 `chat_dify_runs`）、`gateway_runtime.py`、`gateway_api.py`、
`gateway_config.py`、`deploy/dify-chat/`（DSL 与隔离验收栈）

## 背景

ADR-0104 把 App 聊天接到了一个**客户节点**上：网关授权、选单，然后派发，节点领取、跑模型
工具循环、交回同一轮快照。那条路线要求客户侧真的有一个节点。

现在要把同一个入口交给**已发布的 Dify Workflow**：编排、HTTP 取数、模型播报都由 Dify 跑。
App 侧的接口、字段、blocks 形状一个字都不改。

难点不在"调一次 Dify"，而在**授权怎么过海**：业务数据在网关这一侧，跑在 Dify 里的
图需要读到它。任何"把用户的会话凭据、或整租户的 key 交给 Dify"的方案，都会把一个人
的一次查询，放大成 Dify 那边能长期复用的能力。

## 决定

### 1. 引擎由**登记**决定，不由"哪条跑得通"决定

绑定表里每条登记带 `engine`（`node` / `dify`）。缺省是 `node`（既有部署原样可读）；
未知值、node 与 dify 字段混配、同一场景登记两次 ⇒ **启动失败**。

没有隐式优先级，也没有"节点失败就试 Dify"。理由与 ADR-0104 第 3 条相同：回落到另一条路线
就是把"另一次执行"冒充成"本次结果"，而用户看到的是同一个 `qa_id`。

### 2. 取数凭据是**这一次、这一单**的一次性授权

`chat_data_grant` 签发一张 ≤180 秒的凭据：

* ≥256 bit 随机，**库里只存 sha256 哈希**；
* 绑死 主体指纹 / 订单 / 环境 / 租户 / QA / workflow 身份；`run_id` 或 `qa_id` 单独出现
  **不能**取数；
* 只允许**一次业务读取**；重复回调只回同一轮已存的快照；
* 完成、失败、取消三种终态都立即撤销。

Dify 的 HTTP 步骤把它**直接绑定**在 `Authorization` 头上（`{{#start.data_grant#}}`），
URL 是写死的常量。模型拿不到它：模型只收到取数步骤的响应体（已裁剪成五个字段）。

### 3. 成功要三条同时成立，"Dify 返回 200"不算

1. 实际运行的 workflow 身份与登记一致（不是别的图、不是草稿）；
2. 这一次有**同一轮**的取数快照（没有取数却自称成功 ⇒ 失败）；
3. 输出能适配成 blocks，且订单号与本次冻结的订单一致。

快照字段必须**恰好**是那五个：多一个就说明有人往里塞了别的东西，按无数据拒绝。

### 4. Dify 的执行记录用**自己的表**，不塞进 `agent_runs`

`chat_dify_runs` 记 `workflow_run_id` / `task_id` / `app_id` / `workflow_id` / `grant_id` /
快照 / scope / 绑定键 / 状态。复用 `agent_runs` 会逼着填 `node_id` 与 `matched`，
那会让"这次没有节点"读成"节点核对过了"。

### 5. 取消：先落本地终态并撤权，再请 Dify 停

Dify 停不下来**不能**撤回本地取消。取消同时撤掉这次 QA 的取数凭据、把执行记录落
`cancelled` —— 否则 worker 会在 Dify 回来之后把一条已经取消的回答放出去。

## 备选方案（均被否）

* **把用户的会话凭据或整租户运维 key 交给 Dify** —— 被否：它把"一个人、一次、一单"的
  授权放大成编排平台可长期复用的能力，撤销单位是整租户。
* **网关把数据读好、作为 Dify 的 input 直接传进去** —— 被否：等于网关替 Dify 跑取数步骤，
  验收就退化成"Python 代发"，也说不清实际执行的是哪张图。
* **Dify 自己持有业务库凭据** —— 被否：那需要把生产库访问权交给一个编排平台，
  且授权粒度只能是"这个租户"，与本人权限冲突。
* **复用 `agent_runs` 存 Dify 执行记录** —— 被否：会逼着填 `node_id` / `matched`，
  让"没有节点"读成"节点核对过了"。

## 代价与已知限制

* Dify 的 inputs 与运行记录会保存本次 input，因此那张一次性凭据对**能打开这个应用记录的
  人**可见。完成/失败/取消后立即撤销，但不声称能追回此前已披露的数据。这是**被接受并
  写明**的限制，不是已消除的问题。
* 本片只支持「固定 HTTP 取数 → 模型 → 结束」这一种图。
* 默认关闭：没有绑定登记就没有 Dify 路线；有 Dify 登记却没有
  `AIOPS_GATEWAY_DIFY_CHAT_BASE_URL` ⇒ 启动失败。

## 为什么不复用租户运维 key

租户级 key 的问题不是"权限太大"这一句能概括的：它把**一个人、一次、一单**的授权，
变成了 Dify 侧一个可长期复用、与调用者无关的能力。撤销它等于停掉整个租户；不撤销它
就要相信"编排平台不会拿它做别的事"。一次性凭据把这两件事都消掉了。
