# 本人状态查询使用现有聊天响应，不新增模型循环

日期：2026-10-22
状态：已采纳（用户授权同时支持本人最新一单；真实业务未验收）

App 已调用 `/v1/assistant/questions` 并渲染 `type=qa/result.blocks`。带订单号的旧请求直接
进入故障诊断，零订单问答仅有知识检索；operator 的 Dify 服务 key 不能代表个人身份。

## 决定

在既有助手入口的诊断分派前，只对明确的只读状态/最新订单查询增加默认关闭的确定性路径。
指定号优先；未指定号且明确最新时用既有 MySQL `list_orders(page=1,page_size=1)`，
按 `resolve_query_scope` 下推租户与本人（工单认 `consumer_id`）后稳定排序。其余缺号查询要求提供号。
只接受 consumer、非代查 self 及有效 C 身份；先授权，再复用 `read_charging_status`，返回前再授权。
地址沿用个人状态专用的既有配置，不能借运维服务地址或 key 兜底。

使用现有 QA 记录/会话槽与 blocks 输出，中文状态复用既有词表，繁体/英文保留业务角色；记录快照和摘要，
证据持久化失败拒正文。HTTP 沿用 RFC 9110 的 401/403/404/502/503 语义，
依 RFC 9111 §5.2.2.5 带 `no-store`。快照是一次当前观察，不是实时物理枪状态或故障诊断。
私有证据记录五字段快照、范围指纹、调用编号和摘要，不记录凭据；已发送数据无法追溯撤回，
外部授权源/CPMS/本地写入没有跨系统原子事务，最终授权放行时点明确在正文持久化前。

会话表增加可空 `status_qa_id`，历史行保持 null。新状态轮次不进入模型上下文，避免旧快照
被误当当前事实；页面回读通过 QA 记录重验权限及摘要。QA 记录到期后不继续释放会话中的快照。
该关系经现有 SQLite 事务迁移；只测试新增列和原历史保留，不把两份存储宣称为原子事务。
旧版本不知道新列，启用后回滚应优先关闭功能并保留新代码的回读守卫。

## 备选与后果

先把 consumer 全量交给 Dify 再过滤违反身份边界；本片不用。扩充问答模型工具枚举需要
同时解决模型选单、发布权限和最终事实验证，查询已可由现有只读方法完成，故不增加这套循环。
不修改公司仓库、不改故障诊断/快捷动作、不承诺所有自由措辞都能匹配。
这补齐 App 个人状态业务切片，仍不代表 App→Dify 或节点切换、M3 发布版本及 M4 切流验收完成。
