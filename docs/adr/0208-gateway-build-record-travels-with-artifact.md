# 208. Gateway构建记录随制品交付，不写回输入锁

日期：2026-11-04。状态：已采纳。

每个源码PR被要求把源码摘要和构建时间写进同一`images.lock.json`，互不相关的分支因此
触发工作树重叠保护与合并冲突。该锁还被正式节点流程读取，不能把整套资产当作废弃试验删除。
CI通过pytest读取该锁，不能用“CI YAML不直接读”推断它不影响必需检查。

## 决策与依据

沿用现有`identity.json`：源码与uv.lock摘要、镜像ID、构建时间属于一次构建的结果，
与镜像一起保存在制品目录并经受控传送。Git保留Gateway基础镜像输入；平台/Java节点锁不变。
构建侧核对记录与当前源码/依赖；部署侧核对记录、镜像ID、三个标签和批准的基础镜像。
移除的是每个分支争写的生成值，缺记录或错配仍拒绝部署，不增加skip或current开关。

参考[SLSA provenance v1.1](https://slsa.dev/spec/v1.1/provenance)区分构建输入与输出：
输入基础镜像对应resolvedDependencies，输出镜像摘要对应subject，built_at对应完成时间。
本项目继续使用现有简化JSON，未实现完整SLSA schema、签名或SLSA等级；记录与镜像同时被
有权限者篡改不在本次能力内。信任仍来自已合并修订、受控构建和摘要核验的制品传送。

## 备选方案

- 条件skip或允许锁落后：只隐藏冲突；过期锁继续混淆输入和结果，未采用。
- CI只做完整双构建复现：不能处理共享生成文件的职责问题；采用独立摘要算法对照和真实构建验证。
- 归档m2-live-03：正式节点与整链工具仍引用平台/节点/基础镜像身份，缺少退役依据。
- 每个PR独立写一个锁文件：积累仓库生成垃圾；已有任务制品目录能承载它。

代价：旧调用方必须去掉`--update-lock`，显式把本次记录交给`context_digest.py --check`；
部署方必须同时保存镜像与记录。普通源码变更不再更新锁，真正修改基础镜像或Java节点仍需评审。
