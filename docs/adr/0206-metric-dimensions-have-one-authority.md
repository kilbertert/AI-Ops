# 206. 度量维度词表与生产点必须是同一份，且判据只写一次

日期：2026-11-04
状态：已采纳

## 问题

三个度量维度（`route_type` / `outcome` / `retrieval_status`）各自有一张闭合词表，
而**生产点是另一份清单**：写 `route_type="..."` 的人不知道词表里有没有它，
词表也不知道还有谁在写。两者之间没有任何测试、没有类型、没有枚举。

后果不是理论上的 —— 本仓已经因此**静默丢过三次**指标：

| 时间 | 丢的是什么 | 规模 |
|---|---|---|
| #392 | 分类器自身的判定路径 | — |
| #697 | 运维分析面的每一条结果 | — |
| #799 | 试运行终态 | **41 上 181 次运行 / 0 行指标** |

形状恒同：生产者写了词表里没有的值 → `record()` 抛 `MetricsValidationError` →
被 `_record_metric` 的 `contextlib.suppress(Exception)` 吞掉 → **症状为零**：
请求成功、页面正常，只是那一行永远不存在。

抑制本身是**对的**（度量不该让一次运行失败），所以这个问题不可能靠"注意观察"发现。

## 决策

三件事：

1. **词表补上 `trial`** —— 止血。181 次丢失的指标从这一刻起开始落库。
2. **判据收成一处** `check_dimension(name, value, *, allow_empty=False)`。
   `record()` 与 `list_runs()` 此前各写一遍同形判断，改一处漏一处没有任何信号。
3. **生产点引用命名常量**（`ROUTE_TRIAL` / `ROUTE_QA` / …），不再写裸字面量。

## 守卫

`tests/gateway/test_metrics_dimensions.py`：

- **每个词表成员都要真的能落库**（参数化到全体 + 三个维度）：照抄 `operations_analysis`
  那起事故的事后补丁形状，推广到全部成员。
- **`test_every_produced_route_type_is_declared`**：机械读出生产点写的字面量，
  不在词表里就红。**这一条才是防住那三次事故的那一条。**
- **`test_the_dimension_checks_are_not_duplicated`**：判据形态只许出现一次。
- **变异验证**：删掉 `trial` → 2 条红；把判据写回第二处 → 1 条红。

## 被否掉的替代

- **只补 `trial` 不建守卫**：前两次事故就是这么"修"的（`routing`、`operations_analysis`
  各补一次），第三次照样发生。补成员不解决问题，**没有东西把两边连起来**才是问题。
- **加一条「判据而无生产者」的机械断言**：实测会误报 —— `faq` / `debug` / `routing`
  经由 `route_tag` 变量产生，按字面量 grep 读不到。硬写会在第一次运行时就红，
  然后被人用 `xfail` 关掉，守卫等于没有。这正是本仓记录的
  「按字面量 grep 做守卫是不可靠的」。
- **不再用 `suppress` 包 `record()`**：能让问题显形，但度量失败会变成运行失败 ——
  把观测手段的重要性排到业务之上，方向错了。
- **改成事件流 / 引入 ORM**：为一个词表问题引入基础设施，代价与收益不成比例。

## 代价

- 生产者改引用常量是**多处小改动**，本轮只改了 `_record_trial_metric` 这一处
  （正在丢数据的那个）。其余生产点仍是字面量 —— 它们不在词表里缺成员，没有现网损失。
- `retrieval_status` 的**托管值**（由 `QaAnswer` 透传，本仓无字面量生产者）仍未显式化。
  #799 的验收第 5 条留给后续；本轮不动它，也不假装修了。
