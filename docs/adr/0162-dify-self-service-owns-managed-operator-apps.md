# 162. Dify自助开通管理应用身份，平台连接与正式路由分别持有

日期：2026-10-29
状态：已采纳

## 决策

用户确认平台运营在Dify开通客户，租户在自己的工作区管理。开通通过正常Dify公司会话和
既有发布服务密钥双重认证；平台必须具有公司edit/publish权限，目标客户来自公司
`/tenant/list/my`的账号绑定集合。客户端不能提交内部地址、文件路径或业务凭据。

平台连接配置一次，包含已部署节点、CPMS地址和受控模型；每个受管应用在数据库保存profile引用。
旧文件目标与受管目标相同可共存，冲突拒绝；环境清单不得覆盖已由页面管理的正式来源。
现役应用按已核对profile就地登记，不重建workspace/app、不增加版本或改变路由revision。

开通任务持久化来源版本、目标、步骤及结果，以操作者＋请求键幂等，工作区按现有租约创建。
Dify导入新增工作区范围的确定性request_id：同请求重试回同app，不以应用名/描述猜测。
应用创建与依赖准备可重试；服务重启将未完成任务标为可重试，凭据不持久化。
首次node-sop直接生成真实V1；发布源登记和正式路由在同一个SQLite事务内推进。

预览使用受管草稿自身的临时执行绑定，不占用正式入口；当前公司订单与站点权限持续重验。
保存回读草稿摘要匹配才发布；UI显示实际Java模型和预算，首片不支持任意模型渠道切换。
原生同工作区副本经内容和provider校验后登记为受管草稿，沿用当前租户唯一的平台连接；
草稿登记不修改正式来源。登录加入成员失败不签发空工作区会话，保留账号映射供重试，
替代旧版“登录成功但空列表”的行为。
HTTP202表示已接收操作，需通过查询状态确认完成（RFC9110 §15.3.3）；失败不写成功结果。

## 被否掉的替代形态

- 前端串SSH或命令行：调用者需理解文件路径且没有统一身份/恢复边界，继续依赖服务器操作。
- 为每个租户新增Snail执行实例：当前节点已按run冻结清单与授权；复制实例增加维护而未解决开通前置。
- 复制Dify应用名后反查：用户可改名且并发重复，响应丢失时不能证明是哪一次创建。
- 复制就替换正式入口：已有客户的当前管家会无意切版；副本先成为独立草稿，明确发布才切换。

## 后果

业务人员无需编辑TOML/JSON或创建占位V1。代价是新增受管应用/操作记录和Dify导入的窄补丁，
需作为同版制品部署并核对能力。首次环境接入与凭据配置仍由平台维护；配置成功不代表当前账号
具备订单权限，真实业务验收独立记录。普通Dify应用保留原生发布。
