# 39. 试运行实例的隔离是一道启动门，不是一段文档

日期：2026-10-18
状态：已采纳
影响版本：`src/aiops_diagnostics/isolation_guard.py`、`gateway_server.serve`；不改生产行为

## 背景

试运行栈要在同一台宿主上挂载生产的**只读**业务依赖（`/etc/aiops-41/production.env`
与 `keys/`），同时拥有自己的可写状态。这两类路径在同一份配置里，靠命名区分。

M2-LIVE-01 已经出过一次事故：一个临时实例继承了生产的
`AIOPS_GATEWAY_DATABASE_FILE`，而 `create_gateway_app()` 在启动路径上会写库
（作业恢复、助手问题收敛、会话槽清理）。「业务库只读」推不出「没有副作用」——
写的是 Gateway 自己的 SQLite。

第一版修法把断言写进一个**单独的实验启动器**（`tools/m2_live/isolated_shim.py`），
README 也这么写。但正式部署件的启动命令是 `gateway_server serve`，它根本不经过那个
启动器。检查在文档里成立，在执行路径上不存在。

## 决策

**把判据放进产品启动路径，并且只有一份实现。**

- `isolation_guard.assert_isolated` 同时被 `gateway_server serve`（真实启动）与
  `checks.sh preflight`（起容器之前）调用；不存在第二份相似的检查。
- 判定发生在读取设置与 `create_gateway_app()` **之前**：门禁拒绝就没有端口、没有库被打开。
- 判据四组：隔离根、每个可写路径（按 `resolve()` 后的结果）、只读依赖白名单
  （必须在根之外、可读、不与可写路径重叠）、运行 UID 与属主。
- **未设置 `M2LIVE_ISOLATION_ROOT` 时门禁是空操作。** 这不是可选项的妥协：生产
  Gateway 的启动路径因此逐字不变，回滚就是「不设这个变量」。

## 被否掉的替代形态

- **继续用独立的实验启动器，部署件也走它。** 那会把「部署件启动的是不是产品代码」
  变成一个需要持续解释的问题；而且每加一个启动入口就要再复制一次判据。判据在启动
  入口里复制几份，就会有几份漂移（本仓在 `_authenticate_caller` 上已经吃过一次）。

- **只靠 preflight 检查。** preflight 跑在宿主的 shell 里，容器渲染、挂载解析与真实
  进程的 UID 都可能与它看到的不同；而且它可以用 `docker compose up` 绕过。真正的
  保证必须由要写库的那个进程自己做。

- **在生产启动路径无条件执行（不设开关）。** 那会改变生产的行为与启动前提，等于把
  试运行的约束强加给已经在跑的服务。空操作的边界是刻意的：新约束只对声明了自己是
  试运行实例的进程生效。

## 后果

更容易：一个试运行实例无论从哪个入口起来，都不可能写生产状态；门禁失败发生在副作用
之前，错误信息指向具体路径。

更难：新增一个可写挂载时，必须同时更新 `M2LIVE_EXTRA_WRITABLE` 或它所在的挂载集，
否则启动与 preflight 都会拒绝。这是想要的行为，但它确实让「加一个卷」从一行 compose
变成两处改动。

上限：门禁只证明**路径与属主**，不证明进程此后不写别处（例如网络写入、或它自己
`chdir` 到别处）。它拦的是本仓已知的那类误配置，不是通用沙箱。
