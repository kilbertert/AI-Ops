# Dify 控制台入口收口到自有域名的 TLS，且不进第三方代理

日期：2026-10-15
状态：已采纳
影响版本：PRD #772 子票 #776；ADR-0021；`ops/dify-console-bridge/`、`deploy/dify-36/`

## 背景

ADR-0021 定的形状是「同域反代 + 在 Dify 控制台编排页注入一颗发布按钮」，那一轮把
**注入**这件事的边界讲清楚了，但留了一条尾巴没处理：**那个"同域"是
`http://36.156.159.175:10008` —— 明文 HTTP、绑 `0.0.0.0`、公网任何人可达。**

于是控制台会话 JWT 与运营的每一次编辑，**全程明文过公网**。这不是新引入的问题，是
阶段 1 就带着的既成事实（`deploy/dify-36/README.md` 的「暴露与收口」表里写着
「TLS：**无**」，并注明"已知的、临时的暴露，不是疏忽"）。

#776 原本把 TLS 当作 #783 的**硬前置**，理由是一个**很快就不再成立的前提**：

> 公司登录代理会让运营在这个页面上输入**公司账号密码**；没有 TLS，那个密码就是明文
> 过公网。

用户随后决定**第一版继续由 Dify 的 owner/admin 裁定发布权**（桥的
`AIOPS_CONSOLE_BRIDGE_LOGIN_PROXY_URL` 未配置已是既成事实，登录代理未部署）。
第一版里运营用的是 **Dify 邮箱密码**，公司口令根本不经过网络。

所以本记录面对的第一个问题是：**前提没了，这件事还做不做？**

**做。** 理由不依赖那个前提：控制台会话本身一直在明文里，这是**既有缺陷**，
与将来用哪套账号体系无关。而它同时还是 v2 的入口准备 —— 登录代理的
`AIOPS_LOGIN_PROXY_PUBLIC_ORIGIN` **必须**以 `https://` 开头，否则代理**拒绝启动**
（`ops/dify-login-proxy/login-proxy.env.example`）。不做，v2 寸步难行。

## 决定

**控制台入口收口到 `https://dify.ranlei.work`，TLS 由 36 自己终结（不经第三方代理）；
旧入口 10008 保持可用作回滚路径。**

### 一、域名选用户自有的 `ranlei.work`，不占公司的 `xyseeker.com`

`*.xyseeker.com` 已经有十来个子域名落在 36 上（`xyadmin`、`xyapi`、`xyh5`…），
说明有人有那个解析权，沿用它"更顺手"。**否掉**：AI-Ops 自己的控制台挂到公司域名下，
会让"这是谁的入口"这个边界在 URL 上就说不清；而 `ranlei.work` 的解析在用户自己手里，
`dify.ranlei.work` 是一条 DNS 记录 + 一张证书的事。

### 二、灰云：TLS 在 36 终结，**不**放进 Cloudflare

这是本记录真正的决定。`ranlei.work` 的 DNS 在 Cloudflare，36 上**已经预装**了一张
`*.ranlei.work` 的 CloudFlare **Origin CA** 证书（有效到 2041）—— 那是给**橙云**
（CF 代理）准备的，`dify.ranlei.work` 也已经能通过区里的通配 `*` 解析。也就是说
**橙云这条路几乎不用做事就能通。**

**仍然选灰云。** 取舍是两条风险的不对称：

| | 橙云（CF 代理） | **灰云（本决定）** |
|---|---|---|
| TLS 在哪终结 | Cloudflare | 36 |
| 运营的**口令** | 在第三方侧**明文可见** | 只有 36 看得到 |
| 可用性依赖 | 多一个第三方控制平面 | 无 |
| 源站 IP | 被隐藏 | **暴露**（但 10008 本来就已经裸在公网上） |
| 需要的证书 | 现成的 Origin CA | 要签一张公开 CA 证书 |

代价那一栏是这次决定**唯一**多做的事（签一张 LE 证书），换的是"凭据不经过第三方"。
对一个**将来要承接公司口令**的入口，这条优先于"省事"和"隐藏源站 IP"—— 后者本来
也不是靠 CF 挡住的（10008 一直公网可达）。

**因此 36 上那张 Origin CA 证书用不上了**，改签 Let's Encrypt。
灰云 + LE 是可行组合（LE 的 ACME 端点从 36 可达）。

### 三、443 反代到 **10008**，不是 10018

10008 那一层承担四件事：转发、HTML 注入、按钮脚本、发布桥。指到 10018（Dify 自己的
nginx）会把注入与桥**整个绕过** —— 按钮消失、`/__aiops/publish` 不可达。
指到 10008 = 透明复用，**改一处而不重抄**。

### 四、接受 `__Host-` cookie 前缀，不去关掉它

Dify 在 `is_secure() && COOKIE_DOMAIN 为空` 时给控制台 cookie 加 `__Host-` 前缀
（`api/libs/token.py`）。切到 https 后 `is_secure()` 成立 ⇒ **cookie 名会变**。

可以设 `COOKIE_DOMAIN=域名` 让它退回裸名，省掉所有读 cookie 的地方。**否掉**：
`__Host-` 带来的隔离更强（限定到精确主机、必须 Secure、路径必须 `/`），而代价只是
**改一处** —— 我们注入的按钮脚本按名字读 cookie，是本次唯一受影响的地方（桥侧早已
双前缀兼容）。为了省掉一处改动而放弃一个浏览器级的隔离，不划算。

## 被否掉的替代形态

- **保留明文、只做受控来源。** 会话 JWT 仍在明文里；且 10008 的入口是公网，靠
  "受控来源"意味着要维护一张 IP 白名单 —— 比一张证书贵，还不解决根因。**否掉。**
- **收进内网/隧道。** 36 上**没有 tailscale**；而这条路的真实约束是"运营要能访问"，
  没有别的。**否掉。**
- **打开容器内的 `NGINX_HTTPS_ENABLED` 复用上游 TLS 模板。** 那是 **10018 那一跳**的
  TLS，作用在容器与宿主之间 —— 与"公网入口收口"是两件事（`deploy/dify-36/README.md`
  已写明）。**否掉。**
- **橙云（CF 代理）。** 见上面的表。**否掉**，理由是本入口的**未来用途**决定了它必须
  能承接公司口令。
- **直接 `ssl_certificate /etc/letsencrypt/live/...`（省掉拷贝）。** 那是 `700 root`，
  nginx **worker**（宝塔下是 `systemd+`）读不到；现在能起只是因为 **master 以 root
  解析配置** —— 一个不该依赖的隐含假设。改为宝塔惯例：deploy-hook 拷贝到
  `vhost/cert/` 后 reload。**否掉"省这一步"。**
- **acme.sh。** 它的安装器要从 **GitHub raw** 取主体，而 GitHub 从 36 **不可达**。
  改用 `apt install certbot`。**否掉**（不是偏好问题，是可达性问题）。

## 代价（写下来，不藏）

1. **10008 不关。** 它是回滚路径，而"退役旧入口"需要**观测到的流量**作依据 —— 而
   10008 **此前没有任何访问日志**（server 块不含 `access_log`，全局那条写在 http 块内的
   一个 `location` 里、作用域无效）。所以这次顺带在**新入口**补上了 `access_log`：
   **下一代暴露变更第一次会有依据。** 在此之前"10008 有多少人在用"在本机上无法回答。
2. **源站 IP 暴露**，是灰云的直接代价（见上表）。
3. **多一个要续期的证书**（LE 90 天），靠 deploy-hook 自动完成，但这条链断了不会有人
   立刻知道 —— 下次进入此入口时应顺手看一眼到期日。
4. **灰云下 36 的 443 直接面对公网**：这是本决定有意选择的暴露面。

## 后果

- 控制台入口：`https://dify.ranlei.work`（LE 证书，续期自动）。
- 旧入口 `http://36.156.159.175:10008` **仍在、功能不变** —— 回滚是一步。
- 读 cookie 的地方必须两种前缀都试；本次改了**注入的按钮脚本**。
  **v2 待办**：登录代理的 `dify_login_service.py`（`cookie_prefix` 恒为空）与
  `dify_login_server.py` 的 `_logout()`（只清裸名）在 v2 上线前必须一并改。
- 与 ADR-0021 的关系：**没有更正它的任何一条** —— 反代拓扑、注入、发布仍由我们的门做，
  全部不变。本记录只处理它留下的那条尾巴（"同域"当时是无 TLS 的）。
- 与 ADR-0023 / #783 的关系：本记录把 v2 登录代理的入口前置**做掉了**，但**没有**做
  登录代理本身，也**没有**封 Dify 原生登录接口 —— 那两件仍属 #783。
