# 替身要比真上游更苛刻，不是更宽松

日期：2026-10-16
状态：已采纳
影响版本：PRD #772 身份闭环的部署层（#783）；`dify_login_company`、`dify_login_provision`、
`tests/test_dify_login_proxy.py`

## 背景

登录代理（#778 写的）在部署上线那天，连续暴露**三个缺陷**，每一个都让整条链不可用，
而**每一个的单测都是绿的**：

| # | 缺陷 | 单测为什么绿 |
|---|---|---|
| 1 | `fetch_captcha` 发 `Accept: image/jpeg`，而公司网关对 `/code` **按 Accept 过滤**（非 `*/*` 一律 404） | 替身不看 `Accept`，一律回 200 |
| 2 | `company_login` 把参数放 **body**，而公司网关的验证码过滤器与口令解密过滤器**都只读 query string** | 替身只按 body 解析参数 |
| 3 | `_invite_token` 只读 `results`，而 Dify 1.17.1 回的键是 **`invitation_results`** | 替身回的就是 `results` |

三处的形状完全一样：**替身实现的是「我以为上游会接受什么」，而不是「上游真的接受什么」。**
于是它验证的是我们请求的**自洽性**，不是它的**可接受性** —— 前者必然通过，后者才是要被验证的东西。

第 3 个还牵出一条更难看的后果链：解析不到 token ⇒ 激活被静默跳过 ⇒ 账号停在 `pending`，
**而 pending 的账号在这个自签会话模型下照样能登录**（会话是验签 + 查库，不查 `status`）
⇒ 整条链**一处都不报错**。缺陷不是被测试放过的，是被整条链路一致地忽略的。

## 决定

**替身必须复现真上游的拒绝行为；凡是我们依赖上游"会怎么答"的地方，替身就要在那里变苛刻。**

具体到本仓：

1. 替身只加"真上游确实会做"的限制，不加"我们碰巧没遇到"的宽容。
   - `_FakeCompany` 的 `/code` 现在**按 Accept 过滤**（非 `*/*` → 404）；
   - `_FakeCompany` 的登录**按 query string 解析参数**，且**没有 `code` 就回「验证码不能为空」**；
   - `_FakeDify` 的邀请回 **`invitation_results`**；`/activate` **带 `Authorization` 就报
     `invitation_account_mismatch`**（Dify 真规则：激活者被当成会话那个账号）。
2. 每条修复都要有**反向验证**：把实现改回旧写法，对应用例必须转红。
   本次三处分别是 **2 / 13 / 10** 条用例会红。没有反向验证的"修复"只是改了代码。
3. 凡是"上游没回我们期待的形状"的分支，**不许静默通过**。
   `provision_editor` 里"邀请成功却拿不到 token"从跳过改成抛
   `DIFY_INVITE_TOKEN_MISSING`；激活回执从"没抛异常就算成功"改成校验 `result == success`
   （两种信封都认）。

## 为什么不是"多写单测"

单测数量不是问题 —— 那三个缺陷发生在**已经写了 54 个用例**的模块里。
问题在替身的**保真度**：一个比真上游宽松的替身，测再多也只是把同一个假设重复 54 遍。
所以这条决定约束的是替身的**方向**（更苛刻），不是数量。

## 被否掉的替代形态

- **"部署时人工验一遍就好"**。本次恰恰相反：三个缺陷**全部**只在真上游上出现，
  而人工验收的顺序是"先撞第 1 个、修完再撞第 2 个、修完再撞第 3 个" —— 一次只暴露一个，
  排查成本极高（第 2 个我一度归因成"少了一个请求头"，因为表现是 500）。
  **否掉**：把上游的拒绝行为搬进替身，才能在一个回合里全暴露。
- **给替身加"严格模式"开关**（默认宽松，CI 里严格）。听着省事，代价是两套行为，
  而**默认的那一套就是会被到处复制的那一套**。**否掉** —— 替身只有一种模式：像真上游。
- **把真上游的响应录下来当 fixture 回放**。对**上游**是对的（本次三个缺陷的判据都来自真实
  抓包/真机实测）；但回放**不能替代**替身去复现"拒绝" —— 录的是某一个成功回合，
  而缺陷恰恰发生在被拒的那些回合。两者互补，不是替代。

## 后果

- 三个缺陷的修复各自带反向验证，写进 `docs/validation.md`。
- **判错上游行为的代价被前移**：从"部署那天"移到"写替身那天"。
- 新增依赖上游行为的代码时，**先确认上游在边界上怎么答**（抓包 / 读源码），再写替身 ——
  本次三处的答案分别是：`Accept` 过滤（实测）、参数在 query（实测 + 读 `PasswordDecoderFilter`）、
  键名 `invitation_results`（实测）。
- 这条对**所有**与外部系统对接的替身生效，不限于登录代理（消息队列、支付、任何 HTTP 上游）。
