# 202. 管家会话贯通预览与正式入口，订单每轮重新授权

日期：2026-11-04
状态：已采纳

## 背景

#1335仅拼入前文，预览桥却拒绝非空会话，正式分支也未使用活跃订单；
长会话取最早四轮而非最近三轮。测试只断言一句前文出现，未覆盖真实连续问答。

## 决策

复用现有ConversationStore与生成锁。正式和预览分别按主体、入口、应用绑定会话，
首轮返回ID，续问按ID读取。预览ID只属于该应用预览，不能切到正式或其他应用。
明确订单成功通过本轮权限检查后才成为活跃订单；订单相关追问可继承，但每轮重新取证和验权。
站点/未来方案等新话题不自动绑定旧订单；多个或冲突的明确订单先澄清。
只传最近三个已完成问题，排除当前与失败轮；历史答案/金额不作为新证据。

Dify的conversation_id遵循[官方消息接口](https://docs.dify.ai/en/api-reference/chat-messages/send-chat-message)
的首轮返回、后续回传约定。受管预览用Gateway的conv_标识，不伪造Dify原生会话，
不调用Dify原生历史查询获取这个ID的记录；清空预览开启新会话。

## 被否掉的替代形态

- 只给模型拼前文：不解决请求没有会话和订单的接线问题。
- 让模型从旧问题自由选择单号：模型文本不能决定授权对象。
- 把旧答案完整回喂：容易把旧金额与缺证状态当成当前事实。
- 每轮创建独立节点平台会话以外再保留一套模型记忆：重复已有Gateway会话，增加跨主体泄漏面。

## 代价与验证

上下文限三轮问题，不保证任意长对话记忆。用户必须带返回的会话ID；新会话不继承。
应用或用途变化拒绝旧ID；新增字段为可选，不改变无会话旧客户端的请求形状。
验收见operator-followup，覆盖连续HTTP、最近窗口、跨主体/应用、撤权、并发和原生SSE。
