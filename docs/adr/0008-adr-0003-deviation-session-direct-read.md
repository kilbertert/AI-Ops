# ADR-0003 偏离：会话身份为共享 Redis 直读，而非 BFF 委托句柄

Status: Accepted（**这是一条偏离记录，不是对 ADR-0003 的取代**）

ADR-0003 规定：由业务后端验证小程序 `thirdSession` 后创建**一次性不透明身份委托句柄**，
AI-Ops 使用**独立服务身份**回查该句柄，从中解析当前用户、租户与订单授权范围；
并明写「**裸 `user_id` 或 `tenant_id` 也不能作为授权依据**」。

本仓库**从未实现该委托句柄**。实际落地的是另一条路径：AI-Ops 用共享会话 Redis 直读
`app:3rd_session:<token>`，自行解析出 `userId` / `tenantId`。这条偏离自会话接入起就在，
只是从未被记成一条决策；#423（管家端入口与订单运营商级授权）把它推到了要紧位置——
管家端授权现在**建立在会话直读的身份之上**，而不是建立在 BFF 断言的身份之上。
本 ADR 把偏离写成明账，并写明它什么时候必须结束。

## Consequences

- **偏离的实质是身份断言的来源变了，不是身份模型变了。** ADR-0003 要的是「BFF 断言这
  个会话属于谁」；现在得到的是「AI-Ops 自己从共享存储里读出这个会话属于谁」。
  两者给出的**字段**相同（C 端 `userId`、`tenantId`），因此下游的范围解析逻辑不受影响；
  变的是**信任链的根**：从「业务后端的断言」变成「共享 Redis 的可读性」。

- **今天这样做能成立，是因为共享 Redis 本身就在信任边界内。** AI-Ops 与 BFF 同处一个
  受控网络，会话键只有服务侧可读，且 AI-Ops 出示的是服务级凭据而非用户凭据。
  这不是"裸 `user_id`"——`user_id` 来自服务端读取的会话对象，不是请求体里客户端自报的
  字段（后者在本仓由既有守卫拒绝）。但**它与 ADR-0003 的用词仍然冲突**，本条记录不为
  这个冲突辩解，只把它标出来。

- **管家端授权放大了偏离的代价。** 消费者端只读自己的单；管家端要读**整个运营商**的订单。
  同一处偏离，后者的影响面大得多。因此 #423 的实现把这条偏离当作**已知风险入账**：
  授权链上的每一跳都 fail closed，且身份补全的核对规则比 ADR-0003 时代更严
  （同租户 + 同 C 端用户双核对，见 `docs/validation.md` 的 #424 节）。
  这些是**缓解**，不是替代——它们降低偏离被利用的概率，不能把它变成合规。

- **偏离不得被表述为已批准的设计。** 代码注释、运行手册与新写的文档里，**不得**把
  「直接读会话」写成 ADR-0003 的实现。这条在 #423 的交付里被明确要求，本 ADR 把它
  变成一条通用规则：任何提到会话身份的地方，要么写明"偏离"，要么不声称来源。

- **对齐路径不变，且本 ADR 不改变它。** 平台授权服务器支持 OAuth 2.0 Token Exchange
  后，迁移为限定 AI-Ops audience、最小权限、短有效期的标准访问令牌。
  迁移时**运营商站点判定逻辑可原样保留**——它不依赖身份来自哪里，只依赖身份里的
  `userId` / `tenantId` 与 B 端主体。这是当初选择"把范围解析写成纯函数"的回报：
  身份来源换掉时，范围那一层不用动。

- **结束条件是外部的，不是本仓能单方面满足的。** 偏离的关闭取决于业务后端提供委托
  句柄（或 Token Exchange）——那是**另一个团队的能力**。因此本条记录的作用不是
  "择日修复"，而是：**让下一次有人问"会话身份是谁断言的"时，答案不用靠翻代码考古。**

## 被否掉的替代形态

- **（a）现在就实现委托句柄** —— 需要业务后端新建能力，本仓单方面做不到。
  #423 的取舍是"先落地、偏离入账"。
- **（b）不记录，继续当作常规实现** —— 这正是本 ADR 要终止的状态：偏离不可见时，
  它会悄悄变成默认设计，而 ADR-0003 仍在仓库里标着 Accepted。
- **（c）改 ADR-0003 的 Status 为 Superseded** —— 错。ADR-0003 描述的**仍是目标形态**，
  只是尚未实现。把它标成被取代，会抹掉"我们对齐到哪"这个信息。
