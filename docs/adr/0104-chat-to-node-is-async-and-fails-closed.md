# 104. App 聊天接节点：异步派发 + 存储关联，失败不回落

日期：2026-10-24
状态：已采纳
影响版本：`src/aiops_diagnostics/chat_execution.py`（新增）、`gateway_api.py`、
`gateway_runtime.py`、`gateway_config.py`、`agent_runs.py`（`qa_id` 列）

## 背景：两种"已能跑"的东西没接在一起

* `POST /v1/orders/{order_no}/charging-status/delegated` 已经能把一次读取交给客户节点，
  但它**同步**：调用方等到平台派发、节点跑完整轮、结果回到网关。放进 App 聊天会让用户的
  POST 挂整轮节点时间，前端早就超时了。
* `_consumer_order_chat` 是**确定性直读**：网关自己读 SQL + CPMS 当场作答，与节点无关。

ADR-0079 已经把「App 入口」与「执行引擎」解耦，但那条解耦只到"可以各自选"，没有把
"App 聊天选中节点"这条链路真的接起来。

## 决定

### 1. 异步：POST 只建作业，等待搬到既有 QA worker

POST 返回 202 + `qa_id`，App 用**原 GET** 轮询。不新增接口、不新增字段、不换域名。
这不是新机制：QA 生命周期（queued/running/终态、取消、会话轮次、迟到写守卫）本来就存在，
把「等节点」放进去比另起一套轮询形状便宜得多。

### 2. QA 与 run 是**存储关联**，不是字符串

`agent_runs` 增加 `qa_id` 列（幂等迁移，旧行 NULL 不回填）。读取路径按它反查承载的 run。

这一点是刻意不选"把 run_id 编进 `internal_run_id` 再解析"的：字符串既能被写错，也能被
伪造，而"这条 QA 由哪条 run 承载"是一个事实，应该在存储里。实现中真的踩到过这件事 ——
worker 与读取守卫各写了一份前缀字面量，只要有一处不同，回读就会**悄悄**走到别的判据上。

### 3. 失败不回落

命中绑定之后，任何失败（节点失败、平台不可用、执行配置漂移、未预期异常、超时）都落到
QA 的 `failed` 终态。**不**直读补一个答案、**不**回落旧模型、**不**换别的节点。

回落到任何一条，都是把"另一次读取"冒充成"本次结果"；而用户看到的是同一个 `qa_id`，
无从分辨。这条与 M3 那片"领取成功 ≠ 整轮完成"是同一条纪律的延续。

### 4. 共享而不是复制

授权、TTL、执行配置守卫、完成判据、最终放行从既有委派入口抽到 `chat_execution`，
两个入口共用。**不让聊天服务 HTTP 调用自己**（那会多一次网络、多一份超时语义，
并让"谁在授权"变得含糊），也不复制第二套判据（两份必然漂移）。

### 5. 默认关闭，且与委派入口**分键**

新增 `AIOPS_GATEWAY_CHAT_EXECUTION_{CONFIG,MANIFEST}_FILE`，默认空。
不复用 `AIOPS_GATEWAY_AGENT_RUN_*`：共用一个键会让"只开委派"顺带把聊天也接到节点。
半配（只配清单、或缺个人查询地址/逻辑执行环境）是**启动失败**，不是静默降级。

## 被否掉的路线

| 路线 | 为什么不行 |
|---|---|
| 聊天入口同步调用节点，等结果再返回 | App 的 POST 会挂整轮节点时间，前端超时；而且超时后请求仍在跑，用户不知道结果 |
| 复用 delegated 的 HTTP 端点（聊天服务调自己） | 多一跳网络与超时语义，且"谁在授权"变含糊：那一跳的调用者是网关自己，不是用户 |
| 把 run_id 编进 `internal_run_id` 再解析 | 字符串可写错、可伪造；关联应是存储事实。实现中已因此踩到前缀不一致的缺陷 |
| 失败时回落直读补答案 | 把另一次读取冒充本次结果，用户无法分辨 |
| 复用 `AGENT_RUN_CONFIG_FILE` 一个键 | 两个入口的启用会绑在一起，"只开委派"变成"顺带开聊天" |

## 修订（2026-10-24，Codex 复核之后）

复核用五个独立反例证明了原实现的四处缺口，这一节的四条修订都在同一 PR 里补齐：

1. **绑定必须按租户登记**。「配了一个全局文件」不是绑定 —— 未登记的租户照样派到同一个
   节点，而本任务要求的执行位置隔离恰好是这件事。改为一张 `aiops-chat-execution/1`
   登记表，键是（环境，租户，入口，场景），签发时把选中的那条**冻进 run**（`chat_binding`）。
2. **聊天路线必须有执行清单**。没有清单的 run 走旧协议（领取即 succeeded），于是「节点只
   读了业务、整轮模型循环没跑完」被记成成功，完成通知两次都没有。加载期、签发期各拒一次。
3. **最终放行只有一份**。见文末「最终放行」。
4. **停用只拒绝正文**。原文把无正文的终态也一起 404 掉了 —— 于是取消返回 404 而库里其实
   已经 `cancelled`，前端看到的是「取消失败」。现在 `queued/running/failed/cancelled/expired`
   与绑定是否启用无关，本人始终读得到。

## 最终放行

交付前的判定抽成 `chat_execution.final_release`，由**三个**调用方共用：委派入口、
聊天 worker、聊天回读。抽之前聊天那条路自己写了一串 `if`，其中漏掉四项
（`settings.execution_environment`、`actual == expected`、节点登记的 `environment`、
执行配置是否真的核对过）—— 漏得很安静：回读仍是 `200` + 正文。同一个不变量写两遍，
第二遍必然少几句。

## 后果

- App 侧零改动：接口、字段、域名、blocks 形状都不变；
- 失败一律显式：节点不成就 `failed`，不会出现"看起来成功但其实是另一次读取"的答案；
- 停用即拒绝正文：拿掉登记后回读历史结果为 `404 CHARGING_STATUS_DISABLED`，
  与直读路线停用后的纪律一致；无正文的终态不受影响；
- 真 Java 节点整链由 `tools/m2_close/m3node/verify_chat_node_entry.py` 交付
  （见 `docs/validation/2026-10-24-app-runtime-node-completion.md`）；
- **仍未做**：真实外部平台/供应商、真实公司 UPMS 目录、登录 App 验收、SOP 发布绑定。
