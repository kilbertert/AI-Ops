# 184. 工具面由运行类型决定，不由工具名之间的特例决定

日期：2026-10-30
状态：已采纳（设计定型，已实施）

## 决定

「这一次运行允许哪些工具」只有一个判据：**清单的 schema（运行类型）**。
`ToolSurface.allowed(schema)` 是唯一实现，清单解析与工具装配都调它。

```text
operator-exec-config/1   → 声明里 applies_to 含 order 的 CPMS 工具
operator-conversation/1  → 声明里 applies_to 含 conversation 的 CPMS 工具
m3-exec-config/1         → 状态工具 + 含 conversation 的 CPMS 工具
```

原先按工具名硬编码的互斥（「状态工具不能与管家 CPMS 工具混用」）删掉。
**它表达的意思仍然成立**——状态工具与订单诊断工具不能共存——但那现在是允许集合的
**结果**，不是一条名字特例。

## 依据

那条互斥写成特例之后，每加一个工具都要重新想一遍「它和谁不能共存」，而这个问题的
正确答案取决于**这一轮是什么运行**，不是取决于两个工具名。C 端需要「订单状态 + 站点
查询」同清单共存，那条特例就直接挡住了它——不是因为语义错了，而是因为它把语义写成了
名字之间的规则。

同一个形状在清单解析里还有一份：`ExecManifest.parse` 里的
`if (conversation && !tools.isEmpty()) throw "非订单回合不允许订单工具"`。
ADR-0183 放开无订单回合带工具时只改了 Python 侧，这一处漏了——**上一片的 Java 验收
没有解析对话清单，所以没抓到**。本片一并修掉，并把两处判据合并到 `ToolSurface`。

## 被否掉的替代形态

**保留互斥，给 C 端加一个例外分支。** 最强的地方是改动最小、风险最低：加一个
`if (consumer) allow both` 就完事。它输在形状——「哪些工具能共存」变成一张例外表，
每加一个工具就多一行，而每一行的理由都不一样、都要重新论证。

**把允许集合写进清单本身。** 最强的地方是运营可见、可审计：清单里直接写「这一轮能用
哪几个」，代码不需要任何规则。它输在信任方向：清单是发布期产物，而「哪类运行能用什么」
是安全判据；把它写进数据等于让发布者决定工具面，而发布者不该能决定这件事。

**让声明再带一个 `exclusive_with` 字段表达互斥。** 最强的地方是保留「工具之间的关系」
这个信息。它输在关系是**运行类型**的属性而不是工具的属性：同一个状态工具在 C 端与
订单状态工具共存，在管家侧不能——「和谁冲突」离开运行类型就没有确定答案。

## 后果与验证

- **拒绝判据没有放松**：不在允许集合里的工具名整轮失败，只是判据从常量变成数据。
  未声明的工具名在任何运行类型下都不成立。
- **本片只做工具面**：C 端清单现在可以**声明**状态工具 + 站点工具，节点也会装配两者，
  但站点工具在 C 端运行里**取不到授权**——`operator_cpms._current` 只接受两类 operator
  运行，C 端运行的授权路径不存在。这一条单独立票，不在本记录范围内假装成立。
- 验证：`CpmsToolAcceptance` 从 153 涨到 **166** 条断言，新增覆盖三种运行类型的允许集合、
  未声明工具在三类运行下都被拒、未知运行类型被拒、以及对话清单接受站点工具而拒绝订单工具。
- **仓库 CI 不构建 Java**，这些断言是手动跑的（既有缺口，与 #1189/#1190/#1191 相同）。
- **未完成业务验收**：没有真实 CPMS、没有真实账号、没有真实页面。
