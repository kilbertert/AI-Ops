# 317. 发布工作区同租户残留登记按取代处理，不判外来占用

状态：已采纳；修订 central_bundle 工作区占用闸的同血统判定。

`central_bundle` 在发行前查 `operator_apps`：同一 `workspace_id` 下存在
`entry=consumer` 且 `app_id` 异于候选的登记行即拒绝——「一个已有正式消费者
占用此工作区时不能静默覆盖」。该闸按 app 判占用，不看登记归属。

ADR-0312 的重铸血统把这个假设打破：候选 081be053 完成发布后 remint 成
a9624b48，旧 app 的提升登记行按设计留在册（孤儿由独立受管清理面收）——
同一 `(environment, tenant_id)`、同一 workspace、不同 app_id，正中「另一个
消费者」的判据。env95 实测（task_8fe0bcdc）：ADR-0316 恢复续跑后每个
认领周期都在此闸重抛 `workspace has another consumer`，central 步永挂。
且事后推断 09:41 的首跑死亡点即此闸（intent.json 已落、其后无任何落账）——
started 楔形与孤儿占用是同一任务上的两处独立缺陷，缺一都不通。

## 决定

占用闸只判**外来**占用：豁免 `(environment, tenant_id)` 与本发布 spec 相同的
登记行。同一租户在同一环境的同一工作区里换候选是本发布自身的血统——
续发的语义本来就是取代（发行物指向新 app），旧登记行仍在册、其既有凭据
不被改写，请求路由按 app_id 解析互不影响。

他租户或他环境的登记行仍按原判据拒绝：workspace 由 workspace-prepare 按
(environment, tenant) 对开备，跨租户或跨环境的占用是真实的归属冲突，
「显式凭据迁移」的出口语义不变。

## 替代方案

把豁免收窄为「仅提升孤儿」：需要在册数据区分孤儿与现役正式版，目录行不
携带该血统信息，为闸新增血统追踪是更大的面，排除。
按 remint `operation_id` 判血统：闸层拿不到链级 operation 上下文，且同租户
重发的取代语义本就成立，无需更细的键，排除。
给孤儿建受管清理面先行清行：孤儿清理是 ADR-0312 已命名的独立面；即便建成，
靠清理时序救发布仍把「先清后发」变成竞态——同血统取代豁免在语义上更直接，
排除。
手工删行解锁：生产库手工写既违本仓交付约束，也不修产品缺陷，排除。

## 后果

提升孤儿血统下的续发可越过占用闸走到 register/publish，env95 在挂任务
无需账本改写即续跑收口。外来占用面不缩：异租户、异环境的同工作区登记
仍硬拒。同租户再发布（升级）由此获得定义明确的取代语义——新发行物激活
后新流量指向新 app，旧 app 行与凭据原样保留，孤儿清理由既有独立面负责。
已知边界：孤儿行长期残留仍占用目录空间与可读面，清理面的缺席不因本次
豁免而消失。
