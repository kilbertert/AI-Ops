# 169. 拒绝原因带着下一步，不再在桥里统一压成一句话

日期：2026-10-29
状态：已采纳

## 决定

发布桥把网关的每一次拒绝都换成了同一句「发布未通过我们的发布门，请联系工程查看原因」，
试运行 403 一律换成「发布结果无法确认」。网关的错误体里本来就有 `code` 和一句人话，
桥把它们丢掉了——运营因此只能来问工程，而正确的下一步一直写在被丢掉的那句里。

现在按网关自己的 `code` 查一张小词表：

```text
CONSUMER_FLOW_INVALID         → 转出网关的 message（"所选知识库已删除，请重新选择"）
OPERATOR_TRIAL_LOGIN_REQUIRED → 说明公司登录约 15 分钟过期，需重新登录
其余/认不出的 code             → 仍回兜底话术
```

词表优先，网关原文只填空。理由是两者回答的问题不同：我们那句说**下一步做什么**
（重新登录），网关的 `message` 只说明**它拒了什么**（`operator request unavailable`）。
反过来用会拿一句能照做的话换一句看得懂但没用的话。词表留空的项才是"原文比我们写得好"的情形。
`message` 里出现 `UPPER_SNAKE` 标识说明它自己也是内部话术，那时不转。

只换 `reason` 文本与分支：`published`/`submitted` 与 HTTP 状态码不变，没有放宽任何拒绝条件。
提交与轮询两条路径同时生效。

## 被否掉的替代形态

- 把所有网关 4xx/5xx 的 `message` 都直接透传：网关的部分文案是给工程看的内部词，透传会把运营引向错误方向。
- 继续统一一句话、把细节留在日志里：运营看不到日志，这条正是"可诊断性"而不是"日志完备性"的问题。
- 在 UI 上按状态码分色而不改文案：颜色不告诉人该做什么。
