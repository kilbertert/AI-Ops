# 331. 同租户注册表留行永不阻塞登记——重铸候选 app_id 必然全新

状态：已采纳；接续并部分更正 ADR-0327 的冲突谓词，位置/时机/其余判据不变。

## 背景与实证

ADR-0327 收窄 `SETUP_ROUTE_CONFLICT` 时留下一条同租户异应用子句，依据是
「operator app_id 是确定性派生，再登记必然重提同一值」。该前提错误：
app_id 按 `uuid5(NS, workspace_id + ":" + job_id)` 派生（见
`self_service_prepare`），job_id 随每次准备任务全新，而重新登记在设计上
**必然**伴随重新准备——安装任务对父准备的校验读的是请求里冻结的
`plan.expires_at` 嵌入副本（900s），过期不可复活，不存在「沿用旧准备
再登记」的路径。于是凡「发布→恢复→再发布」循环中的再登记，候选 app_id
必然与注册表留行不同，同租户异应用子句**确定性地**把本血统判成占用。

2026-11-25 env95 小趋充电（tenant 1783022023241633792）生产实证全链：
重新准备铸出 operator `2f301f00…`/consumer `e7d0d5ae…` 新候选，注册表
留行仍指上一任 `0292d0c0…`（发布激活写入、恢复按设计保留）；登记任务
`task_0890bddb…` 每次远端观察都在该子句抛 `SETUP_ROUTE_CONFLICT`，
reconcile/unconfirmed 空烧约 8 分钟不收敛，最终经页面取消按资产证据
终态化。同库平高row 对照显示：平高能再登记仅因其升级后再登记未重新
准备（沿用同批候选，app_id 与留行一致）——循环本身对任意租户均不可行。

## 决定

`dify_app_registry` 冲突谓词去掉「同租户且 app_id 不在候选对」子句，
只保留「候选 app_id 被**其它**租户正式绑定」。依据：

- 该表唯一写方是本租户自己的发布激活（`chat_route_bindings` 的 upsert；
  恢复不删行是设计内谱系证据），同租户行**只可能是**本血统留行，
  不存在「同租户异应用=外血统」的真实形状；
- 现役正式占用由 `chat_route_bindings` 的 `state != 'retracted'` 子句
  独立挡住（已发布未恢复的租户活跃绑定仍在），不依赖注册表子句；
- 下一次发布激活对注册表按 `(tenant_id, business_entry)` upsert，
  留行自然换代，登记路径不改写它；
- 失败方向保持封闭：谓词仍在所有写路径之前，异租户占用依旧冲突即中止。

被否方案：恢复时清理注册表留行——撤回墓碑与注册表留行是发布 CAS 与
谱系对账基座（同 ADR-0327 已述）；登记时把留行提前改写成新候选——
登记不激活任何绑定，提前改写会让谱系证据指向从未激活过的应用，
发布激活的 upsert 才是唯一合法的换代点；保留同租户子句但豁免
「app_id 出现在本租户 operator_apps」的行——重铸原位替换发生同事务
更晚，且该豁免仍要求读方理解替换语义，比直接承认「同租户即血统」
复杂而没有多挡任何真实形状。

## 实测

- 单测：`tests/dify/test_runtime_registration.py` 反转并扩展原
  `test_registration_rejects_formal_binding` 语义——同租户异应用留行
  放行且不改写（谱系保留），完整发布消费+撤回+重铸形状登记通过；
  异租户占用与活跃绑定仍冲突的既有测试不动。
- 边界不变：跨租户 app 占用、活跃绑定、工作区/应用归属不一致全部
  维持冲突；该修复不解禁任何激活路径，发布仍走验证+最后准入。
