# 管家主账号沿用租户范围，节点只得单订单站点授权

日期：2026-10-26
状态：已采纳

## 背景与决定

公司管家密码登录的真实主体是租户主账号；既有 `is_tenant_level_account` 与公司店铺隔离规则允许其访问本租户，不要求站点成员行。节点首版只接受非空站点集合，因而拒绝这个合法主体。沿用既有账号类型与 `all` 范围，不修改公司身份和员工权限。

Gateway 签发前调用 CPMS 正式详情接口核对租户、订单和有效站点，将该一个站点固定在任务内存及节点授权。工具取数和历史回读必须保持该站点，账号撤权继续经原认证与范围指纹拒绝。Java 协议保持非空站点集合，无通配值。

控制台试用的公司令牌交换仅在独立 HTTPS 精确路径提供，限定已登记网关的原始 TCP 来源；按 nginx 官方 realip 语义使用 `$realip_remote_addr`，避免继承的地址重写信任客户端头。来源限制之外仍核验独立密钥、有效会话与近期真实登录，明文控制台不挂此路由。

## 备选方案

- 给主账号补虚构站点绑定：会改变公司权限记录且把租户范围伪装成员工范围，弃用。
- 把空站点数组解释为全租户：会放行原本无站点的员工，弃用。
- 给Java新增通配租户协议：扩大节点权限面；绑定单订单现有站点即可，弃用。
- 将公司令牌写进Dify工具配置：保留面太大；仍使用短期会话交换，弃用。

## 后果

同租户换站的订单也使旧任务失效，需要重新提交，避免把旧站点证据当作当前报告。凭据交换新增精确HTTPS路径，部署必须核对出口IP与回滚点。图形验证码不由自动化解决；App密码登录使用公司客户端原流程。此决定不证明业务诊断准确率，也不授权删除旧provider。
