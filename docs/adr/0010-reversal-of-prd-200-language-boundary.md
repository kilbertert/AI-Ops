# 推翻 #200 的 v1 语言边界

Status: Accepted

## 背景

#200（智能问答输出国际化，已 CLOSED）在 `Out of Scope` 里明确划掉三件事：

> - operator（B 端）17 条的多语言文案与 B 端整体国际化（第一版仅 consumer 端）。
> - 新增受支持语言（ja/ko 等）；繁体中文；RTL 排版。

并在用户故事第 10 条把第一条写成了**需求**本身：

> 10. As a 运维人员, I want to B 端（operator）入口第一版保持中文, so that B 端体验不受本次变更影响。

#526 之后，**B 端整体国际化**已经落地：11 门语言、涵盖管家端可达的全部回答面。
不记录这次推翻的代价不是"少一份文档"，而是**后续读者与 agent 会继续按 #200 的口径判断范围**——
认为管家端国际化在范围外，于是把已经做过的决定重新讨论一遍，或把新缺陷当成"本来就不该有"。
本项目已为这种失败模式付过代价：**同一根因以不同面貌反复出现，每次都被当成孤立缺陷修掉。**

## 决定

### 推翻哪几条，以及为什么

| #200 的边界 | 现状 | 理由 |
|---|---|---|
| operator 17 条不翻译、保持中文 | **推翻** | 管家端是真实用户面。一门"渲染一半"的语言（目录有翻译、系统文案没有）正是本项目栽过的那类不报错缺陷 |
| B 端整体国际化 | **推翻** | 射程从"目录层"扩到**管家端可达的全部回答面**：固定问答、统一助手 QA、宣传卡片、单问诊断、健康报告、澄清/兜底、快捷动作 |
| 新增受支持语言（ja/ko 等） | **部分推翻** | 实际落地的是 vi / mn / th / km / zh-Hant 五门，不是原举例的 ja/ko。范围单位从"语言代码列表"变成**该语言在某一用途上是否可用**（见 Consequences 第一节：**一维只在有消费方时才建**，当前清单里只有 `prompting`） |
| 繁体中文 | **部分推翻** | 已落地，但形态与 #200 的想象不同：**不是新增一门翻译**，而是把「语言」与「脚本」两条轴分开，`zh` 语义收窄为简体 |
| RTL 排版 | **仍然不做** | 本刀没有任何 RTL 语言（ar/he/fa），排版方向是独立工程 |
| 检索期原生多语言 | **仍然不做** | 知识库内容仍是中文权威；跨语言检索是独立事项 |

### 与 #200 的关系

**#200 保持 CLOSED，不被改写。** 这与 #526 对 #200 的做法同构，也与本刀对 #526 的做法同构：
**推翻一条边界时，不改写被推翻的那一条**——否则历史记录会变成"当初就是这么定的"，
而真正发生的事（一次有理由的范围变更）就此消失。

范围变更的链条因此是可读的：`#167 → #200 → #526 → #534`，每一环都保留自己的原文。

### 取代关系

#526 记录的是一次真实的范围变更，其**目录那一刀仍然有效**；但它的
`Out of Scope: B 端整体国际化` 已被 #534 取代。#526 同样保持被取代状态，不改写。

## Consequences

- **"语言代码列表"不再是范围单位，能力维才是。** 一门语言在某一用途上是否可用，
  与"这门语言是否受支持"是两件事：**提示**维缺席意味着该语言只能读、不能问——这是对用户的
  承诺边界，必须显式写在契约里，不能留给读者从代码推断。泰语/高棉语就是这一维缺席的实例。
  **但一维只在有消费方时才建**：清单里现在的 `prompting` 是该维目前在代码中的**唯一**落地，
  另三维（渲染/路由/守卫）尚无消费方，因此**尚未**成为清单字段（#527 删除过一个没有消费方的
  四维草稿）。本决策给的是**判断范围的方法**，不是一份已实现的字段清单；按尚未声明的字段
  接入新语言会失败。
- **"是不是中文"必须是语言的声明属性，不能从"是否等于默认语言"派生。** 加入繁体后，
  旧式（`非中文 = 受支持集 − 默认语言`）会把**每一份合法的繁体回答**判成中文泄漏并替换成
  兜底文案——一个静默、返回 200 的错误。这是「语言清单**按逐语言事实声明**、而非从全局规则派生」的必要性证明，而不只是整洁。
- **不引入第二种机制。** 繁体不另立一套翻译流程；它是简体权威原文的**脚本转换**，
  由 `tools/derive_zh_hant.py` 在开发期派生。同一自然语言内的脚本转换**不构成"两份互为翻译"**。
- **推翻边界 ≠ 边界消失。** 每次范围变更都需要理由，而理由写在 ADR 里、不在代码里；
  代码只承载结论。后续若再要扩围（例如 RTL），应再立一条 ADR 而不是编辑本条的表格。

## 已知缺口（本刀登记，不处理）

1. **统一助手入口 Agent 配置的 `quick_commands` 是"语言被烧进字符串"的形态。** 本刀只登记。
   已核对的现状：它被写入 Agent 配置、随配置校验、并**随 Agent 配置序列化进 Gateway API 响应**
   （`AgentConfig.to_dict`），因此**会到达客户端**。本仓库内**没有**渲染它的消费点
   （`grep 'quick_commands' src/` 只命中定义、校验与序列化）；**但客户端读它之后做什么，本仓库
   看不见，也不在本 ADR 的证据范围内**——"客户端不渲染它"是一个**未核实的断言**，不要据它下结论。
   登记的理由是**形态**：语言烧在字符串里，一旦有消费方就会以最难查的方式暴露。
   消掉它要动 Agent 清单 schema 与生产 reconcile，故不在本刀。
2. **存量已发布资源不随种子变化。** 改变种子**不等于**改变线上：已发布的快捷动作与已建立的
   目录行按旧的多语形态存在，新语言不会自动作用于它们。迁移属 #542，不在本刀。
3. **前端硬编码按钮。** 管家端前端当前硬编码按钮，**后端文案做对后用户仍看不到变化**，
   直到前端改造完成。见 `GLOSSARY.md` 的「前端硬编码按钮」条目。
