# 191. 会话回合能用哪些工具，由声明决定，不由模板决定

日期：2026-11-01
状态：已采纳（已实施）

## 决定

管家无订单回合下发的工具表，判据是 `operator_tools.json` 里的 `applies_to`
（含 `conversation` 即为该回合可用），**不是**节点模板 `manifest_file` 里恰好列了哪些。

`operator_conversation.manifest()` 因此做两件事：

1. 模板里有、且属 `conversation` 的工具，**保留**（模板可以收窄描述）；
2. 声明里属 `conversation`、但模板没列的，**按声明补齐**。

模板仍然是「运营在这个源应用里勾了什么」的记录，但它不再能决定"这类运行有没有这个能力"。
计划中的 `cpms_site_search` 之外，将来每加一个会话工具只需改声明一处。

## 依据

2026-11-01 生产实测：管家端站点类问题 **4/4 失败**，服务端
`OPERATOR_SITE_NOTE_WITHOUT_EVIDENCE`。

链条：生产模板 `operator-exec-manifest.json` 只有 `cpms_order_detail` /
`cpms_charging_samples`（都只属 `order`）→ 按模板过滤后 `tools=[]` → 节点无从调用 →
模型只能写一段没有取数依据的说明 → 网关按设计拒收。而同一份 INSTRUCTIONS 又写着
「找站、查站点位置时**先调用 `cpms_site_search`**」。

这与 ADR-0182 的既有决定直接冲突。ADR-0182 说「无订单回合可以带工具，但只能是声明里
允许这类运行用的那些」——**主语是声明**。代码实现把主语换成了模板，而两者的内容在生产上
不相等，于是分叉。

**测试为什么没抓到**：`tests/operations/test_operator_cpms.py` 的 `environment()` 用
`operator_tools.names()` 造模板，三个工具都在。夹具与判据同源，夹具就成了唯一事实来源。
新增的回归测试改用**生产形状**的模板（只有两个订单工具），并在删掉补齐逻辑后确认它会红。

## 被否的方案

**「往生产模板里加一行 `cpms_site_search`」。** 能修好眼前这一台，但把不变量留在了配置里：
模板是每个部署各自的文件，下一个环境、下一次重建都可能再漏。而且它让
「这类运行允许用什么」这个决定同时存在于声明和 N 份模板里——ADR-0181 把工具定义收进
一份声明，正是为了避免这种多点定义。

**「改提示词，不再要求模型调工具，改由网关代查」。** 网关侧确实有这条兜底路径
（模型回空 `text` 时自己调 `query_sites()`），但它把"模型有没有工具"变成了回答质量的
随机变量：同一份提示词下，模型写不写说明决定了走工具还是走兜底。留着它做降级可以，
当主路径不行。

## 取舍

补齐意味着**部署侧无法通过删模板条目来关闭某个会话工具**。这是有意的：关闭能力应该改声明
（那是"这类运行允许用什么"的唯一处），而不是改某个环境的模板文件——后者没有审查路径，
也不会出现在任何一份能力清单里。
