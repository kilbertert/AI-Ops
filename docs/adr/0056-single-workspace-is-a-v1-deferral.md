# 56. V1 维持单一 Dify 工作区：租户只在执行时生效，不在编辑时隔离

日期：2026-10-20
状态：**已到期**（触发条件于 2026-10-20 满足，见「后果与代价」末段）
影响版本：`src/aiops_diagnostics/dify_login_provision.py`（`provision_editor` 无 tenant 入参）、
`src/aiops_diagnostics/dify_login_service.py`（映射表存 `tenant_id` 但准入不用）、
`src/aiops_diagnostics/dify_console_publish.py`（`AIOPS_CONSOLE_BRIDGE_WORKSPACE_ID` 单值）

## 背景

PRD #772 §C 写了一句暂定：

> V1 **暂定**维持**单一固定工作区**（当前发布桥与网关导出钉住的那一个）；所有映射账号
> 加入这一个。按租户划分工作区推迟到出现第二个需要自行编辑智能体的租户。
> 由于同一工作区内 editor 互相可见全部 app，V1 只向公司内部运营/平台人员发放
> `aiops:agent:edit`；这一限制写进 ADR，作为引入多工作区的触发条件。

**最后那句"写进 ADR"没有兑现。** 到 2026-10-20 为止，仓库里没有任何记录说明
「为什么只有一个工作区」「代价是什么」「什么时候该改」。本记录补的就是这个缺口。

这个缺口的实际后果不是学术性的：读代码的人会看到 `provision_editor` 不接
`tenant_id`、映射表的 `tenant_id` 只用来算订单范围，然后合理地怀疑这是漏写。
**它是有意的**，只是没写下来。

## 决策（V1 当时的形态）

**一个 Dify workspace，所有映射账号是它的 `editor`。公司租户只在执行时生效。**

具体到各处：

| 位置 | 表现 | 为什么 |
|---|---|---|
| 开户 `provision_editor` | 无 `tenant_id` 入参；邀请打到 `/console/api/workspaces/current/members/invite-email` | `workspaces/current` 由 owner 会话的 `current` 标志决定，单工作区下它与租户无关 |
| 代理映射表 | 存 `tenant_id`、`user_type`，但**准入不读** | 它们要传给下游算订单范围 |
| 发布桥 | `AIOPS_CONSOLE_BRIDGE_WORKSPACE_ID` 是单一常量 | 钉住"角色来自哪个 workspace"这条安全判据 |
| 试运行 | 按 `tenant_id` + `user_type` 算订单可见范围 | **租户唯一真正生效的地方** |
| 编辑面 | 完全没有租户概念 | 见下 |

### 为什么编辑面不做隔离是当时可接受的

Dify 被定位为**智能体编排的权威编辑面**（ADR-0008 / PRD #772）：它管的是 prompt、
工具、知识库这些**平台级资产**，不是租户各自的业务数据。业务数据的租户隔离发生在
**执行时**（试运行查谁的单），而不是**编辑时**（谁能改哪个 prompt）。

当时的使用者只有公司内部运营/平台人员，所以"同工作区 editor 互相可见"没有真实受害者。

## 被否掉的替代形态

- **V1 就做多工作区**。当时的真实成本不是"建几个 workspace"，而是后面这一串：
  开户要能切 owner 会话的 workspace、映射表要加 `dify_tenant_id`（两套 id 不能混用）、
  发布桥的 workspace 钉住要按发起人解析、发布权要不要加 workspace 维度也要重新裁。
  这些在一个还没有第二个租户的时候做，等于凭想象定契约。
- **一个 workspace + 按租户分 app**。Dify 1.17.1 的 `App.tenant_id` 是 workspace 级，
  没有"app 属于哪个公司租户"这个字段。要靠 app 命名约定来实现隔离 —— 那是一条
  没有强制力的规则，而隔离恰恰需要强制力。
- **每个租户一个独立 Dify 实例**。运维成本与版本漂移都放大一个数量级；而 Dify 自己
  的 workspace 模型已经够用。

## 后果与代价（当时就把代价写清楚的部分）

- **跨租户互相可见且可编辑**：同一 workspace 内的 `editor` 能看到并修改**全部** app。
  两个租户的运营会互相改到对方的智能体。PRD §C 的应对是**限制发放范围**，不是隔离。
- **发布无租户维度**：桥钉死一个 workspace，发布权只有"能不能发"，没有"能发哪个"。
- **`tenant_id` 在映射表里是"记录"不是"依据"** —— 任何以为它在做准入的人都会读错。
- **无法按租户授予编辑范围**：`aiops:agent:edit` 是全局权限码。

## 触发条件与到期

PRD #772 §C 定的触发条件是**出现第二个需要自行编辑智能体的租户**。

**2026-10-20：用户确认该条件已满足**，并指定以 41 与另一个客户环境作为多租户的
开发与测试环境。

因此本记录的状态从「已采纳」改为 **「已到期」**：它记录的形态仍然准确描述**当前**
代码，但不再是目标态。多工作区的设计、迁移与回滚口径需要单独的记录 —— 本记录
**不**代替那一次决定，只负责把"为什么现在是单工作区"与"它已经到期"这两件事写下来。

**一处必须在后续设计里保留的约束**：桥现在用 `AIOPS_CONSOLE_BRIDGE_WORKSPACE_ID`
验证"角色来自配置的那个 workspace"。多工作区之后这条判据必须变成"角色来自**发起人
所在**的 workspace"。否则运营 A 可以在 workspace A 是 owner、在 B 里只是 editor，
而桥读错了那一个 —— 那是本设计里最容易被漏掉的越权口。

现状的完整描述与改造清单见 `docs/agents/dify-tenant-integration.md`。
