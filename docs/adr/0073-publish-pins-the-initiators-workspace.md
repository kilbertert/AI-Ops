# 73. 发布钉住**发起人所在**的 workspace，不回落任何默认值

日期：2026-10-21
状态：已采纳（#884 实施；ADR-0059 §5.2 落成代码）
影响版本：`src/aiops_diagnostics/dify_console_publish.py`（桥）、
`src/aiops_diagnostics/gateway_api.py`（`_publish_bound_app` / `_workspace_for_publish`）

## 背景

发布这条路有两跳，每一跳原先各自钉住一个**配置常量**
`AIOPS_GATEWAY_DIFY_CONSOLE_WORKSPACE_ID` / `AIOPS_CONSOLE_BRIDGE_WORKSPACE_ID`：

- **桥**用它判"运营当前所在的工作空间是不是我们钉住的那个"（第 2 步）；
- **网关**用它作为导出 DSL 时的 `X-Workspace-ID`。

单 workspace 时代两者是同一个值，所以它们对得上。多 workspace 之后这个前提消失，
而**任何一边没改都是真实的越权**：桥放行、网关却从 A 的 workspace 导出；或者反过来，
网关按租户导出、桥却用一个所有人共用的常量放行。ADR-0059 点名这是最容易漏掉的入口。

## 决策

**一、钉住的值改成「发起人所在的那一个」，两条路共用同一次身份查询。**

桥先问代理 `POST /__aiops/publish/check`（它已经在了，发布权判据用的就是它），拿到
发起人的 `company_tenant_id`；再问网关 `GET /v1/dify/workspace?tenant_id=…`
（内部令牌，ADR-0067）拿到该租户的 workspace；最后才比对 Dify summary 的 `id`。

顺序是刻意的：**先身份、再解析、最后比对**。反过来的话，一个还没开户的租户会在
"工作空间不符"上被拒，而真正的原因是"他没有工作区"—— 两种下一步完全不同。

**二、解析不到 ⇒ 拒绝，且不回落任何默认 workspace。**

`UNRESOLVED` / `FAILED` / `UNKNOWN` / `CREATING` 在桥这一侧都归成同一个回答："你所在的
租户还没有可用的 Dify 工作区，请联系管理员为该租户开户后再试"。区别留在网关那一侧
（四个可区分的码）；桥这一侧的问题是"能不能发"，答案是同一个。

**不回落**是这条决策的实质：回落等于把"这个租户还没开户"悄悄变成"发布进别人的工作区"，
而后者**看起来是成功的**。

**三、网关侧的 `_publish_bound_app` 按 `binding.tenant_id` 解析。**

它是共享密钥路由与 operator 会话路由**共用的唯一实现**，所以这一处一改，两条路同时生效。
解析失败时把四个码原样转成 HTTP（404 / 409 / 409 可重试），并**记一笔审计**：被拒的发布
尝试要能回答"谁试图把哪一版发进哪个租户"。

**四、`AIOPS_CONSOLE_BRIDGE_GATEWAY_INTERNAL_TOKEN` 是开关，不是新凭据。**

配了 ⇒ 桥按发起人解析；留空 ⇒ 仍按 `workspace_id` 常量判（迁移期行为，逐字不变）。
这样 36 上今天的部署在补这一行之前完全不受影响，而补上就是一个可回滚的配置变更。

## 被否掉的替代形态

- **只改桥、不改网关**（或反过来）。两条路各钉一个值，改一边就漂；而漂的表现是
  "桥放行、网关从别处导出"，两边各自都觉得自己是对的。
- **解析失败时回落到常量。** 见决策二：它把一次"没有工作区"变成一次"成功但发错地方"。
- **让桥自己去查 `all-workspaces` 按名字匹配。** 那要求桥持有 admin key，而 workspace 的
  真值在网关的 `gateway.db` —— 第二个真值源就是第二处会漂的地方（ADR-0059 已否）。
- **把 `CREATING` 报成"没有工作区"。** 前者是"稍后重试"，后者是"去找管理员开户"。
  在桥这一侧它们被合并了（因为桥的问题是"能不能发"，两个答案都是不能），但**网关侧必须**
  分开 —— 那里是 CI 的判据，也是运维看到的下一条命令。
- **保留常量作为默认值，只在租户解析成功时覆盖。** 那正是"回落"，只是写得更短。

## 后果与代价

- **桥多一次进程间调用**（问网关要 workspace）。与已有的一次（问代理要身份）同类，
  代价可接受；收益是两条路共用同一个真值。
- **发布在"租户未开户"时整体不可用**，而不是"发布进一个默认工作区"。这是有意的：
  一个没有工作区的租户本来就不该能发布。
- **`AIOPS_CONSOLE_BRIDGE_WORKSPACE_ID` 仍必填**：迁移期它还在用。等所有环境都配了
  内部令牌之后才能把它降级为可选 —— 那是一次独立的清理，不在本票。
- **这次没有真机验收**：41 的 `dify_workspaces` 仍为空（没有指定租户开户），所以
  "两个租户各自发布只影响自己的工作区"这条端到端结论要等第一行映射 + 一次真实发布。
  单元与假上游覆盖的是四条判据：按发起人解析、解析失败拒绝且不打网关、迁移期常量行为、
  网关侧按绑定租户导出且拒绝 `creating`。
