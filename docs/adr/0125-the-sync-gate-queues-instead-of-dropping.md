# 125. 同步闸排队，不跳过：切回来那一次不能被丢弃

日期：2026-10-24
状态：Accepted
影响版本：`knowledge_dataset_sync_guard.py`（重写）、`gateway_api.py`（调用点）

## 背景

ADR-0124 上线后做真机验证，一条**看起来已经修好**的路径露了馅：

运营在 RAGFlow 新建 `e2e-切回-20261024`，切回 Dify —— 页面确实发出了
`/__aiops/knowledge-sync`，但新库没出现。网关日志是这三行：

```
08:16:52  knowledge sync: tenant=-1 created=0
08:17:01  knowledge sync: tenant=-1 created=0   ← 距上一次 9 秒
08:18:14  knowledge sync: tenant=-1 created=1   ← 等了 73 秒才出现
```

08:17:01 那一次**就是运营切回来的时刻**，也是他唯一知道自己刚改过的时刻。它被
`knowledge_dataset_sync_guard` 的 15 秒成功下限吞掉了。运营的体验还原封不动：
「要等一分钟 / 要硬刷新」。

## 决策：在飞时排队，删掉时间下限

`KnowledgeDatasetSyncGuard` 从「非阻塞锁 + 成功/失败时间下限」改成
**「带超时的阻塞锁，无时间下限」**：

```python
if not self._lock.acquire(timeout=WAIT_SECONDS):
    return "skipped (another sync still in flight)"
```

排队后的那一次读到的是最新状态，`created` 回来的是真数字，前端照常失效列表。

## 为什么时间下限本身就是错的

下限在断言一件事：**「上游这 15 秒内不会变」**。而这恰恰是这个功能的整个前提的反面
——运营在 RAGFlow 建库、然后切回来，就发生在任意 15 秒里。下限越高，"刚建完就切回"
越容易被挡；下限越低，它越没用。**没有任何一个常数是对的**，所以删掉它。

连开两次弹窗的原始担忧（每次全量比对）仍然成立，但代价被认清了：第二次是一次
**只读**比对，`created=0` 时前端不失效列表，运营看不见任何东西。用一次只读比对换
"切回来一定看得到"，划算。

## 被否掉的两种写法

- **保留下限，调小到 2 秒。** 换一个常数重新猜，同一个 bug 只是变窄。运营停下看
  RAGFlow、心里数三秒，照样中招。
- **保留非阻塞锁，被挡时返回 `skipped: true` 并让前端自己重试。** 把丢弃推到前端，
  每个调用方都得实现退避；三处触发点（弹窗、`visibilitychange`、轮询）要写三遍。

## 排队上限

`WAIT_SECONDS = 30.0`：一次 pass 是「读一次 Dify 列表 + 建缺的几条」，实测秒级。
超时只在上海上游卡死时发生，此时跳过比让 HTTP 请求无限挂着好 —— 60 秒轮询会再来。

## 顺带

- `run(tenant_id=...)` 参数删了。它此前只被用来查时间戳；没有时间戳就没有租户维度的
  状态，锁是全局的。真要按租户分锁时再加，那时它才该存在。
- `forget()` 删了 —— 从未被调用过。
