# 管家诊断以 CPMS API 工具交给节点执行

日期：2026-10-26
状态：已采纳

## 决定与背景

旧七工具在 Dify 只提供说明，真实读取位于旧 Python 运行时；后两个租户服务工具的局部联调也不等于管家个人权限与节点执行贯通。新场景 `operator_order_diagnosis` 使用 Java 工具回调实际读取 CPMS 正式 API，不复用旧 SQL/TDengine/Redis 取数作为业务实现。

公司没有本项目可直接复用的单次 CPMS 委托令牌。公司登录令牌留在 Gateway 在飞任务内存；节点领取随机任务凭据，仅能通过固定路径转发订单详情和最多50条充电监测样本。转发不执行旧诊断逻辑；每次调用及交付核验当前管家站点、订单归属、节点、版本及截止时间。节点核对响应并提交同次证据，只有实际取数、证据确认和完整模型终态全部成立才交付答案。

提交和历史正文回读只接受公司个人令牌与 operator 入口，拒绝旧共享会话模式。共享服务令牌不能冒充 CPMS 个人凭据；不增加隐式凭据转换。历史入口沿用既有诊断认证依赖，不重复认证。公司当前没有独立诊断权限码，因此本项目的 scope 参数不能作为公司该权限已贯通的证据；当前授权约束为公司身份、实时站点和 CPMS 返回归属，真实边界单独验收。

`operator-exec-config/1` 沿用执行清单身份规则，显式支持空工具列表；旧 `m3-exec-config/1` 仍拒空。Dify 的选择经发布冻结进清单，节点只能解析其中已实现的工具。全部关闭后不派发新诊断，也不会恢复旧默认工具。

## 备选方案

- 把旧七工具再包成 HTTP：仍依赖旧运行时与直连数据，不能满足 CPMS API 工具目标，弃用。
- 给节点整租户服务 key：无法表达每位管家的当前范围，弃用。
- 把公司登录令牌存进 Dify inputs 或发布清单：暴露和保留面扩大，弃用。
- 为每个工具另建数据库、工作队列和模型循环：已有 QA/run 生命周期可复用，无需增加。

## 后果与限制

控制台试用复用同一节点路径。显式开启后，登录代理按 Dify 会话哈希在内存保留当次公司令牌，最多128份、15分钟；独立服务密钥与有效会话同时成立才供 Gateway 取得本人凭据。未配置、过期或重启需重新正常登录；不回落固定调试租户。到期在访问/登录时清理，不能声称15分钟时物理内存即时清零。

会话签发增加 RFC 7519 §4.1.7 的 `jti`，每次32随机字节编码为字符串，避免同账号同秒重登产生相同JWT并重新授权退出的会话。Dify 1.17.1 的 PassportService 使用 PyJWT 验证并接受该标准可选字段；退出仍删除该会话的公司令牌映射，不声称注销所有既有Dify会话。沿用秒级到期作为唯一变化量会复用凭据绑定，不能满足本轮边界。

订单签发前、完成前、历史回读的 CPMS 读取只用于授权核对，不替换诊断证据。监测接口没有稳定排序，第一页不是完整时间线。公司时间保留源字符串，观察时间另记 UTC。当前首片限明确站点范围的员工；整租户管理员、代查、照片和自动处置不通过本场景。

标准映射：Spring AI ToolContext 传递运行标识而不发给模型；HTTP 方法与副作用按 RFC 9110 核验，GET 名称不单独证明只读；对象访问按 OWASP API1:2023 核验。真实公司权限、数据与工程师确认结论仍需要业务验收，框架和合成上游测试不能替代。
