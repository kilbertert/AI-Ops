# ADR-0357: 面向交付运维的零命令行自助开通（V2 产品化方案）

Status: Accepted
Date: 2026-11-26

## Context

2026-11-26 首个真实客户环境「捷佳四轮国内充电（`jiejia`）」通过 `/aiops/environments` 完成端到端开通与正式 HTTPS 验收（见 [捷佳验收回执](../validation/2026-11-26-jiejia-live-onboarding.md)）。尽管编排链路最终全绿，但实测暴露了交付运维体验与工程边界之间的 6 类核心缺口：

1. **主机准入与空机前置未自动化**：新客户需改仓库 `.dev-host.toml` 提 PR；空机缺少锁定非登录账号 `aiops` 与 `python3.12-venv` 会导致冷装回滚。
2. **数据面权限与索引晚暴露**：`site-preflight` 未验证只读账号对 `qumall_upms.{sys_user,sys_user_role,sys_role}` 的 `SELECT` 权限与离线监测复合索引，直到正式公网 HTTPS 阶段才返回 `503 PLATFORM_UNAVAILABLE` 或验证阶段报 `OPERATOR_OFFLINE_UNAVAILABLE`。
3. **客户基础设施拓扑差异无自动发现**：例如客户业务网关 `/tsdata/**` 转发目标端口未监听，而本机 `cloud-tsdata-biz` 实际监听于独立回环端口；租户 ID、时区与 Nginx 扩展路径亦需手工 SSH 探测。
4. **外围基建游离在编排之外**：`36`/`41` 出口 IP 白名单、`41` 专属共享执行节点 `node-<env>` 与客户机双 Nginx 扩展（工具入口 + 用户入口）仍需手工 CLI 执行。
5. **知识库上传与三能力验收门槛过高**：需手工找订单/设备号、手工拼 `validation-cases/*.json`、手工抓取 `third-session`/建删临时测试账号，且缺乏发布后公网 HTTPS 4 项冒烟闭环。
6. **控制面工程毛刺**：取消 `tenant-onboard` 后 15 分钟内同 `plan_id` 复用阻碍重跑；开发机工作区存在未跟踪文件会导致 `aiops-site-preflight` 调度器全局拒跑。

交付运维真实拥有的输入仅包含 5 类信息：客户服务器 IP、一次性接入凭证、`admin/api` 域名、内网网关地址（及可选的只读库账号与初始知识文档）。

## Decision

建立面向交付运维的 **V2 零命令行自助开通体系**，按 P0 → P1 → P2 渐进交付，同时严格守住既有的最小权限、零明文持久化与 fail-closed 安全边界：

1. **双模式主机安全引导接入（P1-1）**：
   - **模式 A（一次性口令内存引导）**：支持在管理页输入一次性 SSH 登录凭据，控制面仅在内存中瞬时完成主机指纹钉扎（hostkey pinning）、下发专属 Ed25519 公钥、创建锁定非登录用户 `aiops` 与补齐 `python3.12-venv`，随即销毁内存口令，**严禁将明文密码写入磁盘、SQLite、日志或错误回显**。
   - **模式 B（客户侧零密码单行引导脚本）**：生成带短效一次性签名令牌（TTL ≤ 15 分钟、单次消费即失效）的客户侧引导命令，由客户运维本机执行完成公钥信任、前置补齐与指纹回传。
   - **动态客户主机清单**：平台核心主机（`41`/`36`）保持仓库静态声明；客户业务主机纳入控制面 `0600` 受管主机注册表，接入新客户无需再修改 Git 仓库提 PR。
2. **全量数据面预检与引导期二次确认受限库修复（P0-1 / P1-2）**：
   - 将 `cloud_charging_pile.*`、`qumall_mall.*` 及 **`qumall_upms.{sys_user,sys_user_role,sys_role}`** 的最小只读权限检查、必选复合索引检查（`iot_device_offline_monitor(device_id, offline_time)` 与 `ch_order_info(device_id)`）、`tsdata` 主备通路探测、Redis/UPMS 租户发现和脱敏候选样本采样纳入 `data_preflight`。
   - 对缺失的权限或索引自动生成精确只读授权/在线无锁 DDL（`ALGORITHM=INPLACE, LOCK=NONE`）；引导期内允许运维**显式二次确认**后由受控白名单执行器自动代执行，**严禁执行任何白名单之外的任意 SQL**，执行后立即以 `aiops_ro` 复验。
3. **底座自举与可靠性收敛（P0-2）**：
   - 冷装器显式支持幂等补齐锁定非登录用户 `aiops` 与 `python3.12-venv`；
   - 取消 `tenant-onboard` 后再次提交自动签发同摘要新计划，不再被 15 分钟旧取消态阻塞；
   - `task_ssh_runner` 与 `aiops-site-preflight` 仅校验受追踪代码树干净（或运行于独立只读发布目录），不受开发机未跟踪文档影响；
   - 固化订单验证标准问句（显式覆盖订单详情、时序与过程统计）并新增发布后公网 HTTPS 4 项冒烟检查。
4. **全栈基建自动编排与制品池化（P1-3 / P1-4）**：
   - 控制面按 `(revision, python_minor)` 池化管理已验离线制品，自动匹配目标机；
   - 将 `36`/`41` 出口 IP 白名单同步、`41` `aiops-environment-node@<env>.service` 拉起与心跳等待、客户机 Nginx 双扩展渲染+`nginx -t` 回滚门+即刻探活纳入受控编排；
   - 管理页内置对客/管家双知识库上传代理（附可选默认试跑 FAQ 模板）与免 JSON 瞬时三能力自验（临时凭证内存用完即吊销销毁）。
5. **前端 5 步引导式向导重塑（P2）**：
   - 将 `/aiops/environments` 改造为「接入主机 → 自动体检与修复 → 一键部署与配套 → 知识库与自验 → 正式发布与公网终验」5 步引导流，将 `deployment_target`、`credential_ref` 等底层工程字段收敛至可展开的「高级工程视图」，保留全部既有能力与浏览器回归保护。

## Alternatives considered

### 1. 仅支持客户侧手工执行 SQL 与单行引导脚本，不支持页面一次性口令与受限代执行
- **最强论点**：进一步缩小控制面与高权限凭据的瞬时接触面。
- **否决原因**：交付现场大量中小型客户仅能提供一次性服务器凭据并期望我方运维在单一界面内完成开通；通过「内存即用即毁 + 零落盘 + 白名单 DDL/GRANT + 显式二次确认 + 审计记录 + 提醒轮换密码」可在可审计风险边界内同时满足高安全客户（脚本模式）与托管交付客户（一次性口令模式）。

### 2. 绕过受控白名单在页面开放通用 SSH/SQL 终端
- **最强论点**：能处理任意未预见现场差异。
- **否决原因**：直接违背服务主机变更门禁与最小权限原则，扩大误操作与凭据泄露面；所有自动化动作必须收敛为可静态审计的参数化白名单原语。

## Consequences

- 新客户交付从“跨 4 台主机执行 14 项手工 CLI + 提 PR”收敛为“5 行输入 + 页面 5 步向导闭环”，同时继续保证 `business_mutations: disabled`、零明文持久化、fail-closed 与 `business_accuracy="unconfirmed"` 的诚实边界。
- 本 ADR 对应实现按 P0-1 → P0-2 → P1-1 → P1-2 → P1-3 → P1-4 → P2 七个独立可验证 PR 依次合入，每个阶段均具备独立测试与回归保护。
