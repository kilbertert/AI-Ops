# 221. 工具拒绝按业务结局分流：可回喂的进模型，不可变的按原始码归因

日期：2026-11-05。

Status: Accepted（用户立项实施，复盘待改项）。

工具被授权层拒绝时，旧行为把一切都终结为 `model_failed`：用户只见
`OPERATOR_DEPENDENCY_UNAVAILABLE`，节点还把网关原始拒绝码糊成
`cpms_unavailable`，排查看不到真实原因。2026-11-05 优链充路由恢复复盘中
实测确认「查无此单」类业务结局被当作系统故障交付。

拒绝按**模型能否改变结局**分流，不按 HTTP 状态分流：

- **可回喂的业务拒绝**（`FEEDBACK_REFUSALS` 12 码：未引用订单、参数非法或
  变更、依赖未满足、站点越权、上游数据不可识别等）在 `/v1/internal/` 403
  响应体携带 `feedback:true` 与中文 `hint`；新节点把它作为普通工具结果
  `{"refused":true,"code","message"}` 交回模型。模型据此修正参数、先补
  依赖，或如实向用户说明查无此单——整轮正常完成而非失败。
- **模型无法改变的拒绝**（授权/发布/节点完整性、并发抢占、运行已终结）
  维持整轮失败；节点以 `tool_refused:<原始码>` 上报终局，`run.reason`
  保留归因，用户侧仍归 `OPERATOR_DEPENDENCY_UNAVAILABLE`。

回喂标记只发给执行节点（`/v1/internal/` 路径），用户侧响应体不变。
`hint` 是写给模型的固定中文业务指引，不含内部实现；`task.refusals`
登记本轮被回喂的拒绝（去重、封顶 16），进完成快照与答复复核输入——
复核凭它区分「如实说查无此单」与「编造被拒绝」。

新旧两侧单向兼容：旧节点忽略未知字段，行为与现状逐字一致；新节点遇
旧网关收不到标记，走原失败路径。`reason` schema 只放宽认
`tool_refused:` 前缀一种新形状，自由文本仍进不来。

## 备选方案

- 全部拒绝都回喂模型：授权完整性/并发拒绝模型无法修复，回喂只会让模型
  在死局上空转直至循环上限，否决。
- 拒绝码直译成用户可见错误：跨租户/内部完整性语义不应向用户展开，用户
  侧保持单码归一，否决。
- 不登记拒绝清单、仅靠提示词让模型「记得」：复核需要的是本轮事实而非
  模型自述，快照与复核输入必须来自系统侧登记，否决。
