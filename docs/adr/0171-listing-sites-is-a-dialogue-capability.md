# 171. 列举站点是对话能力，不是搜索的一个特例

日期：2026-10-29
状态：已采纳

## 决定

「我当前有哪些站点？」曾被判 `OPERATOR_INVALID_SEARCH`，外层再包成
`OPERATOR_DIAGNOSIS_FAILED`。用户看到"诊断失败"，而它既不是诊断，也没有失败——
根本原因是 ADR-0165 的实现把 `site_search` 的关键词写成必填。

那条必填没有对应的决定。ADR-0165 只说「模型只能从用户原话提取站名或地址词」，
那是**防编造搜索条件**；空关键词什么都没编，不在它要防的范围里。执行层
`search_sites()` 也从来没假设过必须有词——`name` 为空时只是不发 `name` 参数。
守卫加在了错的一层。

现在：

```text
四个字段全空 + kind=site_search → 列举：该账号可见范围内的站点
带关键词                        → 搜索：按站名/地点收敛
```

**两种问法分开渲染，因为"没有结果"意思不同**：搜索没命中的下一步是"换个更具体的
地址"，列举为空只能说明这个账号确实没有站点。

**总数只在可信时给出。** CPMS 的 `total` 是这次查询自己的计数，员工账号还要再经
站点集合过滤，两者不等时那个数字不是"你有多少个"。所以 `scope_limited=True` 时
只说"显示前 N 个"，不冒充总数。

## 被否掉的替代形态

- **只去掉校验、渲染不动**：列举会拿到"本次查询未找到匹配站点，可换用站名"——答非所问。
- **让模型在 `text` 里写站点名单**：违反 ADR-0165 的事实边界，模型会编站名；
  站点事实只能来自 CPMS 响应。
- **分页翻给用户看全部站点**：一页 50 条、最多 4 页的既有上限是防止一次拉全租户；
  列举只回答"有多少、前几个是什么"，要查具体站点请给关键词。
- **员工账号也报 CPMS 的 total**：那是租户口径，会把"你有 10 个"说成"你有 152 个"，
  是个会被当真的事实错误。

## 后果与验证

范围控制没有变化：`search_sites()` 仍逐行核对 `tenantId` 与站点集合，关键词从来不是
授权手段。契约只增加"空关键词合法"与两个渲染字段，`operator-conversation/1` 的字段
集合不变，不用改草稿。

回归：空关键词通过校验、列举/搜索的空白提示不混用、`scope_limited` 时不报总数。
前两条对"恢复必填"与"无条件信 total"两个变异分别变红。
