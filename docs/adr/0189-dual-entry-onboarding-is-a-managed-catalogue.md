# 189. 客户开通以「受管应用目录」为落点，两端各自准备与发布

日期：2026-10-30
状态：已采纳

## 背景

平台原来的"开通"只认管家：`self_service_api.catalogue` 过滤 `operator`，开通/发布也只生成
管家清单。产品要的是"平台给一个客户开通一套 AI 服务"，默认含客户端客服与管家，也可以只开
一端、以后补开；客户共用自己的 Dify 工作区与 RAGFlow 空间，两端各有独立应用与正式版本。

这一片要回答四个问题，每一个都有更省事但更糟的答案：

1. 受管应用登记放哪里 —— 新开一张表，还是扩展现有的 `operator_apps`？
2. 客户端应用怎么来 —— 用模板生成一份客服编排，还是复制现役已发布应用？
3. 客户端的 Service 凭据怎么进系统 —— 继续人工预置，还是开通时自动申请？
4. 页面怎么区分"发布了"与"用户能用" —— 合成一句话，还是分开报？

## 决策

**1. 受管应用目录不新开表，扩展 `operator_apps`。**

加 `entry`/`scenario`/`environment`/`targets_json` 四列，存量行按默认值补齐为管家，
与现状逐字一致。新开表要迁移两次（建表 + 回填 + 删旧表），收益是零；而表名里那个
"operator" 是历史包袱，改名的唯一效果是让**每一次**部署都要迁移。

代价是：这张表现在同时装两种端，所以**任何按 `app_id` 查行的代码都必须显式说明自己要哪一端**。
这一条在实施时立刻咬了一口 —— `node_publication.all_targets` 遍历全部行并用 `profile_id`
查 profile，客户端行的空 `profile_id` 让 `KeyError` 冒出来，等于"开通一个客户端应用，
顺手把管家端所有节点路由停掉"。`self_service_config.app_binding` 同源同病。两处都改成
只认 `entry='operator'`，并由 `test_both_entries_are_created_and_published_separately` 固定。

**2. 客户端应用是现役 Chatflow 的副本，且从**已发布快照**复制。**

用模板生成一份客服编排等于重写一份已经在服务的编排；运营调好的提示词、分支与选库都在
现役应用里。所以复制来源应用**已冻结的那一版**（`agent_versions` 里带 `workflow_id` 的
快照），并在复制前用摘要核对"来源在本轮期间没变过"（变了就 `SETUP_SOURCE_CHANGED`，
不按"现在的"来）。

**3. 知识引用整段替换，不做 ID 映射。**

映射没命中时最自然的实现是"保持原样"，而原样就是源客户的库 UUID。整段替换让"源 UUID 留在
副本里"在结构上不可能；再补一道 `forbidden_ids`（跨租户时把来源的选库传进来）挡住"调用方
自己把源 ID 传进来"这一条。目标客户没有资料时**建一个空的对客库**，让客服老实说"暂无资料"，
不拿别的客户的资料补。

**4. 凭据先快照、再创建、再核对；对账不唯一就不切指针。**

`GET /console/api/apps/<id>/api-keys` 在 1.17.1 返回**完整 token**（dataset key 才是掩码版），
所以"创建成功但响应丢了"是可以对账的。但只按"创建前没有、创建后有一枚"不够：创建前如果
已有别人的 key，创建后取第一枚就会拿到别人的。快照按 `id+token` 记，新增必须**恰好一枚**；
0 枚或 ≥2 枚即 `SETUP_KEY_AMBIGUOUS`，不切正式指针、也不删别人的 key。达到 Dify 的 10 枚
上限时拒绝，让运维去清理。

**5. 两端不是一个事务；已存在正式版时只建草稿。**

一端失败另一端继续，整体 `partial`，重试只续跑失败端。把两端绑成一个事务，等于让"客户端
凭据被上游限流"顺手把已经成功的管家回滚掉，而回滚外部资源（工作区、知识空间）不可靠。
目标客户已有该端正式应用时，开通只建草稿（`draft_only`），原正式版继续服务 —— 复制不能
自动替换正在服务的那一版。

**6. 渠道状态读声明，不从"已发布"推导。**

"AI 已准备"和"用户能用"是两件事。渠道是否接入读环境清单的 `[[channels]]`；没有声明就是
`pending`（fail closed）。页面把四件事分开说：资源准备 / 该端已发布 / 渠道已接入 / 真实用户
已验证。

**7. 受管行是客户端运行目标的第一权威，现役文件保留。**

现役客户的发布目标写在 0600 JSON 里（`AIOPS_GATEWAY_CONSUMER_PUBLICATION_TARGETS_FILE`）。
新客户走受管行，现役文件继续生效（零迁移）；两边对同一个 `(租户, 环境)` 指向不同应用时
**显式拒绝**，不按"谁优先"裁决 —— 隐式优先级会让"这个客户到底由哪个应用服务"变成一个
问题，而不是一个事实。

## 被否掉的替代形态

- **新开 `managed_apps` 表。** 两次迁移、两套读路径，收益是表名好看。
- **按端各建一张表。** 两端共有的字段（租户、工作区、agent 名、创建者）会复制两份，
  而"这个应用属于哪一端"本来就是一个字段。
- **用模板生成客户端应用。** 等于把现役编排重写一遍，客户改过的东西全丢。
- **知识库 ID 映射（源 ID → 目标同名库）。** 名字不唯一、改名就断，而且映射失败时的
  默认行为是"保持原样"，也就是把源客户资料带过去。
- **先发布再试用。** 试用在临时应用里跑那份 DSL，本来就不需要正式路由；要求先发布才能试，
  等于让客户用一次未验证的内容去替换现役正式版。
- **渠道状态按"有没有正式版"推导。** 那会把刚开通、还没有任何前端在调它的客户显示成"可用"。
- **凭据存数据库（加密列）。** 迁移存储不是业务前置；受控目录 + 0600 原子写已经满足
  "业务人员不碰文件"。未来多 Gateway 实例需要统一凭据服务时再迁移。

## 代价

- `operator_apps` 一名两用，任何按 `app_id` 的查询都必须显式声明端；已用两个真实缺陷
  （见上）证明这条不是理论风险。
- 客户端首次发布需要**先在目标空间有一个对客库**。开通会自动建一个空库，但"空库"意味着
  客服在客户上传资料前只会说"暂无资料"；建库成功与内容可检索是两件事，页面必须分开显示。
- 受管客户端目标只支持**动态知识回答**（`knowledge_answer_mode=documents`）编排。旧 FAQ 流程
  需要内容文件，受管行没有内容文件，因此明确拒绝（`SETUP_CONSUMER_CONTENT_REQUIRED`），
  而不是"发布了但答不出"。
- 每端多一次 `agent_versions` 读与一次应用文档导出；都是一次外部读。
- 客户端 Service 凭据落在一个目录里（`AIOPS_GATEWAY_CHAT_DIFY_KEY_DIR`）。备份、轮换与权限
  必须覆盖这个目录；它不进仓库、不进日志、不进任务 JSON（任务里只存路径）。
