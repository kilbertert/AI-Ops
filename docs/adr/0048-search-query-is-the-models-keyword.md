# 48. 检索词是模型给的关键词，不是它的 reason；缺 query 就重问一次

日期：2026-10-19
状态：已采纳
影响版本：`src/aiops_diagnostics/qa_rag.py`（`_search_query` / `_execute_searches` /
`_missing_query_prompt` / `_initial_prompt`）、`src/aiops_diagnostics/promo_agents.py`
（`promo_prompt`）

## 背景：一次"回答正常但没图"的事故

41 上真实用户问「有客户案例嘛」，回答 `completed`、`retrieval_status=found`、
`searches=1`，但 `result.blocks[]` 里 **0 个 image/video 块** —— 前端因此无图可渲染。
媒体面本身无罪（#834 的 403 修复已在 41 上），因为这次**压根没产出媒体块**。

根因在**送进知识库的那串字**。模型的 tool_request 漏了 `query` 字段：

```json
{"tool":"knowledge_search","reason":"检索宣传库中一个代表性客户案例，用于生成客户案例卡片。"}
```

而 `_execute_searches` 当时写的是：

```python
query = str(request.get("query") or request.get("reason") or "")
```

于是那句**用途说明**被当成检索词发了出去。41 只读回放把这一点钉死（同一知识库，
只换 query 字符串，返回的 `reference_id` 与两次真实 run 的 rollout **逐字对齐**）：

| 送出的字符串 | k=5 返回 |
|---|---|
| `新能源 充电站 客户案例` | 5ch / **1 img** |
| `检索宣传库中一个代表性客户案例，用于生成客户案例卡片。` | 5ch / **0 img** |

同一天 12 次宣传 run 里 7 次走了这条路 —— 症状因此**时好时坏**，看起来像检索不稳。

`query` 之所以能缺，是因为 Responses 的 `text.format` 在声明 tools 时被适配器丢掉
（ADR 0047），schema 里的 `required` **在 wire 上不生效**。所以这不是模型偶发失误，
而是**契约层没有任何东西阻止它**。

## 决策：reason 不参与检索；缺 query 就重问一次，兜底用用户原问句

`_search_query` 只认 `query`。`reason` 是模型**为什么**要搜的散文，不是**搜什么**的
关键词 —— 两者不是可互换的检索输入。

缺 `query` 时按顺序做两件事：

1. **向模型重问一次**（`_missing_query_prompt`）。它发出的 turn 是形状合法的，
   对话里没有任何别的东西提示它少了个关键词，所以必须明说。复用循环内
   `_forced_search_prompt` 已有的同形先例，`_MAX_RUNS=5` 有余量。
2. 重问后**仍**没有关键词，才回退**用户原问句**（既有 empty-request 语义）。

两次降级都记为结构化 warning（`qa_search_query_missing` /
`qa_search_query_fallback_question`）。**静默是这个缺陷能活下来的原因**：一张
`found` 但没有图的卡片，与一个本来就没有媒体的知识库长得一模一样。

`_execute_searches` 自身对无 `query` 的请求**直接拒绝并回一条 error**，而不是替换成
散文 —— 诊断路径也调它，规则放在这里才对所有调用者生效。

## 被否掉的替代形态

**① 继续用 `reason` 兜底（保留现状）。** 最强的理由是它确实"能用"：reason 是模型
自己写的、确实描述了它想找什么，而且改动为零。它输在**这不是同一个问题的答案** ——
实测同一知识库上 reason 句子与同义关键词返回**不同的 chunk 集合**，且只有后者带回
图片块；更糟的是失败带着 `retrieval_status: found` 交付，下游无从分辨"检索到了别的东西"
与"检索到了对的东西"。一个会静默改变证据的兜底，比一个会失败的重问更贵。

**② 一律退到用户原问句，不重问。** 更简单，且**避免了多一次模型往返**（真实成本：
一次完整 turn 的延迟与 token）。它输在实测**同样取不到图**：`客户案例`、
`有客户案例嘛`、`我想看客户案例` 在 k=5 与 k=10 都是 0 img。用户口语问句不是关键词
—— 与 reason 句子是同一类错误，只是来源不同。

**③ 把 `query` 变成真正的 wire 级必填**（修 `text.format` 被丢弃的问题，让 schema 生效）。
这是**唯一能根治**的方向：契约强制 > 客户端兜底，且不花任何往返。它没有被这条采用，
是因为它是**另一个缺陷面**（ADR 0047：适配器为兼容上游而主动丢弃 `text.format`），
修它要动适配器与上游兼容策略，影响面远大于这条。**这是本 ADR 记下的未偿债务**：
重问是兜底，不是保证。

## 后果

**变简单了**：检索输入只剩一个来源，`retrieval_status` 重新可信 ——
`found` 现在意味着"用模型指定的关键词检索到了"。

**变贵了**：模型漏 `query` 时多一次模型往返（约一个 turn 的延迟与 token）。
按 41 的实测比例（12 次里 7 次），这是**常见路径而非罕见分支**，成本是真的。

**被明确接受的**：重问仍可能失败，此时退到用户原问句 —— 这条兜底**已知对图片型
知识库无效**（见替代形态 ②），保留它只是为了不把运行变成"什么都答不出来"。

**仍然欠着的**：③ 那条契约级修复。在那之前，`query` 的必填性只是提示词里的约定，
任何上游都可以继续忽略它 —— 这也是为什么本次的告警必须留着：它是这条债务唯一的
可观测信号。
