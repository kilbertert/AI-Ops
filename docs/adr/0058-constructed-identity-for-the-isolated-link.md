# 58. 隔离栈用构造身份发起真实链路；只在调用者一环放宽并写明

日期：2026-10-20
状态：已采纳
影响版本：`tools/m2_close/m3live/`（新增）、`deploy/m2-live-03/`（两个开关模板、
节点挂载、制品锁）

## 背景

M3 的执行配置身份（签发固定 / 领取对照 / 整轮完成才算成功）已经在合成链路里验过，
但没有在**生产宿主上的真实链路**里跑过：真实 CPMS、真实业务库授权、真实模型出口。
要跑就得打开隔离栈的四个开关，而那条链路的第一跳是**调用者身份**。

本部署只启用 `thirdSession` 会话链，Redis 里是**真实客户会话**。借用任何一条都是冒充
真实客户 —— 这是本仓库既有的、写进 validation 的纪律，不是本轮新加的洁癖。

于是只剩两条路：让业务方签发一条验收会话（不在本主机能力范围内），或者**构造**调用者。

## 决策

**构造调用者身份，并在报告里逐条写明这一环是构造的。**

具体做法：

1. 新增 `tools/m2_close/m3live/identity_launcher.py`：把握手令牌换成固定的
   `ScopeContext`（`self` 范围 + 声明的租户/C 端用户）。
2. **它不传 `order_authorizer`** —— 订单授权仍是真实的 `ScopedOrderAuthorizer`，
   按调用者范围查业务库。构造的范围若与订单归属不符，真实授权器会给出 404，
   链路根本不会往下走。**放宽的只有「谁来发起」，判据本身没有放宽。**
3. 启动器自己补上隔离门禁（它绕过了 `gateway_server serve`，那道门在那里）。
4. 有一条源码级断言钉住「不得传入替身授权器」，并给出反面对照（合成启动器确实传了）。

## 被否的方案

- **借一条真实客户会话**：冒充真实客户。既有纪律明确不做，不论多省事。
- **等业务方签发**：正确但不在本主机能力范围内；本轮要验的是 M3 的判据，不是调用者身份。
  它仍然是**将来**做完整业务验收时必须走的路。
- **用 `gateway_launcher.py`（合成启动器）**：它连订单授权也替换成 SQLite 替身，
  于是「真实授权器会不会放行这次请求」这件事根本没被验证 —— 那正是本片想在生产宿主上
  看到的一半。
- **在生产 Gateway 上开这四个开关**：那是把委派入口真正对外可用，需要单独授权与评审，
  而且 41 宿主机上没有 Snail 平台与节点在跑。

## 后果

- 本轮「真实链路」的诚实描述是：**Gateway / store / 平台 / 节点 / 模型出口 / CPMS /
  订单授权都是真的；调用者身份是构造的。** 不能写成"端到端真实用户链路"。
- 构造身份的租户与 C 端用户必须是**真实存在、且真的拥有那个订单**的，否则真实授权器
  会 404。这条由链路的失败模式自己保证，不需要额外断言。
- 生产 Gateway 全程不重启、不改配置；隔离栈独立网络与数据，`down` 后状态目录保留。
- 执行配置清单两侧读**同一份字节**（节点容器只读挂载单文件），身份天然一致；
  两份副本各自写入时必须逐字节相同。
