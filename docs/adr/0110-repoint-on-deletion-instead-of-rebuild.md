# 110. 库被删时改指，而不是重建

日期：2026-10-23
状态：Accepted
影响版本：`ops/environments/env-41.toml`、
`/etc/aiops-41/production.env`（`AIOPS_GATEWAY_DIFY_KNOWLEDGE_BINDINGS`）、
Dify dataset `66d3481c…`（「41」）、网关 agent `canary-客服` v17 / `canary-宣传案例` v4

## 背景

2026-10-23 18:06–18:07，租户 `1942105476598861824` 的知识库
`8701c742b28111f18637d95f7710e3a3`（「41-客服知识库」，12 文档）**在 RAGFlow 控制台里被
删除**。日志给出的时间线是完整的一条：

```
18:06:35  POST /api/v1/auth/login      200     ← 同一个用户 559af59…，本机回环
18:07:13  DELETE /api/v1/datasets      200
18:07:14  INFINITY dropped table ragflow_559af59…_8701c742…
```

删除之后，凡是指向这个库的路径都变了形状，而且**四种形状互不相同**：

| 入口 | 删前 | 删后 |
|---|---|---|
| kb-service 文书列表 | 12 文档 | `502 upstream_error` / `code=102 You don't own the dataset` |
| 网关 `kb-canary-2`（Dify 已发布 app 用） | 200 + 记录 | **502** |
| 网关 `tenant-…:8701c742…`（库级 id） | 200 + 记录 | **404**（库不在清单里 ⇒ 解析不出） |
| 网关 tenant 级合并形态 `tenant-…` | 200 + 记录 | 200，但只剩别的库 |

也就是说：**同一个原因，在四个调用方看来是四种不同的错误。** 想靠"看报错"判断发生了什么，
会先被这些形状骗一遍。

## 决策

**改指到同租户里还活着的 `5c9313bccdfc11f18637d95f7710e3a3`（「41(1)」），不从 MinIO
重建 `8701c742…`。**

理由不是"重建麻烦"，是重建出来的东西**不完整**：

- 那个库 12 个文档里有 5 张宣传图，2026-10-22 已确认 **MinIO 对象损坏且机器上没有原件**
  （全盘按精确字节数搜过）。重建 = 恢复 7 个真文档 + 5 个坏图。
- `41(1)` 恰好就是那 7 个**逐个核对过 size** 的重建产物（10-22 建，`run=DONE`）。
- MinIO 里 `8701c742…` 的桶**还在**（删除没清桶），所以"以后能恢复"这条路没被堵死；
  只是今天恢复不出比 `41(1)` 更好的东西。

**"还在"的判据是能取回字节，不是桶还在。** 这一条写在 ADR 里，是因为今天很容易把
"MinIO 里 12 个目录都在"读成"数据都在" —— 而 10-22 的结论是其中 5 个内容是乱的。

## 被否掉的替代形态

- **从 MinIO 重建 `8701c742…`**。桶确实还在、12 个对象目录都在，看起来是最忠于原状的
  选择。被否的理由是「桶在」不等于「数据在」：10-22 已逐字节确认其中 5 张 PNG 在第 32
  字节之后就是乱的，且机器上没有原件。重建会得到一个**看起来是原来那个库**、实际少
  5 张图的东西 —— 比明说「换了一个库」更难发现。
- **保留旧 id、把数据搬到新 dataset 上**。RAGFlow 的 dataset id 由建库时生成，不能改；
  要做到"id 不变"只能改数据库，那会让 `docs`、Infinity 表名、MinIO 桶名三处与实际
  不一致。
- **让所有引用方自己处理缺失**（检索失败就回落到纯文本）。这会把一次配置修复变成每个
  调用方各自的一次降级：Dify 侧会表现为"模型说查不到"，而那是**看起来正常的回答**。

## 后果

四条引用一起改（少改一条就留一个静默的空白答案）：

| 引用 | 改法 |
|---|---|
| `env-41.toml` 两个 agent | 清单改 id（仓库是权威；部署目录那份本来就更旧） |
| `AIOPS_GATEWAY_DIFY_KNOWLEDGE_BINDINGS` 的 `kb-canary-2` | 改 `.env` 一行，重启网关 |
| Dify dataset「41」`66d3481c…` | `update_external_dataset`，**只改 external_knowledge_id** |
| 网关 agent 两个已发布版本 | `fork_draft → update → publish`，**不直接 UPDATE 库** |

最后一条是重点：直接改 `agents.config_json` 会绕过 `publish` 的两道校验（模型白名单、
知识库活性）。活性校验要注入生产用的 `KbBindingResolver`，不注入就是
`knowledge-base validation is unavailable` —— 那条错误会把 agent 留在 **draft**
（真实发生过一次，见 `docs/validation.md` 同日条目）。所以这条路径只能走生产代码。

**没改的**：`agent_versions` 里的历史快照（v9–v16 仍写着 `8701c742…`）。那是**审计事实**，
不是待修状态；改写历史快照等于伪造"当时绑定的是什么"。

**代价**：`41(1)` 少 5 张宣传图（内容早已损坏）。要补需要原始素材，与本次删除无关。
