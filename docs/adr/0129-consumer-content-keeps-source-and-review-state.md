# 129. C端内容编译保留来源和审核状态

Status: Accepted

## 背景与决定

WF01复用现有RAGFlow和Dify，但运营原包同时包含工作簿、Markdown和媒体清单。
工作簿具有发布状态、风险和API依赖，直接上传Markdown会丢掉这些约束。
原包的媒体关联两侧实际存在不一致，媒体清单也没有成品地址。

编译器先交叉校验正文/身份，保留媒体关系冲突、原始字段与文件SHA-256，再生成中英文单问答正文。
输出始终是draft，不把编译成功视为业务批准、接口可用或媒体已制作。
首轮禁用业务写动作；只读候选仍待实际接口核验。

读取格式沿用仓库OOXML解析与RFC 4180 CSV；派生JSON遵循RFC 8259，文本UTF-8。
文件与工作表的身份明确，不根据列位置或文件遍历顺序猜语言。

## 替代方案

- 直接导入原Markdown最省事，但丢失运营审核状态及依赖，且会把未制作素材当作已关联。
- 重录到新的内容平台便于编辑，却制造第二份事实源；目前复用工作簿及派生文件足够。
- 自动合并媒体两侧列表能消除冲突数量，却不能证明图片适用性；保留冲突等内容审核。

## 后果

同一原件可重复生成、逐条追溯，未确认配置不伪装成业务事实。
代价是内容编译与正式发布分开；本片不改变在线问答，不宣称WF01已运行。
