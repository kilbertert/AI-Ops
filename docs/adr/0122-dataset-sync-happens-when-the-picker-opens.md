# 122. 建库同步挂在选择器打开那一刻，不靠定时器也不靠人

日期：2026-10-23
状态：Accepted
影响版本：`src/aiops_diagnostics/knowledge_dataset_autosync.py`（新）、
`gateway_api.py`（`_maybe_sync_dify_datasets` + 清单路由）、`gateway_runtime.py`、
`gateway_config.py`（`dify_external_knowledge_api_id`）、`tests/`

## 背景

运营对"打通"的全部期待是：**在 RAGFlow 建一个库，它就该出现在 Dify 里。**

今天实现到一半。#925 让 RAGFlow 的库**立刻**出现在我们自己的清单
（`GET /v1/dify/knowledge`）里，不用登记。但 Dify 编排页的「添加知识库」选择器
读的是 **Dify 自己的 dataset 表**，不是我们那份清单。于是中间横着一条人工命令：

```
aiops admin sync-knowledge-datasets --tenant … --workspace … --api-id …
```

真机上因此出现过两次"我建了库，Dify 没有"——每次都需要运维介入。

## 决策：挂在清单路由上，一次请求最多尝试一次

**触发点选在 `GET /v1/dify/knowledge`**，因为：

- 选择器打开 = 运营马上要选一个库。这是唯一一个"现在不同步就立刻浪费他时间"的时刻；
- 它是**真实用户动作**，不需要常驻作业、不需要 timer 的监督与失败上报；
- 定时器会对**没人在看的租户**持续写 Dify，而那正是恢复不了的写（见约束 3）。

三条约束，缺一条都会变成事故：

1. **失败绝不改变清单的返回。** 同步是"让它更方便"，不是"它能不能用"。一次 Dify
   抖动让运营连**已经有的**库都选不到，比"新库没出现"严重得多。网关层与引擎层
   **各有一道** try —— 引擎坏了也不能带塌路由。
2. **同一租户有最短间隔（30s）。** 选择器可能连打几个请求；没有下限就是每个请求
   都往 Dify 写一遍。间隔内的请求不尝试，却**照常返回清单**。
3. **绝不删。** 只做 create / rename / fix_permission / fix_retrieval_model。
   `plan()` 的 `orphans` 只进日志 —— Dify 没有恢复入口，自动删是单向操作。

还有一条实现上的：**一次只跑一个 pass**（非阻塞锁）。两次并发 pass 会各自读到同一份
dataset 列表、各自决定"要建"，而 Dify 对 `(tenant, name)` **没有唯一约束** —— 输的那
一方会留下一条重复。

## 与 ADR-0096 的关系（它不是反转）

ADR-0096 说"不自动同步"，理由是**正文**：`sync-from-dify` 会把运营打字打到一半的
prompt 推给真实用户。

这里同步的是**建库**：RAGFlow 里出现了一个库，把它落成一条 dataset，是纯增量的幂等
动作，没有"半成品被推上线"的可能。两件事共用一条命令，但风险完全不同 —— 所以这一条
只在读路径上收敛，**不碰任何正文**。

## 被否掉的替代形态

- **定时器轮询**（每 1–2 分钟扫所有租户）。会替没人在看的租户写 Dify，且需要自己的
  监督、重启语义、失败上报；收益只是"更早几十秒"。
- **RAGFlow 建库时回调我们**。最实时，但要改 RAGFlow 源码或拦住它的 API，侵入性最大，
  且把一条只读链路变成有状态的回调链。
- **放宽检索侧去直接用 RAGFlow 的库**（完全绕开 Dify dataset）。那会推翻"选择器不撒谎"
  这条（ADR-0066）：Dify 展示的选项必须都是检索真能用的，反之亦然。

## 代价

- **多一处配置**：`AIOPS_GATEWAY_DIFY_EXTERNAL_KNOWLEDGE_API_ID`。留空 ⇒ 整个自动同步
  不启用（清单照常）。不猜模板 —— 猜错等于把凭据绑到别处（ADR-0096 决策一）。
- **清单路由变成有写副作用的路由**。这是有意的，也是这条 ADR 存在的理由：下一个人读
  `GET` 不该被它的写行为吓到，也不该把它当纯读接口去加重试。
- **最多 30 秒的可见延迟**：同一租户在一个窗口内的第二次打开不会重试。

## 后果

更容易：建库 → 去 Dify 编排页点「添加」→ 它就在那儿。**不需要任何人跑命令。**

更难：这条链路现在跨三个系统（RAGFlow → kb-service → 我们 → Dify），任一环挂了都表现
为"新库没出现"。日志里 `dify dataset autosync tenant=… ok (N write(s))` 是唯一的正向
信号，失败时读那一行的 `failed: <ExcType>`。
