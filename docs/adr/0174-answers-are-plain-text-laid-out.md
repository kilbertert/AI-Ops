# 174. 回答正文按纯文本排版交付，可读性不靠 Markdown

日期：2026-10-29
状态：已采纳

## 背景

2026-10-29 反馈：管家端与客户端的回答"完全不适合人看"。

内容是对的，问题在**形状**：管家诊断报告用 `"\n\n".join([...])` 把九段文字（直接回答、
事实概述、可能原因、建议、缺证、两条来源）拼成同等重要的段落，列表没有编号，没有任何
小标题；客户端状态与账单把五个字段用分号串进一句话，免责说明和数据挤在同一句。
`cpms.orderDetail` 这类内部接口标识、带六位微秒的 ISO 时间，直接摆给用户。

## 约束（决定了解法）

**前端按 `blocks[]` 分派渲染，不解析 Markdown。** 这在
[前端 API 简报](../agents/frontend-api-brief.md) 里写死了两处：块渲染规则
（`text` 块"按顺序渲染段落"）与"不要解析 Markdown、不要从文本里提取 URL"。

所以提高可读性**不能**靠 `**加粗**`、`# 标题`、`- 列表` —— 那些符号会在页面上原样
显示。能用的只有纯文本本身表达得出来的层级：小标题（`【】`）、编号列表（`1.`）、
项目符号（`-`）、空行分段、缩进。

## 决策

- **管家诊断报告**分节：【订单事实】【可能原因】【建议下一步】【证据缺口】【数据来源】。
  列表带编号（用户能说"第 2 条"并能对上）；来源写人话（订单详情／充电监测样本）
  而非 `cpms.orderDetail`；**空章节整节省略**，不打印空标题。
- **客户端状态与账单**逐行一项，免责说明单独成段。
- **时间统一渲染**为 `2026-10-29 12:34:45 UTC`。微秒是给核对用的（快照与证据里保留
  原值），不是给人读的。解析失败原样返回 —— 把读不出来的时间戳硬凑成人类格式，
  比显示原值更容易误导。
- 三条渲染路（未本地化的 `status_answer`／`billing_answer`、本地化模板
  `consumer_language.live_answer`）共用 `consumer_time.readable_time`。

## 被否掉的替代形态

- **改用 Markdown 提升排版。** 页面不解析，等于把 `**` 当正文显示 —— 比现在更差。
- **新增 `kind: "heading"` / `"list"` 块让前端渲染。** 那是**改块协议**，需要前端同步
  发版；而这次要解决的问题用纯文本就能表达。协议扩展应该由真正需要结构化渲染的需求
  驱动，而不是为了让一段报告好看。
- **让模型直接输出排版好的正文。** 排版格式会随模型每轮漂移，而"哪些字节会出现在
  用户屏幕上"必须可复现、可测试。
- **把时间函数放进 `consumer_order_chat`。** `consumer_language` 被
  `consumer_order_chat` 导入，反向 import 会形成包内循环边
  （`tests/test_readme_architecture.py` 实测变红）。独立模块是这个约束下的解，不是
  为了"分层好看"。

## 代价

- 排版是**写死的中文小标题**（【订单事实】等），管家端目前只有中文报告。接入其他语言
  时需要把标题也纳入本地化，届时是一个新的改动。
- 客户端免责句的措辞逐字保留（"支付金额字段不证明已经扣款，退款记录不证明银行到账"）。
  本次只动排版，不动语义 —— 第一版草稿把它简化成"不证明已经到账"，会让用户以为钱
  可能到了，测试拦下并已恢复。

## 验证

`tests/consumer/test_answer_readability.py` 断言**结构特征**（小标题、编号、人话来源、
无微秒 ISO、空章节省略），不比对整段文案 —— 否则测试会退化成文案的副本，每次改措辞
都要改测试。变异验证：把管家渲染退回 `"\n\n".join`，3 条测试变红。

## 未覆盖

知识库回答与零阶自由问答的正文由模型生成，走 Dify 链路，本次未改动。它们的排版是否
同样需要处理，需要先看那条链的实际输出形状。
