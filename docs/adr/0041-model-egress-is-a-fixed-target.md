# 41. 节点的模型出口是一个固定目标，不是一张通用外网

日期：2026-10-19
状态：已采纳
影响版本：`deploy/m2-live-03/`（`model-proxy`、`modellink`）、`tools/m2_live/model_proxy.py`

## 背景

上一版部署件只给平台接了 `egress`，节点只在内部网络里。当时的假设是「模型由平台调用」。
固定平台源码 `10c1d3e` 显示相反：`ClientChatExecutor` 在**执行节点**构造 ChatClient 并发起
流式模型调用，`ClientChatModelSpecFactory` 把下发的 endpoint/key 交给适配器，
`OpenAiCompatibleChatModelAdapter` 用 `.model(spec.modelKey())` 发出请求。

合成验收之所以一直绿，是因为桩模型也在内部网络上：节点够得到它。真实供应商在公网，
节点够不到 —— 合成拓扑把这个问题整个掩盖了。

同时还发现模型标识的问题：`bootstrap` 把 `modelKey` 写成项目内部资源名
`aiops-m2live03`，而 `modelKey` 正是发给供应商的 `model` 字段。供应商会收到一个它不认识
的模型名。

## 决策

**给节点一条只通向一个固定目标的出口，而不是把节点接进通用外网。**

- 新增 `model-proxy` 与 `modellink`（`internal: true`）：只有 node 与代理在这张网络上。
  节点仍然没有任意外联；平台与网关的网络不变。
- 代理**只转发到部署件钉住的一个上游**（`M2LIVE_MODEL_UPSTREAM` 只允许源，带路径前缀
  直接拒绝启动），路径白名单（`/chat/completions`、`/v1/chat/completions`、`/v1/models`），
  不实现 CONNECT，请求里的任何字段都不能改变目标。
- **凭据分离**：供应商 key 只在代理容器里（0600 文件）；平台下发给节点的是**出口专用
  令牌**。两者由 `prepare-secrets.sh` 分别生成，互不混用，也不与公司会话/业务凭据混用。
- 两侧都按真实协议校验 TLS：节点→代理用本栈 CA（节点用 JVM truststore），
  代理→供应商用系统公开 CA。没有关闭校验的开关。
- 模型标识显式化：`M2LIVE_MODEL_ID` 是发给供应商的模型名；内部资源名只用于平台里的
  显示名。正式模式缺它就**在改平台状态之前**拒绝。合成桩会检查 model，把内部名当
  model 时返回 400 并计数。

## 被否掉的替代形态

- **把节点接进 `egress`。** 最省事，也「能跑」；但它把「节点只能做被授权的那一件事」
  换成了「节点能连任何地方」，而节点是三种工具里唯一能执行动作的进程。这条路一旦走上，
  `GovernedToolRuntime` 收敛工具集合的意义就被网络层抵消了。

- **在平台侧代调模型。** 那要求改上游执行框架（模型调用在节点进程里），任务书明确不改；
  而且它会把平台变成第二个能看到完整提示词的进程。

- **让节点直接持有供应商 key 并连供应商。** 这既扩大了凭据的可见面，又要求节点能出网；
  与上一条相比只是把同一个问题挪了个位置。

## 后果

更容易：节点仍然只能到「受控出口」；供应商 key 的所有面收敛到一个容器；模型调用路径可以
被单独验证（停掉出口，委派失败；重启，恢复）。

更难：多了一个要计入预算、要发证书、要单独配凭据的组件；新增受控端点时要改白名单并过审查。
代理只做转发，不重写请求 —— 也就是说它不做协议兼容层，适配器发什么上游就收到什么。

上限：代理证明的是「节点到上游的路径是固定的」，它不证明上游可用、不证明供应商接受这个
模型标识、也不做配额与审计。这三件事要靠真实供应商验收。

## 2026-10-19 修订：响应帧化由出口重新表达，TLS 以 close_notify 收尾

**事实不变，协议面补齐**：代理仍然只转发到一个固定目标、不实现 CONNECT、不改写请求。
这次改的是**响应**这一侧。

41 真实链路第一次跑通时，供应商 200 与模型响应都已收到，curl 却以 56 退出
（`unexpected eof while reading`）。根因有两层，都是出口自己的问题：

1. 代理把上游的 `Transfer-Encoding` / `Content-Length` 全部丢掉，再靠关闭连接表示结束；
   上游给的长度信息在那一跳就没了。
2. HTTPServer 只关 TCP、不做 TLS shutdown，客户端拿到的是没有 `close_notify` 的硬断开。

所以现在：上游给了 `Content-Length` 就原样转达（非流式客户端凭它判定结束）；没有长度
就按 `chunked` 重写；连接在 `finish()` 里以 `close_notify` 收尾。**不缓冲 body** ——
模型调用可能是流式的，缓冲会同时破坏流式语义和内存上限，因此这里没有「大小上限」这个
旋钮，只有按块转发。逐跳头与单例头（`Server`/`Date`）由本进程重新表达，避免重复行。

被否掉的替代方案：**整段读进内存再补 `Content-Length`**（简单、能让所有客户端不靠断开
判定结束，但要求一个大小上限，且把流式响应变成非流式）；**保持关闭连接表示结束、
只补 `close_notify`**（最小改动，但客户端仍无法在帧内知道 body 是否完整，中间设备也
无法缓存或复用）。

上限：这修的是 framing，不是上游行为。供应商自己提前断流时，客户端仍会看到真实错误。

## 2026-10-19 修订二：上游长度自相矛盾时拒绝转发（RFC 9112 §6.3）

上一版把「上游头里写了什么」当作透传依据，这在一处是错的：`http.client` 在
`Transfer-Encoding: chunked` 与 `Content-Length` 同时存在时按 chunked 解帧，而代理却
读原始 `Content-Length` 向下游声明。独立复现的结果是 `curl_exit=0`、`body="{"` ——
一个完整的模型响应被截成语法不完整的片段，比报错更难发现。

RFC 9112 §6.3 的顺序是明确的：`Transfer-Encoding` 覆盖 `Content-Length`，这样的消息
「ought to be handled as an error」；转发方若要转发，**必须先删掉收到的 `Content-Length`**；
重复的 `Content-Length` 只有在逐项可解析且全部相同时才可按单值处理。

所以**下游帧化只按 `http.client` 实际解出的语义写**（`response.length` / `response.chunked`），
不再读原始头；上游出现 TE+CL、重复且不一致、或 CL 无法解析时，返回
`502 proxy.upstream_response_ambiguous`，**不猜、不截断**。上游提前断流时也不补终止块、
不补齐长度，让下游按帧判出不完整。

被否掉的替代方案：**按 §6.3 删掉 CL 后照常转发**（协议上成立，本受控出口选择保守拒绝，
不增加恢复歧义响应的分支）；
**按原始 CL 截断后转发**（就是这次的缺陷，且不报错）；**缓冲全量再按实际字节重算长度**
（要求大小上限，并破坏流式）。

上限：拒绝的是「上游自己在帧上自相矛盾」，不判断内容是否正确，也不是通用 HTTP 校验器。

## 2026-10-19 修订三：完整解释 Connection 选项

RFC 9110 §7.6.1 要求中间件先解析所有 `Connection` 字段，移除每个选项命名的字段。
出口将多行、逗号分隔且大小写无关的选项并入已知逐跳字段集合，保留其余端到端字段；
自己的 `Connection: close` 和响应帧化仍由本进程生成。真实 TLS 回归验证移除与保留两面。

审查中的另外两项：同值逗号 CL 按 RFC 9110 §8.6 可以拒绝，保持 502 策略；
SSE 首事件延迟是已声明的块读限制，低延迟增量交付仍未验收。
