# 197. 结构化输出靠提醒与有界重采样，不假装能强制

日期：2026-11-03
状态：已采纳

## 问题

管家订单诊断约三成失败，日志是 `json_parse plain_text:1248–1504`：模型最后一轮
**根本没输出 JSON**，而是写了一段一千多字的中文正文。

## 事实

节点在每轮最终发送点**强制** `response_format={"type":"json_object"}`
（`GuardedChatModel.outputContract`）。但它对供应商只是**提示**。实测（41 生产，真实上游）：

| 条件 | 最后一轮不吐 JSON |
|---|---|
| 基线（带工具轮次） | 36–44%（9/25、11/25、8/25） |
| 要求写进 system 提示词 | 16%（4/25） |
| **要求写进节点看到的那条用户消息** | **8%（2/25）、12%（3/25）** |
| 上面 + 再要一次 | **0/25** |

## 决策

三件事一起做，都不放宽任何交付判据：

1. **末轮提醒**：把「最后一步只输出那个 JSON 对象本身」写进 `SnailDispatcher.question`。
   这是模型看得到的那条用户消息，改它**只动 Python** —— 节点对 system 消息集合做逐字校验
   （`GuardedChatModel.verifySystemMessages`），改 system 要换 jar 与清单。
2. **有界重采样**：上游失约时**重新派发一次**完整对话，硬上限 `MAX_RESAMPLES = 1`。
   重派位置只能在 `_worker`：`_complete` 是节点回调，从那里抛异常只让这次回调失败，
   节点收到非成功回执后**不重试**（`ReportingChatSessionRuntime.reportCompleted` 返回 false 即终局）。
   只在「这一轮一次工具都没领过」时重派 —— 那时模型还什么都没做，不会重复取证。
3. **失败原因不再被糊掉**：节点一直在发 `model_failed` / `model_stream_incomplete`，
   网关此前把它整个丢掉、统一记成 `operator_node_failed`。现在透传并单独记一行。

## 为什么不追求「彻底」

`response_format` 是提示性的，我们改不了别人的模型。单次调用不可能归零；
能做的只是把**概率**压低并对**持续失约**保持可见。
所以 `MAX_RESAMPLES=1` 而不是 3：再要两次只把失败率从约 1% 压到 0.2%，
却把最坏延迟翻倍、并把「上游持续坏着」伪装成「只是慢」。

## 被否掉的替代

- **只改 system 提示词**：有效但更弱（16% vs 8%），且要换节点 jar 与执行清单。
- **网关侧从正文里抽 JSON**：覆盖不了这一次的形状 —— 通篇正文里**没有** JSON 可抽。
- **无限重试直到成功**：把上游故障变成看不见的延迟。
- **放弃结构化、允许纯文本交付**：等于放弃事实段校验，风险方向反了。

## 代价

- 提醒是概率手段，不是保证；重采样增加一次有界的模型调用与延迟。
- 剩余失败率约 1%（两次独立失约）。**这是估计，不是保证** —— 下次复测才算数。
- 重采样只在「没领过工具」时发生；已经取过证据后失约的，仍按失败交付。
