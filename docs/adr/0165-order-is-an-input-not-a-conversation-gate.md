# 165. 订单是诊断输入，不是管家对话门槛

日期：2026-10-29
状态：已采纳

## 背景与决定

产品在管家编排页询问“广州天河附近的充电站”，却被要求填写订单号。原生预览在模型前
调用`_native_order`拒绝，正式问答也把全部operator请求路由到单订单诊断。旧术语和产品入口
承诺的是智能问答，首片实现的单订单限制却扩散为整个聊天的门槛。用户确认本轮也要真实找站。

没有明确订单时，仍在本应用的可信Java节点运行一个无订单工具的回合；模型选择正常回答、
补充订单的对话澄清或站点搜索。该回合使用`operator-conversation/1`，四个固定字段
`kind/text/name/address_terms`；有订单继续使用原五字段诊断协议。两个协议都逐轮启用JSON模式，
仅取最后完整模型轮。空站点范围允许咨询，诊断仍拒绝，找站返回无分配站点且不发CPMS请求。

站点搜索由Gateway执行已核对的`GET /chSite/page`：当前公司Bearer、租户头、固定type/current/size；
模型只能提取用户原话中的站名或地址词，不能生成租户、站点范围、URL或坐标。每页50条、最多4页、
每次请求3秒、最多展示10条；响应逐条校验租户与当前站点范围，只存id/name/address及来源时间。
结果确定性渲染，不让模型重写站名/地址或猜实时状态。每页前与完成后检查任务、授权、取消和版本。

未提供定位时按地址词搜索，不能声称距离排序；显示结果可能不完整及无匹配/空权限的具体限制。
普通试运行接受业务问题，也兼容已有order_no。C端工作流仍需要它既有的订单输入，不放宽其契约。
本轮不自动复用历史订单，不新增地图定位、价格或空闲枪口查询，不恢复已退役的Python执行器。

## 依据与映射

公司`iot/cloud-charging-pile:release`的ChSiteController/GetPage、ListSiteRequest与ChSiteMapper
定义分页name/address过滤；Mapper标注ShopDataScope，响应具有id/tenantId。已按公司源码只读规程
取当前release，并用正常公司身份实测`code=0,data={records,total,size,current,pages}`。
Gateway额外逐条核对，避免仅依赖上游拦截器。HTTP查询参数按RFC3986编码；HTTP202沿用RFC9110
的已接收语义，成功要回读completed。JSON沿用RFC8259及ADR0163的供应商JSON对象模式。

## 被否掉的替代形态

- 只删预览订单检查：正式入口、执行清单、证据校验仍要求订单，故障只会向后移动。
- 随便选一张订单承载普通问题：混淆数据权限，可能泄露无关业务数据。
- 回落Dify原生循环或旧Python：形成第二套身份/工具边界，违反已确定执行路线。
- 模型返回附近站点名单：缺少权威数据，可能编造站名与距离，不能满足用户要求。
- 任意HTTP/SQL工具：超出找站需求；固定接口、白名单字段和参数足够。

## 后果与验证

跨文件协议增加一个明确的无订单回合；复用现有run/QA状态、取消、公司身份、节点认证和发布绑定。
不需要修改已有草稿或重发正式路由，但Gateway、节点和桥需配套部署。执行清单的双语言解析器
均拒绝带工具的非订单协议。验收见[场景](../agents/operator-cpms/conversation.feature)及
[QA计划](../agents/operator-cpms/conversation-qa.md)。真实模型、权限和页面验收单独记录。
