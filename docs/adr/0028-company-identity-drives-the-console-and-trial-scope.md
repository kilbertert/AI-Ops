# 公司身份是控制台会话与试运行范围的唯一来源

日期：2026-10-16
状态：已采纳
影响版本：PRD #772 的收口（子票 #783）；`dify_console_publish.py`、`gateway_api.py`、
`dify_login_*`、`ops/dify-console-bridge/dify-console-10008.conf`

## 背景

PRD #772 的三条闭环里，工具（#775）与试运行的**执行**（#781 / #782 / #795）已经上线并
真实验收。缺的是**身份**这一条，而且缺口不是一个，是三层：

| 层 | 到本记录为止的现状 |
|---|---|
| **谁进得来** | 运营打开控制台看到的是 **Dify 原生登录页**。登录代理（#778）写完了但**从未部署**，而且仓库里**根本没有登录页** —— `/__aiops/login` 是纯 JSON API。 |
| **谁发得了** | 桥的 `AIOPS_CONSOLE_BRIDGE_LOGIN_PROXY_URL` 未配 ⇒ 仍按 Dify owner/admin 放行（#780 的过渡态）。 |
| **谁看得到哪些单** | 桥只转发了三个头，把代理**已经返回**的 `company_tenant_id` / `company_user_type` 丢掉了 ⇒ 网关每次都退回固定调试租户。**「按人范围」的代码早就写好了，只是从没被驱动过。** |

本记录定的是把这三层接起来时的形状与代价。

## 决定

### 1. 身份与放行是**两件事**，一次调用同时回答

代理的 `/__aiops/publish/check` 回两样东西：**这个会话是谁**（公司用户 id、租户、
`sys_user.type`）与**他能不能发布**（`allowed`）。身份五字段只要映射存在且 active 就回，
与 `allowed` 无关。

为什么这样切：试运行与发布用**同一个**调用取身份，但它们要的不是同一种授权 ——
试运行只要"我是谁"来算订单范围（#782），发布还要"我能不能发"。把两者合成一个布尔，
后果是**只有编辑权的人连试运行都做不了**，而那不是任何一条要求。

放行的判据没有变：发布路径读的仍是 `allowed`，`false` 的处理逐字不变。

### 2. 一条键，三处生效

`AIOPS_CONSOLE_BRIDGE_LOGIN_PROXY_URL` 从"发布权开关"变成**公司身份的来源开关**，
一个值同时决定发布权、试运行范围、审计发起人：

| 状态 | 发布权 | 试运行范围 |
|---|---|---|
| 留空 | Dify owner/admin | 固定调试租户 |
| 配了、代理可达、会话有效 | 公司 `aiops:agent:publish` | **发起人的公司身份** |
| 配了、代理查不通 | **拒**（ADR-0024） | **退回固定调试租户**（见下） |

不给试运行一个独立的开关：一个键 = 一处回滚 = 没有"半开"状态。半开意味着同一次上线在
两个维度上进度不同，而这两个维度背后是同一件东西（公司身份）。

### 3. 「查不通」在两条路上**方向不同**，这是刻意的

- **发布**：配了但查不通 ⇒ **拒绝**。退回 owner/admin 等于把"核对不通"悄悄变成"按旧规则
  放行"，而那是放宽**授权**（ADR-0024 已定）。
- **试运行**：配了但查不通 ⇒ **退回固定调试租户**（用户 2026-10-16 选定）。

第二条要写清楚，因为它看起来与第一条矛盾：退回调试租户意味着订单范围从"只看自己据点"
放宽到"看整个调试租户"。理由与边界：

- 那是一个**已经上线并被验收过的既有行为**（#781 的第一版就是这个），不是新的越权；
- 钥匙仍是那把独立的试运行钥匙，调用方仍是控制台里的会话；
- 身份闭环刚上线时可能有人还没映射，退回能让功能不断。

**代价明写**：这段窗口里，一个未映射的人能对调试租户的订单试运行 —— 与 #781 完全一样。
收紧的方式只有一处（`submit_trial` 里那个分支换成拒绝），切换点单一，不会漂。

本条**更正 ADR-0025 的一句措辞**：它写"桥没给全身份 ⇒ 退回调试租户"，那是在"桥根本不会
问代理"的世界里写的。现在"没配代理"与"配了但查不通"是两种不同的输入 —— 行为相同，理由不同，
而后者是一个**有意的选择**而不是默认。ADR-0025 原文不改（它记录的是当时的决定）。

### 4. 试运行的**提交与读取必须走同一个范围构造**

`GET /v1/dify/trial/{trial_id}` 原来用 `trial_run_context()`，而提交路由在有发起人时用
`trial_context_for()`。作业行按 `scope_fingerprint` 隔离，而那个哈希含数据范围与主体类型 ⇒
**按人范围一启用，返回的 `trial_id` 就永远读不回来**，且表现与"这个 id 不存在"完全一样。

修法：把"四个头 → 范围"的选择抽成一个 `_trial_run_context(context, initiator)`，两条路由都调它。
更值得记的是**它为什么一直没被发现**：`tests/test_dify_trial.py` 的替身把
`trial_context_for` 桩成了 `trial_run_context`，于是两个指纹恰好相等，缺陷没有藏身处之外的地方。
所以那条桩**故意改成不同范围**，并新增一条"带着同一个发起人头读回自己提交的那条"的回归 ——
已反向验证：把 GET 改回旧写法，那条测试立刻红。

## 一处必须先证实、不能假定的东西：refresh token

Dify 的 refresh token **不是 JWT**，是 Redis 里的一次性随机串
（`deploy-api-1`：`account_login_adapters.resolve_refresh_token` 就是 `redis.get(key)`）。
而 #778 的自签会话把 `refresh_token` 下成**与 access 同值的 JWT** ⇒
`POST /console/api/refresh-token` 永远 401。

它是不是致命缺陷，取决于**前端在有 access cookie 时会不会先走 refresh**。实测（36 上自签一枚
会话）：

- 不带 cookie `GET /` ⇒ `307 → /auth/refresh?redirect_url=%2F` ⇒ `303 → /signin`；
- 带 `__Host-access_token` + `__Host-csrf_token` ⇒ `GET /` 与 `GET /apps` 都是 **200**。

⇒ 前端**不会**把有有效 access cookie 的人打回去；refresh 失败的那一天，落到的是**我们的**
登录页。这正是期望的行为，所以不改（改它要动 `SECRET_KEY` 的签发模型，代价远大于收益）。
**会话寿命因此是硬上界**：`AIOPS_LOGIN_PROXY_ACCESS_MINUTES` 到期即需重新登录。

## `__Host-` 前缀：共**三处**，不是两处

#776 把控制台收到 https 之后，Dify 自签的 cookie 名带 `__Host-` 前缀（ADR-0026 已核实）。
待办原本只记了两处（代理下发、登出清理），实现时发现**第三处**：
`dify_login_provision._console_headers()` 里 `Cookie: f"csrf_token=..."` 写死裸名 ——
Dify 的 `check_csrf_token` 要求头与它**自己读到的那个 cookie** 逐字相同，而 https 下
`_real_cookie_name` 会加前缀 ⇒ 读到空值 ⇒ 401 `CSRF token is missing or invalid`。

它的后果形态值得记：**开户那一跳**（`invite-email`）走 `@login_required`，撞上它的后果是
**新账号开不出来**，而**已有映射的账号完全不受影响** —— 间歇性、极难定位。所以验收里必须有
"用一个从未登录过的账号走完整登录"。

前缀同时要求 `Secure` + `Path=/` + 无 `Domain`，浏览器对不满足的三条**静默丢弃**。因此
`ConsoleSession.cookies()` 在"带前缀却不带 Secure"时**直接抛错**，而不是发一个注定被丢掉的
东西 —— 静默丢弃的表现是"登录成功但立刻又要求登录"，界面上完全看不出原因。

## 登录页由我们提供，`/signin` 被接管

`location = /signin`（**精确匹配**）指向我们自己的单文件登录页。这一条同时完成两件事，
所以它们不可能是两个会漂的开关。

- **为什么挂在 10008 而不是 TLS 层**：10008 被 `dify.ranlei.work:443` 与明文
  `36.156.159.175:10008` **两个入口共用**。挂在 TLS 层等于给明文入口留一条绕过口，
  而收口 Dify 原生登录必须覆盖它。挂一处，两个入口同时生效。
- **`redirect_url` 是外部输入**，所以服务端过 `safe_redirect_path` 白名单
  （只认单个 `/` 开头，拒 `//evil.test` 与 `/\evil.test` 这两类协议相对 URL）。
  页面**不做第二遍判断** —— 页面能被绕过，服务端不能。
- 登录页的静态判据在 `tests/test_dify_login_page.py`：不许出现 storage / `document.cookie`
  等会留下凭据的 API（判据落在**去掉注释与 style 之后**的可执行部分上）。

## 被否掉的替代形态

- **给试运行一个独立的开关**（例如 `AIOPS_CONSOLE_BRIDGE_TRIAL_IDENTITY`）。那样可以
  "按人范围先上、发布权后上"，但要新增一个键、多一处能配错的地方、多一种没人能解释的
  线上状态（同一次上线在两个维度上进度不同）。而且**不能**拿"把 `PUBLISH_PERMISSION`
  留空"当中间态 —— 那会让所有发布显示"公司账号没有发布权限"，把运营指向**错误的联系人**。
  **否掉**：一个键、一处回滚，没有半开。
- **把身份与放行合成一个布尔**（沿用原来的 `(allowed, headers)`）。最省事，但后果是
  **只有编辑权的人连试运行都做不了** —— 而试运行不产生版本、不改路由，它不需要发布权。
  **否掉。**
- **让试运行也 fail-closed**（拿不到身份就拒绝）。更严格、更贴"彻底纳入公司鉴权"这句目标，
  但登录代理一抖，试运行就整体不可用，而它退回的本来就是**已经验收过的既有行为**。
  用户 2026-10-16 选择了退回。**否掉，但记下收紧点只有一处**。
- **让桥自己去读草稿 / 让桥自己解析会话**。前者是 ADR-0027 已否过的（第二份映射规则），
  后者要桥持 `SECRET_KEY`（ADR-0023 的代价会从一个进程扩散到两个）。**否掉。**
- **修 refresh token**（让自签会话也去 Redis 里放一枚随机串）。那要把代理从"只签 JWT"
  改成"Dify 的会话存储参与者"，代价远大于收益，而实测已经证明不修**不影响可用性**
  （前端不会把有有效 access cookie 的人打回去）。**否掉。**
- **把收口只做在 TLS 层**。明文入口 `36.156.159.175:10008` 会立刻成为绕过口。
  **否掉** —— 收口必须与"回滚路径"同层。
- **登录页用前缀匹配 `location /signin`**，或新建第二个注入脚本文件。前者会把
  `/signin/...` 一类路径一起吃进来；后者撞上 `sub_filter_once on`（ADR-0027 记过：
  第二条 `sub_filter` 静默不生效且 `nginx -t` 不报错）。**否掉。**

## 后果

- 运营不再需要 Dify 邮箱密码；范围是他在公司体系里的可见范围；进不去时的提示指向"该找谁"。
- 发布账本记下**谁**（含被拒的尝试），试运行记下**发起人与草稿摘要**。
- 桥的环境键语义变了，`ops/dify-console-bridge/README.md` 的三态说明必须跟着改 ——
  一个键现在驱动三件事，读的人得知道。
- 应急 owner 与 10018 全程不动；`LOGIN_PROXY_URL` 一清即回滚。
