# 131. 原聊天入口的Chatflow会话属于调用者

Status: Accepted

## 决定

WF01在原POST/GET/取消接口增加显式consumer_service路由，默认关闭。
部署登记固定app/workflow/已发布agent身份；请求不能选择租户、应用或上游会话ID。
复用ConversationStore的主体与入口隔离、生成锁，以及DifyRunStore的运行终态；
API通过Runtime的start_consumer_chatflow交接轮次，与其他异步入口的源码守卫一致；
新增本地会话/上游会话/消息ID/绑定摘要字段，空值兼容旧记录，不伪造节点身份。

首次POST创建当前用户的会话并返回conversation_id。后续每轮核对所有权和发布版本，
只有前轮QA与Dify运行均成功才复用其上游会话。失败/取消后需新会话，避免Dify残留部分消息污染下一轮。
文件登记同版变更凭据引用、app或配置仍改变摘要，旧会话与结果拒绝；管理登记还核对revision。
取消立即写终态并向本次task请求stop，迟到结果不覆盖已取消作业。

QA与会话详情共用结果核对：同调用者、当前绑定、成功且未过期、缓存正文等于执行记录。
首片仅接文本消息；只读工具、知识源与安全分支后续接入，不能用这条文本能力声称完整客服已上线。
SSE与Chatflow契约沿用ADR-0130，原Workflow/节点状态路线保留。

## 备选方案

- 让App携带Dify conversation_id更简单，但把上游关联和跨主体隔离责任交给客户端；采用服务端映射。
- 遇到失败自动开新上游会话可减少错误提示，却让用户误以为前文仍在；显式要求新会话。
- 复用订单状态scenario省字段，但会混淆五字段业务快照与普通客服答复；新增明确场景并独立开关。

## 限制

默认关闭仍会增加Dify运行表四列；无业务数据写操作。Dify模型和服务可记录用户问题，
不传登录会话或公司服务令牌。尚未切换线上，也未扩展公司App发版权限。
