# 228. SOP 蒸馏的落点纪律：每节只许「工具名」或「缺口」

日期：2026-11-05。

Status: Accepted（PRD #1393 第二项 #1395）。

`operator_sop.md` 从 41 行骨架扩为对 556 行排查 SOP（`充电桩问题排查SOP.md`
与 `SOP.md` 并集）的逐节转译。原文大量内容是 SQL 原文、DDL 与控制台动作——
模型拿不到的指令写在提示词里只会诱发「我查过了」式幻觉，所以这份蒸馏
定下一条硬纪律：

- **每节只有两个落点**：绑定一个已声明工具（`cpms_order_detail`/
  `cpms_order_tariff`/`cpms_order_billing`/`cpms_order_amount_check`/
  `cpms_order_process_stats`/`cpms_charging_samples`/`cpms_charging_timeline`），
  或显式写「缺口」并给人工核查路径。不存在第三种「差不多能做」的落点。
- **可执行的判断逻辑进提示词**：状态码解释、时序判读（断崖/超阈值/
  txSerialNo 一致性）、停机码分类、服务费=0 只是信号——这些是模型能
  直接用的知识。
- **不可执行的不进提示词**：SQL 原文、DDL、Redis 命令、账号权限清单
  一律不抄；它们只能变成「缺口声明 + 人工路径」，否则模型会照着
  文本演出一遍并不存在的查询。
- 三类数据源结构性为缺口：`tx_data` 硬件上报（detail 无该字段）、
  `charging-pile_comm` 原始报文、`third.order.sync.queue` 等 Redis
  Stream——在工具面补齐前，答复必须声明而非演出。

评审判据：对照原 SOP 逐节核对，每节均能找到工具名或「缺口」字样，
无一节被静默略过。

## 备选方案

- **把原 SQL 一并写进 SOP 供模型参考**：模型没有任何执行 SQL 的
  通道，文本里的 SQL 只会被当成「已执行过」的素材复述，否决。
- **保留 41 行骨架、长知识放文档站**：工具面在变化时提示词与文档
  会分叉，而模型只读提示词；蒸馏的意义正是让判断逻辑随提示词
  一起被冻结进发布快照，否决。
- **按场景拆多份 SOP 文件**：应用只有一个 `pre_prompt` 入口，拆分
  只是文件组织，不改变进模型的文本总量；单文件按「分工→流程→
  速查→回答」组织已覆盖全部场景，否决。
