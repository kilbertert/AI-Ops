# 快捷动作扩展为意图入口与站内导航入口

Status: Proposed

产品快捷动作原为一个一元概念：动作只声明业务意图和输入要求，点击后经统一助手入口发起预设提问。产品设计要求其中一部分动作点击后**直接跳转到站内页面**（首个为故障上报跳转 H5 故障申报表单），不发起提问。本决策把它拆为两种动作形态——**提示动作**（经统一助手入口）与**跳转动作**（由客户端导航，不经入口、不创建作业）——并选择**跳转路径非空即为跳转动作**这一唯一判别依据。

## Consequences

- 一个只读诊断网关会向客户端下发前端路由。这是必要的：跳转路径由服务端下发，客户端无需为新增页面发版；若改为客户端硬编路由表，每加页面都要等一次 APK 发版。
- 不引入第二个判别字段。产品面板文案（「填写路径链接后用户点击将导航到对应界面，预设提示词不起作用」）、领域判断与前端实现三方均收敛到"有路径即跳转"；显式 `kind`/`type` 会引入"类型说跳转但无路径"这一非法状态，且与统一助手入口的响应 `type`（`faq`/`clarification`/`qa`/`diagnosis`）**同名不同值集**，易致客户端误用。
- 字段落在既有自由字段集合中，**不新增数据库列**，因此无 DDL、无索引、无数据迁移；既有已发布动作不重发布即继续工作，读取时路径为空。
- **不做路由白名单或存在性校验**。仓库内不存在权威 H5 路由约定；白名单等于把客户端路由表复制进后端，每加页面都要改后端并发布。页面可达性属客户端验收范围，须在验收记录中标注为未验。
- 跳转动作**永不经过统一助手入口**：该入口对误投的跳转动作同步返回澄清且不创建任何作业。这条守卫置于订单路由**之前**且不依赖订单上下文，因为跳转动作不应仅因请求附带订单就启动诊断。
- 路径**不国际化**。名称的国际化早已通过按语言键的文案字典实现；路径是客户端路由的键，属客户端职责。
- 被否掉的替代形态：(a) 由统一助手入口中介跳转——多一次往返换取客户端已知的信息；(b) 后端维护路由白名单——需要一份不在我们手里的权威路由清单；(c) 显式判别类型字段——见上。
- 提示动作的行为完全不变，`requires_order` 的订单守卫与其回归测试保持有效。
