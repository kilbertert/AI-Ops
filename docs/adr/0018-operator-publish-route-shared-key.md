# 运营自助发布：一个写端点，凭据是独立共享密钥，作用域是注册表

日期：2026-10-13
状态：已采纳
影响版本：PRD #577（Dify 作为权威编辑面）；`ops/dify-exposure-registry.md` 第一节

## 背景

PRD #577 让 Dify 成为正文的编辑面，但「运营改完 Dify → 线上生效」这条链一直缺**触发**：
`aiops admin sync-from-dify` 修掉了「要记 7 个参数」，可它仍要有人 SSH 进 41 去跑。
于是运营改一次口径，要等一个运维。

本 ADR 决定的是：**把触发权交给运营，并且用什么凭据、给多大作用域。**

两条测量把最省事的路排除了（都是 41 实测，不是推断）：

1. **Dify 的 chat app 没有草稿区。** `AppDslService.export_dsl` 读的是
   `app.app_model_config_id` 这个**单指针**，而保存就是覆盖它。所以 Dify 说不出
   「这一版还没定稿」⇒ **不能做定时/自动同步**，那会把运营打字打到一半的正文推给真实用户。
   （Dify 的 webhook 只有**入站**触发，没有"保存后通知"的出站钩子。）
2. **这一部署的用户令牌是可自报的。** company-parity 模式不验签
   （`AIOPS_GATEWAY_COMPANY_TRUST_PAYLOAD` 未设）。实测：一个用**编造密钥**签的 JWT 打
   `/v1/standard/diagnoses` 得到 `404 ORDER_NOT_FOUND` —— 它**穿过了鉴权层**。
   拿它当发布授权，等于没有授权。

`nginx` 的形状再收一次口：只有 `location ^~ /v1/dify/` **不覆盖** `Authorization`
（`location ^~ /v1/` 会用服务令牌盖掉它）⇒ 这个面只能落在 `/v1/dify/` 前缀下。

## 决定

新增 `POST /v1/dify/publish`，鉴权用一把**独立的共享密钥**
（`AIOPS_GATEWAY_DIFY_PUBLISH_API_KEY`），**请求体只有一个 `app_id`**。

作用域由**数据**而不是由请求决定：`app_id` 必须命中 `dify_app_registry` 里已声明的绑定，
租户、agent 名、类型、输出契约、知识库绑定全部从那行读。它调用**与 CLI 同一个**
`sync_binding_from_dify`，所以两条路径不会漂。

因此爆炸半径**恰好等于已声明的绑定集合**：拿到钥匙的人不能加绑定、改路由、换类型、
挂知识库、注入任意正文；而内容没变时 `sync` 先与已发布快照逐字比较，**什么都不写** ——
"最坏情况"收敛成 no-op。

四条附带约束，都在 `GatewayServerSettings.validate()` 里是**启动错误**（不是运行时才发现）：

1. 发布密钥必须与 `DIFY_KNOWLEDGE_API_KEY` 不同 ⇒ 否则「能读知识库」等于「能发布」；
2. 必须与 `DIFY_DEBUG_API_KEY` 不同 ⇒ 调试身份不得顺带获得发布权；
3. 配了发布密钥就必须配控制台地址与凭据 ⇒ 否则得到一个"门开着、每次调用都 502"的部署；
4. 未配置发布密钥 ⇒ 路由整体 404（与检索路由同一条「未配置即不启用」）。

## 被否掉的替代形态

**① 定时/轮询同步（Dify 改完自动生效）。** 否掉的理由是测量 1：Dify 没有草稿区，
导出读的就是"当前保存的东西"。定时器会把半成品推上线，而且**没有任何信号**能区分
"改完了"与"正在打字"。

**② 挂在用户 JWT 后面（operator 入口，与诊断/分析卡同一个门）。** 否掉的理由是测量 2：
本部署不验签，编造的令牌能穿过鉴权层。这与 #448 记下的是同一个事实。要让它成立，
前提是**先换掉那把签名密钥并打开验签** —— 那是另一件事，且会与「管家端用户长时间停留、
不重登」的既有取舍冲突（见 #448 用户裁定）。

**③ 复用知识检索那把共享密钥。** 否掉：那把出现在**每一次检索**上（运营的调试预览也用它），
把发布权绑上去等于把"读知识库"升级成"改生产"。

**④ 复用服务端的控制台凭据（`DIFY_CONSOLE_API_KEY`）。** 否掉：它是**服务端**凭据
（我们调 Dify 用的），要给到触发方就不再是服务端的了。触发方拿到的应该是一把
**只能触发这一件事**的钥匙。

**⑤ 不做这个端点，运营继续找运维。** 否掉：这正是要修的那个缺口。代价对比也很清楚 ——
端点这条路把"改口径"的等待从一次人工转交降到一次 HTTP 调用，而作用域反而**比**
`admin sync-from-dify` 更小（后者跑**全部**绑定，前者只跑请求点到的那一个）。

## 与「只读暴露面」的关系（一次显式的例外，不是把定义放宽）

`ops/dify-exposure-registry.md` 原写「任何会改生产数据的端点都不得进这张表」。这个端点
**确实写状态**，所以它是一次**显式例外**，理由逐条可复核：

- 它改的是**我们自己的智能体配置**（`agent_versions` 一行新版本），**不碰**充电库、
  订单、用户、TDengine，也不调用任何公司侧写操作；
- 它走的是 `/v1/agents/{id}/publish`、`admin reconcile`、`admin sync-from-dify`
  **同一条**发布路径与**同一道**发布门（角色校验、模型白名单、KB 活性校验）；
- 它的作用域由注册表数据决定，请求只能点名。

登记表里那段论证与该表本身一样，受 CI 的**集合相等**判据约束：新增 `/v1/dify/` 端点
漏登记会被拦下（这次就是这么被拦的）。

## 后果

- 运营侧多一个可自查的动作：改完 Dify → `POST /v1/dify/publish {"app_id": …}` → 看
  `action` 是 `synced` 还是 `unchanged`。**不需要懂那条链的内部机制。**
- **密钥泄露的后果是有限的、已知的**：最坏是"重新发布一条已声明绑定的当前内容"。
  这条是刻意设计出来的，不是碰巧。
- **仍不是全自动**：人来触发是唯一诚实的"我改完了"信号（测量 1）。要变成真正的
  事件驱动，前提是 Dify 给出一个"已发布"的出站信号 —— 它今天没有。
- **新的一把钥匙要管**：多一处凭据分发与轮换。它与另外两把 Dify 钥匙**必须不同值**，
  这一点是启动错误而不是约定。
