# 200. 通用失败必须说清「在哪一步、哪一类异常」

日期：2026-11-04
状态：已采纳

## 问题

`SETUP_STEP_FAILED` 是 `_error_code()` 对**非受控异常**的兜底（`self_service.py`）。
一次开通失败时，页面只有一句"这一端未完成"，journal 里也没有栈 —— 因为捕获后只写了一个
固定码。同一句话背后可以是十几种完全不同的缺陷。

这不是理论风险，是 2026-11-04 实际发生的事：优链充双端开通的第一轮重试返回
`SETUP_STEP_FAILED`，资源字段已写到 `key_ref`，但失败点无从确定。为了定位，我在两次重试
之间用服务身份单独调了一次 `service_keys.ensure` —— **那个动作本身改变了现场**，于是
"第一次为什么失败"再也无法从生产证据里证明。

一个失败在生产上事后不可查，且唯一可行的定位手段会破坏证据，这本身就是缺陷。

## 决策

通用失败的公开形状增加两个字段，语义固定：

| 字段 | 内容 | 为什么可以给页面 |
| --- | --- | --- |
| `failed_step` | `save()` 当时的步骤名（`consumer:key`、`operator:dependencies`…） | 代码里的**固定字面量**，不是外部输入 |
| `failure_kind` | 异常类名（`KeyError`、`TimeoutError`…） | 只泄露"哪一类"，不含任何值 |

**异常正文与栈不进任务行、不进公开形状，只进 journal**（logger `aiops.dify_self_service`）。
理由：这一层接的是供应商响应与资源操作，正文里可能是 URL、app id，甚至凭据片段 ——
`service_keys` 的文档已经明说"供应商响应可能含凭据"。

页面只对 `SETUP_STEP_FAILED` 追加「「步骤」出错（`Kind`）」；受控业务码（
`SETUP_BUSINESS_CONNECTION_REQUIRED` 这类）本来就是可读的，保持原文不动。

## 被否掉的替代形态

- **把异常正文放进任务行。** 那是把供应商原文写进数据库、再经接口发给浏览器；一次凭据
  泄漏就够了，而"正文有用"这个收益在 `failure_kind` + 栈（在日志里）之后就不成立。
- **只加异常种类，不加步骤。** `KeyError('prompt')` 与 `KeyError('model_config')` 是同一
  种类、两个完全不同的缺陷；只有种类时仍然要翻整条链。
- **给每个步骤一个专属业务码。** 那要求现在就枚举所有失败点，而兜底码存在的意义正是
  "这个位置我们还没想到"。步骤名是现成的、不需要预先枚举的信息。
- **失败时把完整请求重放到日志里。** 请求里有租户、应用 id 与来源快照；要的是"哪一步哪
  一类"，不是再存一份业务副本。

## 代价

- 任务行的公开形状多了两个字段（`_ENTRY_FIELDS` 是显式白名单，所以是明确的一处改动，
  不是 `dict(row)` 透传）。
- journal 里会出现完整栈。日志本来就只留在主机上，且它比"查不出来"更有用。
- 前端文案改动需要重建 Dify web 镜像才生效；后端字段随 CD 就能在接口回读里看到，
  两者不同版时页面不会崩（旧前端忽略未知字段，新前端读不到字段就退回通用句）。

## 验收

`tests/dify/test_self_service.py`：通用失败带 `failed_step=operator:dependencies`、
`failure_kind=KeyError`；异常正文不在任务行/公开形状里、但在日志里；受控码保留自己的码。
本机全量 `pytest`、`ruff check`、`format --check` 通过；`images.lock.json` 在最终树上重算。
