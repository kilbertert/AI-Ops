# 72. 登录代理按租户开户：解析走网关、建不在这里、join 不阻断登录

日期：2026-10-21
状态：已采纳（#883 实施；ADR-0059 §5.1 的开户路径落成代码）
影响版本：`src/aiops_diagnostics/dify_workspace_directory.py`（新）、
`src/aiops_diagnostics/dify_login_service.py`（解析 + join + 映射两列）、
`src/aiops_diagnostics/dify_login_server.py`（四个新键，成对校验）、
`ops/dify-login-proxy/login-proxy.env.example`

## 背景

ADR-0059 定下"开户是唯一该建 workspace 的时机"，但没有说代理**怎么知道**该建哪一个、
以及建不了时它该做什么。这一张票把那段落成代码，并且必须先把三件事分清 —— 它们的
失败后果完全不同。

## 决策

**一、解析走网关，代理不存第二份。**

管理映射表在**网关的** `gateway.db`（41），代理跑在 36。代理经
`GET /v1/dify/workspace?tenant_id=…`（内部令牌，ADR-0067）问，得到 UUID。
它自己的库 `mappings.db` **只多两列**（`workspace_id` / `workspace_joined`），那是"这个人
上次 join 成功过"的本地事实，不是 workspace 映射表。验收里"查不到第二张表、第二个文件"
因此成立。

**二、建不在这里。**

`ensure-workspace` 必须在**库的属主机器**上跑（41 本机），因为它要"先占位、再建、再写回"
同一次运行（ADR-0068）。代理够不到 41 的库，所以它绝不自己建 —— 建了就是没人写映射的
孤儿，而 Dify 没有删 workspace 的 API。

**三、解析失败是**带命令的拒绝**，不是空工作区。**

| 网关回的码 | 代理给运营的话 |
|---|---|
| `UNRESOLVED` / `FAILED` / `UNKNOWN` | "你的工作区还没有准备好（<码>）。请联系管理员在网关所在主机执行：`aiops admin ensure-workspace --tenant <id>`" |
| `CREATING` | "你的工作区正在创建，请一两分钟后重新登录。" |

"给一个空工作区"是最坏的选项：运营会以为自己进去了、只是没有内容，于是去问"为什么看不到
智能体"，而不是"为什么没有工作区"。把**那条命令**写进错误里，是因为下一步是确定的。

**四、join 失败**不阻断登录**，二次登录不重复 join。

workspace 已经在（`created`），join 失败只意味着他打开控制台看到空列表 —— 那比登录页
报错、连自己的编辑面都进不去轻。所以 join 只记审计与日志，下一次登录会再试。

反之，已经 `workspace_joined=1` 且 workspace 没变的人，第二次登录**不再发 member 请求**：
join 本身幂等，但每登录一次就多一次可失败的写，而"他已经在里面"是我们上次亲眼确认过的事实。

**五、四个新键**成对**：半配置是启动错误。**

`AIOPS_LOGIN_PROXY_GATEWAY_URL` + `_GATEWAY_INTERNAL_TOKEN` +
`_INNER_API_BASE_URL` + `_INNER_API_KEY`：全配 ⇒ 按租户开户；**全空 ⇒ 维持单一固定工作区**
（ADR-0056 的 V1 暂定），一个还没采纳多 workspace 的环境因此照常工作。只配一半在运行时的
表现是"解析得到、join 不了"或反过来 —— 两种都看起来像"登录成功了、只是看不到东西"，
所以交给启动失败。

## 被否掉的替代形态

- **代理自己存一份 workspace 映射。** ADR-0059 已经否过：一份表放不进三个进程各自的私有库，
  而新建一个共享 SQLite 是"多一个要备份、要迁移、要防护的存储"。
- **缺行时代理顺手建一个。** 那会让第一次登录与运维命令争同一个租户，而且代理写不了 41
  的库 —— 它只能建出一个**没有映射行**的 workspace，即永久孤儿。
- **直接给一个空工作区（登录成功、内容为空）。** 见决策三：它把"没有工作区"伪装成"工作区
  是空的"，而两者的下一步完全不同。
- **join 失败就拒绝登录。** workspace 已经建好，人只是还没进去；下一次登录就会再试一次。
  用"登录失败"处理一个可自愈的瞬时故障，代价是这个人当天完全用不了 Dify。
- **每次登录都 join 一次（不做记忆）。** member 端点幂等，但它是一次网络写；把它做成
  "每次必发"意味着网关抖动会变成"登录变慢"，而没有任何收益。

## 后果与代价

- **代理多两次进程间调用**（解析 + join）。解析走回环网关，join 走 inner_api（今天只有
  36 本机可达，见 #889）。ADR-0059 已接受这一跳的代价。
- **四个键必须成对部署**。36 上现有的 `login-proxy.env` 里没有它们 ⇒ 现在仍是单一固定
  工作区，行为逐字不变。要切到多 workspace 是一次**配置变更 + 一次真实租户的开户**。
- **`mappings.db` 多了两列**（ALTER TABLE，旧库自动补）。旧行 `workspace_id=''`、
  `workspace_joined=0` ⇒ 下次登录会解析并 join 一次。
- **这次的验收仍缺真机一段**：41 的 `dify_workspaces` 还没有行（没有指定租户开户），
  所以"两个租户各看各的 app"这个端到端结论要等第一行映射存在。单元与假上游覆盖的是
  解析、拒绝、join 记忆三条判据。
