# 在 Dify 控制台里注入「发布到 AI-Ops」：一次对边界的显式更正

日期：2026-10-14
状态：已采纳
影响版本：PRD #577；ADR-0018；`dify_console_publish.py`、`ops/dify-console-bridge/`

## 背景

PRD #577 定下的形状是：**Dify 只做作者面**（编辑 + 调试预览），**生命周期**（冻结 /
发布 / 回溯）与**运行面**（身份 / 租户 / 语言 / 只读边界）全部留在我们这边。那轮
把这条缝讲得很清楚，并且**刻意否掉了两条**：

1. **「同域反代 + UPMS 建 `ROLE_AGENT_ADMIN` 角色族」** —— 原话是
   「本期**不再作为前置**」；
2. **把发布做成 Dify 侧的动作** —— 原话是
   「这条缝是**拉**不是**推**：Dify 发布时只有进程内 DB 信号，没有任何外发
   webhook / 事件总线。所以「发布」必然是**我们这边的运营动作**，这在设计上就定了。」

实测复核那两条论证**都仍然成立**（本轮重新测过）：

- 触发「发布更新」时，Dify 前端打的是 `POST /console/api/apps/<id>/model-config`
  —— **与"保存"同一个接口**，chat app 没有独立的发布接口；
- 而"保存"是我们拉回侧真正读到的那个动作（只保存不发布，`export` 立刻反映）；
- 发布确实改了东西，但改的是 `agent_mode.strategy`（`router` → `function_call`）+
  `max_iteration` —— **Dify 自己的编排参数**，我们一个都不读。

于是有一个**当时没被解决、但用户真实需要**的东西落了空：

> 运营改完，**还是要找工程敲一条命令**。PRD #577 写的「运营主动执行我们的发布动作」
> 一直没有"运营够得着"的那个动作 —— `/v1/operator/publish`（ADR-0018）把门做出来了，
> 但**没有界面**。

## 决定

**在 Dify 控制台的编排页注入一颗我们自己的「发布到 AI-Ops」按钮。**

用户明确要求"点了 Dify 的发布就能端到端上线"，并在我指出这与 #577 那条边界相反之后
**仍然选择注入 Dify 前端**。本记录不是把那个决定重新论证一遍，而是把**它更正了哪一条**
写下来，让下一个读到 #577 的人不会以为这里失控了。

## 更正的是哪一条（以及没有更正哪一条）

| #577 的原文 | 本决定 |
|---|---|
| 「同域反代…本期不再作为前置」 | **更正**：现在把它作为前置。运营的编辑面就在 Dify 上，任何"让运营少敲一条命令"的做法都必然落在 Dify 的控制台里 |
| 「发布必然是**我们这边的运营动作**」 | **保留**。发布**仍然**由我们的发布门做（`_publish_bound_app`）；Dify 只是**发起的地方**变了 |
| 「这条缝是拉不是推」 | **保留**。Dify 没有推送、我们也不订阅它。按钮打的是**我们**的端点，是**拉** |
| 「管理身份消解到 Dify 自己的账号体系」 | **保留**（本决定之后用户又把它挂起：公司账号登 Dify 走 Dify 企业版 SSO，不在本轮） |

一句话：**更正的是"按钮画在哪"，不是"发布由谁做"。**

## 为什么这**不**引入新的权限（本决定的安全论证）

一个人能登进 Dify 控制台**改这个 app 的提示词**，他就已经能改这个智能体的**全部行为**
—— 提示词就是智能体的定义。所以"点一下让这个改动上线"**不给**他任何他本来没有的能力：
它只把他**已经做出的**改动走完最后一步。

因此本层的授权模型**恰好等于**"能编辑"：

- **唯一凭据是运营自己的 Dify 会话**（桥拿它问 Dify「你是谁、看得见这个 app 吗」）；
- **app_id 只从页面 URL 取**，不由请求体给 ⇒ 伪造不了"我要发哪个"；
- **那把服务端发布密钥不进浏览器** —— 它在桥这一层被使用；
- 跨租户 / 跨 app 由 `/v1/operator/publish` 的门兜底（它只接受"该 (租户, operator)
  绑定的那一个 app"）。

## 被否掉的替代形态

- **给浏览器发一把（哪怕收窄的）密钥。** 任何进浏览器的凭据都等于公开；
  "收窄"只减小后果，不改变"它已经在别人手里"这个事实。**否掉。**
- **接管 `model-config` 接口，把"保存"当发布信号。** 自动保存打的是同一个接口 ⇒
  区分不了"改完了"与"打字打到一半" ⇒ 会把半成品推给真实用户。**这正是 ADR-0018
  写下"人来触发是唯一诚实的信号"的实测依据。否掉。**
- **用 Dify 的 workflow trigger / webhook。** 那要换 app 类型（chat → workflow），
  丢掉 chat 应用的调试体验，而且仍不是"我们控的界面"。**否掉。**
- **维持现状（运营找工程）。** 它满足不了"给产品经理用"这个明确要求。**否掉。**

## 代价（写下来，不藏）

1. **这是嫁接，不是 Dify 的原生能力。** 注入的按钮靠 DOM 挂靠，**Dify 升级后可能失效**。
   实现上做成**静默降级**：注入不上就只是没那颗按钮，**绝不影响 Dify 本身**。
2. **它重演了 #577 拒绝过的形状** —— 这是本记录存在的原因，不是遗漏。
3. **`sub_filter` 只对文本响应生效**，且要 `Accept-Encoding` 收敛（Dify 前端的静态
   产物是 gzip 的，HTML 是未压缩的）。所以注入的范围天然只剩 HTML —— 这反而是我们
   要的范围。

## 后果

- Dify 控制台的编排页多一颗按钮；**运营不点，什么都不会发生**（包括自动保存）。
- 发布仍然只由我们的发布门执行，登记表、发布门、不可变快照全部不变。
- 与 ADR-0018 的关系：**两条门并存**。共享密钥那条给机器（运维/脚本），
  这颗按钮与 `/v1/operator/publish` 那条给人。三条路最终都走同一个 `_publish_bound_app`。
- **本轮交付的是后端桥**（`dify_console_publish.py`，已合并）。nginx 注入层与容器
  端口内迁属于部署资产，随该资产一起评审。
