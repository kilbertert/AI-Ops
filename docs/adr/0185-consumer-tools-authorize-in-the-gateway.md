# 185. C 端工具的授权在网关侧，节点一行不改

日期：2026-10-30
状态：已采纳（设计定型，已实施）

## 决定

C 端运行里的 CPMS 只读工具走**网关侧的一条新授权与代理路径**，节点协议、契约版本、
`CpmsReadTool`、清单解析都不变。

- 授权端点仍是 `/v1/internal/operator-runs/{run}/tools/{tool}/authorization`，网关按
  **run 自己的 `operation`** 决定走管家那条还是 C 端这条。
- 代理端点是新的 `/v1/internal/consumer-tools/{run_id}/{path}`，`base_url` 取自这条 run
  所属节点目标的 `proxy_base_url`（与管家同源），不猜 `public_base_url`。
- 授权状态放在一个**不持有任何业务凭据**的内存表里，随 run 到期清理。

## 依据

节点把请求发到**网关代理**，带的是网关签发的 grant token；公司令牌从头到尾只在网关手里
（`operator_cpms.proxy()` 用 `task.bearer` 调 CPMS）。所以「C 端要一套新协议」是个误判——
节点根本不知道自己在替谁取数，它只知道自己拿了一个 token 和一个请求目标。

这条事实把 #1209 从「给 C 端建任务注册表 + 契约升版」缩成「网关侧多一条授权与代理路径」。

## 与管家那条路的四处差别

| | 管家 | C 端 |
| --- | --- | --- |
| CPMS 凭据 | 公司令牌 + `client-type: admin` | `tenant-id` + `user-id`，无令牌 |
| 可见范围 | 订单站点 / 账号站点集合 | 本人订单里出现过的站点 |
| 范围外的行 | **拒绝**（上游带了集合还越界 = 违约） | **跳过**（上游按租户返回，越界是预期） |
| 授权状态 | 持有公司令牌 | 不持有任何业务凭据 |

范围推导用 `consumer_sites.own_site_scope`，单页校验用 `operator_cpms.site_page` ——
两个都是**既有实现**，C 端没有第二份。

## 顺手修掉 #1191 的一个真 bug

#1191 让节点把模型参数放进 authorization 请求体，但那个端点的请求模型是
`extra="forbid"` 的空模型：**带参数就 422，而且参数从来没被读出来**。合成节点一直发
`{}`，所以那一批测试全绿。

现在授权请求体是 `OperatorToolAuthorizationRequest`，只允许 `arguments` 一个字段，
空体仍然合法（订单诊断工具）。这条同时修好了管家侧的站点工具与 C 端的站点工具。

## 被否掉的替代形态

**给 C 端复制一套节点协议（新的 grant 契约版本）。** 最强的地方是语义干净：两种运行
两种载荷，谁也不用猜。它输在没有任何必要——载荷本来就一样，差别全在网关怎么取数。

**让 C 端节点直接带 `user-id` 调 CPMS。** 最强的地方是省掉一跳，节点直连更快。它输在
把「哪些行属于这个用户」搬到节点：那正是范围判据，而范围判据必须在网关手里，节点只该
执行一个被批准的请求。

**复用管家的 `OperatorCpms.tasks`。** 最强的地方是一处状态机，没有第二套。它输在它按
`operator_*` 两种 operation 做准入、按订单站点冻结范围，而 C 端两样都不是；往里加分支
等于把两条不同的判据塞进一个类。

## 后果与验证

- **C 端运行现在能真的取到数**，这是 #1193 AC1/AC4 缺的那一半。
- 授权请求体的变化对旧节点是兼容的：它们发 `{}`，`arguments` 取默认空表。
- 验证：`tests/consumer/test_consumer_tool_grants.py` 七条覆盖范围、请求目标白名单、
  参数放行、运行类型、清单勾选、证据逐项相等、节点凭据。
- **未完成业务验收**：没有真实 CPMS、没有真实账号、没有真实页面；本片的 CPMS 与订单
  列表都是合成的。

方案与分期见 [工具架构](../agents/operator-cpms/tool-architecture.md)。
