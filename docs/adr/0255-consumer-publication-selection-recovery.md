# 255. 客服选库与发布恢复使用当前应用草稿

Status: Accepted（2026-11-14，用户确认实施本轮修复）。

生产事故：运营在受管发布中勾选新库，实际只授予租户级对客权限，应用草稿仍指向
已删除库；整次发布被拒，提示词同样未上线。首次失败又先创建了本地草稿，改提示词
重试被配置相等性校验拒绝。两个可变内容不应充当应用身份。

决定：发布抽屉展示并编辑本应用实际选库，权限区明确为租户级对客授权。两者不自动
互相替代；选库复用 Dify 原生节点更新和草稿同步（含 hash 并发检查），提示词、模型、
授权参数等其他字段保留。空选择、已删除/失权库在预览和发布前提示，服务端仍独立校验。

发布状态从本次导出的草稿读取选库，不再把开通时的 targets 快照当当前配置；同时展示
当前正式应用/版本，失败明确表示本次提示词与选库均未发布。按 Dify 1.17.1 原生
`useNodeDataUpdate`、`useNodesSyncDraft` 接口保存，不增加第二条草稿写入 API。

发布合同先验证再创建 Agent 草稿。旧失败留下的草稿只在受管注册匹配租户、工作区、
consumer 应用和固定生成名，且原创建者为系统、revision=1、从未发布/未人工更新时
允许将当前已确认 Dify 草稿冻结为正式版；旧半成品不先更新，避免外部发布失败后再次失去恢复资格。仍通过既有权限与乐观锁。非受管或手工编辑草稿拒绝
接管，不删除重建，不用提示词相等代替归属判断。

备选：只改报错文案不能解决双重选择；勾选授权即改全部应用会影响其他客服；放开所有
未发布草稿会覆盖人工工作，均不采用。发布与历史恢复保留不可变版本和路由 revision。

标准映射：Dify 固定版本的草稿 hash 是其并发契约；本地 Agent revision 延用既有
乐观并发规则。无跨系统分布式事务承诺，未推进正式路由的草稿/失败记录保留供重试。
