# 206. CI 按改动范围分档：文档提交不跑全量测试

状态：已采纳。日期：2026-11-04。

全量测试 4114 条、192 秒，占 `verify` 整个 job 的 86%（实测 run 41810218900）。
而最近 40 个提交里有 15 个只改 `docs/` —— 它们跑的是与上一次完全相同的代码。

## 决定

`ci.yml` 在跑测试前判定这次改动落在哪里：

- 改动**全部**落在 `docs/` 或根层 `*.md` → 只跑"读文档的那批"（683 条 / 26 秒）；
- 其余任何情况 → 全量，一行不减。

判定写成「**默认全量，白名单才降级**」。反过来写（默认降级、列举需要全量的路径）
会在漏配一个路径时静默少测，而这个仓已经踩过一次同类：`ci.yml` 顶部记着
"path filter 让改 README 的提交绕过了一条读 README 的测试"。漏配的后果必须是
**多跑三分钟**，不能是少测一格里最贵的那格。

降级档的集合不写死文件名，按"测试源码里提没提到文档"现算，因此新增一个读文档的
测试会自动进档；集合算空时退回全量，而不是让它在 0 条上绿（那是这个仓库反复记录的
假绿形状："没有任何东西会失败，只有事后人工比对才发现"）。

## 被否掉的替代形态

- **删掉全量测试**。`verify` 是保护 main 的必需检查（ruleset 23760870），删掉测试
  它只剩静态检查，等于把"合并进 main 的代码跑没跑过测试"交给作者自觉。否决理由不是
  覆盖率，是**失败形态**：分档写错会多跑三分钟并被人注意到，删测试写错会一直绿。
- **拆成并行 job**。实测拆两半是 3:03 与 3:46，受 `tests/conftest.py` 的主机锁约束，
  收益不抵改动量。若将来 CI 换到无主机锁的独立机群，可以重开这条。
- **按改动文件用 `pytest --co` 选相关测试**。做不到可靠：跨文件的契约（`conftest`
  夹具、`operator_support.py`、跨目录 import）让"哪些测试会受影响"无法从文件依赖
  推出来，猜错的形态同样是假绿。

## 代价

降级档靠"测试源码提到 `docs/`"这条启发式选集合，不是完备性证明。新增一条**必须**
在文档改动时跑、却不在源码里提 `docs/` 的测试，会被漏掉。这个缺口写进了
`docs/validation/2026-11-04-ci-test-tiering.md`，判据本身由
`tests/test_ci_test_tier.py` 驱动 `ci.yml` 里的脚本原文把关 —— 判定写宽了会立刻红。
