# 123. 源库没了，Dify 那条 dataset 就该退休

日期：2026-10-24
状态：Accepted
影响版本：`src/aiops_diagnostics/dify_knowledge_datasets.py`（`Plan` / `run`）、
`dify_console_admin.py`（`delete_dataset`）、`admin_cli.py`（`--retire`）、
`gateway_api.py`（自动同步开 `retire_orphans`）、`tests/test_dify_knowledge_datasets.py`

## 背景

ADR-0122 把建库同步挂到了「添加知识库」弹窗上，但那条 ADR 的第 3 条约束写的是
**"绝不删"**：

> `orphans` 只进日志 —— Dify 没有恢复入口，自动删是单向操作。

2026-10-24 真机上运营报了一个很具体的问题：**在 RAGFlow 删掉一个库之后，Dify 里
那张卡片永远留着。** 点它得到的是 502，而运营以为那个库还在。

"只报告不删"在纸面上是保守的，在运营眼里是**界面在撒谎**。

## 决策

`run()` 新增 `retire_orphans`（默认 **False**）。开的时候，`plan()` 算出的 orphan
对应的 Dify dataset 会被删除。

**四道保护，缺一条这个功能就是危险的：**

1. **默认关。** 只有调用方显式传 `retire_orphans=True`（或在 CLI 上加 `--retire`）
   才会删。
2. **只删派生形状。** `tenant-<租户>:<库>` 才算孤儿。人工登记的 `kb-canary-2`
   与租户级合并形态 `tenant-<id>` **永远不是** —— 41 上真的差点把它们删掉过一次。
3. **上游读失败时调用方不得调 `run()`。** 这是这条参数唯一的危险用法：传空的
   `libraries` 会让它把**所有** dataset 都当成孤儿。网关那条路由在读失败时**在调用
   `run()` 之前就 return 了**，所以自动同步这条路是安全的；手工 CLI 默认关，正是
   因为那里"读失败"与"库真的没了"看起来一样。
4. **`--dry-run` 永不删。** 那条承诺是"一个写请求都不发"，删除也是写。

## 为什么自动同步可以开，手工 CLI 默认不开

区别只有一个：**上游可达性在不在手上。**

- 网关那条路由：`libraries` 就是刚刚从 kb-service 读到的行。读失败的分支在
  调用 `run()` 之前就返回了 —— "库不在列表里"**必然**意味着"上游回答了，而且没有它"。
- 手工 CLI：`--tenant` 是人给的。上游短暂不可达时，`libraries_for` 会得到空列表，
  于是看起来"所有库都没了"。默认关 + `--retire` 显式开，是让人在一次可回滚的操作里
  承担这个判断。

## 被否掉的替代形态

- **保持只报告。** 就是今天的状态。运营看到的是一个点开就 502 的卡片，而日志里那句
  `orphans: […]` 没人看。
- **软删 / 打标记**（Dify 的 dataset 没有软删字段）。要加就得打前端补丁 + 改数据库，
  而收益只是"以后能恢复"——但库都已经在上游删掉了，恢复的是一条指向不存在东西的记录。
- **两次确认才删**（第一次记下嫌疑、第二次真删）。它防的是"上游抖一下"，而第 3 条
  保护已经防住了那件事（读失败根本不进这个分支）。加一层状态反而引入了新的失败面。

## 代价

**删除不可逆。** Dify 没有恢复入口，删掉的那条 dataset 只能重建。

补偿是：`run()` 在删之前把 `knowledge_id → dataset_id` 打进日志（`retire … -> dataset …`），
这是事后唯一能追回"删了什么"的东西。以及第 2 条保护把范围压到"确实由 RAGFlow 派生"的那些。

## 后果

更容易：RAGFlow 里删库 → 下次打开弹窗 → Dify 里那张卡片消失。**两端一致。**

更难：一个 brief 的上游故障仍然可能让某个库**看起来**不在了 —— 但第 3 条保护把这种情况
挡在了 `run()` 之外，所以今天不会误删。**如果以后有人给 `run()` 加一条新的调用路径，
必须同时确认那条路径也满足第 3 条。** 这就是为什么它写在 docstring 与这里两处。
