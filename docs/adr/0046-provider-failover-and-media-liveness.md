# 46. 供应商故障时自动换备用 provider；媒体 URL 不因重新发布而失效

日期：2026-10-19
状态：已采纳
影响版本：`src/aiops_diagnostics/config.py`（`provider_chain`）、
`src/aiops_diagnostics/codex_runtime.py`（`ProviderOutage` / `is_provider_outage` /
`SDKCodexSession.run`）、`src/aiops_diagnostics/gateway_runtime.py`（`_is_active`）

## 背景：一次事故里的两个独立缺陷

41 上"知识库能不能回图片和视频"这个需求，被两个互不相关的问题同时挡住：

**① 付费 provider 余额耗尽，且无处可退。** 上游对每一次调用返回

```
403 Forbidden [sk-x4CF…] 预扣费额度失败, 用户剩余额度: ¥0.007319,
需要预扣费额度: ¥0.017302
```

配置里只有 `AIOPS_PROVIDERS=baoyun` 一个 provider（`select_provider` 是静态查表，
全仓没有跨 provider 的故障转移）。于是一个**能用但没钱**的上游，把整个产品面全停了：
知识库问答、寒暄、宣传卡片一起 `QA_FAILED`，而同一份配置里另一把**有余额**的 key
从头到尾没被使用过。

**② 媒体 URL 一律 403。** `_is_active` 额外要求"签发 grant 的版本 == 该 agent 当前
`published_version`"。`canary-宣传案例` 在 2026-09-20 从 v2 重新发布到 v3，而
`case_exploration` 快捷动作的钉子仍是 `#v2` —— `3 != 2`，于是**从那一天起，宣传路径
产出的每一张图、每一个视频都是 403**。媒体被生成、写进 `result.blocks[]`，
用户一次都没真正看到过。

## 决策一：注册表顺序即优先级，故障自动转移

- **`AIOPS_PROVIDERS` 里排在选中 provider 之后的条目就是备用**，按声明顺序依次尝试。
  刻意**不新增配置键**：一份必须与 `AIOPS_PROVIDERS` 保持一致的备用名单，迟早会与它
  漂移，而漂移在这里的失败方式是静默的——"没被选中的备用"与"从没配过的备用"长得
  一模一样，这正是本次事故的形态。
- **排在默认项之前的条目不算备用**：把默认项设为第二个，意思是第一个被取代，
  而不是它在下次故障时又抢回优先级。
- **只有 `ProviderOutage` 才转移**：401/402/403/429/5xx、余额/额度不足、连不上。
  契约违规（`AgentContractError`）、超时、以及任何**未识别**的错误都在原地抛出——
  换一个 provider 重问，会把一个真实缺陷伪装成一个来自别处的、看起来正常的回答，
  那正是 `AgentContractError` 存在的理由（2026-09-17 的教训）。
- **备用拿到新线程，不 resume 旧线程**：线程属于失败的那个 provider，
  把它重放到另一个模型上，等于把前一个 provider 的上下文送给别人。
- **判定标记必须包含配额/余额词汇，不能只看 HTTP 状态码**：41 那次故障的文本是中文
  「预扣费额度失败…」，不含任何英文状态词。只看状态码的规则会漏掉它要修的那个故障。

## 决策二：媒体 URL 只随"撤销发布"失效，不随"重新发布"失效

- 判据改为：**该 agent 仍处于 published**，且**签发 grant 的那个版本仍存在、
  且仍绑定该 grant 引用的知识库**。
- **去掉**"签发版本仍是最新 `published_version`"这一条。
- 代价写清楚：旧版本签发的图/视频在**剩余 TTL（约 10 分钟）内**仍可访问，即使期间发布了
  新版本。这是刻意的取舍——URL 自己会过期，而另一条路是让产品面静默地什么都不显示。
  重新发布是正常的编辑行为（改提示词、换知识库），它不该吊销上一个版本已经产出的**字节**；
  那些字节没有变。
- **撤销发布依旧立即生效**：disable agent 仍然当场让它的 URL 全部 403 —— 这才是
  #168 验收真正要的那条撤回能力。

## 被否掉的替代形态

- **新增 `AIOPS_PROVIDER_STANDBYS=` 显式名单。** 与 `AIOPS_PROVIDERS` 重复且会漂移；
  见上。顺序本身就是最不易错的表达。

- **把故障转移做在 `aiops-responses-adapter`（8799）。** 那是 wire 协议 shim
  （补 `status` 字段），只转发到一个上游；把"选哪家"塞进协议转换层，会让
  "谁是主、谁是备"这个产品决策藏在一个协议组件里。而且它只服务 `wire_api=responses`
  这一条路，换个 wire 就失效。

- **所有错误都转移。** 最省事，也最危险：任何未识别的缺陷都会在第二个 provider 上
  拿到一个看似正常的回答，缺陷从此不可见。

- **`_is_active` 直接放行（只查 agent 存在）。** 会让"撤销发布"也失去即时性，
  丢掉 #168 已经验收过的那条能力。

- **保留旧判据，改去改快捷动作的钉子版本。** 治标：任何一次重新发布都会再造一次同样
  的静默 403，而钉子是运营数据，不是代码。

## 后果

更容易：付费上游欠费/限流不再等于产品停摆；一次重新发布不再让历史媒体全部失效。
"谁是主、谁是备"在 env 里一眼可读。

更难：**备用 provider 的存在是一份需要维护的承诺**——它得有余额、得与主 provider
的模型能力相当，否则故障转移只是把"明确的错误"换成"更慢的错误"。这条没有自动化检查，
靠运维纪律。

上限：本次不改"主 provider 自己选谁"（仍是 `AIOPS_DEFAULT_PROVIDER`），也不做
跨 provider 的**负载均衡**或**按能力路由**——只为故障可用。备用链**不做健康探测**：
只有真的失败了才转移，不做提前避让。

**故障转移只在会话的第一个回合发生。** 这是 ADR 评审指出后加的硬约束，原因是
备用拿的是**全新线程**：一个线程携带对话本身，而 `AgentCoordinator` 的多回合诊断里
`next_prompt` 是**接着模型上一轮的报告**往下问的。中途换 provider，等于把一个指代
前文的追问丢给一个没听过前文的模型——那不是重试，是另一个更差的问题，而且会以
"成功回答"的样子交付。所以一旦这个线程已经跑过任何一回合，供应商故障就如实抛出，
由调用方自己决定是否重开。代价是：**长时间的诊断跑到一半时主 provider 挂了，
这一轮仍然会失败**（重开整轮可以恢复）。这条取舍是刻意的——宁可失败得明白，
不要成功得可疑。

连带修了一处：`AgentCoordinator` 原本只在开跑前存一次 `thread_id`。备用换线程后
那个 id 指向一个已不存在的线程，若持久化下去，下一次 resume 会回到**失败的那家**，
丢掉备用答过的所有回合。现在每回合结束后重新读取并持久化 `thread_id`。

**构造期也走备用链。** 主 provider 可能在**建会话时**就失败（key 文件缺失、base URL
不可达）——那时一个回合都还没跑，而"建不起来"与"答不出来"是同一类供应商故障、同样
可恢复。原先只在 `run` 里走链，等于对这种最早的故障不设防。现在 `__init__` 也走同一条
链；但 **resume 不走**（`thread_id` 存在时链退化为单元素）：线程属于某一家 provider，
换家 resume 等于去 resume 别人的线程。

**知识库绑定对"当前版本"也要成立。** 这条是评审提出的安全问题，成立：只查签发版本的
快照，会让"重新发布时**移除了**某个知识库"的情形继续放行 —— 历史快照里那个库仍在，
于是运营刚把这个库从该 agent 上拿掉，图/视频在剩余 TTL 内**还取得到**。现在两个版本
都要绑着它：既满足"运营此刻确实允许该 agent 服务这个库"，又不影响单纯的提示词/关键词
重新发布（那不会动绑定，也正是 41 上被卡住的那种情形）。
