# 178. C 端站点范围来自本人订单，计数不给总数

日期：2026-10-30
状态：已采纳（设计定型，已实施）

## 决定

C 端（`consumer` 入口）的站点可见范围由**本人订单里出现过的站点**推导，不是整个租户；
新增只读接口 `GET /v1/sites` 并登记进公网 OpenAPI。

四条具体规则：

1. **取数永远显式带 C 端用户标识。** 订单列表请求固定带 `user-id`
   （服务端从会话推导，不来自任何请求参数）；标识缺失时**拒绝**，不构造那个请求。
2. **范围外的站点是预期内的，本地过滤而不是整份拒绝。** 上游按租户返回站点列表，
   落不在本人订单站点集合里的行直接丢弃。租户不符仍然是硬拒绝。
3. **不给总数。** 响应里 `total` 恒为 `null`：上游那个计数是租户口径的匹配数，与
   「本人可见」不是同一个集合。
4. **空结果分两种。** `empty` 取 `none_visible`（本人订单里确实没有站点）或
   `no_match`（有站点但关键词没匹配），因为两者的下一步不同。

## 依据

**上游的 `user-id` 头是 `required = false`，而过滤条件是条件式的。**
`iot/cloud-charging-pile:release` 的 `ChOrderInfoMapper.xml` 里 `getOrderPage` 写的是
`<if test="param.userId != null and param.userId != ''"> and coi.user_id = #{param.userId}</if>`
—— 头缺失或为空串时这一段整体消失，返回整个租户的订单。控制器
（`ChOrderInfoController.getOrderUserPage`）只在 `orderRequest.userId` 为空时才回落到
请求头，所以「不带」与「带空串」是同一种后果。这条已经在仓库里被实测记录过
（两个不同账号各打一次，`total` 都是 180），这次读到了源码，是同一件事的两份证据。

`OrderPageResp` 用 `select coi.*` 带出 `site_id` 与 `tenant_id`，两者都可逐行核对；
分页是 MyBatis-Plus 的 `Page`，参数是 `current` / `size`。

**为什么不能直接复用管家那条路。** 管家的可见范围来自 `DataScope` 的站点集合；C 端的
`DataScope` 是 `self`，`resolve_query_scope` 对 `self` 返回 `site_ids=None` —— 而在
`query_sites` 里 `None` 表示**不过滤**。照抄等于把整个租户的站点名单交给任何 C 端用户。

## 被否掉的替代形态

**让 C 端也走 `DataScope`，把 `self` 解释成「不过滤」。** 最强的地方是零新增代码：
站点查询原样复用，不需要另一套推导。它输在 `None` 在同一个函数里已经表示「不按站点
集合收窄」，而 C 端没有任何东西可以替代它——把「本人」翻译成「不限」是把两个相反的
意思写成同一个值，下一个读代码的人会照着这个先例继续用。

**范围外的行按违约拒绝（沿用管家的 `reject`）。** 最强的地方是判据只有一条、不分入口，
且它对管家是正确的：管家请求已经带上站点集合，出现范围外的行说明上游没按约定收窄。
它输在 C 端的上游请求**没有**站点过滤参数可用，返回租户全量是设计行为；按违约处理会让
「本人只有一个站点」的用户永远查不到自己的站点，而且失败长得像上游故障。

**给出上游的 `total`，用字段说明它是租户口径。** 最强的地方是信息更多，调用方能自己判断。
它输在 ADR-0172 已经踩过一次：一个标着「口径」的数字照样会被当成「你有多少个」展示出去。
一个不会被正确使用的数字，不如不给。

**让前端先拉订单再逐单查站点。** 最强的地方是 AI-Ops 不需要新建任何接口，全部逻辑留在
客户端。它输在把授权判据搬到客户端——范围就取决于前端肯不肯老实——而且 C 端每查一次
站点都要先自己列举订单。

## 后果与验证

- **两个入口的 `outside_scope` 语义必须分开，且不能互相沿用。** 它现在是 `query_sites`
  的一个显式参数（`reject` / `skip`），不是两条独立的实现：范围推导、读取、结果对齐、
  分页上限仍然只有一份。
- **本人站点很多时可能漏。** 站点接口本身是「最多 4 页、展示最多 10 条」的既有预算，
  本人订单站点再多也只能在这 4 页里找。这是既有边界的后果，如实写进接口说明，不在
  这里悄悄放宽。
- **订单与站点都有上限**（订单 4 页 × 50、站点 200），超限在响应里标 `scope_truncated`，
  不冒充完整。
- **公网规范多一条操作。** `tests/gateway/test_public_openapi.py` 断言规范与
  `docs/testing-api-guide.md` 的表格逐条相等，所以新增接口必须同时出现在那两张表里，
  否则 CI 红——这是 ADR-0156「显式登记」的机械形式。
- 验证：`tests/consumer/test_consumer_sites.py` 覆盖本人范围、`user-id` 必带、空身份拒绝、
  跨租户拒绝、截断标注、上限拒绝、空结果两种原因、以及「接口拿到的集合等于直接调范围
  推导函数」。
- **未完成业务验收**：没有真实 CPMS、没有真实账号、没有真实页面。本决定证明的是契约与
  授权模型，不是站点在真实租户里列得对。
