# 运维分析走的只读面：范围下推，而不是公司运维 HTTP

日期：2026-10-12
状态：已采纳
影响版本：PRD #693 的子票 #697（#698 / #699 沿用同一决定）

## 背景

PRD #693 的 ③ 号路径要一张「站点集合 + 时间窗」的跨订单聚合卡。公司 CPMS 后端**已经实现**了
这些运维数据的采集、打标、统计与端点（`OperationsStatistics/board`、`iotDeviceOfflineMonitor/page`、
`iotDeviceFailureRecords/getErrCode`，以及 `ErrorOrderTagJob` 打标）。第一版 PRD 写的是
「读面映射到公司运维端点，让 `@ShopDataScope` 生效」。

复核把这一条打穿了，三条依据都是既成事实而不是偏好：

1. **本仓基线 L3-3**：AI-Ops 三类出站**都不带 `client-type`**，而公司后端
   `ShopIdInterceptor.judge()` 要求它属于 `admin`/`supply-admin`/`tenant-app` 才做数据隔离
   ⇒ 这是**绕开**隔离，不是「隔离不适用」。
2. **41 活链路实测**（无凭据）：三个运维端点全部 `HTTP 200` / `json_code=0`；
   `tenant-id` 头（真租户 / 假租户 / 不带）三份响应 **sha256 相同**。这些端点今天返回的
   是一份与身份无关的默认切片。
3. **公司网关** `cloud.auth.enable: false`：无令牌打即 200 并返回真实数据体。

也就是说：那些端点今天**不是授权边界**。把「打公司运维 HTTP」写成隔离门，会让一个
与身份无关的默认切片看起来像是按租户取的数据。

## 决定

**四点。**

### 一、聚合执行落在 QueryScope 下推的只读 SQL 上

新增 `MySQLSource.aggregate_order_statuses`：租户谓词**永远**下推（`_scope_where`），
请求的站点集合**先与调用者可见站点取交集、再**成为 `site_id IN (...)`，时间窗是半开的
`created_time >= start AND created_time < end`。空可见范围**短路、一条 SQL 都不发**。

交集放在**取数层**而不是调用方：本层是「不得超出范围」的守卫边界，把「调用方已经窄过了」
当前提，意味着任何一次调用方疏忽都会**如实统计出无权看到的站点**——而查询成功、数字合理。

### 二、公司 mapper 只作**公式参考**，不是执行面

`getErrorOrderRate` / 离线看板 / 故障码排行那些 SQL 的形状被参考（分母是什么、怎么分组），
但执行不走它们。这条区分是：**复用公式**（业务语义已经由公司定义，我们不该另起一套）与
**复用端点**（那会引入一个不成立的授权边界）是两件事。

### 三、数字确定性，模型只写叙述

`failure_rate` / `risk` / 计数由后端算，模型写 `main_cause` 与 `recommendation`。
两道墙而不是一道：结构化输出 schema 里**没有数字字段**（模型连可填的位置都没有），
装配时**按名字读两个键**（即使 provider 无视 `additionalProperties`，一个写进 payload 的
数字也没有路径进入契约）。规则版本 `ops-analysis-v1` 与「异常 = `order_status=5`」这一定义
随数字一起交付。

### 四、切流条件（写下来，本期不执行）

公司侧给统计 mapper 补上 `@ShopDataScope`（或等价隔离）**并且**有一条服务间鉴权真正成立的
路径之后，③ 的读面**可以**切到那些 HTTP。那是一次显式切流，验收判据是
「无凭据不再 200」+「不同身份得到不同哈希」两条同时成立——缺任何一条都不算。

### 五、同一张面上的新卡是**种类**，不是新机制（#698）

离线桩与故障码两张卡落在同一个路由上，靠 ``card`` 参数区分，而不是各开一条路由。理由：
三张卡的作用域、时间窗语义、范围下推、入口门与错误形状**完全相同**——开三条路由等于把
入口门、参数校验与响应构建各复制三份，而漂移的方向永远是放宽（一条路由漏了入口检查）。

作业行上多存一列 ``card``，轮询时据此还原成调用方要的那张卡；调用方不必记住它调过哪条路由。
语言守卫与散文路径**只有一处实现**（``ops_analysis._prose_fields``），三张卡共用——所以
「第 5 个调用点」在 #698 之后仍然是**一个模块、一个函数**，而不是三个。

### 六、设备与故障的列名抄 DDL，不猜（#698）

``iot_device_offline_monitor`` 与 ``iot_device_failure_records`` 的建表语句与后续
``ALTER`` 都在公司仓的 ``db/migration`` 下（``V1.0.110`` / ``V1.1.37`` / ``V1.1.92`` /
``V1.0.89`` / ``V1.0.104`` / ``V1.0.109``）。本仓据此写下列名，出处写进各聚合函数的
docstring。**离线时长只累计已恢复的记录并被窗口末端截断**：仍在离线中的记录结束时间还不
存在，用「现在」去算会让同一窗口两次查询给出不同数字——那正是这张面承诺要避免的事。

⚠️ **``iot_device_offline_monitor.tenant_id`` 可空**（DDL 如此），因此租户谓词会漏掉
``tenant_id IS NULL`` 的行。本实现**仍然下推租户**：范围边界不能因为某张表恰好写得松就
放宽。漏掉的行是**数据缺口**，量级未在 41 上测过，如实记下而不是靠放宽范围去"补上"。

## 被否掉的方案

- **打公司运维端点当读面**（首发 PRD 的方案）。它的最强理由是真的：**公式与表结构已经在
  公司侧实现**，直接调用能少写一遍业务语义，也天然贴近 CPMS 的统计口径。它输在**它不是
  授权边界**：无凭据即 200、`tenant-id` 不改变响应哈希，于是「按租户取数」这句话在链路上
  没有对应物。把这样一个响应接进一个对外契约，等于把一份与身份无关的切片署名给某个租户。
- **新建 `om_task` / `om_analysis` / `ai_report` 那套表与服务**（文档里的远期形态）。
  它给出的边界更干净，但本期要长的是**行为**而不是表：既有作业表的状态词汇、claim guard、
  过期清扫与重启收敛都已经是对的，为同一件事再造一份表就是再造一份它们的副本。表后长。
- **按成因聚合出「次因占比」**。这正是契约里 `secondary` 字段的直觉读法，也是最诚实的
  读法。它输在**本仓算不出来**：成因分类住在 `rules.classify_stop_reason` 里，是 Python
  而不是一列，按成因聚合需要把窗口内的行全拉回来——那会把「不下推就不查」这条房规拆掉。
  本票给的替代是**可直接行动**的那一维：异常最集中的站点。契约里字段名因此是 `secondary`
  而不是 `second_cause`，免得读的人以为它是成因占比。
- **把 `order_no` 列改成可空**。语义上更干净，代价是 SQLite 需要重建整张表——本仓从未做过，
  且会把既有每一行诊断置于风险中。改用 `order_no = ''` 满足 `NOT NULL`，响应构建器对
  `kind='analysis'` 不输出该字段，空串因此不上线。

## 后果

- **收益**：这张卡的数字**可复核**——同一条 `QueryScope`，审查者用只读 SQL 能重算出同一个值；
  范围不会因为「公司端点恰好返回了什么」而变化。
- **代价**：聚合公式由我们维护。公司侧改了统计口径（例如「异常」的定义变了），我们不会
  自动跟随，需要一次显式的公式变更 + 规则版本递增。
- **代价**：`SUM(CASE ...)` 是目前唯一的聚合形态；再复杂的分析（按成因、按时间分桶）会需要
  新的下推 SQL，而不是「多打一个端点」。
- **已知上限**：`secondary` 是站点维度而不是成因维度（见上）。
- **未定的**：支付失败那一刀（#699）在本仓的字段是否足以区分「支付失败」与「未支付/退款」
  尚未验证；若不足，那一票必须诚实标 `unavailable` 并写明缺口，不由模型补数字。

## 验证

- `tests/test_ops_analysis.py`：确定性、模型写不进数字、空范围不发 SQL、越界站点在拼 SQL 前
  被剔除、半开窗口、NULL 计数、语言守卫的第 5 个调用点（数字不被改写）、非文本叙述被拒。
- `tests/test_ops_analysis_api.py`：operator 可创建/轮询、consumer 403、`an_` 与 `qa_`/`dx_`
  三个 id 空间不串、分析作业不出现在诊断列表、倒置窗口与显式空集合在建行前被拒。
- **未验证（据实）**：41 上对真实租户跑过一次这张卡；真实模型写出的叙述质量；以及
  「切流条件成立后那些端点真的会开始拒绝无凭据请求」——那要等公司侧改动落地后才能验。
