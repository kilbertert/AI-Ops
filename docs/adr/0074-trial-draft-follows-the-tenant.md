# 74. 试运行的草稿来源跟人走，订单范围仍然跟身份走

日期：2026-10-21
状态：已采纳（#885 实施；ADR-0059 §5.3 落成代码）
影响版本：`src/aiops_diagnostics/gateway_api.py`（`_trial_draft_from_console`、
`_workspace_for_publish` → `_workspace_for_tenant`）

## 背景

试运行有**两个**输入，它们原先各自钉在一个地方：

| 输入 | 来源 | 多 workspace 之后 |
|---|---|---|
| **草稿**（方法论正文 + 工具白名单） | `DifyDslSource(workspace_id=常量)` | **错**：读的是那个常量指向的工作区 |
| **订单范围**（能看哪些单） | 发起人的公司身份（#782 已交付） | 正确，且与 workspace 无关 |

所以这张票只需要改第一行 —— 但它不能顺手改第二行。ADR-0059 把两者分开写，正是因为
"读哪份草稿"与"能看哪些单"是两个问题：前者是租户的，后者是人的。

## 决策

**一、草稿来源按 `binding.tenant_id` 解析，与发布共用同一个解析函数。**

`_workspace_for_publish` 改名 `_workspace_for_tenant`，发布与试运行都调它。两个调用方
各自再写一份"怎么拿 workspace"就是 ADR-0067 那个函数要防止的漂移。

**二、解析发生在查 agent 之前。**

这一条是实施中实测出来的，不是推演：先把它写在 `_find_by_name` 之后时，"租户没开户"
会被报成 `AGENT_NOT_REGISTERED`（那个 agent 确实没在当前库里找到，因为查它之前就该失败）。
workspace 是**绑定**的属性，不是 agent 的属性 —— 顺序表达这个关系。

**三、租户没有 workspace ⇒ 明确拒绝，不回落平台工作区。**

设计与发布同一条：宁可拒绝，也不给一个看起来能用的空壳。试运行这一侧的后果更具体 ——
回落到平台工作区会让运营把**别人的方法论**当作自己的跑一遍，然后从结果里得出"我的草稿
效果是这样"的结论。

**四、订单范围一个字不改。**

范围仍然来自发起人的公司身份（`TrialInitiator.from_headers` → `scope_context`），
与 workspace 无关。把两者合并会让"换一个 workspace"变成"换一个可见范围"，那是更大的
一次授权变化，不在本票。

## 被否掉的替代形态

- **同时改订单范围**。范围与 workspace 是两个维度（人 vs 租户）；一起改会让一次"读草稿
  的位置"变更顺带扩大可见范围。
- **回落平台工作区**。见决策三。
- **在桥那一侧读草稿**。DSL 里的工具条目只有提供方 UUID、没有名字，解析必须当场做映射；
  那套映射（`resolve_pulled_config` + `partition_aiops_tools`）只在网关有一份。
- **给试运行单独写一个 `_workspace_for_trial`**。它就是同一件事的第二个写法；共用一个
  函数的成本是零。

## 后果与代价

- **试运行在"租户未开户"时不可用**，返回 404 `DIFY_WORKSPACE_UNRESOLVED`。这与发布的
  行为一致，也是运营此刻唯一能行动的信息（去开户）。
- **平台租户的落点仍是待办**（#882）：平台账号要不要有自己的平台 workspace、以及它在
  试运行时怎么解析，是另一张票的事。本票只保证"解析用的是绑定租户，而不是常量"。
- **这次没有真机验收**：41 的 `dify_workspaces` 仍为空，"租户 A 的人只看得到 A 的草稿"
  要等第一行映射 + 一次真实试运行。
