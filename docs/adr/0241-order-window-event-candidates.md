# 241. 订单日志交付设备窗口候选，缺失原始报文保持缺口

Status: Accepted

日期：2026-11-10。用户批准三个反馈的方案实施；本轮只读核验发现当前无原始通讯历史可复原。

## 决定

工具只接受order_no，从已交付且当前授权的订单详情派生父设备、枪和时间窗。
通讯、桩事件、枪事件、桩调用、枪调用分别报告记录、空窗或不可用；
每源最多12条，总量60条、窗口24小时。入库时刻与事件/调用名仅为
`device_window_candidate`，不能据此认定本单交易或设备执行成功。

源事实来自tsdata f44ea003指定写入/查询源码及父会话的只读核验：无comm表，
MySQL日志表无记录，目标窗口事件为空，枪遥测存在。未知方向、code、decoded与正文
不查询、不透传；遥测不补造成原始报文。Gateway接线与缓存回读复核保持现有授权边界。

## 被否掉的替代形态

- 从枪遥测或历史回答复原原始日志：缺独立来源，会把推断包装成已取得的报文。
- 只保留父设备fi：已证实存在枪fi，父设备调用不能覆盖枪级调用，故纳入第五源并收紧单源行数。
- 透传decoded后交由模型判断关联：可能暴露同设备其他订单正文，且没有已确认交易关联合同。

## 后果

现有缺失历史仍不可用，空窗不证明正常；后续启用原始通讯持久化和正文交付须另核源合同。
复用统一object工具装配，无需Java工具名分派；节点声明、模板和应用发布仍须配套。
本地Gateway/Java检查不替代原Dify/H5及业务验收。验证与生产边界见
[集成回执](../validation/2026-11-10-operator-communication-integration.md)。

## 2026-11-10：源查询共用预算

Devin指出五源串行耗时累加，作者用实际HTTP复现每源3秒→总15.049秒，超过Java工具10秒请求时限。
改为进程级固定5个工作线程、最多5个在途任务，不排队；所有源共用单调时钟4秒截止点，
read callable必须接受`timeout`关键字（启动时剩余预算）。输出仍按固定源顺序组合。
忙/超时分别为source_busy/source_timeout，总数未知，已返回结果不被迟到线程修改。
取源前后各核对当前授权和订单，工作线程只处理已裁定的设备/窗口，不并发访问授权状态。

不扩大Java通用时限，也不每次调用创建新线程池。urllib超时是socket等待上限，不能强杀慢滴流；
聚合只等共同截止点，仍在读的最多5个任务占住槽位直到结束，后继请求显式报告忙。
4秒是取源预算，不承诺公司授权/订单读取或宿主调度始终在其余6秒完成；源故障不能绕过读后授权。
