## 第一段：固定输入的真实 Dify 工具联调

1. 开始前保存目标 app 的完整配置、DSL 摘要、当前已发布快照和配置摘要到私有目录，
   只读确认它仍是原目标；若有运营正在编辑、版本/摘要变化则重新协调，不能覆盖。
   程序化 `model-config` 的完整 body 写回先按环境手册在一次性 app 排练，排练资源只清本次创建的。
2. 按首片手册登记 provider、编辑两个工具并发布；回读实际 `allowed_tools`，
   schema 相同的 `unchanged` 和掩码 key 都不算凭据通过。
3. 固定输入调用 Dify 工具执行路径：一次 `order_list`，`{"page":1,"page_size":1}`；
   只从该响应选择一单，一次 `charging_info`。禁止自动重试、其他页、其他订单或旧工具取数。
   可复用 `ops/dify-tools/README.md` 的 `/tool-provider/api/test/pre` 形状；
   该入口显式提供凭据时只证明 Dify 凭据组装/出站，不证明已存 provider key 或模型调用。
   存储凭据的调用路径须在执行前按当前 Dify 版本核实，未经核实不假报覆盖。
4. 私有保存两次响应和 call_id，核对来源、时间、目标、权限版本及正文 SHA-256。
   对同一单做一次只读业务 SQL 和一次 CPMS GET 独立对照，输出脱敏判据。
   列表内部为判断 `has_more` 最多读取两行，Dify 返回至多一行；状态工具还会做两次归属 SQL。
5. Dify 中显式关闭新两个工具后发布，回读权限；用同一服务 key 各调用一次应为
   `403 OPS_TOOL_NOT_PUBLISHED` 且无业务正文。授权守卫前置由已交付本地证据支持，
   线上只有拒绝响应/审计时，不夸称已独立观测业务调用数为零。

以上上限仅适用于人工固定输入的脚本；它不是服务 key 的权限上限。
