# 主机访问声明（`.dev-host.toml`）

仓库根目录的 `.dev-host.toml` 声明**本项目可以访问哪些主机、以及各自的路径约定**。
它由 `dev-host` 读取，用途是让"够到另一台机器并搬东西过去"这件事有一个固定形态，
而不是每次现场手写 `ssh` 与拷贝脚本。

## 为什么分成两半

同一份 schema 分两处存放：

| 半 | 位置 | 权限 | 内容 |
|---|---|---|---|
| **项目侧** | 本文件，**进仓库** | 640 | 逻辑名、指向的 host 键、路径约定 |
| **主机侧** | `~/.config/dev-host/hosts.toml`，**库外** | 600 | 角色、信任平面、归属、访问方式、主机公钥 |

本文件**只写逻辑名，不写地址、不写指纹、不写任何凭据**——这是它能进本仓库（公开）
的原因。地址由 `ssh -G <alias>` 从 `~/.ssh/config` 解析，避免制造第二个可能与既有
配置矛盾的真值来源。

## 这里声明了什么

见仓库根的 `.dev-host.toml`。当前只有一台：

- **`41`** —— Gateway 生产环境（`aiops-41`）。它是**服务类主机**，因此：
  - **写入需要产物身份**：`--artifact-sha256 <hex>`。这不是额外手续，是把
    "变更只能作为产物到达服务主机"这条规则变成工具会强制执行的条件。
  - **`exec` 需要显式 `--allow-service-exec`**：读用 `read`/`ls`/`find`，不受限；
    执行要显式承认。
  - **执行前会断言主机公钥指纹**，不符则**中止**（不是警告）。

## 与新机器打交道

主机侧清单**未登记的主机 = 不可用**。新增一台机器时：

1. 在 `~/.config/dev-host/hosts.toml` 里登记它：角色、信任平面、归属、访问方式、
   主机公钥。角色必须取自策略已有的五个角色词，不新造词。
2. 确认 `~/.ssh/config` 里有对应别名（地址不写进 registry）。
3. 在本文件里加一条 `[[targets]]`，用 `host` 指向第 1 步的键。
4. 验证：`dev-host show <name>`，再 `dev-host exec <name> -- hostname`。

第 1、2 步涉及地址与指纹，属**内部记录**，不进本仓库。

## 部署流程里的位置

本文件**不改变**既有的部署流程。41 的部署仍然是"**备份 → 传 → 校验 sha → 重启**"
（见 `docs/agents/env-41-runbook.md`），各步照样手工执行；`dev-host` 提供的是：

- `dev-host cp 41 <tarball> --dest /tmp/… --artifact-sha256 <sha>` —— 传输这一步，
  产物身份不符会被拒
- 逐文件 sha256 对比（`hash-tree.sh`）—— 替代 runbook 里手工标注"必做"的那一步

回滚路径、备份位置、重启方式都不变。

## 射程边界

`dev-host` 挡得住"**传错了 / 传坏了**"，**挡不住"构建时就标错了版本"**。
后者是构建期写假信息的问题，归构建步骤——别指望这个工具有它没有的能力。
本仓库被这件事烧过一次（`生产 jar 不等于分支 HEAD`），所以这条边界写在这里，
而不是留给读者推测。
