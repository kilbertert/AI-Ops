**D-3 · Nacos 路由 —— ✅ 已执行（2026-09-30）**

```yaml

    uri: http://172.18.0.1:8788
    predicates:
    - Path=/v1/**

    - RewritePath=/(?<segment>.*),/v1/$\{segment}
```

🔴 **三个实测出来的坑，缺一条这条路就不通**：

1. **`RewritePath` 是必需的，不是可选项。** 少了它，AI-Ops 收到的路径变成
   `/faq/recommendations`（少了 `/v1`）⇒ `404`。原因：本网关会把**匹配到的那一段前缀剥掉**
   （既有 35 条全都用 `RewritePath` 把它加回来 —— 那就是它们存在的理由）。
   `Path=/v1/**` 剥掉 `/v1` 之后再拼 `/v1/$\{segment}`。
2. **更新 Nacos 之后必须重启网关容器。** `DynamicRouteInit` 的监听器**会打印
   「加载路由：…」并且保存**，但新建的 route **不生效** —— 既有路由不受影响，只有新的那条
   404（实测：同一批 `save` 里既有路由正常响应，新路由不行）。⇒ 容器 `docker restart`
   之后正常。**不要被那行「加载路由完成」的日志骗了。**
3. **路由 id 不能叫 `aiops`**（会撞上既有 `Path=/aiops/**` 的那条）——取自 `aiops-gateway`。

**D-3a · 网关对同名头是「覆盖」还是「追加」？ —— ✅ 已离线测定（2026-09-30）**

⚠️ 这正是 nginx 那一跳**已经踩过**的坑：同一 location 内两条同名 `proxy_set_header`
**不覆盖**、两条都发给上游、应用取第一条 ⇒ **静默用错凭据**。所以这一条必须先问清楚。

**结论：Spring Cloud Gateway 的头过滤器用 `set` 语义 ⇒ 覆盖。** 三种机制都查过：

| 机制 | 结论 | 证据 |
|---|---|---|
| 短式 `SetRequestHeader`（**推荐用它**） | **覆盖** | 线上那个 jar 里 `SetRequestHeaderGatewayFilterFactory$1` 的**字节码常量池**含 `headers` / `org/springframework/http/HttpHeaders` / **`set`**，且**没有** `add`（部署产物本身，非源码）；与 SCG 4.1.2 上游源码 `httpHeaders.set(config.name, value)` 一致 |
| 字符串短式过滤器工厂 | **都能用** | jar 的 `filter/factory/` 里 `Set/Add/Remove/MapRequestHeader…` 都在；**没有** `DedupeRequestHeaders`（"合并同名头"的那个是**响应**侧的 `DedupeResponseHeader`）⇒ **"先追加再删"的组合在这个网关里不成立** |
| 公司自己的三个过滤器 | **覆盖** | 源码即 `headers(h -> h.set(k, v))`（`AdminProxyHeadFilter` / `ApiProxyHeadFilter` / `AuthGlobalFilter`） |

⚠️ **但"覆盖"不解决全部问题**：它覆盖的是网关**自己收到的**那个头。**若上游 nginx 先给
`operator` 加了同名头**（今天的 nginx 正是这么干的），网关那一步 `set` 只改它看到的那一份
—— **同一请求上仍可能并存两个来源**。⇒ **D-3 与 D-4 必须一起改**：
网关这一跳**只在写入侧**（`set` 覆盖），nginx 那一跳**必须同时不再注入**，
否则「谁最后写」决定了上游读到什么，而那正是静默用错凭据的形状。

**因此这一步不再阻塞 D**，但把它降级成**验收里的一条断言**：

- **判据**：`operator` 经网关时，AI-Ops 收到的 `X-AIOps-Source-Key` **只有一个值、且是网关那份**；
- **对照**：故意让 nginx 也注入一个**不同的**值 ⇒ 断言上游读到的是**哪一个**
  （这条对照就是用来钉死"谁最后写"的，不能省）；
- **注意判据的分辨率**：只看「上游收到几个头」不够 —— nginx 那一跳踩的就是
  「两条都到、应用取第一条」。必须同时记「应用**实际读到**的那个值」。

> ⚠️ **本节的证据来自部署产物与源码，不是端到端实测**。真正的端到端断言在 D-5 的验收里，
> 那时通道才通（今天网关还够不到 AI-Ops，见 §2 的 exposure 决定）。
> **离线结论足以决定 D-3/D-4 怎么写**，这也是把它从"第一个实验"降级为"验收断言"的理由。

**D-4 · nginx 改向 —— ✅ 已执行（2026-09-30）**

- 形状：按入口分上游。`proxy_pass` 的**变量形式会丢掉 URI**（实测），
  因此必须配 `rewrite … break` —— 不用变量形式则 `map` 白做；
- **目标态**：`operator` 分支由**网关覆盖式注入 `X-AIOps-Source-Key`**；
  🔴 **`Authorization` 必须仍然是用户 JWT，不能被覆盖成服务令牌** —— 公司令牌解析器
  就是从这个头读身份的（`company_token_auth.py`），覆盖它等于把管家端认证打断。
  **nginx 不再为 operator 注入来源密钥** —— 这一步做完，A2 才算真正消掉；
- `consumer` 分支**逐字不变**。
