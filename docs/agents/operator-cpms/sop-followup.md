# 测试反馈接续：SOP分析、连续问答与计费

来源：2026-11-04测试反馈，承接#1335。两份业务参考是根目录`SOP.md`与
`充电桩问题排查SOP.md`，不是现役应用里的两段短提示词。SOP中的人工改配置、重启、
退款等不是自动执行授权；已退役的SQL/TDengine/Redis工具不恢复。

## 交付顺序

1. 连续问答：正式入口与Dify原生预览都返回可续用会话；最近三轮按时间尾部读取。
   同一主体、入口、应用内继续，订单每轮重新授权；新会话、错主体或错应用不得继承。
2. 分析结果：根据问题交付相关证据、计算与限制，避免后台字段列表代替分析。
3. 计费：历史读取订单当时的模板快照与分时费用；未来读取指定可见站点的适用规则，
   在给定电量、功率、可充时间及规则适用条件下比较总费用。

## SOP要求与可证明结果

| 问题 | 所需信息 | 可计算/核对 | 缺证时 |
|---|---|---|---|
| 电压/电流 | 同订单监测值、时间、样本边界 | 有效样本范围/变化，明确只代表已取样本 | 不用额定功率推电压，不由无样本断言正常或故障 |
| 功率/电量 | 电量、明确分钟时长、监测功率、额定功率 | 平均功率与样本统计；额定值与实测分开 | 零/缺时长拒绝除法，不能猜单位 |
| 电费/服务费 | 当时模板、时段用量/费率、费用记录、协议/启动类型 | Decimal计算与原记录对照，保留舍入/缺项 | 不从合计除电量倒推官方费率，不混用当前站点模板 |
| 未来方案 | 明确站点、日期/时间窗、所需电量、可持续功率、适用费率/套餐/附加费 | 比较约束内可执行方案及总费用 | 条件缺失则追问；未覆盖的优惠/节假日/停车费用不得默认为零 |
| 停机/故障 | 停机码、时序、协议与异常证据 | 分清记录事实、候选原因和可执行排查建议 | 不据单个空值或旧状态推根因 |

普通查询只读，不改业务订单或实际计费。计算结果是基于指定证据与条件的核对/估算，
不等于后台重算、银行到账或实际设备必然达到设定功率。

## 接续发现

- #1335确有一次真实Dify电费/电压两题复验（不同正文、相关字段和缺值提示）；
  该回执不证明连续问答，也没有读取两份完整SOP或计费接口。
- 现役历史查询取最早四轮再截三轮，长会话时读错窗口；正式管家分支未使用活跃订单。
- 原生预览桥拒绝非空conversation_id，试运行显式不带会话；页面连续气泡不等于服务端连续上下文。
- 公司只读订单计费快照接口已有真实返回，现役工具尚未接入；源码与生产适用范围分别留私有证据。

本片先交付连续问答；SOP分析与计费接入按上述顺序继续，不把接口发现记成用户功能上线。

## 历史计费实现片

`cpms_order_tariff`读取已授权订单的历史快照，由节点调用、网关重新验订单归属。
费率按快照展示；分时费用做加总和差额核对。订单独立分时电量齐全且价格唯一、
协议已知、无套餐时，可做电量乘单价核算。上游分时展示电量可能由费用反推，不能用其证明计量正确。

部署先安装兼容节点与同一工具声明，再部署Gateway。旧工具保留request-target/1，
新嵌套工具使用/2；正常发布前节点声明摘要须一致。应用需显式勾选新工具并正常发布，
不把全局声明当成已有订单应用的授权。已有历史结果不重新渲染。

验证脚本依赖从当前Maven可执行jar的`BOOT-INF/lib/`解出，避免混用旧缓存的日志库。
`verify_operator_cpms.py`会把本checkout的声明拷入临时classpath；无订单场景仍仅开放站点查询。
未来站点最低费用计划仍为后继片，未在本片实现。
