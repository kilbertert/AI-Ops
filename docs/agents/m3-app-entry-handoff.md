# M3 App 入口交接与上线前条件

适用：消费者订单详情页接入已交付的同 run 充电状态接口。
先读 [接线契约](m3-app-bff-contract.md) 与 [正常登录验收手册](m3-user-entry-acceptance.md)。
本页区分已部署后端、私有 App 候选、尚未应用的入口配置。

## 1. 当前交付边界

- Gateway #920 已合并并由 CD 部署；源码摘要与合并制品一致。生产四个 M3 开关仍关闭。
- App 候选在公司源码只读快照上制作，未写入公司仓库，未发布 App/H5。
- 已查的 H5 同源 `/v1/shortcuts` 返回 **200 HTML 首页**；API 域名对应路径无身份时为
  **401 JSON**。这证明 H5 同源缺少该转发，不能把 200 当成接口成功。
- App 的实际发版分支、部署来源提交与合入负责人仍待公司侧确认。README 的分支说明与
  现有 AI 模块所在分支不一致；不以最后提交时间或作者姓名代替发版决定。

## 2. App 候选做了什么

外部源码和补丁只放在 gitignored 的 `.scratch/company-repos/`，取回方法见
[公司源码只读规程](company-code-recon-procedure.md)。私有回执记录仓库、固定修订、
逐文件原始/候选 SHA-256、补丁与验证结果；本仓不提交公司源码正文或 diff。

候选包含六个文件的变更：

1. 把原 AI 请求模块移到公共 `utils`；旧路径保留 re-export，既有调用不迁移。
   订单页与 AI 页是不同分包，公共代码放主包，避免跨分包依赖。
2. 去掉该请求模块的请求头/响应正文日志。旧调用保持原返回行为；新方法选择结构化
   HTTP 状态和 code，网络失败记结果未知，不复制上游敏感错误正文。
3. 新方法仅发送空对象、既有会话与 consumer 入口，显式超时 90 秒，无自动重试。
4. 新组件显示本次观察的 status_role 和 observed_at；防重复点击，切换订单/卸载组件后
   丢弃旧请求结果，未知角色或无效响应不冒充成功。
5. 订单详情页按环境配置 `aiopsM3Enabled === 'true'` 才显示；默认隐藏。该键尚未在生产配置。
6. 文案沿用 App 本地化，候选提供简体、繁体、英文；其余语言明确使用英文兜底，未验译文质量。

依据：[uni.request](https://uniapp.dcloud.net.cn/api/request/request.html) 的 timeout 单位为毫秒、
默认 60000；本接口的平台同步请求可能超过默认等待时间，因此新方法显式配置 90000。
[uni-app 分包说明](https://uniapp.dcloud.net.cn/collocation/pages.html#subpackages)将跨包公共 JS
放入主包；不为这一步新增通用 SDK。

## 3. 已跑验证及其限制

| 层 | 判据 | 结果/限制 |
|---|---|---|
| 补丁应用 | 对固定源修订 `git apply --check`、应用后逐文件摘要等于候选 | 六文件一致；不是公司远端合入 |
| JS / 组件逻辑 | H5/App/小程序条件代码、headers/空体/90s、错误分类、日志、重入、迟到结果 | 29 条断言通过；uni.request 为替身，零公司请求 |
| Vue 模板 | 新组件和改后订单页用 Vue 2 模板编译器编译 | 两模板零错误；不是完整 HBuilderX 构建 |
| Chromium | 显示状态/观察时间、未启用提示、清除旧结果、网络未知、不自动重发 | 六项通过；浏览器壳将 uni 的 view/text/tap 映射为 div/span/click，非真机 App |
| Nginx 候选 | 本地动态回环端口，匹配路由、JSON/no-store、服务身份覆盖、consumer固定、移除来源密钥、其它路由不变 | 九项通过；合成上游，未应用生产配置 |

公司 package.json 的 test 是显式失败的占位命令，未提供可直接执行的完整构建脚本。
不能将独立模板编译与组件浏览器验证报成 App 打包通过；发版负责人需用其 HBuilderX/小程序
构建链验证条件编译、分包体积、真机行为及全部现有调用方。

## 4. H5 同源入口的最小候选

本片仅准备**单条本人订单委派路径**的 location，未改任何生产入口或整个 `/v1/`。
它复用现有 Gateway 地址和服务令牌文件，在服务端覆盖 Authorization、固定 consumer、
把外部 third-session 转成内部 X-Third-Session，并清空 X-AIOps-Source-Key。
保留 JSON 与 Cache-Control；120s 上游等待，不自动切上游重试 POST。

应用之前仍须按主机规则记录路径暴露决定，确认目标 vhost、现有 location 优先级、
配置备份/恢复及 nginx 校验。未批准时留在候选；不要为了让 H5 有响应而复制整个管理接口范围。
M3 功能开关与 App 显示开关是另外两件事，不能随转发配置顺手开启。

## 5. 部署后核对的方法

主机身份先按 `dev-host show 41` 确认，命令经
`dev-host exec 41 --allow-service-exec -- '<只读核对>'` 执行：

- 从 systemctl 取 MainPID 与启动时间，检查进程 env 中四个 M3 键是否启用，只输出布尔值；
  配置文件比较内容摘要，不输出密钥。
- 对 gateway_api.py / agent_runs.py 计算 SHA-256，与合并提交的文件内容对照；
  `/health` 版本应包含已部署修订且 business_mutations=disabled。
- SQLite 使用 `mode=ro` 核对 agent_runs 数量；不构造第二个生产 Gateway 应用。
- H5 与 API 两个域名分别做无身份 GET；保留 HTTP、Content-Type 与是否 HTML，不保存首页正文。
  必须注明观测位置；本轮为宿主回环解析原 HTTPS 域名、证书校验开启。

这些检查只证明版本、关闭状态和入口响应，不能证明已关闭的 M3 正向业务链路。

## 6. 接手者下一步

1. 公司侧确认实际发版分支与合入负责人，核对固定源修订是否仍适用，再在所属仓流程应用补丁。
2. 用公司构建链跑完整 H5/App/小程序构建；验原有助手请求兼容、新组件状态与日志。
3. 单独评审并应用 H5 同源委派转发；未登录应得到 JSON 鉴权拒绝，不能仍回首页 HTML。
4. 明确授权的正常会话及同主体订单 access=200 到位后，按正常登录验收手册跑一轮隔离 M3。
5. 全链证据通过后，单独决定生产 M3 和 App 显示开关；再以小范围真实用户观察验收。

用户已停止登录排查，样本未满足前不重试登录、不改账号、不制造订单或借他人会话。
