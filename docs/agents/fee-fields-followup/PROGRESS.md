## 一、#1307 在生产上没有修好，已回滚

这是我这一轮最重要的事实，先写清楚。

**做了什么**：按「不就是一个更新版本的问题吗」把节点清单重发成 v3
（`business_prompt(v2) + 当前 OPERATOR_OUTPUT`），路由指针推进到 v3 / revision 14。

**文本是对的**：核对过 v3 与**受支持的发布链产物逐字节相同** ——
`business_prompt(v2_system_message) + OPERATOR_OUTPUT` 重新序列化后与库里 v3 完全相等，
清单也能被 `execution_manifest.from_text` 解析。

**结果是负的**：v3 上连跑 8 次，**0 次成功**。同期旧契约（rev 12）是 13 成功 / 30 次。

```
(12, 'old') {'succeeded': 13, 'failed': 15}
(14, 'new') {'failed': 8}
```

这不是抽样噪声：按旧契约 43% 的成功率，连败 8 次的概率约 1.1%；而且失败原因**种类**
变了 —— 出现了旧契约没有出现过的 `reason=shape` 与 `OPERATOR_EVIDENCE_MISSING`。

**已回滚**：路由指针退回 `agent_version_no=2` / revision 15
（`updated_by=rollback-v3-to-v2`）。回滚后同一句话恢复 `completed`。

**教训（已并入 ADR-0193）**：`OPERATOR_OUTPUT` 那段不是普通的措辞，它是**输出契约**。
把「一个问题一种失败方式」改成「禁止一切数字 + 禁止提费用项」之后，模型不是更守规矩，
而是**换了失败方式**（结构不完整、缺证据）。改这段文本要按改协议对待。

## 二、订单提取：Codex 报的两条都是真缺陷，已修（本地）

复现（`099c1207` 上）：

```
'订单 A2116050516255272961'      → 2116050516255272961   ← 前缀被吃掉
'订单 ORDER-1001 和订单2116…'    → 2116050516255272961   ← 两张单静默选一张
```

根因不是正则写错，是**两个入口各有一份提取逻辑**，且都只认「第一个/唯一一个长数字段」。

修法：`common/order_reference.order_candidates()` 成为**唯一**候选集来源，两个入口都调它。
规则：

- 有「订单」标记时，**显式写法优先**，并并入 15 位以上的裸数字段；
- 并入时按**数字内容**归并（`订单 A2116…` 的裸数字段是同一张单的后半截，不是第二张）；
- 同一张单重复出现 → 一张；
- 两张不同的单 → 正式入口返回 `CLARIFY_ORDER_REQUIRED` 澄清，**不问 CPMS**；
- 没有「订单」标记时退回形状判据（19 位雪花 id / 整条消息就是单号），站点日期、
  时刻、手机号仍然进不来。
