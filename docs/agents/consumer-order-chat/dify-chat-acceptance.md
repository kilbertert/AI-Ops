# APP-RUNTIME-02 验收契约：原 App 聊天接入 Dify

本契约定义「现有 App 聊天 → **Dify 已发布 Workflow** → 受限本人取数 → 同一轮快照 → 原 GET」
必须满足什么。它与节点路线（`node-chat-acceptance.md`）**并存**，由绑定表的 `engine` 二选一。

对外形状与接线前完全一致：不新增字段、不换接口、不换域名。差别只在「谁来跑这一轮」。

## 两条路线的关系

```gherkin
功能: 本人订单状态由选定的执行引擎回答
  背景:
    给定 服务端绑定表里有 (环境, 租户, consumer 入口, 本场景) 的一条登记
    并且 该登记的 engine 是 node 或 dify 之一
    并且 调用者是 consumer 入口、self 范围、非代查、有 C 端主体

  场景: 一条登记只能有一个引擎
    当 同一场景登记了两次
    那么 启动失败
    并且 不按文件顺序裁决，也没有"节点失败就试 Dify"的回落

  场景: 旧节点登记继续可用
    给定 登记里不写 engine
    那么 按 node 读，行为与 APP-RUNTIME-01 逐字一致
```

## Dify 路线

```gherkin
  场景: 本人最新一单
    当 App 用原接口提问「查询我最新一单的状态」
    那么 POST 立即返回 202 与 qa_id
    并且 网关按本人 SQL 范围选出最新一单后才调 Dify
    当 App 用原 GET 轮询
    那么 终态 completed，blocks 由该轮快照渲染
    并且 Dify 的 HTTP 步骤**自己**带着一次性凭据回调网关取数

  场景: 正文指定本人订单
    当 正文里带一个本人订单号
    那么 交给 Dify 的是那一单，不是最新一单

  场景: 取数凭据的边界
    给定 为这次 QA 签发了一张取数凭据
    那么 它 ≥256 bit 随机，库里只存哈希
    并且 绑死主体/订单/环境/租户/QA/workflow 与 180 秒有效期
    并且 只允许一次业务读取；重复回调只回同轮已存快照
    并且 run_id 或 qa_id 单独出现不能取数
    并且 完成、失败、取消之后立即撤销

  场景: 模型看不到凭据
    当 Dify 的模型步骤收到输入
    那么 输入里只有裁剪后的状态事实
    并且 不含取数凭据、不含内部接口地址

  场景: Dify 失败
    给定 Dify 调用失败、超时、断流，或实际运行的 workflow 身份不符
    那么 终态 failed，无正文
    并且 不重发启动 POST、不换引擎、不回直读
    并且 没有取数却自称成功也算失败

  场景: 上游失败
    给定 业务上游在取数那一步失败
    那么 终态 failed，业务读取只尝试了那一次，不制造第二份快照

  场景: 取消
    当 调用者在终态前取消
    那么 QA 先落 cancelled，并撤销取数凭据
    并且 按已绑定的 task id 请求 Dify 停止
    并且 Dify 停不下来**不能**撤回本地取消（也不声称供应商立刻停费）

  场景: 回读
    当 回读本窗口内已完成的结果
    那么 仍要过当前本人授权、绑定、TTL、同 QA/执行记录与快照完整性
    并且 缓存正文必须就是该快照的渲染
    并且 停用后正文 404，无正文终态（queued/running/failed/cancelled/expired）仍可读
```

## 判据（每条都能被测试或脚本观察到）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 一条登记只指向一个引擎；冲突即启动失败 | 隐式优先级会让"这次到底谁跑的"变成不可核对 |
| 2 | 旧节点登记不写 `engine` 仍按 node 运行 | 兼容既有部署是硬要求 |
| 3 | 取数凭据 ≥256 bit、库存哈希、绑死范围、180 秒、一次性 | 复用人会话或整租户 key 都会把个人权限放大 |
| 4 | 回调**每次**都重做当前授权 + 有效期 + 取消 + 绑定 | 只在签发时判一次，撤销与到期就漏了 |
| 5 | 一次业务读取；重复回调只回同轮快照 | 第二次读业务就是第二个答案 |
| 6 | 模型输入不含凭据与内部地址 | 模型能读到的凭据等同于泄漏给编排平台 |
| 7 | 成功必须同时有：workflow 运行成功、同轮取数快照、可核对输出 | "Dify 返回了 200"不是成功 |
| 8 | 失败不回落节点/直读/旧模型 | 回落 = 另一次执行冒充本次结果 |
| 9 | 取消先落终态并撤销凭据，再请求 Dify stop | 供应商停不停不能决定我们的取消 |
| 10 | 执行记录不伪造 `node_id` / `matched` | 那会让"这次没有节点"读成"节点核对过了" |

## 已知限制（写出来，不当作已消除）

- Dify 的 inputs 与运行记录会保存本次 input，因此取数凭据对**能打开该应用记录的人**可见。
  完成/失败/取消后立即撤销，但不声称能追回此前已披露的数据。
- 本片不实现 SOP 的编辑/试用/发布/撤回（留待 M3）；这里只固定并核对**实际执行的已发布
  workflow 身份**，不运行草稿、不自动追最新版本。

## 不在本契约内

- 真实外部模型供应商与真实业务库（本片验收用本地合成上游）；
- 真实公司 UPMS 目录、登录 App 真机验收；
- 任意 Function Calling 图的通用支持 —— 本片只有"固定 HTTP 取数 → 模型 → 结束"这一种图。

## 实现要点（真 Dify 1.17.1 实测）

这几条不是风格建议，每一条都来自一次**看起来成功、实际没跑**的现场：

| 形状 | 症状 | 原因 |
|---|---|---|
| 边的 `target` 必须写 | 整轮只有 start 节点执行，导入与写草稿都是 200 | `graphon` 的 `_build_edges` 对缺 `target` 的边直接 `continue`，不报错 |
| streaming 开始与结束事件 | 运行中无法停止或错认版本 | 版本必须在 URL；开始事件保存 task/run，结束事件核对同一身份 |
| HTTP 步骤的 `body` 是**字符串** | 端节点交出 `"snapshot": "{...}"`，网关判 `DIFY_NO_DATA` | `graphon` 的 `HttpResponse.text` 不解析 JSON；Jinja2 沙箱也没有 `fromjson` 过滤器 |
| 模型 provider 是三段式标识 | "已装好"被判成"没装上" | `langgenius/openai_api_compatible/openai_api_compatible`，不是插件短名 |
| 装完 provider 要**重启 api** | provider 列表一直是空的 | api 进程缓存 provider 列表；plugin_daemon 里已经可用也不够 |
| 凭据校验由 **plugin_daemon** 发出 | 400 `Failed to resolve 'host.docker.internal'` | 真正连模型上游的是插件宿主，不是 api；它也需要 `extra_hosts` |
| 数值型 provider 选项是 **string** | 注册凭据 500 `Variable context_size should be string` | 该 provider 的 credential schema 把这些声明为字符串 |
| 验收容器网络 | 无需改宿主防火墙 | driver、Dify 与合成上游共用一次性网络命名空间，宿主不发布端口 |
| 节点 id **不能含连字符** | 模型收到字面的 `{{#read-status.body#}}`，工作流仍 succeeded | `graphon` 的 `VARIABLE_PATTERN` 把节点段限定为 `[a-zA-Z0-9_]`；不匹配的占位符原样保留 |

因此 Dify 侧的快照是**文本**：网关收到后严格解析成对象，并要求字段恰好是
`SNAPSHOT_FIELDS`；解析失败或多一个字段都按 `DIFY_NO_DATA` 拒绝。
`tests/dify/test_dify_chat_dsl.py` 把其中可静态判定的几条固化成可运行断言
（缺 `target`、链路形状、端节点变量、节点 id 字符集、凭据绑定位置），不依赖人记得。
