# APP-RUNTIME-01 验收契约：App 聊天接入客户执行节点

本契约定义「现有 App 聊天 → 客户节点 → 同一 run 的状态快照」这条新路线必须满足什么。
它与既有 `POST /v1/assistant/questions` 的**对外形状**完全一致：不新增字段、不换接口、
不换域名。差别只在「谁来读」。

## 场景（默认关闭，只有服务端显式绑定才启用）

```gherkin
功能: 本人订单状态由客户执行节点回答
  背景:
    给定 服务端配置了聊天入口的节点绑定
    并且 调用者是 consumer 入口、self 范围、非代查、有 C 端主体

  场景: 本人最新一单
    当 App 用原接口提问「查询我最新一单的状态」
    那么 POST 立即返回 202 与 qa_id
    并且 网关按本人 SQL 范围选出最新一单后才派发
    当 App 用原 GET 轮询该 qa_id
    那么 状态先可为 queued/running，最终为 completed
    并且 回答的 blocks 等于该 run 的 succeeded 快照
    并且 每个成功请求只派发一次、只读一次业务

  场景: 正文指定本人订单
    当 App 在正文里带一个本人订单号
    那么 派发的是那一单，不是最新一单
    并且 回答里的订单号与该 run 快照的订单号一致

  场景: 绑定外或未配置
    给定 服务端未配置聊天入口绑定
    当 App 提问同样的状态问法
    那么 走原来的确定性直读，形状与接线前逐字一致

  场景: 非本人订单
    当 调用者的请求指向不属于自己的订单
    那么 在派发之前就以 404 拒绝
    并且 没有任何业务读取发生

  场景: 节点失败
    给定 派发或领取失败
    当 App 轮询该 qa_id
    那么 终态是 failed
    并且 不会用直读、旧模型或别的节点补一个答案

  场景: 执行配置漂移
    给定 节点回传的配置身份与清单不符
    当 领取被拒
    那么 任务落 failed，不交付正文

  场景: 取消
    当 调用者在终态之前取消
    那么 QA 先落 cancelled，并撤销已关联的 run
    并且 节点迟到的成功不能把它覆盖回 completed

  场景: 停用后回读
    给定 绑定被清空（等价于停用）
    当 回读本窗口内已完成的结果
    那么 404 CHARGING_STATUS_DISABLED，不继续交付正文
    并且 queued/failed/cancelled 仍能按原协议读到
```

## 判据（每条都能被测试或脚本观察到）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | POST 立刻返回 202 + `qa_id` | App 等不起节点整轮；同步等待会让前端超时 |
| 2 | GET 是**同一个** `qa_id`，且状态单调到终态 | 轮询不能被「还没有快照」挡住 |
| 3 | 回答 = 该 run 的 succeeded 快照 | 不另读 CPMS 补数据，否则等于两套答案 |
| 4 | QA↔run 是**存储关联**（`agent_runs.qa_id`） | 从 `internal_run_id` 字符串反推是猜测，不是关联 |
| 5 | 选单在**网关**、派发之前 | 否则「选哪一单」变成节点或客户端的决定 |
| 6 | 失败不回落 | 回落 = 另一次读取冒充本次结果 |
| 7 | 取消撤销关联 run；迟到结果不覆盖 | 用户点过停止，就不能再收到正文 |
| 8 | 停用/撤权/过期后拒绝正文 | 与直读路线停用后 `CHARGING_STATUS_DISABLED` 同一条纪律 |
| 9 | 默认关闭；绑定外请求走原分支 | 新路线不能借合并顺手打开 |

## 不在本契约内

- 真实外部平台/供应商、真实 Java 节点的整链验收（另列，见验收记录）；
- 常驻开放、四小时自然流量观察、全链路追踪、新管理台。
