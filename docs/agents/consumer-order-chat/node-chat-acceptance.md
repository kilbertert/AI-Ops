# APP-RUNTIME-01 验收契约：App 聊天接入客户执行节点

本契约定义「现有 App 聊天 → 客户节点 → 同一 run 的状态快照」这条新路线必须满足什么。
它与既有 `POST /v1/assistant/questions` 的**对外形状**完全一致：不新增字段、不换接口、
不换域名。差别只在「谁来读」。

## 场景（默认关闭，只有服务端**按租户登记**的绑定才启用）

```gherkin
功能: 本人订单状态由客户执行节点回答
  背景:
    给定 服务端有一条 (环境, 租户, consumer 入口, 本场景) 的登记，指向它自己的执行配置与清单
    并且 调用者是 consumer 入口、self 范围、非代查、有 C 端主体

  场景: 本人最新一单
    当 App 用原接口提问「查询我最新一单的状态」
    那么 POST 立即返回 202 与 qa_id
    并且 网关按本人 SQL 范围选出最新一单后才派发
    当 App 用原 GET 轮询该 qa_id
    那么 状态先可为 queued/running，最终为 completed
    并且 回答的 blocks 等于该 run 的 succeeded 快照
    并且 每个成功请求只派发一次、只读一次业务

  场景: 正文指定本人订单
    当 App 在正文里带一个本人订单号
    那么 派发的是那一单，不是最新一单
    并且 回答里的订单号与该 run 快照的订单号一致

  场景: 绑定外或未配置
    给定 服务端没有这个租户的登记（或整份绑定表为空）
    当 App 提问同样的状态问法
    那么 走原来的确定性直读，形状与接线前逐字一致
    并且 一次派发都没有发生

  场景: 两个租户各登记各的节点
    给定 TENANT-A 与 TENANT-B 各有一条登记，指向不同节点与不同 app
    当 两个主体的请求各自进入这条路线
    那么 各自的 run 冻结各自的绑定，派到各自登记的节点
    并且 互不串单

  场景: 非本人订单
    当 调用者的请求指向不属于自己的订单
    那么 在派发之前就以 404 拒绝
    并且 没有任何业务读取发生

  场景: 节点失败
    给定 派发或领取失败
    当 App 轮询该 qa_id
    那么 终态是 failed
    并且 不会用直读、旧模型或别的节点补一个答案

  场景: 只领取、没有整轮完成
    给定 节点领到了业务（已有快照），但从未发出整轮完成通知
    当 App 轮询该 qa_id
    那么 终态是 failed
    并且 记录绝不 succeeded

  场景: 执行配置漂移
    给定 节点回传的配置身份与清单不符
    当 领取被拒
    那么 任务落 failed，不交付正文

  场景: 取消
    当 调用者在终态之前取消
    那么 QA 先落 cancelled，并撤销已关联的 run
    并且 节点迟到的成功不能把它覆盖回 completed

  场景: 停用后回读
    给定 这个租户的绑定被拿掉（等价于停用）
    当 回读本窗口内已完成的结果
    那么 404 CHARGING_STATUS_DISABLED，不继续交付正文
    并且 queued/running/failed/cancelled/expired 仍按原协议读到 —— 包括取消，
         否则前端看到「取消失败」而库里其实已经取消
```

## 最终放行只有一份

交付前的判定（同主体、同订单、同环境、app/agent/预期节点一致、实际节点=预期节点且此刻
仍有效、执行配置核对一致、未过期、快照五字段自洽）在 `chat_execution.final_release` 里
**只写一遍**，由三个调用方共用：委派入口、聊天 worker、聊天回读。

这不是为整洁：写第二遍时**漏掉了四项**（settings 执行环境、actual==expected、节点登记的
environment、执行配置是否真的核对过），而且漏得很安静 —— 回读仍是 200 + 正文。
同一个不变量写成两遍，第二遍必然少几句。

## 判据（每条都能被测试或脚本观察到）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | POST 立刻返回 202 + `qa_id` | App 等不起节点整轮；同步等待会让前端超时 |
| 2 | GET 是**同一个** `qa_id`，且状态单调到终态 | 轮询不能被「还没有快照」挡住 |
| 3 | 回答 = 该 run 的 succeeded 快照 | 不另读 CPMS 补数据，否则等于两套答案 |
| 4 | QA↔run 是**存储关联**（`agent_runs.qa_id`） | 从 `internal_run_id` 字符串反推是猜测，不是关联 |
| 5 | 选单在**网关**、派发之前 | 否则「选哪一单」变成节点或客户端的决定 |
| 6 | 失败不回落 | 回落 = 另一次读取冒充本次结果 |
| 7 | 取消撤销关联 run；迟到结果不覆盖 | 用户点过停止，就不能再收到正文 |
| 8 | 停用/撤权/过期后拒绝正文 | 与直读路线停用后 `CHARGING_STATUS_DISABLED` 同一条纪律 |
| 9 | 默认关闭；绑定外请求走原分支 | 新路线不能借合并顺手打开 |
| 10 | 绑定按（环境，租户，入口，场景）登记，QA/run 冻结选中的那一条 | 「全局配了一个文件」不是绑定：那等于任何能通过本人授权的租户都派到同一个节点 |
| 11 | 聊天路线**必须**有执行清单；签发时也拒绝缺清单 | 没有清单的 run 走旧协议（领取即 succeeded），会把「只读了业务」记成成功 |
| 12 | 回读的正文必须就是该快照的渲染 | 一份被改过（或写着别的 run）的正文不能被当成本次结果交出去 |

## 在本契约内（本片补齐）

- **真 Gateway → 真 Java 节点 → 同一 run 快照 → 原 GET** 的整链可复跑，
  由 `tools/m2_close/m3node/verify_chat_node_entry.py` 交付；
- 外部平台（编排）、模型上游、CPMS、调用者身份、订单授权与选单数据用本地替身，
  但**领取与整轮完成通知由节点自己发出** —— 不用 Python 派发器代劳。

## 不在本契约内

- 真实外部平台/供应商、真实公司 UPMS 目录、登录 App 真机验收（另列，见验收记录）；
- 执行配置身份 ≠ 运营 SOP 发布绑定（后者明确留待 M3）；
- 常驻开放、四小时自然流量观察、全链路追踪、新管理台。
