## 1. 业务目标与已确认入口

用户要知道**本人订单在本次观察时的充电状态**。执行成功的回执不能代替状态；另外再直读
一次 CPMS，也不能把第二次观察称为这个 run 的快照。现有实时充电页已有公司接口的状态展示，
本片只验证受控委派链路能把同一份结果交给页面，不替换实时页或统一助手。

| 组件 | 核对结果 | 证据范围 |
|---|---|---|
| App AI 客户端模块 | 已封装 FAQ、助手、诊断等接口；采样源码无 M3 委派调用 | 外部仓固定内容取回；发版分支、负责人未确认 |
| 本人订单详情页 | 采样源码无 AI-Ops 入口 | 不代表所有分支或所有 App 版本 |
| 实时充电页 | 已轮询公司 `chargingInfo`，不经 M3 | 源码事实 |
| H5 请求源 | 生产 H5 的 `AIOPS_BASE_URL` 为空，走同源；开发 H5 用 `/aiops`；非 H5 用环境 APIURL | 不能从 env.js 单独推定 H5 的完整入口 |
| 服务端转发 | 已核对的 API 入口注入 Bearer，外部 `third-session` 转内部 `X-Third-Session`，缺入口头补 consumer | H5 同源 `/v1/` 到这段配置的完整入口链仍须在其 vhost/网络记录核对 |
| 部署产物与访问窗口 | 全部 689 个 JS 块未命中 `charging-status`；最近 40 万行日志无 delegated | 有限窗口，不宣称从未调用或精确来源提交已知 |
| 生产开关 | 已核对的四个 M3 键未配置 | 正常认证与请求校验后返回 AGENT_RUN_DISABLED |

**App 请求封装不能原样复用**：取回源码及离线驱动证实，它记录完整 `myHeader`（含会话）和
响应正文，把 502 错误码丢成维护文案，并且没有显式超时。接线必须删掉敏感日志、保留结构化
HTTP/code/网络错误分类，并核对同步请求的端到端超时。公司侧发版分支、制品来源提交与
责任人仍待确认，不从提交作者推定负责人，不接管外部仓库。

## 2. 当前请求与错误契约

```http
POST /v1/orders/{order_no}/charging-status/delegated
Content-Type: application/json

{}
```

- 正式入口使用已授权的正常会话；内部请求带 Bearer、`X-Third-Session`、`X-Business-Entry: consumer`。
  服务令牌不进入 App。解析结果必须是 consumer/self/非 delegated，订单属于同一主体。
- body 是空严格模型，禁止携带主体、租户、模型或平台配置。路径号非法为 `400 INVALID_ORDER_NO`。
- 顺序不能概括成“401 总在 422 前”：**无 Bearer + 合法 JSON 多字段 → 401**，
  **无 Bearer + 无法解析的 JSON → 422**；独立探针已复现。未启用时，合法 body → 404，
  多字段 body 仍先 → 422。App 应按实际 HTTP/code 分类，不猜校验顺序。

| HTTP | 形状/代码 | 页面行为要求 |
|---:|---|---|
| 200 | 执行回执；目前无业务状态字段 | 修订 B 实施前不显示“充电中/已结束” |
| 400 / 422 | INVALID_ORDER_NO / INVALID_REQUEST | 参数错误，不自动重试 |
| 401 | ACCESS_TOKEN_REQUIRED / INVALID_ACCESS_TOKEN | 引导重新登录 |
| 403 | CONSUMER_SCOPE_REQUIRED / INSUFFICIENT_SCOPE | 当前身份或入口不可用，不换身份重试 |
| 404 | ORDER_NOT_FOUND | 不存在与非本人同形 |
| 404 | AGENT_RUN_DISABLED | 功能未启用，不能显示成订单不存在 |
| 502 | AGENT_RUN_UNAVAILABLE / AGENT_RUN_NO_RESULT | 本次检查未确认成功；不自动重发 |
| 503 | 配置、执行清单或授权源不可用 | 展示暂不可用；retryable=true 也不自动重发 POST |
| 404 / 405 | 框架 `{"detail":...}`，没有 error.code | 通用不可用，记录脱敏的 HTTP 状态 |
| 无响应 | 超时/断连 | **结果未知**；服务端可能已派发，不自动重试 |

已定义的业务成功/错误带 `Cache-Control: no-store`；框架 404/405 不带，不能声称全部响应都一致。
当前没有客户端幂等键，也没有消费者按 run_id 查询该结果的端点；`/v1/runs` 属于另一套设备接口。

## 3. 两方案的审查结果

**A 只显示执行回执，不满足本片业务目标，不作为产品入口发布。** 可保留为工程检查能力。

**选择修订 B：消费者路由增加 `charging_status`，来自同 run 的持久化快照。**
不改共用 `AgentRun.receipt()`，也不把内部领取端点的整个响应下发给页面。

| 新对象字段 | 来源/语义 |
|---|---|
| order_no | 快照中的本人订单号，必须与该 run 及本次路径一致 |
| status_code | CPMS 原始状态码，保留现有类型 |
| status_role | 现有 order_status 映射；未知码保持 unknown |
| observed_at | CPMS 响应被网关读取后的服务端时间，不是 claimed_at 或设备上报时刻 |
| source | 固定 cpms.chargingInfo |

`read_charging_status()` 与库中的 snapshot 实际都是 **5 字段**；领取响应另外加 4 个执行字段。
`result_sha256` 按现有 `sha256(json.dumps(snapshot, sort_keys=True).encode('utf-8'))` 计算，覆盖这
5 字段对象。实施时断言返回对象与存储对象完整一致及摘要一致；不让 App 自行发明 JSON 规范化。
历史损坏、缺字段、额外字段或订单不符必须拒绝并保留排查证据，不改写快照凑出匹配。

### 3.1 消费者最终放行是必需实现，不能用领取时授权替代

独立反例：让节点正常取数，再在平台返回前把订单转给另一主体。当前端点仍回 200 回执；
若直接应用原 B 草案，会同时交出旧授权快照。**这是新业务响应的设计缺口，不是本轮已经
在线上泄漏快照的结论。** 原草案的“只加九行、无需授权代码”不采纳。

返回正文前：先重新核对本次调用者的本人订单授权，再读取现行绑定与 run 做最终判定。
至少核对同一主体/范围指纹、订单、环境/app/agent/节点绑定仍有效，run 仍 succeeded、未到期、
未撤销/拒绝，启用清单时 expected/observed 已匹配，快照完整且订单一致。
授权可能阻塞，最终本地判定不得使用授权之前的陈旧 run。终态与时间判据复用现有 store 原语，
不增加另一套 TTL；已有失败原因不得被覆盖、记录不得复活。

消费者的订单不可见仍返回 `404 ORDER_NOT_FOUND`，授权源失败为 503；其余运行判据失败不交
业务正文。明确放行判定时点与跨系统边界：已获准发出的数据无法追溯撤回，不承诺外部订单库
与 SQLite/网络发送的分布式原子性。配置/撤销在最终复核前已发生时必须被拒。

### 3.2 三项裁量

1. **保留同步完成语义，不加轮询或额外等待器。** SnailDispatcher 调 `/chat/sync`；受控节点
   `ReportingChatSessionRuntime.wrap()` 先同步 `reportCompleted()` 并验证 Gateway 回执，
   然后才 `request.acceptCompletion()`。另一个 HTTP 通知本身不能证明它落后于平台成功。
   既有成功链路支持这个顺序；替身若在完成前返回，只证明 Gateway 会拒绝，不能称为真实竞态。
   下一片补可执行顺序断言；若真实适配路径违背契约，报告反例后修该接缝，不先增加轮询。
2. **本片不加 Idempotency-Key。** 点击期间锁定，超时/断开不自动重发；用户明确再次检查
   是新 run、新观察，可能再次调用模型。页面不得假装恢复上一次未知结果。
3. **状态文案归 App 本地化。** Gateway 沿用现有 status_role，不增加 status_label。
   页面显示“本次观察”及 observed_at，未知角色显示未知；不以执行成功推断业务正常。

TTL 是签发后 180 秒，不等于 claimed_at。现有 `_expire_in` **包含 succeeded**，
所以它也会变 expired；refuse/revoke 也能终止成功记录的继续访问。不要写成“成功终态永不变化”。

## 4. 下一片实施与验收边界

先交付 Gateway 的消费者快照和最终放行，独立分支/PR；App 侧在确认发版归属后再接线。
不改旧直读语义、统一助手默认路由、共用回执、节点完成协议、生产开关或登录实现。

必须有同一组正反判据：

- 一次派发/一次业务读取；响应快照等于同 run 存储快照，摘要与观察时间一致；无额外敏感字段。
- 节点领取后订单转他人/授权源失效；最终授权期间撤销、到期、节点停用或绑定变化：全部拒正文。
- 两个用户/订单交错不串用，未知状态码不编造；未启用路径与共用回执字段保持原样。
- 完成通知确认先于向平台上报完成；running+快照或坏完成回执不能作为成功。
- 一次性数据根上真 Gateway HTTP 驱动，既有判据不退；有可复跑的失败反证。
- App 离线验收覆盖 200/401/403/两类404/422/502/503/网络未知；日志无会话/订单正文，
  忙态防重入、超时不自动重发。上线还需同源入口实测与正常登录的本人订单样本。

本页是审查后的实施契约，**不是实现或业务验收回执**。真实用户整轮仍须同时具备明确授权、
正常登录有效会话、同主体订单 access=200；生产启用和客户环境交付继续分别验收。
