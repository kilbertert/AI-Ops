# order-visibility

「这次运行可以看见哪些订单」是只读诊断边界上的一条业务规则。它曾被独立实现**六次**
（两个入口守卫、agent 工具层、三个数据源），并且**已经漂移**：同一订单在不同入口
得到不同的可见性结论，连失败原因都不同。

## raw source

规则定义一次，渲染三次。收敛点在**规则**而不是执行点——因为设备路径没有 SQL 可下推
（它经 `/diag/*` HTTP 读订单），而调用者路径有。

- `resolve_device_tenant` —— 入口渲染：由「入口被授权的租户」与「请求点名的租户」决定本次运行的
  有效租户，**拒绝任何会扩大范围的请求**。它先于另外两种渲染运行：一次运行的有效租户在这里定一次，
  之后每种渲染都与这个决定比对。
- `visible_orders` —— 行级渲染：给手上已有行的调用者（fixture 源、agent 工具层）。
- `scope_where_sql` —— 参数绑定的 `WHERE` 渲染：给把规则下推进 SQL 的调用者。

## 不变量

- **入口或在数据源里另写一份过滤，就是这次漂移的成因。** 改可见性只改这一处，三种渲染一起生效。
- 扩大范围的请求是**拒绝**，不是"取交集后放行"。
- 三种渲染必须对同一输入给出一致结论；不一致即回归。
