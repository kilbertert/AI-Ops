# AI-Ops

充电桩运维的诊断系统。它把一次「这台桩为什么坏」的问题，变成一份**有证据可回查**、
**范围可证明**、**不越权**的答复。

## raw source

三个不可协商的事实决定了系统形态：

1. **运维人员要的是结论，但要的是能自己复核的结论。** 一条诊断没带证据链就不能交付。
2. **模型不可信。** 所以边界必须由 harness 保证，而不是由提示词保证——提示词是建议，
   代码是约束。任何"模型应该不会…"的推断都不构成安全论证。
3. **一条业务规则只能有一处定义。** 这不是整洁偏好：租户可见性规则曾被实现六次并已经漂移，
   同一订单在不同入口得到不同结论。副本是缺陷的温床，不是冗余的安全网。

## expanded spec

六个推论，各自落在代码里（见 [[l0-contracts]] 到 [[l6-boundary]] 的对应节点）：

- **只读的证据收集 + 解释** —— 系统收集证据、解释证据，不改业务数据。
- **边界由 harness 保证** —— 工具白名单、预算上限、输出合同在代码里强制，不在提示词里。
- **失败是常态，运行必须可恢复** —— 每个阶段落盘，崩溃后从已持久化状态继续。
- **凭据不能到达客户端** —— 因此有 Gateway，密钥留在服务端。
- **成本与确定性要求保留一条不调用模型的路径** —— `--mode deterministic` 不是降级，
  是一等能力。

## 不变量

- 任何一次诊断的可见范围，最终都能追溯到一份 [[l2-identity]] 冻结出的 `ScopeContext`。
- 任何一次证据读取都经过 [[l3-evidence]] 的有界查询，不存在无范围直查的入口。
- 模型写出的数字不进数字字段（见 [[ops-analysis]]）；模型只写叙述。
