# 自助开通面（受管应用目录）

问题：一个新客户如何被开通到能用。受管目录在 `operator_apps`（**名字是遗留债：该表同时装 consumer 与 operator 两种 entry**——任何查询代码必须声明要哪个 entry；ADR-0189：一行 consumer 记录的空 `profile_id` 曾让所有 operator 节点路由崩掉）。

## 词表（dual_entry 一处持有）

- `entry` = 业务入口（`consumer`/`operator`）；`scenario` = 执行路由（首个切片每入口一条已注册）；`channel` = 该入口是否接线。
- channel 语义 = **声明优先 + 观测兜底**：有声明看声明；无声明且无成功 run = `pending` fail-closed。`has_succeeded_for_tenant` 看的是成功运行记录不是配置——"AI 准备好了"≠"用户能用上"。

## 幂等作业与顺序

- `operator_setup_jobs`：`UNIQUE(actor, request_key)` + step + resources JSON + 租约；服务重启把中断作业标 retryable；**凭据绝不入库**（ADR-0162）。HTTP 202 = "已受理"，完成只能由读作业状态证明——失败永不写成功结果。
- 一次开通 = 公共准备一次 + 每入口准备：`workspace → knowledge → dependencies`（共享客户空间）然后 `consumer: application → key → register → publish` / `operator: application → register → publish`。**两入口不是一个事务**——一个失败不回滚另一个（外部资源无法可靠回滚），`partial` 是诚实状态；`failed_step` 记进 resources，重试只续失败的那个入口。
- 开通必须装配：环境登记（business-environments manifest）、工作区（claim→create→ready）、知识空间（RAGFlow 租户，`knowledge_ready` 才算 "complete"）、模型凭据（写+激活+读回）、cpms-node 工具 provider（OpenAPI 派生目录带 `x-` 规格哈希做漂移检测）、每工作区知识连接、Service key、节点能力检查。**依赖每次重试都要对权威重验**——不读全局默认插件版本（ADR-0235：工作区已跑 0.0.2 还装 0.0.1 是真事故）。

## Service key 生命周期（service_keys.py）

snapshot-先 → create → reconcile：Dify 只在创建时返回完整 token（1.17.1 的 list 会带全量——这个依赖就是对账路径）；对账歧义（0 或 >1 个 key）= **不切指针、不猜**别人的集成 key；key 只以 `<key_dir>/<app_id>.key` 0600 原子文件交付——发布推的是**路径**不是密钥进表/日志/作业 JSON；Dify 10 key 上限到 → `SETUP_KEY_LIMIT` 拒绝而不是删一个可能还活着的 key。schema 委托 `gateway_schema.ensure`；`clean_legacy()` 是网关启动维护（先只读探测，再把旧 dict 形 `before_json` 清成 ID 列表）；`get()` 对存量 dict 形记录也只回吐排序 ID 列表——独调路径同样不暴露 token。

## 边界与守卫

- `self_service_bridge` 同源闸：Origin==console_origin **且** Referer 同源 **且** `Sec-Fetch-Site∈{∅,same-origin}` **且**有效 Dify 会话 **且**`角色∈{owner,admin,editor}` **且** `application/json`——之后只转发服务端验证过的浏览器会话；浏览器永远见不到内部令牌或平台 key。
  环境任务白名单已扩到约一打固定形状（`environment-update`/`environment-draft-save`/`environment-plan`/candidate_task+installation/installation_task+registration_plan/registration_task+validation_plan+capabilities/validation_task+publication_plan/verify_task/site、workspace、knowledge、connection 各 `*_task`/`id+cancel` 等），全部正则钉字段，仍不接受工作区ID、任意URL或执行参数；准备串联须Gateway与桥配套，旧单步骤保持。
  D37安装只接`candidate_task/installation=true`确认，部署材料由控制端冻结、运维搬运；原平台/目录权限不变，浏览器不能提交制品路径或执行参数。
- `self_service_identity`：管理身份只经真 Dify 登录交换读，浏览器不提供任何身份声明。`identity()`/`require_target()` 在配 `environment_registry_file` 时先过登记准入：平台哨兵（`type=-1` ∧ `tenant_id=-1`）只查登记本身 enabled（`require_enabled()`），普通租户按行 `require(tenant)`——未开通/停用 → `SetupRefused("TENANT_ENVIRONMENT_NOT_ENABLED")`（非 `SETUP_` 前缀的共享拒码，ADR-0256/0332）；准入/平台权限两闸均可按调用点关断（`require_admission=`/`require_platform_permissions=`），环境管理面就绕开它们（其授权走显式目录授权而非登记准入）。`self_service_config` = 平台维护的 profiles（JSON 0600）被应用引用；不接受浏览器给的路径/凭据/端点。
- `self_service_api` 会话分两层：`session()` 保 `SETUP_DISABLED` 闸+operator-profiles 委派；`management_session` 只要发布 key Bearer、**不吃 operator-profiles 闸**——`onboarding/management.py`（本地别名 `environment_management`）的 `register` 把环境目录管理面挂在其下，所以无 operator profiles 的安装仍可做环境管理。配登记文件时 catalogue 的租户选项/工作区/来源再与 `enabled_tenant_ids()` 求交（ADR-0332）——停用租户从自助目录里消失，不只是被准入闸拒。
- 草稿完整性：发布比对当前草稿指纹与创建时冻结值；并发发布或源版本变化 → `SETUP_DRAFT_CHANGED`/`SETUP_SOURCE_CHANGED`/`SETUP_ACTOR_CHANGED`——让运营刷新，不是系统猜。consumer 的 `change_version` 另有 `SETUP_VERSION_ENVIRONMENT_MISMATCH` 写路径闸（ADR-0333，语义归 [execution-delegation](../execution/execution-delegation.mdx)）——钉着别的执行环境的冻结快照不能被重指上路由。
- consumer 选库与草稿接管（ADR-0255）：detail 的 `knowledge_base_ids` 从**当前草稿导出的 workflow** 经 `consumer_source_ids` 投影（非开通时 targets 快照），并附 `live_app_id`/`live_version_no`——抽屉看/改的是应用真草稿的选库。拉 DSL 同步**先验证选库再建本地草稿**（坏选库不留半成品 Agent）；失败首次接管只认 `self_service_store.recoverable_consumer_draft` 身份（`entry=consumer`、`consumer-<app_id>` 名、`created_by=aiops-admin`、status=draft、revision=1、`published_version IS NULL`、无 agent_versions 行）——配置/提示词相等不再证明归属，不符 → refused `existing draft is not the one this operation created`；快照顶层 `knowledge_base_ids`（有 bootstrap 时连 `prompt`/`model`）由同一份冻结 workflow 投影，绝不继承上一版。
- `dify/operator_run_logs_api.py`（本包的 FastAPI 管理面）：Java run 元数据只读视图——`POST /v1/dify/management/run-logs` 列表 + `.../detail` 按 run_id 单条（缺则 `OPERATOR_RUN_NOT_FOUND`），逐请求重验公司身份+app 归属+租户；过期业务结果不恢复，但问题全文/订单号属输入标识仍投影（ADR-0249），ADR-0251 起行级摘要（入参+白名单结果字段的 `tool_summaries`）也过同一 `qa_id + scope_fingerprint` 闸进 detail 响应，不投影面不变；`no-store`。与 `execution/operator_run_logs.py`（账本投影白名单，列表与详情同一 `metadata()`）同名不同层，别混。
- `knowledge_connection.py`：`ExternalKnowledgeApis.tenant_id` 是**工作区级**的；只有平台端点/key 可作创建模板。`ensure()` 的 `pending`/`save`/`name` 参数：名字 ≤40 字符（Dify 上限）；pending-attempt 跟踪让重试抛 `DIFY_KNOWLEDGE_CONNECTION_UNCONFIRMED` 而非重发 POST；对账时重读行并 `hmac.compare_digest` 核对 `api_key`（不符 = `knowledge connection credential mismatch`）——未知结果不只对账，还重验凭据。
  候选knowledge-connect另用复合范围凭据，先保存创建意图；未知结果只对账，不触发原首次开通发布流程。
- `SelfServiceStore(path, readonly=True)` 只读模式：`validate_private_file`+`gateway_schema.check`，不建目录不加保护——给不能物化存储的观察方用。

## 失败语义

环境页operator-prepare只创建停用候选：模型取唯一已批准模板，SOP/工具取当前仓内声明，工具地址取目标草稿。
持久UUID导入未知后只回读原app；Dify候选能力在实际创建时API/site=false，普通导入默认保持。
候选不注册正式路由或生成app key，执行profile及业务验证仍独立后继。
消费者consumer-prepare由平台管理员明确选正式Agent快照；冻结workflow与批准模型，替换目标单库。
共用候选导入与资源恢复，advanced-chat创建时API/site停用；ckx只返回复合单库目录，不能业务取数。
直接插件选库不另建dataset，不写正式grant；控制回调到目标环境的业务接线仍待后继验证。
environment-runtime以有效计划/双端观察与明确专属节点导出私有运行工件，Console只读，不写准入/路由。
同环境/工作区/单库、模板和取消边界重核，秘密仅在私有工件；导出不等于安装或真实业务验证。

稳定 `SETUP_*` 码族——**每个码命名失败的步骤和下一步动作**（`SETUP_KEY_DIRECTORY_UNWRITABLE` → 修 systemd 保护目录；`SETUP_BUSINESS_ENVIRONMENT_AMBIGUOUS` → 标 `default:true`；`SETUP_APP_FORBIDDEN`/`SETUP_TENANT_FORBIDDEN`/`SETUP_IDENTITY_MISMATCH` → 授权问题不是配置）。`TENANT_ENVIRONMENT_NOT_ENABLED` 是唯一非 `SETUP_` 前缀成员——它来自登记准入闸，不是装配步骤。拒绝 ≠ 冲突 ≠ 流程非法——三条不同的异常路径（`self_service_api.py`）。

## Canonical anchors

目标已安装运行工件通过固定安装器register-runtime接原aiops-admin登记；原工作区与双端应用表
在一个短事务写入，workspace状态created。部分/归属/能力/版本冲突拒绝，相同登记只回读；
候选重装**原位替换**旧的 `created_by="environment-runtime"` 行（新 app_id；旧行须同 tenant+environment+entry、
revision 1、同 workspace、`agent_name==entry-app_id`、同 profile/scenario——不符 `SETUP_APP_CONFLICT`，ADR-0313）；
任一作业表存在在飞工作 → `SETUP_INFLIGHT_WORK`，workspace/路由/登记冲突与部分双入口态各有专码。
路由占用判定按**真实占用**收窄（ADR-0327/0331）：`retracted` 绑定留行不算占用（否则撤回一次就永久堵死重登记——撤回留行是设计不是占用），
但同租户同环境现役（非 retracted）`chat_route_bindings` 行**就是占用**——重登记撞上自己还活着的绑定同样冲突，须先撤回（第一条闸）；
同租户 `dify_app_registry` 行无论 app_id 新旧都是**本血统**留行从不冲突（重铸候选的 app_id 按 (workspace,job) 派生必然换新的，
同租户异应用是谱系证据不是外血统）；候选 app_id 被**外租户**正式绑定是第二条独立闸——两条查询任一命中即 `SETUP_ROUTE_CONFLICT`。
正式路由/密钥/准入不变，目标不取得共享Console管理凭据。依据`docs/adr/0290-inactive-runtime-registration.md`。
