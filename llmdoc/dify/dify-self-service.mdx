# 自助开通面（受管应用目录）

问题：一个新客户如何被开通到能用。受管目录在 `operator_apps`（**名字是遗留债：该表同时装 consumer 与 operator 两种 entry**——任何查询代码必须声明要哪个 entry；ADR-0189：一行 consumer 记录的空 `profile_id` 曾让所有 operator 节点路由崩掉）。

## 词表（dual_entry 一处持有）

- `entry` = 业务入口（`consumer`/`operator`）；`scenario` = 执行路由（首个切片每入口一条已注册）；`channel` = 该入口是否接线。
- channel 语义 = **声明优先 + 观测兜底**：有声明看声明；无声明且无成功 run = `pending` fail-closed。`has_succeeded_for_tenant` 看的是成功运行记录不是配置——"AI 准备好了"≠"用户能用上"。

## 幂等作业与顺序

- `operator_setup_jobs`：`UNIQUE(actor, request_key)` + step + resources JSON + 租约；服务重启把中断作业标 retryable；**凭据绝不入库**（ADR-0162）。HTTP 202 = "已受理"，完成只能由读作业状态证明——失败永不写成功结果。
- 一次开通 = 公共准备一次 + 每入口准备：`workspace → knowledge → dependencies`（共享客户空间）然后 `consumer: application → key → register → publish` / `operator: application → register → publish`。**两入口不是一个事务**——一个失败不回滚另一个（外部资源无法可靠回滚），`partial` 是诚实状态；`failed_step` 记进 resources，重试只续失败的那个入口。
- 开通必须装配：环境登记（business-environments manifest）、工作区（claim→create→ready）、知识空间（RAGFlow 租户，`knowledge_ready` 才算 "complete"）、模型凭据（写+激活+读回）、cpms-node 工具 provider（OpenAPI 派生目录带 `x-` 规格哈希做漂移检测）、每工作区知识连接、Service key、节点能力检查。**依赖每次重试都要对权威重验**——不读全局默认插件版本（ADR-0235：工作区已跑 0.0.2 还装 0.0.1 是真事故）。

## Service key 生命周期（service_keys.py）

snapshot-先 → create → reconcile：Dify 只在创建时返回完整 token（1.17.1 的 list 会带全量——这个依赖就是对账路径）；对账歧义（0 或 >1 个 key）= **不切指针、不猜**别人的集成 key；key 只以 `<key_dir>/<app_id>.key` 0600 原子文件交付——发布推的是**路径**不是密钥进表/日志/作业 JSON；Dify 10 key 上限到 → `SETUP_KEY_LIMIT` 拒绝而不是删一个可能还活着的 key。schema 委托 `gateway_schema.ensure`；`clean_legacy()` 是网关启动维护（先只读探测，再把旧 dict 形 `before_json` 清成 ID 列表）；`get()` 对存量 dict 形记录也只回吐排序 ID 列表——独调路径同样不暴露 token。

## 边界与守卫

- `self_service_bridge` 同源闸：Origin==console_origin **且** Referer 同源 **且** `Sec-Fetch-Site∈{∅,same-origin}` **且**有效 Dify 会话 **且**`角色∈{owner,admin,editor}` **且** `application/json`——之后只转发服务端验证过的浏览器会话；浏览器永远见不到内部令牌或平台 key。
- `self_service_identity`：管理身份只经真 Dify 登录交换读，浏览器不提供任何身份声明。`self_service_config` = 平台维护的 profiles（JSON 0600）被应用引用；不接受浏览器给的路径/凭据/端点。
- 草稿完整性：发布比对当前草稿指纹与创建时冻结值；并发发布或源版本变化 → `SETUP_DRAFT_CHANGED`/`SETUP_SOURCE_CHANGED`/`SETUP_ACTOR_CHANGED`——让运营刷新，不是系统猜。
- `dify/operator_run_logs.py`（本包的 FastAPI 管理面）：Java run 元数据只读视图——`POST /v1/dify/management/run-logs` 列表 + `.../detail` 按 run_id 单条（缺则 `OPERATOR_RUN_NOT_FOUND`），逐请求重验公司身份+app 归属+租户；过期业务结果不恢复，但问题全文/订单号属输入标识仍投影（ADR-0249），ADR-0251 起行级摘要（入参+白名单结果字段的 `tool_summaries`）也过同一 `qa_id + scope_fingerprint` 闸进 detail 响应，不投影面不变；`no-store`。与 `execution/operator_run_logs.py`（账本投影白名单，列表与详情同一 `metadata()`）同名不同层，别混。
- `knowledge_connection.py`：`ExternalKnowledgeApis.tenant_id` 是**工作区级**的；只有平台端点/key 可作创建模板。

## 失败语义

约 55 个稳定 `SETUP_*` 码——**每个码命名失败的步骤和下一步动作**（`SETUP_KEY_DIRECTORY_UNWRITABLE` → 修 systemd 保护目录；`SETUP_BUSINESS_ENVIRONMENT_AMBIGUOUS` → 标 `default:true`；`SETUP_APP_FORBIDDEN`/`SETUP_TENANT_FORBIDDEN`/`SETUP_IDENTITY_MISMATCH` → 授权问题不是配置）。拒绝 ≠ 冲突 ≠ 流程非法——三条不同的异常路径（`self_service_api.py`）。
